# 第五周教案：使用编码 Agent 阅读代码与理解项目

## 一、课程基本信息

- **课程名称**：YatOL 人机协作课程
- **授课主题**：使用编码 Agent 阅读代码与理解项目
- **建议课时**：2 学时（90 分钟）
- **适用对象**：具备基础代码阅读能力的计算机相关专业学生
- **先修内容**：Prompt 工程、需求分析、项目上下文与 `AGENTS.md`
- **实践载体**：编码 Agent、具有多个入口和外部依赖的示例仓库

## 二、教学目标

完成本节课后，学生应能够：

1. 使用由广到窄的方式让编码 Agent 建立陌生项目地图。
2. 区分启动入口与具体功能入口。
3. 定位 Web、CLI[^1]、定时任务、消息消费者和前端事件等不同入口。
4. 分析核心模块的职责、公开接口、依赖、状态和失败行为。
5. 追踪正向调用链[^2]、反向调用方和动态实现绑定[^3]。
6. 说明数据流[^4]在验证、转换、持久化、事件和响应阶段的变化。
7. 追踪配置来源、覆盖优先级和第三方依赖的真实用途。
8. 要求 Agent 为关键结论引用真实文件与符号。
9. 区分代码可见事实、运行后验证和尚未确认的推断。
10. 生成围绕具体功能、可由其他开发者复查的项目说明。

[^1]: CLI 是通过终端命令操作程序的界面。
[^2]: 调用链是从入口开始的“谁调用谁”路径。
[^3]: 动态实现绑定是程序运行时选择具体实现的方式。
[^4]: 数据流是数据如何输入、变化、保存和输出的过程。

## 三、教学设计与课前准备

### 1. 教学重点与难点

#### 教学重点

- 只读分析边界和证据要求。
- 项目地图、功能路径和运行验证的三遍阅读法。
- 启动入口、功能入口、核心模块与参考实现的定位。
- 调用链和数据流的区别与组合使用。
- 配置、依赖、测试和运行结果在项目理解中的作用。
- 避免局部文件、同名符号、旧代码和测试替代造成误判。

#### 教学难点

- 一个项目可能存在多个入口，`main` 文件不等于目标功能入口。
- 静态搜索只能证明代码关系存在，不能自动证明当前运行经过该路径。
- 依赖注入[^5]、插件、装饰器和事件机制会隐藏真实实现绑定。
- 调用链关注“谁调用谁”，数据流还要解释数据怎样变化。
- 配置或依赖出现在文件中，不代表当前环境实际启用。
- Agent 的流畅解释可能混入合理但未经证实的推断。

[^5]: 依赖注入是由外部代码把需要的对象交给当前组件。

#### 课程边界

- 第四周已经讲解项目上下文，本周重点是让 Agent 从真实仓库中找到上下文证据。
- 本周以只读理解为主，不进入代码修改和完整开发计划。
- 完整的 Explore、Plan、Implement、Verify 工作流留到第六周。
- 工具权限和执行安全留到第七周。
- 本周利用测试理解行为，但不展开测试驱动开发。

### 2. 教学准备

#### 教师准备

- 准备一个小型但结构真实的示例仓库，至少包含：
  - Web API；
  - CLI、worker 或定时任务中的一种；
  - route、service、repository 分层；
  - 依赖注入或接口实现绑定；
  - 配置文件和环境变量；
  - 一个第三方服务封装；
  - 单元测试和集成测试；
  - 一个生成目录或遗留目录。
- 准备“创建订单”或“用户登录”完整功能路径。
- 准备一个旧版同名模块，用于说明按文件名判断的风险。
- 准备一个测试替代实现和一个生产实现。
- 准备可运行的最小请求或已有测试，并提前核验命令。
- 准备认证、消息队列和搜索模块的只读说明示例。

#### 学生准备

- 复习第四周的仓库级、目录级、任务级和运行级上下文。
- 了解函数调用、模块导入、接口和基本数据类型。
- 能够阅读 README、依赖清单、脚本和简单测试代码。

#### 环境准备

- 编码 Agent 能够读取和搜索示例仓库。
- 运行环境不依赖真实生产密钥或用户数据。
- 最小验证命令可以稳定执行。
- 示例日志不包含敏感信息。
- 预留静态判断与真实运行不一致的可观察案例。

## 四、核心知识体系

### 1. 代码阅读的目标

代码阅读不是逐行看完所有文件，而是建立一张可核查的项目地图：

```text
项目怎样启动
-> 功能从哪里进入
-> 核心模块怎样协作
-> 数据怎样变化
-> 配置和依赖怎样生效
-> 怎样验证当前路径
```

编码 Agent 适合快速搜索、关联和整理，但使用者必须限定阅读目标并要求证据。

### 2. 只读边界

阅读要求应明确：

```text
本次只读分析，不创建、编辑或删除文件，也不安装依赖。
```

“解释”“分析”和“查找”并不授权 Agent 修改项目。只读边界可以避免在尚未理解项目时发生无意修改。

### 3. 三类证据

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| 代码可见事实 | 当前仓库文件直接证明 | `src/server.ts` 调用 `app.listen()` |
| 运行后验证 | 测试、日志或请求确认 | 登录请求实际经过 `AuthService.authenticate()` |
| 未确认推断 | 有线索但尚未证明 | Redis 可能只在功能开关开启时使用 |

文件引用应写到能够复查结论的最小符号，例如函数、类、配置键、路由或测试名称；只写目录不能支持结论时，还要补充行号或调用关系。

### 4. 三遍阅读法

#### 4.1 第一遍：项目地图

读取根目录、README、依赖清单、lockfile[^6]、脚本、CI[^7]、项目指令和顶层目录，回答项目用途、技术栈、启动方式和模块边界。

[^6]: lockfile 是记录依赖准确版本的文件。
[^7]: CI 是代码变更后自动运行构建、检查和测试的流程。

#### 4.2 第二遍：功能路径

围绕一个具体行为，从真实外部入口向下追踪业务逻辑、数据访问、外部依赖和副作用，再从目标函数反向搜索其他调用方。

#### 4.3 第三遍：运行验证

使用已有测试、最小请求、日志或断点确认当前配置和输入是否真正经过静态阅读得到的路径。

### 5. 仓库根目录分析

根目录阅读包括：

- README 和贡献指南；
- 依赖清单和 lockfile；
- 构建、启动和测试脚本；
- 容器与部署配置；
- lint、类型和测试配置；
- CI 工作流；
- workspace 或 monorepo[^8] 配置；
- `AGENTS.md` 等项目指令。

依赖存在不代表运行时使用。脚本和 CI 通常比记忆中的命令更接近当前项目状态。

[^8]: monorepo 是在一个代码仓库中管理多个应用或软件包。

### 6. 目录结构分析

目录说明应包含职责、代表文件、上下游关系和对应测试，而不是只把目录名改写一遍。

| 目录 | 职责 | 代表文件 | 主要关系 |
| --- | --- | --- | --- |
| `src/routes` | HTTP 输入输出 | `orders.ts` | 调用 service |
| `src/services` | 业务流程 | `order-service.ts` | 调用 repository 和 publisher |
| `src/repositories` | 数据访问 | `order-repository.ts` | 连接 database |
| `tests` | 行为验证 | `orders.test.ts` | 使用 fixture[^9] 和替代依赖 |

[^9]: fixture 是测试前准备好的数据、对象或环境。

还应识别生成代码、构建产物、遗留目录和已废弃实现。

### 7. 入口定位

项目可能具有：

- 服务启动入口；
- HTTP、GraphQL 或 RPC 入口；
- CLI 子命令；
- 消息消费者；
- 定时任务；
- 后台 worker；
- 前端页面和事件处理器；
- 插件注册点。

找到 `main.py` 或 `server.ts` 只说明项目怎样启动。目标功能入口还要从 URL、命令名、事件名、UI 文本、错误消息或测试继续搜索。

### 8. 核心模块与参考实现

若模块承担目标功能的业务规则、状态变化、公共接口或外部系统连接，就把它列为本次阅读的核心模块，并用入口或调用方证明关系。

分析时说明：

- 职责；
- 公开接口；
- 输入输出；
- 依赖方向；
- 状态和生命周期；
- 异常与副作用；
- 对应测试；
- 被哪些入口使用。

参考实现应选择仍在使用、同一架构层、由当前测试覆盖且业务语义相近的代码。参考实现展示项目模式，但不能替代具体需求。

### 9. 调用链分析

调用链回答“谁在什么条件下调用谁”。

```text
POST /orders
-> createOrderRoute
-> OrderService.create()
-> InventoryService.reserve()
-> OrderRepository.save()
-> EventPublisher.publish()
```

每一跳记录调用者、被调用者、输入输出、分支、异常和副作用。

#### 正向追踪

从入口向下寻找最终实现和副作用。

#### 反向追踪

从目标函数向上搜索所有调用方，防止遗漏其他入口和兼容关系。

#### 动态绑定

遇到接口、依赖注入、装饰器、多态或插件时，应继续找到 factory、容器注册、环境条件和测试替代，不能停在抽象类型。

#### 事件驱动关系

事件发布和消费不是直接函数调用，还要查找 topic、消息结构、消费者注册、重试、死信[^10]和幂等[^11]。

[^10]: 死信是多次处理失败后被转到专门位置的消息。
[^11]: 幂等是同一操作重复执行，结果仍与执行一次相同。

### 10. 数据流分析

数据流回答数据怎样验证、转换、保存和返回。下面示例中的 DTO[^12] 用于在模块或接口之间传递结构明确的数据。

[^12]: DTO 是只用来在模块之间传递数据的对象。

```text
原始 JSON
-> 请求 schema
-> 业务命令对象
-> 领域实体
-> 数据库记录
-> 事件消息
-> 响应 DTO
```

重点包括：

- 字段重命名；
- 类型转换；
- 默认值与可空性；
- 金额精度；
- 时间和时区；
- 状态变化；
- 事务[^13]边界；
- 敏感字段；
- 序列化[^14]。

[^13]: 事务让一组数据操作一起成功或一起撤销。
[^14]: 序列化是把程序里的数据转成便于保存或传输的格式。

许多问题发生在模块之间的数据转换，而不是某一个函数内部。

### 11. 配置分析

配置追踪路径是：

```text
定义
-> 读取
-> 类型转换
-> 默认值
-> 覆盖优先级
-> 注入
-> 实际使用
```

配置文件中存在某个键，不代表当前环境使用它。命令行参数、容器环境变量、测试 fixture 或远程配置都可能覆盖本地文件。

分析过程中不得输出真实密钥、token 或用户数据。

### 12. 第三方依赖分析

依赖分析包括：

- 锁定版本；
- 直接或传递依赖；
- 导入位置；
- 项目内部封装；
- 初始化条件；
- 功能开关；
- 生产和测试实现；
- 调用方；
- 超时、重试和降级。

查阅外部文档前要确认实际版本，避免用新版 API 解释旧版代码。

### 13. 使用测试理解项目

测试可以展示公开行为、fixture、错误情况、依赖替代和项目认可的调用方式。测试也有边界：

- 单元测试可能使用内存实现；
- 测试配置可能不同于生产；
- 没有断言的副作用不一定正确；
- 测试名称和注释也可能过期。

因此应比较测试 bootstrap 和生产 bootstrap。

### 14. 静态阅读[^15]与运行验证

[^15]: 静态阅读是不运行程序，只通过代码和配置分析行为。

静态阅读适合快速建立候选路径，但动态注册、配置、死代码和并发时序可能无法仅靠搜索确认。

运行验证用于确认实际入口、当前配置、实现绑定、调用顺序和副作用。无法运行时，应明确：

```text
代码可见：route 调用 AuthService.authenticate()。
尚未验证：当前部署是否启用该 route；本地环境缺少数据库。
```

### 15. 解释关键代码

Agent 解释函数或模块时，不应只逐行翻译。推荐顺序是：

1. 代码目的；
2. 所属功能路径；
3. 输入和输出；
4. 调用者与被调用者；
5. 关键分支；
6. 状态变化和副作用；
7. 异常与失败行为；
8. 配置影响；
9. 对应测试；
10. 尚未验证的推断。

### 16. 项目说明

项目说明应围绕当前阅读目标，包括：

- 项目用途与技术栈；
- 目录地图；
- 启动和外部入口；
- 核心模块；
- 目标功能调用链；
- 数据流和状态变化；
- 配置和外部依赖；
- 测试与运行验证；
- 已确认事实；
- 尚未确认事项。

说明应引用文件和符号，不复制大段源代码，也不扩张为项目百科全书。

## 五、课堂教学过程（90 分钟）

| 教学环节 | 时间 | 教师讲授内容 | 讲解重点 |
| --- | ---: | --- | --- |
| 情境导入 | 8 分钟 | 展示局部文件解释正确但项目结论错误的案例 | 代码阅读必须证明运行路径 |
| 三遍阅读与证据 | 14 分钟 | 讲解项目地图、功能路径、运行验证和三类证据 | 文件、符号与结论强度 |
| 目录与入口 | 15 分钟 | 分析根目录、模块职责和多入口项目 | 启动入口不等于功能入口 |
| 调用链与数据流 | 18 分钟 | 追踪订单创建的调用与数据变化 | 正向、反向、动态绑定和副作用 |
| 配置、依赖与测试 | 12 分钟 | 讲解配置覆盖、依赖绑定和测试替代 | 声明不等于当前运行 |
| 教师现场演示 | 18 分钟 | 只读解释认证流程并用运行结果修正静态判断 | 证据引用和未知事项 |
| 总结 | 5 分钟 | 回顾三遍阅读和常见误判 | 可核查项目地图 |

### 1. 情境导入（8 分钟）

教师展示仓库中的 `auth.py`。该文件包含完整认证代码，Agent 的逐行解释也没有语法错误，但真实 Web 入口已经迁移到 `security/session/`，旧文件只被一个遗留测试引用。

由此引出：

```text
局部解释正确 != 当前项目理解正确
```

代码阅读的目标不是找到名称最像的文件，而是从真实入口证明当前运行路径。

### 2. 三遍阅读与证据（14 分钟）

教师介绍三遍阅读法：

```text
第一遍：项目地图
第二遍：具体功能的调用链和数据流
第三遍：测试、日志或最小请求验证
```

随后对比三类表达：

```text
代码事实：`src/server.ts` 调用 `app.listen()`。
运行验证：本地启动日志显示该文件是当前服务入口。
未确认推断：部署环境可能通过另一个启动脚本运行。
```

教师强调关键结论应引用文件和符号，而不是只给出模块名称。

### 3. 根目录、目录地图与入口（15 分钟）

教师按以下顺序阅读示例仓库：

1. README；
2. 依赖清单和 lockfile；
3. 启动、测试和构建脚本；
4. CI；
5. 顶层目录；
6. 项目指令；
7. 生成与遗留目录。

然后区分：

```text
启动入口：创建应用、注册模块、监听端口
功能入口：具体 URL、命令、事件或用户操作进入的位置
```

教师展示 Web route、CLI 子命令、消息 consumer 和定时任务的不同注册方式，并说明动态注册需要继续查找容器或 factory。

### 4. 调用链与数据流（18 分钟）

教师从 `POST /orders` 开始追踪：

```text
createOrderRoute
-> OrderService.create()
-> InventoryService.reserve()
-> OrderRepository.save()
-> EventPublisher.publish()
```

在每一跳旁标注：

- 调用者与被调用者；
- 输入输出；
- 分支条件；
- 异常传播；
- 数据库和事件副作用。

然后在同一图上叠加数据变化：

```text
JSON
-> CreateOrderRequest
-> CreateOrderCommand
-> Order entity
-> OrderRow
-> OrderCreated event
-> OrderResponse
```

教师解释调用链与数据流互补，并补充库存不足、事务回滚和事件发布失败等异常路径。

### 5. 配置、依赖与测试（12 分钟）

教师展示依赖清单同时包含两个搜索客户端的项目。不能因为依赖存在就判断当前系统使用哪一个。

需要继续检查：

- lockfile 版本；
- 内部 `SearchClient` 接口；
- factory 或依赖注入注册；
- `SEARCH_BACKEND` 配置；
- 测试中的内存实现；
- 生产启动配置。

教师强调测试是项目说明的重要证据，但单元测试中的替代实现不能自动代表生产路径。

### 6. 教师现场演示（18 分钟）

#### 6.1 演示要求

教师向 Agent 输入：

```text
请把当前仓库当作陌生项目阅读，本次只读，不修改文件。

目标：解释 Web 用户提交登录表单到创建 session 的完整路径。

请先给出最小项目地图，再说明：
1. 前端和后端入口；
2. 认证调用链；
3. 登录数据怎样验证和转换；
4. session 怎样创建和写入响应；
5. 失败路径；
6. 影响实现的配置；
7. 对应测试与生产绑定差异。

关键结论引用文件和符号。
区分代码事实、运行验证和尚未确认的推断。
```

#### 6.2 建立最小项目地图

教师观察 Agent 是否先确认：

- 前端和后端目录；
- 框架与实际版本；
- 服务启动入口；
- 测试目录；
- 认证配置；
- 项目指令。

如果 Agent 直接进入名为 `auth` 的文件，教师将其拉回到路由注册和实际用户行为。

#### 6.3 追踪认证路径

```text
LoginForm.onSubmit
-> authClient.login
-> POST /login
-> loginRoute
-> AuthService.authenticate
-> UserRepository.findByEmail
-> PasswordVerifier.verify
-> SessionStore.create
-> Set-Cookie
```

教师要求每一跳说明文件、符号、数据和异常。

#### 6.4 检查数据与安全边界

演示重点包括：

- email 规范化；
- 密码字段只在请求边界短暂存在；
- 密码哈希比较；
- 用户不存在和密码错误的统一映射；
- session id 创建和存储；
- cookie 安全属性；
- 日志与响应是否过滤敏感字段。

#### 6.5 比较测试与生产绑定

测试 fixture 可能使用 `InMemorySessionStore`，生产 bootstrap 使用 Redis。教师要求 Agent 找到两处注册，而不是根据测试断言整个系统不依赖 Redis。

#### 6.6 用运行证据修正

教师运行已有登录测试或最小请求，对照日志检查实际路径。如果静态分析遗漏中间件或使用了错误实现，要求 Agent更新说明并标出原假设为何失效。

#### 6.7 形成简短项目说明

最终说明只保留：

- 当前登录入口；
- 认证与 session 调用链；
- 数据和失败路径；
- 配置与实现绑定；
- 测试证据；
- 仍未确认事项。

不扩展到与 Web 登录无关的移动端 token 或后台认证。

### 7. 课堂总结（5 分钟）

教师用以下结构回顾：

```text
阅读目标：建立可核查的项目地图

三遍：
地图 -> 功能路径 -> 运行验证

两条线：
调用链 = 谁调用谁
数据流 = 数据怎样变化

三类结论：
代码事实 | 运行验证 | 未确认推断
```

## 六、典型案例讲解

### 1. 认证流程

认证流程应从真实登录入口开始，追踪用户查找、密码比较、账号状态、session 或 token 创建、错误映射和响应。还应区分 Web、API、后台和遗留认证路径。

重点是安全敏感数据怎样流动，以及测试替代是否不同于生产实现。

### 2. 消息队列

消息队列说明应覆盖：

```text
业务操作
-> 发布位置
-> 消息结构
-> broker/topic
-> consumer 注册
-> handler
-> 外部副作用
```

还应分析事务提交时机、outbox、重试、死信、重复投递和幂等。只找到 handler 文件不能证明消费者已注册。

### 3. 搜索模块

搜索模块应同时解释查询和索引写入：

```text
查询：用户输入 -> 规范化 -> 过滤 -> 后端查询 -> 权限过滤 -> 排序分页 -> 响应

索引：数据更新 -> 事件或任务 -> 索引转换 -> 搜索后端写入
```

重点检查后端选择、权限过滤位置、缓存、排序稳定性和测试中的替代实现。

### 4. 配置未生效

开发者修改 `.env` 后程序行为不变。应追踪配置定义、加载、类型转换、默认值、命令行覆盖、容器环境和实际使用位置。

不能只反复修改 `.env`，也不能在说明中输出真实密钥。

### 5. 同名函数误导

仓库中存在多个 `save()`、`execute()` 或 `handle()`。文本搜索结果最多的实现不一定是当前入口使用的实现。

应结合 import、类型、实例创建、依赖注册、调用位置和当前配置确认。

### 6. 参考实现选择

目标是增加一个新 API 时，Agent 可能找到多个相似模块。优先选择当前仍被调用、位于相同架构层、使用当前框架并由测试覆盖的实现。

教师应提醒：结构可参考，权限、事务、敏感数据和业务规则不能机械照搬。

## 七、常见课堂问题与处理

### 1. 一开始解释最大文件

教师应将阅读拉回根目录、启动脚本和目标功能入口。大文件可能只是生成代码，不能代表项目核心。

### 2. 只输出目录树

要求说明每个主要目录的职责、代表文件、上下游和对应测试。目录树本身不能形成项目理解。

### 3. 把 `main` 文件当成功能入口

说明名为 `main` 的文件只能证明候选启动点，不能证明目标功能入口。应从 URL、命令、事件或用户操作继续追踪到实际处理代码。

### 4. 只正向追踪

要求从目标函数反向搜索其他调用方，以发现 CLI、worker、测试和兼容关系。

### 5. 在抽象接口处停止

继续寻找 factory、依赖注入容器、启动注册、环境条件和测试替代，确认当前实现绑定。

### 6. 只画调用链，不分析数据

在每一跳旁补充数据类型、字段变化、验证、状态、事务和敏感信息处理。

### 7. 把依赖声明当实际启用

要求查找导入、内部封装、初始化条件、配置开关和生产注册。

### 8. 把测试实现当生产实现

比较测试 fixture 与生产 bootstrap。内存 repository 或模拟队列只说明测试环境行为。

### 9. 把注释和 README 当当前事实

将文档与当前脚本、代码、测试和运行结果比较。发生不一致时明确报告。

### 10. 把推断写成设计意图

没有 ADR、注释或其他直接证据时，使用“可能用于”而不是“作者这样设计是因为”。

### 11. 无法运行就声称已经确认

要求明确区分代码可见关系和运行后验证。环境受限时写出未验证原因。

### 12. 项目说明无限扩张

始终围绕当前阅读目标。解释登录时不需要详细展开报表、头像上传和所有后台模块。

### 13. 只读分析中发生代码修改

重申任务动词和权限边界。本周的核心是理解项目，不在理解尚未稳定时进入修改。

## 八、课堂总结与板书

### 1. 课堂总结

优秀的项目理解不是生成一篇流畅摘要，而是建立一张可核查的地图。

教师应强调：

1. 先明确只读边界和具体阅读目标；
2. 第一遍建立项目地图；
3. 第二遍从真实入口追踪调用链和数据流；
4. 第三遍用运行证据修正静态判断；
5. 启动入口不等于具体功能入口；
6. 调用链和数据流需要结合；
7. 配置或依赖存在不等于当前启用；
8. 关键结论必须引用真实文件与符号；
9. 无法确认的内容应明确标为推断或未知；
10. 项目说明应帮助下一位开发者继续工作。

### 2. 板书设计

```text
Week 5  使用编码 Agent 阅读项目

边界：只读 + 具体问题 + 仓库证据

三遍阅读：
1. 地图：根目录 / 技术栈 / 目录 / 启动 / 测试
2. 路径：入口 -> 调用链 -> 数据流 -> 副作用
3. 验证：测试 / 日志 / 请求 / 运行状态

入口：
启动入口 != 功能入口
Web | CLI | Consumer | Cron | UI | Plugin

调用链：谁调用谁
数据流：数据怎样验证、转换、保存和返回

配置：定义 -> 覆盖 -> 注入 -> 使用
依赖：声明 != 初始化 != 当前启用

结论标签：
代码事实 | 运行验证 | 未确认推断

流畅解释 != 真实运行路径
```

## 九、与前后课程的衔接

### 1. 与第三周的衔接

第三周学习事实、推断和待确认事项。本周将这种区分用于文件、调用关系、配置和运行路径的证据表达。

### 2. 与第四周的衔接

第四周学习编码 Agent 需要哪些项目上下文。本周学习如何从陌生仓库中找到真实入口、模块、调用方、测试和依赖证据。

### 3. 与第六周的衔接

本周得到的项目地图、功能路径、未知事项和验证方法，将成为第六周制定计划、执行修改和观察结果的输入。

### 4. 与第七周的边界

本周只说明何时需要搜索、读取、运行测试或查看日志。工具权限、命令执行和安全审批将在第七周展开。

### 5. 与第八周的边界

本周把现有测试作为理解项目的证据。测试设计、回归测试和测试驱动开发将在第八周系统讲解。
