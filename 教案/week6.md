# 第六周教案：编码 Agent 的完整工作流

## 一、课程基本信息

- **课程名称**：YatDS 人机协作课程
- **授课主题**：编码 Agent 的完整工作流
- **建议课时**：2 学时（90 分钟）
- **适用对象**：具备基础项目阅读与测试结果理解能力的计算机相关专业学生
- **先修内容**：需求分析、项目上下文、`AGENTS.md`、代码阅读与项目理解
- **实践载体**：编码 Agent、包含可复现 Bug 与验证命令的示例仓库

## 二、教学目标

完成本节课后，学生应能够：

1. 说明 Explore–Plan–Implement–Verify[^1] 四阶段工作流。
2. 使用 Plan–Act–Observe–Update[^2] 解释 Agent 怎样根据结果调整下一步。
3. 在修改前建立基线，确认目标、范围、约束和验证方式。
4. 把任务拆成包含动作、依赖和验收点的可执行步骤。
5. 根据任务风险选择 Plan Mode 或直接执行模式。
6. 使用小步迭代、修改预算和人工检查点控制执行过程。
7. 根据需求、验证结果和最终差异判断任务是否完成。

[^1]: Explore–Plan–Implement–Verify 是先探索、再计划、然后实现、最后验证的工作顺序。
[^2]: Plan–Act–Observe–Update 是先决定下一步，执行后读取结果，再更新判断的循环。

## 三、教学设计与课前准备

### 1. 教学重点与难点

#### 教学重点

- 四阶段主流程与阶段回退。
- Plan、Act、Observe、Update 反馈循环。
- 修改前基线和可执行计划。
- Plan Mode 与直接执行模式的选择。
- 小步迭代、错误分类和 Human-in-the-loop[^3]。
- 验收点、最终 diff[^4] 和未验证风险。

[^3]: Human-in-the-loop 是让人在自动流程的关键节点参与决定。
[^4]: Diff 是文件修改前后的内容差异。

#### 教学难点

- 理解计划可以被新证据更新，不是固定剧本。
- 区分动作完成、结果观察和步骤验收。
- 失败后形成新假设，而不是机械重复命令。
- 只在真正影响方向或风险的节点请求人工决定。
- 区分通用工作流与各产品 Plan Mode 的具体行为。

#### 课程边界

- 第三至五周已经讲解任务拆解、上下文和项目阅读，本周只做必要承接。
- 第七周系统讲解工具、权限与执行安全；本周只讨论工具结果如何进入反馈循环。
- 第八周系统讲解测试驱动开发；本周只把现有验证作为验收证据。
- 第九周系统讲解 Git、PR 和代码审查；本周只使用最终 diff 确认修改范围。

### 2. 教学准备

#### 教师准备

- 准备“空搜索词返回全部用户”的示例仓库和稳定复现条件。
- 准备一段连续修改但没有读取完整错误的 Agent 记录。
- 准备一份只有“分析、编码、测试”的低质量计划。
- 预设一个会否定初始根因的证据：问题发生在 route 默认值，而非 repository。
- 准备重复用户名迁移和窄屏按钮遮挡两个边界案例。
- 提前核验演示命令、预期输出和官方文档链接。

#### 环境准备

- 编码 Agent 能读取、搜索和修改示例仓库。
- 最相关测试可稳定执行并显示完整结果。
- 演示不连接生产系统，不使用真实密钥或用户数据。
- 可查看修改前后差异；页面案例可使用固定视口。

## 四、核心知识体系

### 1. 两层工作流

```text
主流程：Explore -> Plan -> Implement -> Verify
小循环：Plan -> Act -> Observe -> Update
```

| 阶段 | 主要问题 | 输出 |
| --- | --- | --- |
| Explore | 当前行为和项目事实是什么 | 基线、证据、未知项 |
| Plan | 准备怎样修改 | 步骤、依赖、验收点 |
| Implement | 当前最小修改是什么 | 局部变化 |
| Verify | 是否达到目标 | 检查结果、diff、风险 |

Verify 发现新路径时可以回到 Explore；影响范围扩大时可以回到 Plan。

### 2. Plan–Act–Observe–Update

```text
Plan：决定当前下一步和预期结果
Act：执行与当前假设直接相关的动作
Observe：读取文件、命令或页面的真实结果
Update：更新假设、计划和状态
```

教师应强调：只 Act 不 Observe，就是连续猜测；Observe 不进入 Update，计划就会与现实脱节。

### 3. 修改前基线与分析

基线[^5]是修改前可重复的当前状态。

[^5]: 基线是开始修改前记录下来的当前行为或检查结果。

```text
输入：GET /users?q=%20%20
当前：200，返回 53 条记录
目标：400，EMPTY_QUERY
正常基线：q=alice 返回 2 条记录
```

修改前确认：目标、现状、影响范围、项目约束和验证方式。如果测试在导入阶段失败，只能说明环境或入口有问题，不能据此修改业务逻辑。

### 4. 可执行计划与任务拆解

每一步至少包含：

| 字段 | 含义 |
| --- | --- |
| 目标 | 本步确认或改变什么 |
| 动作 | Agent 具体做什么 |
| 证据 | 怎样判断完成 |
| 依赖 | 开始前必须满足什么 |

任务应按可验证行为拆解：

```text
建立基线
-> 定位参数转换
-> 确认产品规则
-> 最小修复
-> 验证正常行为
-> 检查差异
```

计划还应写出修改范围和停止条件，不只列出要编辑的文件。

### 5. Plan Mode 的目标与完整流程

Plan Mode[^6]把“研究和决策”与“正式修改”分开，使错误方向、遗漏范围和验证困难在代码改变前可见。

[^6]: Plan Mode 是让 Agent 在正式修改前先研究项目、澄清问题并提出可审查方案的模式。

教师应按完整流程讲解，而不是只把它描述为“先列计划”：

```text
确认目标和边界
-> 只读探索项目
-> 区分事实、推断和未知项
-> 澄清会改变方向的问题
-> 比较方案与取舍
-> 形成可执行计划
-> 人工审查、修改和批准
-> 小步实现；新证据出现时更新计划
```

只读探索可以包括读取代码、搜索调用关系和运行非破坏性诊断，但具体允许的工具由产品决定。教师要纠正“Plan Mode 等于什么都不能做”和“能运行命令就已经开始实现”这两种误解。

### 6. 计划产物与审查方法

计划至少包含目标与基线、已确认事实、修改范围、非目标、实施步骤、依赖、验收方法、风险和暂停条件。

```text
目标：纯空格 q 返回 EMPTY_QUERY，保留缺失 q 的原行为。
证据：转换发生在 route，repository 只接收转换后的值。
范围：参数规范化和对应验证。
非目标：排序、分页、依赖升级。
步骤：修改边界 -> 补充验证 -> 检查正常行为 -> 检查 diff。
暂停条件：发现其他公共入口依赖当前转换规则。
```

教师审查计划时逐项检查：

1. 是否引用真实文件、调用关系或命令结果；
2. 是否覆盖入口、实现、调用方、配置和现有验证；
3. 是否把事实、推断和待决定事项分开；
4. 每一步是否有可观察的完成证据；
5. 是否夹带无关重构、升级或相邻功能；
6. 是否写明范围扩大或关键假设失效时如何暂停。

批准计划只是认可当前方向和范围，不表示所有假设已经成立，也不自动授权部署、发布、删除或权限扩大等后续动作。

### 7. Plan Mode 与直接执行

| 判断维度 | 直接执行 | 先计划 |
| --- | --- | --- |
| 范围 | 单文件、局部 | 跨模块、多入口 |
| 歧义 | 目标明确 | 多种合理方案 |
| 影响 | 低、易恢复 | 公共接口、数据或迁移 |
| 验证 | 快速确定 | 多环境或人工判断 |
| 熟悉度 | 路径和约束清楚 | 陌生仓库或隐含规则较多 |

直接执行仍要确认真实文件并验证结果；Plan Mode 也不要求为明确错字写长计划。没有专门模式按钮时，可以在 Prompt 中明确“第一阶段只读，方案确认后再修改”，并要求范围或关键假设变化时暂停更新计划。

### 8. 不同产品的 Plan 行为

依据 2026 年 8 月 9 日访问的官方文档：

| 产品 | 当前官方说明的重点 | 教师需要强调的边界 |
| --- | --- | --- |
| Claude Code | `plan` 是权限模式，用于分析代码库和提出方案；可读取文件并运行探索性命令 | 进入方式、模式切换和批准选项是 Claude Code 的产品行为 |
| Gemini CLI | Plan Mode 是受工具限制的只读环境，经过研究、计划、审查和批准，并可在指定目录写计划文件 | 计划文件例外和允许工具以当前 Gemini CLI 配置为准 |
| GitHub Copilot CLI | 分析请求和代码库、提出澄清问题、生成结构化计划并等待批准 | 官方流程在批准后继续实施和验证 |
| OpenAI 官方指导 | 按用户授权范围区分分析、实现和需要确认的外部、高影响或扩大范围动作 | 这是任务边界原则，不能据此虚构统一的 Codex Plan Mode 命令 |

快捷键、命令、计划文件位置、工具限制和批准选项不能在产品之间互相套用。

### 9. 小步迭代与修改预算

修改预算[^7]限定当前一步允许改变的范围。

[^7]: 修改预算是当前一步允许改变的最大范围。

```text
允许：参数规范化和对应验证
不允许：API 改名、依赖升级、排序重构
扩大条件：共享函数影响其他公共入口
```

每步结束后检查文件变化和局部结果，避免顺手重构、无关格式化和覆盖用户内容。

### 10. 错误反馈与重新规划

失败先分为：

```text
需求 | 代码 | 测试 | 配置 | 依赖 | 权限 | 环境
```

随后形成新假设，并选择能区分候选原因的最小动作。结果符合预期时继续；目标范围内的路径或依赖变化时更新计划；若出现公共接口变化、范围外文件、生产数据或高影响外部动作，则暂停并重新确认。

### 11. Human-in-the-loop 与检查点

人工检查点适合：产品行为选择、难恢复数据操作、外部写入、权限扩大、证据冲突和视觉体验判断。

Agent 应提供事实、选项、影响和建议，而不是只问“可以继续吗”。范围内的读取、局部修改和非破坏性验证不必每步确认。

中间检查点只保留：当前目标、已完成证据、修改范围、被否定假设、最新验证、下一步和待决定事项。

### 12. 验收与完成

验收点[^8]必须可观察，并逐项对应需求。

[^8]: 验收点是用来判断某一步是否真正完成的证据。

```text
步骤验收：纯空格不再进入查询
阶段验收：空输入和正常查询都符合规则
最终验收：需求、检查、diff 和剩余风险均已核对
```

最终报告包含：完成结果、修改范围、实际验证、未运行项和剩余风险。不能把“应该通过”写成“已经通过”。

## 五、课堂教学过程（90 分钟）

| 教学环节 | 时间 | 教师讲授内容 | 讲解重点 |
| --- | ---: | --- | --- |
| 情境导入 | 7 分钟 | 展示 Agent 连续修改却越修越错的记录 | Act 后缺少 Observe 与 Update |
| 两层工作流 | 13 分钟 | 讲解四阶段和内部反馈循环 | 阶段可以回退 |
| 修改前分析与计划 | 12 分钟 | 建立基线，改写低质量计划 | 计划来自真实证据 |
| Plan Mode 完整流程 | 14 分钟 | 讲解只读探索、澄清、方案比较、计划生成与审查 | 计划是可审查的决策阶段 |
| 模式选择与产品差异 | 8 分钟 | 对比直接执行及各产品 Plan 行为 | 通用方法与产品规则分开 |
| 小步、反馈与人工检查点 | 11 分钟 | 修改预算、错误分类和暂停条件 | 每轮产生信息增量 |
| 教师现场演示 | 20 分钟 | 演示空搜索 Bug 的完整循环 | 真实结果改变下一步 |
| 总结 | 5 分钟 | 回顾验收与完成条件 | 计划、行动、证据一致 |

### 1. 情境导入（7 分钟）

教师展示：Agent 看到一次 `AssertionError` 后连续修改 repository、service 和 route，却没有记录输入、期望、实际值和失败阶段。

教师指出：问题不在于修改次数，而在于每次 Act 后都没有形成 Observe，也没有用结果更新假设。

```text
只 Act，不 Observe = 连续猜测
```

### 2. 两层工作流（13 分钟）

教师先讲四阶段：

- Explore 建立基线和影响范围；
- Plan 确定步骤、依赖和验收点；
- Implement 做当前最小修改；
- Verify 重新验证原问题、正常行为和最终差异。

然后讲一轮小循环：

```text
Plan：检查 repository 是否转换空字符串。
Act：读取查询构造函数和调用方。
Observe：repository 只接收 "*"，转换发生在 route。
Update：不修改 repository，下一步检查 route 默认值。
```

教师强调，第一次假设被否定并不代表工作流失败；能够根据证据纠偏正是工作流的价值。

### 3. 修改前基线与计划（12 分钟）

教师把“搜索有时不正常”改为可复查基线：

```text
GET /users?q=%20%20
当前：200，53 条记录
目标：400，EMPTY_QUERY
```

随后将“分析、编码、测试”改写为：

```text
1. 定位 q 第一次转换的位置；
2. 确认缺失 q 与纯空格的产品规则；
3. 在责任层做最小修改；
4. 验证空输入、正常查询和分页；
5. 检查最终差异和未验证风险。
```

每一步补充动作、证据、依赖和停止条件。

### 4. Plan Mode 完整流程（14 分钟）

教师先说明 Plan Mode 的目的：不是生成更长的回答，而是把研究、取舍和风险在修改前变成可审查内容。

教师按七步依次展示：

```text
目标与边界 -> 只读探索 -> 澄清未知项 -> 比较方案
-> 形成计划 -> 审查批准 -> 实施中更新计划
```

以空搜索为例，教师演示 Agent 如何读取 route、service、repository 和现有验证，怎样把“route 中出现 q.strip()”记录为事实，把“其他入口可能复用该规则”记录为待验证推断。

随后展示三个候选责任层：route、service 和 repository。教师从错误表达能力、调用方影响和验证成本说明取舍，避免只给结论。

教师使用以下六问审查生成的计划：

```text
有真实代码证据吗？
入口、实现、调用方和验证是否覆盖？
事实、推断和待决定事项分开了吗？
每一步有可观察证据吗？
是否夹带无关改动？
何时必须暂停或重新规划？
```

教师指出：批准只确认当前方向和范围；若实现中发现共享入口或兼容性约束，仍要暂停并更新计划。

### 5. 模式选择与产品差异（8 分钟）

教师按范围、歧义、影响和验证难度选择模式。明确错字或低风险局部修改可以直接执行；跨模块功能、公共接口和迁移应先计划。

随后分别说明 Claude Code、Gemini CLI、GitHub Copilot CLI 的 Plan 行为，以及 OpenAI 官方指导中的任务授权边界。强调各产品允许的工具、快捷键、计划文件和审批方式不能混写。

### 6. 小步、反馈与人工检查点（11 分钟）

教师为搜索案例设置修改预算：

```text
只修改纯空格输入处理和对应验证；
不改变缺失参数、排序、分页和依赖。
```

然后说明失败分类和三种后续状态：继续、更新计划、暂停。

教师用重复用户名迁移说明人工检查点：如果自动重命名会改变真实账号，应先展示重复数量、处理选项和影响，再请求决定。人工确认方向后仍需自动验证。

### 7. 教师现场演示（20 分钟）

#### 7.1 演示 Prompt

```text
任务：修复纯空格搜索词会返回全部用户的问题。

第一阶段只读：
1. 建立当前行为基线；
2. 定位参数解析、查询实现和现有验证；
3. 区分事实、推断和必须确认的问题；
4. 给出不超过 5 步的计划和验收点。

计划确认后再小步实现。
结果与预期不同时先更新计划，不扩大到排序、分页或依赖升级。
```

#### 7.2 建立基线与形成计划

教师记录输入、状态码、返回数量、正常查询基线和测试收集数量。若测试在导入阶段失败，先将其归类为环境问题。

教师先展示一份只有“分析、编码、测试”的低质量计划，再要求 Agent 根据已发现的文件与调用关系重写。教师检查计划是否引用真实文件，是否区分缺失参数与纯空格，是否包含修改范围、非目标、正常行为验收和停止条件。

#### 7.3 审查并批准计划

教师逐项核对事实来源、步骤依赖和验收证据，删除计划中无关的排序重构。对“纯空格是否等同于缺失参数”使用预设产品决定，并明确批准范围只包含参数规范化和对应验证。

#### 7.4 用证据纠正误判

Agent 首先检查 repository，但证据表明转换发生在 route 默认值。教师要求更新假设和计划，不允许两个模块一起修改。

教师说明：计划批准后仍可被证据纠正。此时应更新责任层和验证范围，而不是机械执行原计划。

#### 7.5 最小修改与分层验证

教师要求 Agent 只修改参数规范化和对应验证，再按以下顺序检查：

```text
纯空格 -> 空字符串 -> 缺失 q -> 正常搜索
-> 排序与分页 -> 相关检查 -> 最终 diff
```

最后形成包含结果、修改、验证、未验证项和剩余风险的交付说明。

### 8. 课堂总结（5 分钟）

```text
主流程：Explore -> Plan -> Implement -> Verify
小循环：Plan -> Act -> Observe -> Update

修改前：目标 + 基线 + 范围 + 约束 + 验收
修改中：小步骤 + 修改预算 + 真实反馈
需要人：产品歧义 + 高影响 + 范围扩大
完成：需求对应 + 实际验证 + diff + 未验证项
```

## 七、常见问题与处理

| 常见问题 | 教师处理方式 |
| --- | --- |
| 把工作流理解为固定顺序 | 强调 Verify 可以回到 Explore 或 Plan |
| 计划只有三个抽象标题 | 补充范围、动作、依赖、证据和停止条件 |
| 所有任务都先写长计划 | 让计划成本与任务风险相称 |
| 没有复现就修改 | 先建立可重复基线 |
| 把命令结束当作验证通过 | 检查退出状态、数量和失败阶段 |
| 失败后重复同一命令 | 先形成新假设和最小诊断动作 |
| 一次修改多个独立行为 | 重新设置当前修改预算 |
| 所有步骤都请求确认 | 只在关键决策和高影响节点介入 |
| 局部检查通过就完成 | 区分步骤、阶段和最终验收 |
| 把一种 Plan Mode 写成通用规则 | 回到对应供应商最新官方文档 |
| 提前深入工具权限或测试驱动 | 明确第七、八周课程边界 |

## 八、课堂总结与板书

### 1. 课堂总结

教师应再次强调：

1. 完整任务不是一次代码生成；
2. Explore 提供基线和影响范围；
3. Plan 把证据变成可更新步骤；
4. Implement 使用小步和修改预算；
5. Verify 用真实结果支持交付；
6. 失败应增加信息并改变下一步；
7. 人工判断集中在关键决策；
8. 产品 Plan Mode 行为必须分别确认。

### 2. 板书设计

```text
Week 6  编码 Agent 工作流

Explore -> Plan -> Implement -> Verify

Plan -> Act -> Observe -> Update -> ...
         小动作   真实证据   新判断

修改前：目标 | 基线 | 范围 | 约束 | 验收
计划：目标 | 动作 | 证据 | 依赖
执行：小步骤 + 修改预算
失败：分类 -> 新假设 -> 最小动作
人工：产品选择 | 高影响 | 范围扩大
完成：需求 + 验证 + diff + 未验证项
```

## 九、与前后课程的衔接

### 1. 与第三至五周的衔接

第三周的任务拆解、第四周的运行级上下文和第五周的项目地图，共同成为本周探索与计划的输入。

### 2. 与第七周的衔接

本周知道工作流需要搜索、读取、编辑、运行和查看差异。第七周将系统讲解工具调用、权限管理和执行安全。

### 3. 与第八、九周的边界

本周只把测试和 diff 作为反馈与验收证据。测试驱动开发安排在第八周，Git、PR 和系统代码审查安排在第九周。
