# 第十二周教案：多 Agent 协作与代码重构

## 一、课程基本信息

- **课程名称**：YatOL 人机协作课程
- **授课主题**：多 Agent 协作与代码重构
- **建议课时**：2 学时（90 分钟）
- **适用对象**：完成前十一周课程内容的学生
- **先修内容**：需求、上下文、工作流、工具、测试、审查、风险、MCP 与 Skill
- **实践载体**：支持 Subagent 的编码 Agent 环境、具有测试的示例仓库

## 二、教学目标

完成本节课后，学生应能够：

1. 说明 Subagent[^1]、主 Agent 和最终集成负责人的关系。
2. 区分 manager[^2]、handoff[^3]和代码编排三类协作方式。
3. 为分析、编码、测试、文档和审查角色编写可验证的任务契约[^4]。
4. 判断哪些子任务适合并行，哪些必须按依赖顺序串行。
5. 通过统一基线、需求版本、项目规则和证据格式保持上下文同步。
6. 识别重复工作、结论冲突、文件覆盖和无人负责集成等协作失败。
7. 区分保持外部行为的重构[^5]与新增或改变产品行为的功能修改。
8. 使用基线、特征测试、小步修改、diff 审查和回滚完成安全重构。
9. 输出包含动机、范围、行为不变项、验证和剩余风险的重构说明。
10. 将十二周课程能力组织为完整的编码 Agent 工程闭环。

[^1]: Subagent 是主 Agent 为一个有边界的子任务启动的专业 Agent。
[^2]: Manager 模式是主 Agent 保持控制并调用专业 Agent，最终由主 Agent 汇总结果。
[^3]: Handoff 是当前 Agent 把后续处理控制权交给另一个专业 Agent。
[^4]: 任务契约是对子任务目标、输入、权限、输出和完成条件的明确约定。
[^5]: 重构是在保持外部可观察行为的前提下改善代码内部结构。

## 三、教学设计与课前准备

### 1. 教学重点与难点

#### 教学重点

- **重点**：多 Agent 的收益来自独立任务和清楚分工，不来自 Agent 数量。
- **重点**：读密集工作更容易并行，写密集工作必须明确所有权和合并策略。
- **重点**：重构必须有行为基线、可审查的小步变化和持续验证。

#### 教学难点

- **难点**：不同产品用相似词表示不同编排能力，不能把 SDK 模式写成所有编码 Agent 的统一行为。
- **难点**：多个 Agent 给出相同结论仍可能共同依赖错误上下文。
- **难点**：测试绿色不自动证明重构保持全部行为，尤其是公共接口、性能和副作用。

#### 课程边界

- 第三周已经讲任务拆解，本周只讨论拆解结果怎样形成 Agent 间契约和依赖图。
- 第八、九周已经讲测试和代码审查，本周把它们作为重构保护与多 Agent 集成证据。
- 第十、十一周已经讲风险、MCP 和 Skill，本周只讨论怎样把这些能力按最小权限分给不同 Agent。
- 不展开分布式 Agent 平台部署、跨组织身份联邦或复杂架构迁移实现。

### 2. 教学准备

#### 教师准备

- 准备一个同时包含权限、测试覆盖和依赖方向变化的 diff，供三个只读角色分别审查。
- 准备两个 Agent 同时编辑同一文件造成覆盖的反例。
- 准备一个混合输入验证、金额计算、库存写入和通知职责的订单处理函数，并为这四类行为各准备至少一个现有测试。
- 保存重构前测试基线、每一步 diff 和重构后验证输出。
- 准备 OpenAI Codex Subagents、OpenAI Agents SDK、Anthropic Claude Code 和 Google ADK 的官方模式对照。

#### 环境准备

- 固定同一仓库、基线提交、需求版本和项目指令。
- 分析、测试与审查角色默认只读；只有一个实现角色拥有目标文件写权限。
- 不连接生产数据，不执行外部写入或发布。
- 能查看每个 Agent 的任务输入、返回摘要、修改文件和最终验证结果。

## 四、核心知识体系

### 1. 什么时候需要多 Agent

满足以下条件时，可以考虑使用多 Agent：

- 可以拆成相互独立的证据收集或专业视角；
- 单个子任务边界清楚并能独立验收；
- 并行节省的时间大于协调成本；
- 主 Agent 能比较、去重和整合结果；
- 工具、权限和写入所有权可以清楚分配。

以下情况使用单 Agent：任务只有一个有边界的输出、后一步必须读取前一步结果、多个步骤反复修改同一文件，或各分支无法独立验收。

### 2. Subagent 与主 Agent

```text
用户目标与授权
-> 主 Agent：拆分、分派、同步、汇总、验证、交付
   -> Subagent A：限定分析
   -> Subagent B：限定测试检查
   -> Subagent C：限定安全审查
-> 单一实现者：修改已确认范围
-> 主 Agent：集成检查与最终说明
```

Subagent 应在独立上下文中处理限定任务，并把摘要和证据返回主 Agent。独立上下文可以减少主会话噪声，但也会带来信息缺失，因此任务契约必须包含必要规则、基线和输出格式。

### 3. 三种编排方式

#### Manager：主 Agent 保持控制

主 Agent 把专业 Agent 作为工具调用，自己保留用户对话和最终答案所有权。适合代码审查、资料核验和多视角分析。

#### Handoff：专业 Agent 接管

当前 Agent 把控制权交给更适合继续处理的 Agent。适合需要专业角色直接与用户持续交互的场景。

#### 代码编排

应用代码确定顺序、并行、循环、重试和停止条件。当这些控制规则必须固定、可测试或可审计时，使用代码编排。

OpenAI Agents SDK 官方文档明确区分 agents as tools 的 manager 模式与 handoffs；Google ADK 提供 Sequential、Parallel、Loop 等工作流编排；这些都是对应 SDK 的具体能力。Codex 和 Claude Code 的 Subagent 工作流又有自己的触发、线程和配置方式。

### 4. 产品差异必须分别说明

| 产品或框架 | 官方当前重点 | 课程中的通用抽象 |
| --- | --- | --- |
| OpenAI Codex | 可按请求或项目/Skill 指令启动 Subagent，并在主任务汇总 | 有边界的并行子任务 |
| OpenAI Agents SDK | agents as tools 与 handoffs，也可由代码编排 | manager、handoff、代码流 |
| Anthropic Claude Code | 自定义 Subagent 有独立上下文、工具和权限 | 专业角色与上下文隔离 |
| Google ADK | LLM 路由及 Sequential、Parallel、Loop 工作流 | 动态或确定性编排 |

![Google ADK 官方架构图：模型、Agent、工具、会话、运行器、事件与服务共同组成 Agent 应用](https://storage.googleapis.com/gweb-developer-goog-blog-assets/images/ADK-architecture.original.png "Google ADK 官方架构图")

图片来源：[Google Developers Blog：Agent Development Kit—multi-agent applications](https://developers.googleblog.com/agent-development-kit-easy-to-build-multi-agent-applications/)（访问日期：2026-08-11）。授课时应明确：该图只说明 Google ADK，不是所有编码 Agent 的统一架构。

产品入口、默认权限、是否主动委派和上下文传递方式会变化。课堂只把已由官方文档确认的行为归给对应产品。

### 5. 任务契约

每个子任务至少写明：

| 字段 | 示例 |
| --- | --- |
| 目标 | 找出权限 diff 中的高置信风险 |
| 输入 | `main...HEAD`、需求说明、AGENTS.md |
| 范围 | 只读 `src/auth` 与相关测试 |
| 工具与权限 | 搜索、读文件、运行指定测试；不编辑 |
| 输出 | 严重度、位置、触发条件、证据、未知项 |
| 完成条件 | 检查所有变更文件并报告未验证路径 |
| 停止条件 | 基线不明、需要外部凭据或结论无证据 |

只写“检查代码”会导致角色边界、深度和输出互不一致。

### 6. 角色分工

| 角色 | 核心职责 | 建议权限 |
| --- | --- | --- |
| 需求分析 Agent | 固定事实、歧义、范围和依赖 | 只读 |
| 代码地图 Agent | 找入口、调用链、数据流和影响文件 | 只读 |
| 测试 Agent | 检查行为基线、覆盖和验证命令 | 只读或测试文件限定写入 |
| 安全审查 Agent | 检查输入、权限、秘密和依赖风险 | 只读 |
| 编码 Agent | 按确认方案实现一个明确步骤 | 限定工作区写入 |
| 文档 Agent | 根据已验证实现更新说明 | 文档限定写入 |
| 集成负责人 | 解决冲突、运行完整验证、决定交付 | 由主 Agent 或人承担 |

角色名称不是重点，关键是避免职责重叠和无人承担最终判断。

### 7. 并行与串行的判断

适合并行的条件：输入独立、没有先后依赖、写入不重叠、结果可分别验证。

```text
适合并行：
安全审查 | 测试缺口 | 架构影响 | 文档核验

适合串行：
确认需求 -> 建立测试基线 -> 修改代码 -> 运行验证 -> 更新文档
```

OpenAI Codex 当前官方建议优先把并行 Agent 用于探索、测试、分诊和总结等读密集任务，对多个 Agent 同时编辑代码保持谨慎。即使使用独立 worktree[^6]，语义冲突仍需集成负责人处理。

[^6]: Worktree 是让同一 Git 仓库在多个目录中同时检出不同工作状态的机制。

### 8. 上下文同步

所有角色需要共享：

- 同一需求版本和已确认产品决定；
- 同一基线提交与比较范围；
- 适用的项目指令和禁止修改项；
- 当前已完成步骤与文件状态；
- 术语、输出格式和证据标准；
- 新出现的风险、失败和用户决定。

主 Agent 不应把完整嘈杂日志复制给所有角色，而应传递与各自任务相关的最小充分上下文。关键决定变化时，要明确通知受影响角色，不能期待它们自动知道。

### 9. 冲突处理

冲突分为四类：

1. **事实冲突**：对 API、版本或代码行为判断不同，回到官方文档和运行证据；
2. **方案冲突**：多个实现都可能成立，由负责人按需求、风险和维护成本取舍；
3. **写入冲突**：多个 Agent 修改同一行或相互依赖文件，停止并指定单一所有者；
4. **优先级冲突**：安全、性能和交付目标竞争，需要人确认取舍。

技术事实不能通过多数投票决定。三个 Agent 使用同一错误文档，仍会一起得出错误结论。

### 10. 多 Agent 的成本与停止条件

每个 Agent 都会消耗时间、token 和工具调用，并增加协调与验证工作。停止继续分派的条件包括：

- 新角色无法提供不同证据或独立视角；
- 子任务已经小到单 Agent 更快；
- 写入边界无法安全分离；
- 汇总成本超过预计收益；
- 当前缺口需要用户决定而非更多分析。

### 11. 重构与功能修改

重构保持外部可观察行为。以下对照要明确：

| 修改 | 是否属于纯重构 | 原因 |
| --- | --- | --- |
| 将长函数按职责拆成私有函数 | 满足条件时是 | 参数、返回值、副作用和调用顺序均不变 |
| 修改内部变量名 | 满足条件时是 | 所有引用已同步，且不影响序列化、反射或公开契约 |
| 改变折扣规则 | 不是 | 产品结果变化 |
| 修改公开 API 参数 | 不是纯重构 | 调用契约变化 |
| 消除同一概念的重复代码 | 满足条件时是 | 两处由同一规则驱动，合并后结果与错误行为不变 |

行为修复与结构整理应分步提交和验证，避免失败时无法判断原因。

### 12. 重构前建立基线

先确认：

- 相关测试当前是否通过；
- 公共接口、错误和副作用是什么；
- 性能或资源约束是否重要；
- 当前工作区是否已有用户修改；
- 哪些行为没有测试保护。

遗留代码缺少规格时，可添加特征测试[^7]记录当前可观察行为。特征测试不是宣布旧行为合理，而是先建立可比较基线。

[^7]: 特征测试是记录现有系统当前行为、用于保护重构过程的测试。

### 13. 小规模重构

#### 命名优化

名称要表达领域含义。修改前搜索所有引用，并区分内部变量、公共字段、序列化键和数据库列；后几类可能属于兼容性变化。

#### 函数拆分

按职责和副作用切分，明确每个函数的输入、输出和状态变化。目标不是减少行数，而是让责任和验证边界更清楚。

#### 重复代码消除

两段代码外形相似不等于同一业务概念。只有规则、变化原因和生命周期一致时才适合抽取公共实现，否则会制造错误耦合。

### 14. 大规模重构

```text
定义目标结构
-> 建立基线与特征测试
-> 引入接口或兼容层
-> 迁移一条完整路径
-> 对比旧新结果
-> 设置阶段检查点
-> 逐步扩大范围
-> 删除旧路径
```

每个阶段应保持可构建、可验证、可审查和可恢复。多 Agent 可以并行分析模块边界和测试缺口，但跨模块集成仍应由明确所有者推进。

### 15. 重构验证

验证不只看测试数量：

- 基线测试与新增特征测试；
- 相关模块和项目完整检查；
- 公共 API、序列化和配置兼容；
- 数据写入、日志和外部副作用；
- 性能、并发和资源使用；
- 最终 diff 是否只包含结构变化；
- 未验证环境与剩余风险。

### 16. 重构说明

```text
动机：为什么需要整理结构
范围：修改和未修改哪些模块
结构变化：职责怎样重新分配
行为不变项：哪些接口、结果和副作用保持不变
验证：实际命令、结果和比较证据
剩余风险：哪些环境或路径未验证
下一步：后续候选，不混入本次 diff
```

## 五、课堂教学过程（90 分钟）

| 教学环节 | 时间 | 教师讲授内容 | 讲解重点 |
| --- | ---: | --- | --- |
| 情境导入 | 6 分钟 | 三个 Agent 同时改同一文件造成覆盖 | 并行不等于协作 |
| 协作模式 | 13 分钟 | manager、handoff、代码编排和产品差异 | 谁拥有最终输出 |
| 任务契约与角色 | 14 分钟 | 目标、输入、权限、输出和停止条件 | 可独立验收 |
| 并行、同步与冲突 | 13 分钟 | 依赖、写入所有权和证据冲突 | 读并行、写谨慎 |
| 重构闭环 | 16 分钟 | 基线、特征测试、小步修改、验证 | 行为保持 |
| 教师现场演示 | 23 分钟 | 多角色分析并拆分订单函数 | 单一实现者、主 Agent 集成 |
| 课程总结 | 5 分钟 | 十二周能力闭环 | 工程证据与人类责任 |

### 各环节实施详案

#### 1. 导入：并行不等于协作

教师展示两个 Agent 分别“提取函数”和“修复折扣错误”，最后一方覆盖另一方修改的记录。指出速度、文件变化和测试绿色都不能证明协作成功，必须先明确任务依赖和代码所有权。

#### 2. 选择协作模式

用代码审查说明 manager：安全、测试、架构角色返回结果，主 Agent 汇总。用专业支持路由说明 handoff：专业 Agent 接管后续交互。再说明固定迁移流水线更适合代码编排。

#### 3. 编写任务契约

把“检查订单代码”改写为三个有边界的只读契约：职责地图、测试保护、兼容风险。逐项讲清输入、范围、权限、证据格式和停止条件。

#### 4. 并行、同步与冲突

绘制依赖关系：三个只读分析可以并行，方案选择依赖分析结果，代码修改依赖方案，完整验证依赖修改完成。事实冲突回到共同基线、官方资料和运行证据，不进行简单投票。

#### 5. 重构与功能修改分离

对比“提取金额计算函数”和“改变折扣规则”。前者应保持输入输出，后者需要新需求与新测试。两者混在同一 diff 会让失败原因、审查范围和回滚对象都不清楚。

#### 6. 大规模重构的检查点

教师讲解接口层、兼容层、单路径迁移、双跑对比和逐步删除旧路径。强调每个阶段都要能运行、能审查、能停止，不能把一次性重写描述成“更彻底的重构”。

## 六、典型案例与边界

### 案例一：并行审查同一 diff

安全 Agent 检查越权，测试 Agent 检查覆盖，架构 Agent 检查依赖方向。三者只读、共享同一比较基线且输出维度不同，可以并行；主 Agent 负责去重、验证和排序。

### 案例二：两个 Agent 编辑同一服务

一个提取函数，另一个修 Bug，修改相互覆盖。应由分析角色只读给建议，再指定一个实现者按顺序完成；或把任务切成真正不重叠的文件边界。

### 案例三：研究结论冲突

两个 Agent 对第三方 API 参数给出不同结论。应比较官方文档版本、项目锁定依赖和本地类型定义，不能以 Agent 数量决定事实。

### 案例四：长函数拆分

先固定输入验证、金额计算、库存写入和通知副作用，再逐个提取。每一步运行相关测试并检查公共接口与调用顺序。

### 案例五：错误消除重复

两段折扣代码形式相同，但服务于不同业务规则。机械合并会让未来变化互相牵制。先确认是否同一领域概念，再决定抽取。

### 案例六：旧系统大迁移

通过 repository 接口建立兼容层，先迁移一个读路径并对比旧新结果，再逐步扩大。并行分析可加速准备，但数据库迁移和最终集成必须受控串行。

## 七、教师现场演示

### 演示任务：多角色分析并小步拆分订单处理函数

```text
目标：在不改变外部可观察行为的前提下，拆分过长的订单处理函数。

共同上下文：
- 基线：main 的指定提交；
- 需求：只做结构重构，不改变折扣、库存、错误和通知行为；
- 项目规则：遵守 AGENTS.md，禁止新增依赖；
- 最终所有者：主 Agent 负责汇总、验证和交付。

分工：
1. 代码地图 Agent：只读描述职责、调用方、副作用和候选切分点；
2. 测试 Agent：只读检查现有测试能否保护关键行为；
3. 审查 Agent：只读列出兼容、安全和数据一致性风险；
4. 主 Agent：汇总冲突，只选择一个最小重构步骤；
5. 编码 Agent：只实现该步骤，不改变公共接口；
6. 主 Agent：运行测试、检查 diff，确认行为证据后决定是否继续。
```

### 演示步骤与预期结果

1. 记录基线测试、工作区状态和公共接口。
2. 向三个只读角色发送同一需求版本、基线和项目规则。
3. 并行收集职责地图、测试缺口和风险，要求引用文件证据。
4. 主 Agent 对冲突结论回到代码和测试验证，不投票。
5. 选择“提取纯金额计算函数”作为本轮唯一重构目标。
6. 单一编码 Agent 修改目标文件；其他角色不写入。
7. 运行最相关测试、相关模块测试和项目规定的完整检查。
8. 检查 diff 没有改变公共接口、折扣结果或通知顺序。
9. 输出本轮重构说明和下一轮候选，下一轮不自动继续。

### 演示交付格式

```text
动机：订单函数同时承担验证、计算和持久化，难以独立理解。
本轮范围：只提取 calculate_order_total；无依赖和接口变化。
行为不变：折扣规则、舍入、错误类型、库存和通知顺序。
协作：3 个只读分析角色；1 个实现角色；主 Agent 集成。
验证：订单模块 42 passed；完整测试 286 passed；lint 通过。
差异：1 个生产文件、1 个测试文件，无范围外修改。
未验证：未运行生产性能基准；本次提取不改变 I/O 路径。
下一步候选：分离库存写入，但需先补失败回滚测试。
```

### 课堂追问

- 三个 Agent 都支持同一结论，为什么仍可能错误？
- 仅按文件不同就能判断任务可并行吗？
- 多 Agent 在什么情况下反而更慢、更贵？
- 没有测试的遗留代码应怎样开始重构？

## 八、常见问题与处理

### 多 Agent 是否一定提高质量

不会。若所有角色使用同一错误假设、边界重叠或无人验证，更多 Agent 只会复制错误并增加沟通成本。质量来自独立证据、清楚契约和最终集成。

### 重构测试全绿是否足够

不够。还要核对测试是否覆盖本次必须保持的成功、失败和边界行为，并检查公共接口、数据副作用、性能要求和最终 diff。未被测试或观察记录覆盖的行为仍可能变化。

### 常见误区

- 为简单任务启动多个 Agent。
- 子任务没有输入版本和输出格式。
- 让多个 Agent 同时编辑相同文件。
- 认为使用 worktree 就不会有语义冲突。
- 用多数投票解决事实分歧。
- 子 Agent 完成后不由主 Agent 核对原始证据。
- 没有明确最终集成与交付负责人。
- 重构时顺便修 Bug、改规则和升级依赖。
- 一次性重写后只运行少量测试。
- 把未验证的性能或兼容性写成“保持不变”。

## 九、课堂总结与板书

### 十二周课程能力闭环

```text
明确 Prompt 与目标
-> 分析需求、风险和影响范围
-> 提供项目与文件上下文
-> 阅读真实代码并引用证据
-> 规划、执行、观察和纠偏
-> 在权限范围内调用工具
-> 用测试建立可重复反馈
-> 审查 diff、Git 和质量证据
-> 控制数据、依赖、权限与外部影响
-> 用 MCP 连接能力、用 Skill 复用方法
-> 必要时用多 Agent 分工
-> 在验证保护下重构与演进
```

成熟的人机协作不是把责任交给更多 Agent，而是设计清楚的目标、上下文、分工、权限、反馈和验收，并由明确负责人完成最终集成和交付判断。

### 板书设计

```text
Manager：主 Agent 保持控制并汇总
Handoff：专业 Agent 接管后续处理
Code orchestration：程序控制顺序、并行、循环与停止

并行条件：独立输入 + 无前置依赖 + 不重叠写入 + 可独立验收
冲突处理：共同基线 + 官方来源 + 运行证据，不靠投票

重构闭环：基线 -> 小步修改 -> 测试 -> diff -> 决定下一步
最终必须有一个集成与交付责任人
```

## 十、与课程整体的衔接

本周不是新增一个孤立工具，而是把前十一周能力整合为完整开发闭环。无论单 Agent 还是多 Agent，Prompt、上下文、工具、测试、审查、风险和人的责任都不会消失。
