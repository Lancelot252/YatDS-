# 第四周教案：编码 Agent 的上下文工程与 AGENTS.md

## 一、课程基本信息

- **课程名称**：YatDS 人机协作课程
- **授课主题**：编码 Agent 的上下文工程与 `AGENTS.md`[^1]
- **建议课时**：2 学时（90 分钟）
- **适用对象**：具备基础项目阅读能力的计算机相关专业学生
- **先修内容**：Prompt 工程、需求分析与任务拆解
- **实践载体**：编码 Agent、包含构建与测试脚本的示例仓库

[^1]: `AGENTS.md` 是写给编码 Agent 看的项目规则文件。

## 二、教学目标

完成本节课后，学生应能够：

1. 解释 Prompt[^2] 与编码 Agent 上下文[^3]的区别。
2. 按仓库级、目录级、任务级和运行级组织项目信息。
3. 识别编码 Agent 需要的项目、文件、依赖、规范、测试和修改约束。
4. 识别上下文不足、上下文污染、过时信息和指令冲突。
5. 在长会话失真时整理干净会话重建包。
6. 区分当前 Prompt、README、设计文档和 `AGENTS.md` 的用途。
7. 编写简短、准确、可执行、可验证的 `AGENTS.md`。

[^2]: Prompt 是用户交给 Agent 的任务说明。
[^3]: 上下文是 Agent 完成任务需要知道的文件、规则和运行情况。

## 三、教学设计与课前准备

### 1. 教学重点与难点

#### 教学重点

- Prompt 与 Context[^4] 在编码 Agent 使用中的分工。
- 仓库级、目录级、任务级和运行级上下文。
- 文件、调用关系、规范、测试和修改约束的组织方式。
- `AGENTS.md` 的内容边界、目录作用域和核验方法。
- 长会话中的信息更新、压缩和干净重建。

[^4]: Context 是“上下文”的英文写法，指任务所需信息。

#### 教学难点

- 理解上下文充分不等于把整个仓库提供给 Agent。
- 区分真实项目事实、未经证实的推断和快速变化的运行结果。
- 区分跨任务长期规则与一次性需求。
- 理解不同编码 Agent 对项目指令文件的发现规则可能不同。
- 清理旧信息时保留仍然有效的决定和证据。

#### 课程边界

- 第二周已经讲解 Prompt 的组成与常用方法，本周不重复展开 Role、Few-shot 和输出格式。
- 本周只说明入口、调用方和测试为何属于上下文，系统的代码阅读和调用链分析留到第五周。
- 本周只说明上下文怎样随执行更新，完整 Agent 工作流留到第六周。
- 本周记录测试与质量命令，但不展开工具权限和测试驱动开发。

### 2. 教学准备

#### 教师准备

- 准备同一编码要求在空白会话和真实仓库中的输出对比。
- 准备一个小型示例仓库，包含：
  - README；
  - 依赖清单和 lockfile[^5]；
  - 应用入口；
  - route、service 和测试目录；
  - 生成文件与生成脚本；
  - lint[^6]、类型检查或 CI[^7] 配置；
  - 根目录规则和局部目录例外。
- 准备一份包含错误命令、抽象规则和临时要求的 `AGENTS.md` 反例。
- 准备一段包含旧代码、旧日志和已取消方案的长会话案例。
- 提前核验演示中需要运行的命令。

[^5]: lockfile 是记录依赖准确版本的文件。
[^6]: lint 是自动检查代码格式和常见问题的工具。
[^7]: CI 是代码变更后自动运行构建、检查和测试的流程。

#### 学生准备

- 复习第二周 Prompt 的背景、目标、输入、输出和约束。
- 复习第三周事实、推断和待确认事项的区别。
- 了解 README、依赖清单、脚本和测试文件的基本作用。

#### 环境准备

- 示例仓库可由编码 Agent 正常读取。
- 演示环境能够进行项目搜索和文件读取。
- 测试中预留一个稳定、可复现的失败。
- 演示不依赖生产密钥、真实用户数据或外部生产系统。
- 预先保存必要的官方文档链接和关键说明。

## 四、核心知识体系

### 1. Prompt 与编码 Agent 上下文

```text
Prompt：本次要完成什么
Context：完成本次编码工作必须知道什么
AGENTS.md：跨任务长期有效的仓库工作规则
```

Prompt 负责说明本次目标、交付物、边界和验收。Context 包括项目文件、配置、测试、错误输出、当前决定和持久项目指令。

只有 Prompt 而缺少项目上下文，Agent 容易猜测框架、文件和测试方式；只有项目上下文而没有明确 Prompt，Agent 又不知道本次应解释、诊断、规划还是修改。

### 2. 编码 Agent 为什么需要上下文

面对“增加用户查询接口”，Agent 需要判断：

- 项目使用哪种语言和框架；
- 路由、服务和数据访问代码位于哪里；
- 是否已有相似接口；
- 认证、响应和错误格式怎样定义；
- 测试如何组织；
- 修改后应运行哪些检查；
- 哪些接口和目录不能随意改变。

上下文帮助 Agent 完成四种判断：理解目标、定位代码、遵循项目和验证结果。

### 3. 四层上下文

| 层级 | 典型内容 | 主要来源 | 时效性 |
| --- | --- | --- | --- |
| 仓库级 | 技术栈、顶层目录、通用命令 | README、配置、CI、根指令 | 长期 |
| 目录级 | 模块职责、局部命令、特殊限制 | 模块文档、嵌套指令 | 中长期 |
| 任务级 | 当前目标、相关文件、验收和范围 | Prompt、issue、用户决定 | 单次工作 |
| 运行级 | 测试失败、日志、截图和当前 diff[^8] | 工具输出 | 快速变化 |

教师应强调：越靠近运行级，信息变化越快；旧测试输出不能继续代表修改后的项目状态。

[^8]: diff 是文件修改前后的内容差异。

### 4. 六类具体上下文

#### 4.1 项目上下文

包括项目用途、语言、框架、运行时版本、目录结构、依赖管理、应用入口和生成关系。

可靠来源包括依赖清单、lockfile、运行时版本文件、容器配置、CI 和真实入口代码。目录名只能形成初步判断，不能自动证明模块职责。

#### 4.2 文件上下文

文件上下文应包含：

- 真实路径；
- 相关函数、类或配置项；
- 文件职责；
- 与当前问题的关系。

只粘贴一个函数可能隐藏相邻错误处理、类型、调用方、fixture[^9] 和目录规则。

[^9]: fixture 是测试前准备好的数据、对象或环境。

#### 4.3 模块依赖关系

Agent 需要知道当前模块依赖谁，以及谁依赖当前模块。

```text
POST /login
  -> login route
  -> AuthService.authenticate
  -> UserRepository.findByEmail
  -> password verifier
  -> session issuer
```

本周只使用最小关系图说明上下文，不系统展开调用链追踪方法。

#### 4.4 代码规范上下文

包括命名、类型标注、错误处理、日志、架构分层、格式化、lint 和兼容要求。

规则应来自当前配置、CI、项目文档、成熟代码或团队确认的项目指令。应把“保持高质量”改成 Agent 可以执行的说明，例如“route 只处理 HTTP 输入输出，业务规则放入 service”。

#### 4.5 测试上下文

包括测试框架、目录、文件命名、fixture、相关测试命令、全量命令和需要验证的行为。

应区分“项目存在这个测试命令”和“本次已经运行且通过”。未运行的检查不得写成已经验证。

#### 4.6 修改约束

修改约束应明确允许范围、禁止事项、兼容要求和完成检查。公开 API[^10] 等已被调用方依赖的接口尤其需要保持兼容。

[^10]: API 是软件之间约定好的调用方式。

```text
- 只修改金额计算和对应测试；
- 不改变公开 API 字段和状态码；
- 不新增生产依赖；
- 不直接编辑 generated/；
- 修改 schema 后运行生成命令；
- 完成前运行相关测试并检查 diff。
```

禁止事项应同时给出正确操作路径。

### 5. 上下文选择原则

面对一条候选信息，可以判断：

1. 是否会改变当前分析或实现方案；
2. 是否帮助定位相关代码；
3. 是否帮助验证结果。

如果三项都不满足，就不应优先进入当前上下文。

编码 Agent 应按决策需要逐步取得上下文：先建立项目地图，再定位入口和相关文件，随后补充会影响修改或验证的测试、规范和当前运行结果。

### 6. 上下文不足

常见表现包括：

- 猜测语言、框架和版本；
- 使用不存在的文件；
- 重新实现已有功能；
- 选择错误测试命令；
- 随意改变公开接口；
- 无法说明结论来源；
- 询问本可从仓库查证的问题。

改进时应补充能够改变决策的证据，而不是重复“请认真完成”。

### 7. 上下文污染与过时信息

常见污染来源包括：

- 与当前代码问题无关的文件；
- 多个不同版本的旧代码片段；
- 修复前的旧测试日志；
- 未经验证的根因；
- 已取消的需求；
- 互相冲突的根目录和局部规则。

处理顺序是重新读取当前真实文件、保留最新运行状态、删除无关与重复材料、重新标记推断，并按来源、目录作用域和时效处理冲突。

### 8. 长会话与干净重建

当 Agent 反复引用旧方案、旧代码和旧日志时，应整理重建包：

```markdown
## Current goal
[当前唯一目标]

## Confirmed evidence
- [事实与来源]

## Confirmed decisions
- [已经确认的技术或产品决定]

## Relevant files
- `[当前真实路径]`

## Constraints
- [允许范围和禁止事项]

## Current state
- [最新测试、构建或错误状态]

## Open questions
- [仍然会改变方案的问题]
```

重建新会话时不应复制旧聊天全文。长期架构决定、业务规则和项目约定还应写入设计文档、测试或项目指令，不能只依赖聊天记录。

### 9. AGENTS.md 的作用

`AGENTS.md` 用于保存编码 Agent 跨多个工作反复需要的仓库指导，包括：

- 项目用途和技术栈；
- 关键目录职责；
- 安装、构建、测试和质量命令；
- 架构与编码规则；
- 生成文件和敏感区域；
- 公共接口限制；
- 完成前检查。

不应写入当前错误日志、当前分支目标、临时排期、无来源偏好、敏感信息和 README 的大段复制。

### 10. AGENTS.md 与其他文件

| 信息 | 推荐位置 |
| --- | --- |
| 项目用途、安装和使用 | README |
| 架构决定与理由 | ADR 或设计文档 |
| 当前需求、范围和验收 | Prompt 或 issue |
| 编码 Agent 长期工作规则 | AGENTS.md |
| 当前测试输出和日志 | 当前会话 |
| 可机械执行的格式和质量规则 | lint、测试、CI |

`CLAUDE.md` 等文件也可用于部分编码 Agent 的项目指导，但具体文件发现、作用域和优先级取决于产品。团队使用多个 Agent 时，应明确共同规则的权威来源，避免复制后产生冲突。

### 11. AGENTS.md 的目录作用域

大型仓库可以在根目录保存通用规则，在子目录保存局部规则：

```text
repo/
├── AGENTS.md
├── services/
│   └── payments/
│       └── AGENTS.md
└── frontend/
    └── AGENTS.md
```

以当前 Codex 文档为例，Codex 从项目根向当前工作目录逐层收集指导，更靠近当前目录的规则用于覆盖更早的通用指导；同一目录还可以使用 `AGENTS.override.md`。这是 Codex 的具体产品行为，不能直接推广为所有编码 Agent 的统一规则。

### 12. 高质量 AGENTS.md 的特点

- 简短，只保留跨任务高价值信息；
- 每条事实和命令有真实来源；
- 规则说明适用目录；
- 抽象要求改写为可执行语言；
- 禁止事项附有正确操作路径；
- 测试和质量命令经过核验；
- 详细教程放在专门文档中；
- 机械规则同时由自动化工具检查。

## 五、课堂教学过程（90 分钟）

| 教学环节 | 时间 | 教师讲授内容 | 讲解重点 |
| --- | ---: | --- | --- |
| 情境导入 | 8 分钟 | 对比同一编码要求在空白会话和真实仓库中的结果 | 结果差异来自项目上下文 |
| Prompt 与四层上下文 | 15 分钟 | 讲解 Prompt/Context 分工和四层模型 | 长期规则与动态状态 |
| 六类项目上下文 | 17 分钟 | 结合登录案例讲项目、文件、依赖、规范、测试和约束 | 从真实来源取得证据 |
| 不足与污染 | 12 分钟 | 分析猜测路径、旧代码、旧日志和冲突规则 | 更新、删除和重新确认 |
| AGENTS.md | 18 分钟 | 讲解用途、内容边界、目录作用域和产品差异 | 持久规则必须稳定可验证 |
| 现场演示 | 15 分钟 | 从示例仓库提取并核验 AGENTS.md 初稿 | 生成后逐条核验 |
| 总结 | 5 分钟 | 回顾上下文选择与持久化方法 | 能支持入口、行为、范围和验证判断，且内容准确、不冲突 |

### 1. 情境导入（8 分钟）

教师分别展示两个环境：

- 空白会话，只输入“增加一个用户查询接口”；
- 已打开真实项目的编码 Agent，能够读取依赖、路由、服务、测试和项目指令。

空白会话可能自行选择语言、框架和目录。项目内 Agent 能够沿用现有 Fastify 路由、用户服务、错误格式和测试 fixture。

教师由此引出：Prompt 描述本次工作，上下文限定工作所处的真实代码环境。

### 2. Prompt 与四层上下文（15 分钟）

教师先展示金额舍入示例：

```text
Prompt：修复订单结算的金额舍入错误，保持 API 契约不变。

Context：
- 使用 Decimal；
- 结算入口和舍入函数路径；
- 10.005 的当前与预期结果；
- 相关测试和项目命令。
```

随后解释四层上下文：

- 仓库级提供技术栈、目录和通用命令；
- 目录级提供模块职责和局部例外；
- 任务级提供当前目标、文件和范围；
- 运行级提供最新测试、日志和 diff。

重点说明一次测试失败属于运行状态，不适合永久写入 `AGENTS.md`。

### 3. 六类项目上下文（17 分钟）

教师使用“空密码登录返回 500”案例逐层展开：

```text
项目：Python 3.12、FastAPI、cookie session
文件：登录 route、认证 service、现有测试
依赖：route -> service -> password verifier -> session issuer
规范：复用项目错误类型，route 不放业务逻辑
测试：pytest、client fixture、相关测试命令
约束：session 响应格式不变，移动端不在范围
```

教师强调路径和规范必须来自真实仓库。尚未搜索时，应要求 Agent 先定位，而不是在 Prompt 中虚构 `src/auth/login.ts`。

### 4. 上下文不足与污染（12 分钟）

教师展示以下问题：

- 依赖文件已经使用 Node.js 22，旧会议记录仍写 Node.js 18；
- 会话内存在三份不同版本的认证文件；
- 修复后只剩一个测试失败，但 Agent 继续围绕旧的十二个失败分析；
- 未经验证就断言根因是数据库精度；
- 修复后端金额问题时附入整套前端视觉规范；
- 根目录规范和 `legacy/` 局部规则看似冲突。

教师说明处理原则：当前真实文件和最新运行结果用于更新旧信息；无关材料应删除；推断必须标注；局部规则应按目录解释；真正的产品冲突不能由 Agent 偷偷决定。

### 5. AGENTS.md 讲解（18 分钟）

教师先对比三类信息：

```text
README：怎样安装和使用项目
AGENTS.md：编码 Agent 应怎样修改和验证项目
当前 Prompt：本次要完成什么以及本次范围
```

然后展示适合与不适合持久化的内容：

```text
适合：修改 API 后运行 contract tests。
适合：不得手改 generated/，应修改 schema 后运行生成命令。
不适合：本周四前完成登录页。
不适合：当前测试有两项失败。
不适合：本次只修改登录模块。
```

接着讲解根目录与嵌套目录的作用域，并说明 Codex、GitHub Copilot 和其他编码 Agent 对指令文件的支持不完全相同，具体行为必须核对当前官方文档。

### 6. 教师现场演示（15 分钟）

#### 6.1 只读盘点

教师向 Agent 输入：

```text
请先只读检查仓库，不要修改文件。
从 README、依赖清单、脚本、CI、测试和现有规范中整理：
1. 项目用途与技术栈；
2. 关键目录职责；
3. 安装、构建、测试、lint 和类型检查命令；
4. 生成文件与正确生成路径；
5. 无法确认的事项。
每项结论引用真实文件路径，不要按模板补全。
```

#### 6.2 整理候选规则

教师将 Agent 输出整理为：

| 候选规则 | 证据来源 | 作用域 | 是否长期稳定 |
| --- | --- | --- | --- |
| 使用 `npm run test:unit` | `package.json`、CI | 全仓库 | 是 |
| 本次只修复登录 | 当前要求 | 当前工作 | 否 |
| 不手改 generated | 文件头、生成脚本 | 前端 | 是 |
| 最好使用函数式写法 | 无来源 | 不明确 | 否 |

教师删除一次性要求和无来源偏好。

#### 6.3 形成初稿

```markdown
# Project guide

## Project
- [已核验的项目用途、语言、框架和运行时]

## Structure
- `[真实路径]`: [已核验职责]

## Commands
- Install: `[真实命令]`
- Test: `[真实命令]`
- Lint: `[真实命令]`

## Rules
- [项目特有、跨任务稳定、可执行的规则]

## Modification limits
- [禁止区域和正确修改路径]

## Before completion
- [验证和报告要求]
```

#### 6.4 逐条核验

教师打开对应文件，核对：

- 运行时版本；
- script 名称；
- 测试目录和命令；
- 生成文件头与生成脚本；
- 局部规则的适用目录；
- 尚未实际运行的命令。

教师强调：由 Agent 生成的 `AGENTS.md` 只能作为候选初稿。错误命令一旦持久化，会在后续多个编码工作中重复产生失败。

### 7. 课堂总结（5 分钟）

教师用以下结构回顾本课：

```text
Prompt：当前编码要求
Context：项目事实与最新证据
AGENTS.md：长期仓库规则

仓库级 -> 目录级 -> 任务级 -> 运行级

项目 | 文件 | 依赖 | 规范 | 测试 | 修改约束

可用上下文 = 能改变当前判断 + 来源可核对 + 能支持下一步 + 内容不冲突
```

## 六、常见课堂问题与处理

### 1. 把整个仓库理解为最完整上下文

教师应指出：整个仓库包含大量与当前问题无关的模块。应先建立项目地图，再围绕真实入口、调用方、测试和约束逐步聚焦。

### 2. 只列文件名，不说明关系

要求补充相关符号、文件职责和与当前问题的关系。文件路径只是上下文的起点。

### 3. 把目录名推断写成事实

追问证据来源。目录名只能形成候选判断，真实职责还要从代码、导入、注册或项目文档确认。

### 4. 认为 README 已经可以替代 AGENTS.md

通过读者和目的区分：README 重点是理解、安装和使用；`AGENTS.md` 重点是编码 Agent 怎样修改、验证和避免误改。

### 5. 把当前错误日志写进 AGENTS.md

说明运行结果变化快，只应留在当前会话。只有跨多个工作长期有效的规则才适合持久化。

### 6. 使用“保持高质量”等抽象规则

将其改写为目录边界、具体命令、兼容要求或完成前检查。

### 7. 从课堂模板复制项目命令

要求回到真实 `package.json`、`pyproject.toml`、Makefile 或 CI。模板中的命令只能表示结构，不能代替项目事实。

### 8. 只写禁止事项

要求同时说明正确路径，例如应修改的 schema、生成命令或需要确认的条件。

### 9. 在被污染的旧会话中不断追加说明

先整理当前目标、有效决定、真实文件和最新测试状态；旧信息过多时用重建包开启干净会话。

### 10. 把某一产品规则推广到所有编码 Agent

将表达限定为“以当前 Codex 文档为例”，并说明其他产品应查看各自官方支持范围。

### 11. 用项目指令替代自动检查

说明自然语言指导负责提供意图与工作路径，格式、类型和测试规则仍应由 lint、类型检查和 CI 强制执行。

### 12. 在本周深入展开全部调用链

本周只保留与当前上下文有关的最小关系图。系统的入口定位、调用链和数据流分析安排在第五周。

## 七、课堂总结与板书

### 1. 课堂总结

本周的核心不是让 Agent 读取更多文件，而是让它获得当前编码工作需要的真实项目信息。

教师应再次强调：

1. Prompt 说明本次做什么；
2. Context 提供完成工作所需的项目事实和最新证据；
3. 上下文按仓库、目录、任务和运行四层组织；
4. 文件、依赖、规范、测试和修改约束应来自真实项目；
5. 旧代码、旧日志和已取消方案会造成上下文污染；
6. `AGENTS.md` 只保存跨任务稳定、可执行、可验证的仓库规则；
7. 重要机械规则仍应由自动化工具检查。

### 2. 板书设计

```text
Week 4  编码 Agent 的上下文工程

Prompt  = 本次做什么
Context = 完成它必须知道什么

仓库级 -> 目录级 -> 任务级 -> 运行级
长期       局部       当前       动态

六类：
项目 | 文件 | 依赖 | 规范 | 测试 | 修改约束

质量：支持当前判断 + 来源可核对 + 覆盖下一步 + 内容不冲突

不足：补充会改变决策的证据
污染：删除无关、旧版本和旧日志
冲突：检查来源、目录和时效

AGENTS.md：
结构 | 命令 | 规则 | 限制 | 完成检查

长会话：
目标 + 决定 + 证据 + 真实文件 + 最新状态
```

## 八、与前后课程的衔接

### 1. 与第二周的衔接

第二周学习如何写清 Prompt 的背景、目标、输入、输出和约束。本周将视角扩展到编码 Agent 从项目文件、工具结果和持久指令中获得的完整工作上下文。

### 2. 与第三周的衔接

第三周区分事实、推断和待确认事项。本周继续要求上下文标明来源，避免把推断、旧信息和临时要求写入项目持久指令。

### 3. 与第五周的衔接

本周知道入口、调用方、测试和依赖关系应进入编码 Agent 上下文。第五周将系统学习怎样在陌生仓库中找到这些证据并建立项目地图。

### 4. 与第六周的衔接

本周说明上下文会随定位、运行和验证而更新。第六周将把探索、计划、实现和验证组织成完整 Agent 工作流。

### 5. 与第七、八周的边界

本周只记录项目命令、测试位置和修改限制。工具权限、执行安全和测试驱动开发分别在第七、八周展开。
