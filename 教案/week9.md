# 第九周教案：代码审查、Git 与质量控制

## 一、课程基本信息

- **课程名称**：YatOL 人机协作课程
- **授课主题**：代码审查、Git 与质量控制
- **建议课时**：2 学时（90 分钟）
- **适用对象**：具备基础 Git 和测试知识的学生
- **先修内容**：工具调用、测试驱动开发和项目影响范围
- **实践载体**：编码 Agent、Git 仓库和示例 Pull Request

## 二、教学目标

完成本节课后，学生应能够：

1. 按目标、范围、正确性、测试和安全顺序审查 diff[^1]。
2. 使用 Agent 解释修改，同时独立核对真实文件和证据。
3. 说明 branch[^2]、commit[^3]、Pull Request[^4] 和 review[^5] 的作用。
4. 综合使用格式化、lint[^6]、类型检查[^7]、测试和安全扫描[^8]。
5. 生成并核对 Commit Message 与 Pull Request 说明。
6. 输出包含严重程度、位置、触发条件、影响和修复方向的审查发现。
7. 区分 revert[^9] 与历史改写，并理解人工合并责任。

[^1]: Diff 是两个版本之间新增、删除和修改内容的对比。
[^2]: Branch 是从某个基线分出的独立开发线。
[^3]: Commit 是保存一组版本变化及其说明的 Git 记录。
[^4]: Pull Request 是向目标分支提出合并变化并进行讨论和审查的协作页面。
[^5]: Review 是在合并前检查代码变化并给出反馈的审查过程。
[^6]: Lint 是按规则检查代码中常见错误和不规范写法的静态工具。
[^7]: 类型检查是检查值与函数是否按声明的类型关系使用。
[^8]: 安全扫描是用自动规则或查询寻找潜在漏洞的检查。
[^9]: Revert 是用一个新提交撤销已有提交效果的 Git 操作。

## 三、教学设计与课前准备

### 1. 教学重点与难点

#### 教学重点

- **重点**：先理解需求再看实现；逐文件审查；小而聚焦的变更；检查依赖与生成文件。

#### 教学难点

- **难点**：流畅的 Agent 摘要可能遗漏问题；测试、lint 和安全扫描各自覆盖不同风险；“格式更好”可能制造巨大无关 diff。

#### 课程边界

- 第七周已经讲解 Git 状态与基础 diff，本周深入比较基线、分支、提交、PR 和审查。
- 第八周已经讲解测试设计，本周只判断测试证据是否覆盖变更风险，不重讲 TDD。
- 第十周再系统讲解隐私、依赖、工具执行和人类责任；本周只在代码审查中识别相关信号。
- 不展开复杂 Git 内部对象、发布流程或组织级安全治理。

### 2. 教学准备

#### 教师准备

- 准备一个测试通过但含权限漏洞的 diff。
- 准备一个混入格式化、依赖和生成文件变化的 PR。
- 准备 Git branch、commit、PR、review 和 revert 的演示仓库。

#### 环境准备

- 示例仓库包含明确基线、功能分支、多个提交和可重复的质量检查。
- PR 不连接生产系统，不包含真实密钥或用户数据。
- 能分别查看文件清单、逐文件 diff、测试结果和自动检查状态。
- 预先保存“无发现”“有阻塞问题”和“仅有未验证风险”三种审查输出。

## 四、核心知识体系

### 1. Diff Review 顺序

1. 重述变更目的与不应改变的行为。
2. 查看文件清单，发现超出范围的修改。
3. 逐文件检查控制流、数据边界、异常和安全。
4. 检查测试是否真正对应需求和 Bug。
5. 查看依赖清单、锁文件、迁移和生成产物。
6. 根据变更类型运行检查：格式变化运行 formatter，类型边界运行类型检查，行为变化运行相关测试，依赖变化运行依赖或安全检查；记录无法运行的项目。

### 2. Git 在 Agent 工作流中的作用

- branch 隔离开发；
- commit 保存一组有意义的变化；
- diff 呈现基线与当前变化；
- PR 提供上下文、讨论、检查和批准；
- revert 通过新提交撤销已共享变更并保留历史；reset 或强推会改写引用，可能使协作者基于旧历史的工作失效。

### 3. 质量控制组合

| 检查 | 能发现 | 不能保证 |
| --- | --- | --- |
| 格式化 | 风格不一致 | 逻辑正确 |
| Lint/类型检查 | 常见错误、类型问题 | 业务需求正确 |
| 自动测试 | 已编码的预期行为 | 未想到的风险 |
| 安全扫描 | 已知模式与依赖漏洞 | 完整安全性 |
| 人工审查 | 意图、设计、可维护性 | 永不出错 |

### 4. Branch、Commit、PR 与版本回滚

Branch 隔离开发；Agent 可根据真实 diff 生成 Commit Message，但人要核对目的和验证结果；Agent 也可生成 Pull Request 标题与说明，内容应包含背景、范围、测试和风险。PR 审查结合逐文件 diff、自动检查和人工批准。已共享提交通常使用 revert 生成可追踪撤销；reset 和强推可能影响协作者，应谨慎使用。

### 5. 审查前先确定比较范围

教师要求先确认：目标需求、基线分支、当前 head、包含的提交以及是否混入用户已有变化。`git diff` 可以比较工作区、暂存区、提交或分支；命令不同，得到的变更集合也不同。没有确认基线，后续“只改了两个文件”可能就是错误结论。

```text
目标：普通用户不能访问 /admin。
基线：main 当前共同起点。
审查范围：feature/auth-guard 相对 main 的全部变化。
不应改变：登录流程、管理员成功路径、依赖和 CI。
```

### 6. 文件清单与逐文件审查

先用统计和文件清单识别范围，再逐文件阅读上下文：

```text
需求与基线
-> 提交与文件清单
-> 生产代码
-> 测试
-> 配置、依赖、迁移、生成文件
-> 自动检查
-> 审查结论
```

审查新增行、删除行和旧逻辑之间的关系，追踪输入、分支、状态变化、错误路径和调用者。文件多时可按风险排序，但不能只读最显眼的文件。

### 7. 风险优先的 Bug 检查

教师按以下顺序讲解：错误结果、数据损坏、越权、兼容破坏、资源泄漏、缺失测试、范围外变化、可维护性。严重程度来自实际影响和可触发性，不来自代码风格偏好。

权限变化必须同时检查管理员、普通用户和未登录用户；数据写入要检查失败后的状态；公共接口要检查旧调用者与返回结构。

### 8. 高质量审查发现

每条发现至少包含：

| 字段 | 内容 |
| --- | --- |
| 严重程度 | 是否阻塞合并，影响有多大 |
| 位置 | 具体文件和最小相关行 |
| 触发条件 | 什么输入、状态或调用路径会出现 |
| 实际影响 | 错误结果、越权、损坏或兼容问题 |
| 证据 | diff、调用方、测试或运行结果 |
| 修复方向 | 最小可行方向，不代替作者重写全部代码 |

“这里可能有问题”缺少可操作信息；若无法给出触发输入、受影响路径或运行证据，应标为待验证风险，并说明缺少哪项证据，而不是编造确定 Bug。

### 9. Lint、格式化、类型检查、测试与安全检查

自动检查覆盖不同问题：格式化统一排版；lint 发现规则命中的常见问题；类型检查验证可推导的类型关系；测试验证已经编码的行为；安全扫描发现其规则或查询能够识别的模式。任何一项通过都不能替代需求审查和人工判断。

教师还要区分“工具报告无告警”与“没有风险”。安全工具未配置、扫描未覆盖目标语言、结果尚未完成，都不能汇报成安全检查通过。

### 10. 分支与提交边界

分支应从正确基线创建，并围绕单一目标。Commit 应保存一组有意义、可解释的变化；生成 Commit Message 前先读取 staged diff[^10]，避免把未暂存或未验证内容写进说明。

[^10]: Staged diff 是已经放入暂存区、准备进入下一次提交的变化。

文件修改、暂存、提交和推送属于不同动作。Agent 只有在用户明确授权时才能继续到对应动作，不能因用户要求“修复代码”就自动创建提交或远程 PR。

### 11. Commit Message 与 PR 说明

```text
fix(auth): reject non-admin access to admin routes
```

标题应概括目的，正文可说明原因和关键取舍。PR 说明至少包含背景、行为变化、范围、验证、截图或迁移信息、已知风险和回滚方式。GitHub 官方文档建议 PR 小而聚焦，并在请求他人审查前先自查 diff 与相关构建、测试。

### 12. PR 审查与 Agent 产品边界

GitHub Copilot code review 可以提供审查反馈，Copilot CLI 也提供 `/review` 来分析本地代码变化；这些是 GitHub Copilot 的具体产品行为，不应写成所有编码 Agent 都有的统一命令。GitHub 官方同时明确要求验证 Copilot 反馈并补充人工审查。

通用使用方式仍是：给 Agent 明确基线、任务边界、风险优先级和输出格式，再由人核对真实 diff 与证据。

### 13. 版本回滚

回滚前区分未共享工作区变化、未共享本地提交和已共享提交。`git revert` 通过新提交撤销指定提交引入的变化，适合保留可追踪历史；`reset` 或强推会改变引用或公共历史，可能影响协作者。

代码回滚不自动撤销数据库迁移、外部消息、已发送邮件或生产数据。遇到这些情况应暂停并按项目方案处理，本周不展开第十周的完整风险体系。

### 14. 审查结束状态

审查可以有三种合格结论：

1. 发现可复现、可操作的问题；
2. 未发现可操作问题，但列出实际检查与未验证风险；
3. 因基线、环境或证据不足无法完成审查，并准确说明缺口。

不能为了显得有价值而凑问题，也不能把 Agent 的“未发现”直接当作批准依据。

## 五、课堂教学过程（90 分钟）

| 教学环节 | 时间 | 教师讲授内容 | 讲解重点 |
| --- | ---: | --- | --- |
| 情境导入 | 7 分钟 | 展示测试通过但存在越权的 diff | 自动检查有边界 |
| 基线与文件清单 | 12 分钟 | 确认比较范围并分类变化文件 | 先确定审查对象 |
| 逐文件风险审查 | 18 分钟 | 追踪权限分支、调用方和失败路径 | 触发条件与实际影响 |
| Git、Commit 与 PR | 15 分钟 | 解释分支、提交、PR 和授权边界 | 变更记录与协作上下文 |
| 质量控制组合 | 12 分钟 | 对比格式、lint、类型、测试、安全扫描 | 各证据不能互相替代 |
| 教师现场演示 | 21 分钟 | 让 Agent 审查并与人工证据核对 | 风险优先、无证据不猜 |
| 总结 | 5 分钟 | 回顾结论、回滚与人工责任 | 是否合并由人决定 |

### 各环节实施详案

#### 1. 导入：先不看摘要，只看变更事实

教师隐藏 PR 标题和 Agent 摘要，只展示文件树。请学生判断：一个“修复管理员页面按钮”的任务为什么修改了认证中间件、锁文件和 CI？通过文件范围先建立风险直觉，再打开具体 diff。

#### 2. 明确基线与需求边界

审查前先确认比较的是哪个基线、当前分支包含哪些提交、目标需求是什么、哪些行为不应改变。错误基线会混入其他提交，使审查结论失真。

#### 3. 文件清单审查

按源代码、测试、配置、依赖、迁移、生成文件和文档分类。教师说明：新增依赖但没有锁文件变化、修改 schema 但没有迁移、修改生产代码但没有测试，都是值得进一步检查的信号。

#### 4. 逐文件审查

先理解旧逻辑，再读新增与删除行。围绕输入、分支、异常、状态变化和调用者思考触发条件。对于权限代码，必须同时检查允许和拒绝路径，不能只看管理员成功流程。

#### 5. 质量检查的证据边界

教师分别展示 formatter、lint、类型检查、测试和安全扫描的输出，要求说明每项能证明什么、不能证明什么。尤其强调自动检查之间不是相互替代，而是覆盖不同问题空间。

#### 6. Git 与审查沟通

commit 应保持有意义的粒度；PR 说明提供原因、范围、验证和风险；review comment 要指出触发条件与影响。对于已共享错误提交，演示 revert 怎样保留可追踪历史。

#### 7. 教师总结（5 分钟）

教师将一次审查收束为：需求、基线、文件清单、逐文件证据、自动检查、发现与未验证风险。再次强调 Agent 可辅助导航和候选问题识别，但不能代表负责人批准合并。

## 六、典型案例与边界

### 案例一：布尔权限判断反了

Agent 将 `if not user.is_admin` 改成 `if user.is_admin`，测试只覆盖管理员路径。格式、lint 均通过，但未授权用户获得访问。审查必须结合需求与负向测试。

### 案例二：一行修复带来 500 行格式变化

功能修改被全文件格式化淹没。应要求最小 diff，把机械格式化单独提交，方便定位真实行为变化。

### 案例三：新增依赖

Agent 为一个简单日期格式引入大型库。审查应问现有标准库是否足够、锁文件是否变化、许可证与漏洞如何、生产包体是否受影响。

### 案例四：虚假的回滚安全

已经推送并被他人基于其开发的提交，不适合随意 reset 和强推。可使用 revert 产生可追踪的撤销提交，并在 PR 中解释原因。

### 案例五：Agent 摘要遗漏

摘要写“只修改验证逻辑”，文件清单却包含 CI 配置。审查者必须以 diff 为准，摘要只是导航。

## 七、教师现场演示

### 演示任务：对测试通过的权限修改进行风险优先审查

```text
请审查当前分支相对基线的 diff，不要修改文件。

按以下优先级报告：
1. 会导致错误结果、数据损坏、越权或兼容性破坏的问题；
2. 缺失或无效的测试；
3. 超出任务范围的修改；
4. 可维护性问题。

每条发现必须包含文件位置、触发条件、影响和最小修复方向。
如果没有高置信问题，请明确说明剩余未验证风险，不要为了凑数量而猜测。
```

### 现场审查步骤

1. 读取任务描述，写下“必须改变”和“不得改变”的行为。
2. 查看 `git diff --stat` 和文件树，标出异常范围。
3. 从权限入口追踪到中间件和服务，核对条件判断及默认行为。
4. 阅读新增测试，确认是否覆盖普通用户被拒绝、未登录用户和管理员成功。
5. 检查配置、依赖和锁文件是否有非必要变化。
6. 运行最相关测试和项目质量命令，保留真实输出。
7. 让 Agent 生成审查发现，再与人工发现对照，删除没有证据的猜测。
8. 按严重程度输出：阻塞合并、建议改进、未验证风险。

### 审查意见示例

```text
[阻塞] src/auth/guard.py：条件将普通用户也视为管理员。
触发方式：已登录但 is_admin=False 的用户访问 /admin。
影响：未授权访问管理页面。
证据：当前新增测试只覆盖 is_admin=True。
建议：恢复拒绝分支，并增加普通用户和未登录用户测试。
```

这样的意见比“权限逻辑可能有问题”更容易复现、讨论和修复。

### 课堂追问

- 为什么 PR 很小时仍不能跳过审查？
- 文件被自动格式化后，怎样降低审查噪声？
- Agent 没有发现问题，能否作为批准依据？
- revert 与 reset 分别适合什么情形？

### 演示最终报告

```text
结论：1 个阻塞问题，1 个测试缺口。

[阻塞] src/auth/guard.py:42
触发：is_admin=False 的已登录用户访问 /admin。
影响：普通用户获得管理权限。
证据：条件分支反转；新增测试只覆盖管理员。
方向：恢复拒绝分支，并补普通用户与未登录用户测试。

实际检查：权限模块测试 18 passed；lint 通过。
未验证：完整集成测试未运行，测试数据库不可用。
范围：锁文件和 CI 变化与任务无关，需从本 PR 移出。
```

## 八、常见问题与处理

### PR 说明应包含

问题与背景、解决方式、范围边界、关键设计选择、测试与检查结果、截图或迁移信息、已知风险和回滚方式。GitHub 官方建议提交前自行构建和测试，并保持 PR 小而聚焦。

### 常见误区

- 只看最终文件，不看相对基线的变化。
- 先读 Agent 摘要并被其结论锚定。
- 测试通过就直接批准，未检查权限、异常和兼容性。
- commit message 描述“做了什么”，却不说明“为什么”。
- 使用危险历史改写处理已经共享的变更。
- 不确认 base/head 就让 Agent 解释错误的 diff。
- 把依赖 rich diff 当作源文件审查的替代。
- 只给笼统意见，不写触发条件和实际影响。
- 为了凑数量，把低置信猜测写成阻塞问题。
- Agent 修改后不重新检查新增 diff 和对应评论。

## 九、课堂总结与板书

Agent 可以帮助导航 diff、解释调用关系和发现候选问题，但不能替代负责合并的人。高质量审查以真实 diff、可运行检查和需求边界为证据。

### 板书设计

```text
需求 -> 文件清单 -> 逐文件 diff -> 测试 -> 依赖/迁移 -> 风险结论

质量证据：format + lint/type + test + security + human review
摘要用于导航，diff 才是变更事实。
共享历史优先 revert，谨慎 reset/force push。
发现：严重度 | 位置 | 触发 | 影响 | 证据 | 修复方向
结论：可操作问题 | 未发现问题 + 剩余风险 | 证据不足
```

## 十、与前后课程的衔接

### 1. 与第七、八周的衔接

第七周的 Git 状态和 diff 成为本周审查入口；第八周产生的测试证据成为质量控制的一部分，但不能替代人工审查。

### 2. 与第十周的衔接

第十周将进一步放大审查中的安全、隐私、依赖、工具权限和人类责任问题，建立系统化风险边界。
