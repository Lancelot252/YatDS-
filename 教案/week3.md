# 第三周教案：需求分析与任务拆解

## 一、课程基本信息

- **课程名称**：YatOL 人机协作课程
- **授课主题**：需求分析与任务拆解
- **建议课时**：2 学时（90 分钟）
- **适用对象**：具备基础编程能力的计算机相关专业学生
- **先修内容**：Prompt 的背景、目标、输入、输出和约束
- **实践载体**：网页对话工具或编码 Agent、小型认证示例项目
- **教学范围**：严格对应《总计划.md》第三周；本课形成需求分析与任务计划，不提前完整讲授上下文工程、代码库系统阅读、Agent 工作流、工具权限、测试驱动、Diff Review 或风险治理；讲义第六部分的 Prompt 模板作为选读材料，不纳入课堂必讲和核心考核
- **参考依据**：OpenAI Codex Prompting 与实践指南、Claude Code Best Practices 与 Plan Mode 文档、OpenAPI Specification[^1]、OAuth 2.0[^2] Security Best Current Practice

[^1]: OpenAPI Specification 是说明 API 如何调用的标准格式。
[^2]: OAuth 2.0 是不让应用取得密码也能授权访问的方式。

## 二、教学目标

完成本课后，学生应能够：

1. 用解释、诊断、规划、实现、修复和审查等明确动词限定编码 Agent 的任务边界。
2. 将一句模糊自然语言需求还原为用户、场景、行为、边界和可验证目标。
3. 区分功能需求[^3]、非功能需求[^4]、约束和验收标准[^5]。
4. 将分析结论分为已确认事实、合理推断和必须确认的问题，并说明各自依据。
5. 从入口、调用方、业务服务、数据、外部系统、配置、测试和文档识别影响范围[^6]。
6. 把复杂目标拆成目的单一、存在依赖、可以独立验证的小任务。
7. 根据依赖、风险、用户价值和成本安排任务优先级。
8. 为复杂登录或 OAuth 需求形成包含影响文件、步骤、风险、待确认事项和完成证据的开发计划。

[^3]: 功能需求说明系统必须提供什么功能或行为。
[^4]: 非功能需求说明系统在性能、安全等方面要达到什么水平。
[^5]: 验收标准是判断需求是否完成的具体条件。
[^6]: 影响范围是一项需求可能涉及的文件、模块、数据、配置和测试。

## 三、教学设计与课前准备

### 1. 教学重点与难点

#### 教学重点

- 任务动词与交付物、修改边界之间的关系。
- 用户场景、功能需求、非功能需求、约束和验收标准。
- 事实、推断、待确认事项的证据化表达。
- 影响范围表和带依赖的任务清单。
- OAuth 案例中的跨文件规划与关键澄清。

#### 教学难点

- 不把技术方案直接当成用户需求。
- 不把根据经验得到的推断写成项目事实。
- 判断哪些问题应先查仓库，哪些必须由用户或产品负责人决定。
- 既不把任务写成“前端、后端、测试”这样过粗的类别，也不拆成没有独立价值的函数级动作。
- 在不提前编写实现代码的前提下，计划中写明真实入口或待调查方法、依赖顺序、风险、完成条件和未确认项。

### 2. 教学准备

#### 教师准备

1. 准备同一认证示例项目的目录、关键路由、会话服务、用户模型、配置和测试片段。
2. 准备三条模糊需求：“加 Google 登录”“导出坏了”“把搜索做快一点”。
3. 准备六张任务动词卡：解释、诊断、规划、实现、修复、审查。
4. 准备事实—推断—待确认三栏工作纸。
5. 准备影响范围表和任务卡模板。
6. 准备一份故意包含虚构文件、方案先行、缺少依赖和无验收证据的问题计划。
7. 提前确认课堂所用 Agent 只能读取示例项目，演示前关闭自动修改模式。

#### 学生准备

- 复习第二周 Prompt 五要素及明确任务动词的写法。
- 能够识别页面、HTTP 路由、函数调用、数据模型和基础测试文件。
- 自备可访问的网页对话工具或编码 Agent；两人一组也可完成练习。
- 课前阅读一条简短的登录需求，不要求预先提出实现方案。

## 四、核心知识体系

### 1. 用任务动词限定工作边界

#### 1.1 六种常见任务

| 任务 | 主要问题 | 交付物 | 默认状态变化 |
| --- | --- | --- | --- |
| 解释 | 现有内容如何工作 | 原理、流程、模块职责 | 无 |
| 诊断 | 问题为何发生 | 复现、证据、根因或候选原因 | 无 |
| 规划 | 达到目标需要做什么 | 范围、步骤、依赖、风险 | 无 |
| 实现 | 如何增加已定义行为 | 代码、配置和必要说明 | 有 |
| 修复 | 如何恢复预期行为 | 最小变更与回归证据 | 有 |
| 审查 | 现有变更有什么问题 | 可操作发现与证据 | 无 |

教师应强调：“看看”“改一下”“处理登录”都属于模糊任务。任务动词同时影响回答内容和 Agent 的文件修改边界。

#### 1.2 对比示例

模糊版：

```text
看看登录 Bug。
```

解释版：

```text
解释当前登录请求从页面到会话创建的流程，不修改文件。
```

诊断版：

```text
诊断会话过期后首次登录失败的原因，报告复现、证据和影响范围，暂不修改代码。
```

修复版：

```text
修复已确认的会话续期问题，保持登录接口不变，并用原复现步骤验证。
```

#### 1.3 复合任务的阶段条件

```text
先诊断并报告证据；
只有在根因可以由项目和本地复现确认时，才实施最小修复；
若需要改变会话策略，先停止并提出待确认问题。
```

这段 Prompt 同时说明了阶段顺序、继续条件和停止条件。

### 2. 从自然语言还原需求

#### 2.1 用户场景六问

| 问题 | 课堂表达 |
| --- | --- |
| 谁 | 哪一类用户或系统？ |
| 在哪里 | 哪个页面、接口或环境？ |
| 何时 | 哪种前置状态或触发条件？ |
| 做什么 | 用户执行了什么动作？ |
| 期望什么 | 哪个结果可以被观察？ |
| 失败时怎样 | 错误、取消和异常如何表现？ |

#### 2.2 从“导出坏了”到问题描述

```text
角色：管理员
入口：订单列表的“导出 CSV”按钮
前置：选择日期范围，筛选结果为 50 条
实际：页面提示成功，但没有下载
期望：下载包含当前筛选结果的 UTF-8 CSV
环境：Chrome 与 Edge 均稳定复现
保持：现有列名、顺序、权限和筛选语义
```

学生应能指出：这仍然没有说明根因，因此任务首先是诊断，直接修改响应头缺少证据。

#### 2.3 目标与方案的区别

方案先行：

```text
用 Redis 优化搜索。
```

结果导向：

```text
在 10 万条测试数据下将商品搜索 P95 从 1.8 秒降至 500 ms 以内；
结果内容和排序保持不变；先定位各阶段耗时，再比较方案。
```

如果 Redis 是已经批准的架构约束，应明确其来源；否则不能把它当作唯一答案。

### 3. 需求的四类信息

#### 3.1 分类方法

| 类别 | 回答的问题 | 示例 |
| --- | --- | --- |
| 功能需求 | 系统必须做什么 | 用户可使用学校账号登录 |
| 非功能需求 | 行为达到什么质量 | 回调不得跳转到站外地址 |
| 约束 | 实现不能突破什么 | 不修改现有用户主键 |
| 验收标准 | 如何判断已经完成 | 取消授权后不创建会话 |

#### 3.2 课堂分类材料

请学生将以下句子放入四类：

```text
用户可以从登录页发起 Google 登录。
原有密码登录行为保持不变。
client secret 不得写入仓库。
用户取消授权后显示提示且不建立会话。
登录成功后返回发起登录前的站内页面。
认证服务短暂不可用时不能显示底层异常信息。
```

其中“原有密码登录行为保持不变”既可视为兼容性要求，也可转化为验收标准。教师应接受有依据的分类，并强调最终要把抽象质量变成可观察结果。

#### 3.3 验收标准的完整性

验收场景至少从四方面检查：

- 正常路径；
- 失败路径；
- 边界条件；
- 兼容行为。

本周只定义验收行为，不展开测试框架和测试驱动流程。

### 4. 事实、推断与待确认事项

#### 4.1 三类信息

| 类型 | 判断标准 | 书写要求 |
| --- | --- | --- |
| 已确认事实 | 可由需求、代码、配置、测试、日志或批准文档证明 | 写出证据 |
| 合理推断 | 根据已知信息得到的暂时判断 | 写出依据和可能影响 |
| 待确认事项 | 不同答案会改变行为、范围或风险 | 给出选项与取舍 |

#### 4.2 认证案例

```text
事实：密码登录成功后调用 session service。
证据：登录处理函数与会话测试。

推断：OAuth 成功后可以复用 session service。
依据：该服务接收本地 user id，不依赖密码。
影响：若其存在密码登录专用假设，计划需要调整。

待确认：首次 OAuth 登录是否自动创建用户。
选项 A：自动创建，流程更短，但需要定义允许范围与资料来源。
选项 B：仅绑定已有账号，控制更严格，但需要绑定入口和失败提示。
```

#### 4.3 提问原则

能从仓库获得的信息，先自行调查；会改变产品行为或风险边界、且没有权威答案的问题，再向人提问。

低价值问题：

```text
项目使用什么测试框架？
```

高价值问题：

```text
相同 email 的 Google 身份是否自动绑定现有账号？
这一决定会改变账号归属风险和用户流程，请确认策略。
```

### 5. 影响范围分析

#### 5.1 追踪路径

```text
用户入口
→ 路由或控制器
→ 业务服务
→ 数据模型与存储
→ 外部服务

横向检查：配置 | 调用方 | 测试 | 日志 | 文档
```

本课聚焦需求规划中“应检查哪些位置”和“结论必须有何种证据”。大型项目的系统阅读，以及入口、调用链[^7]和数据流[^8]分析，将在第五周深入学习。

[^7]: 调用链是从入口开始的“谁调用谁”路径。
[^8]: 数据流是数据如何输入、变化、保存和输出的过程。

#### 5.2 影响范围表

| 文件或符号 | 当前职责 | 受影响原因 | 证据 | 处理方式 |
| --- | --- | --- | --- | --- |
| 登录页面 | 发起认证 | 增加 Google 入口 | 页面组件 | 修改 |
| 回调路由 | 处理认证结果 | 新流程入口 | 路由注册 | 新增/修改 |
| 会话服务 | 创建本地会话 | 成功后复用 | 现有调用关系 | 复用 |
| 用户模型 | 保存身份关系 | 可能缺少 provider id | 模型字段 | 待确认 |
| 配置加载 | 读取环境变量 | 需要 client id/secret | 现有配置方式 | 修改 |

没有真实仓库时，只能写“候选组件”。不允许虚构 `oauth.ts`、`auth_controller.py` 等具体文件名。

#### 5.3 确定影响与候选影响

```text
确定影响：登录入口、授权发起、回调、会话创建。
候选影响：用户模型迁移、账号绑定页面、审计日志。
确认方法：检查身份字段、已有绑定能力和日志要求。
```

候选项应附带确认方法，并与确定范围分开记录。

### 6. 任务拆解与优先级

#### 6.1 任务卡字段

每张任务卡包含：

```text
任务目标
影响范围
前置依赖
预期结果
完成证据
主要风险
待确认事项
```

#### 6.2 粒度判断

合适的小任务应：

- 只有一个主要目的；
- 围绕一个可独立验收的行为，且不混入无依赖关系的第二个目标；
- 结果可以独立说明；
- 可以独立验证；
- 失败后能够定位；
- 保留与业务目标的关系。

对比例子：

```text
过粗：完成登录。
过细：创建 providerName 变量。
合适：实现 OAuth 回调中的身份验证与本地会话创建，并处理已定义失败行为。
```

#### 6.3 排序依据

优先顺序建议：

```text
阻塞决策
→ 高风险未知项
→ 依赖项
→ 可独立交付的用户价值
→ 收尾说明与完整性检查
```

排序必须说明原因，不能只标 P0、P1、P2。

#### 6.4 OAuth 任务清单示例

| 顺序 | 任务 | 完成证据 | 主要风险 |
| ---: | --- | --- | --- |
| 1 | 确认开户、绑定、组织域和范围外事项 | 决策记录 | 错误账号归属 |
| 2 | 追踪现有登录、会话、用户与配置 | 真实文件和调用关系 | 遗漏影响 |
| 3 | 定义授权与回调行为 | 成功/失败行为表 | CSRF、开放重定向 |
| 4 | 确定身份数据与兼容策略 | 数据设计说明 | 重复绑定 |
| 5 | 接入后端认证与现有会话 | 回调结果符合契约 | 密钥或异常泄露 |
| 6 | 更新登录页面和提示 | 用户状态可观察 | 流程混乱 |
| 7 | 完成验收场景与配置说明 | 场景结果和文档 | 环境差异 |

## 五、课堂教学过程与活动设计

### 1. 90 分钟教学流程

| 环节 | 时间 | 教师活动 | 学生活动 | 教学目的 |
| --- | ---: | --- | --- | --- |
| 导入：一句需求的多种实现 | 7 分钟 | 展示“加一个登录功能”的三种冲突结果 | 圈出 Agent 自行决定的内容 | 感受需求空白的代价 |
| 任务动词 | 9 分钟 | 讲解六类任务及状态变化 | 为六条 Prompt 匹配任务类型 | 确定工作边界 |
| 场景与需求分类 | 14 分钟 | 将“导出坏了”改写为场景；讲四类信息 | 补全六问并完成分类 | 从愿望得到可观察需求 |
| 事实、推断与澄清 | 12 分钟 | 展示认证项目证据 | 填写三栏表并改写问题 | 建立证据意识 |
| 影响范围 | 12 分钟 | 从登录页追踪到会话与数据 | 在项目材料中标出影响链 | 避免单文件思维 |
| 任务拆解与排序 | 13 分钟 | 比较无法独立验收、细到单行修改和围绕单一行为的任务 | 展示任务卡并按依赖排序 | 形成可执行计划 |
| Agent 现场演示 | 14 分钟 | 依次输入模糊版与分析版 Prompt | 使用量表检查输出 | 观察约束如何改变结果 |
| 小组互评 | 6 分钟 | 发放问题计划 | 找出三项关键缺陷 | 练习审查计划 |
| 总结与退出卡 | 3 分钟 | 回顾板书和衔接 | 提交一条事实与一条待确认项 | 快速评价学习结果 |

### 2. 课堂导入设计

#### 2.1 导入材料

教师展示三份对“给系统加一个登录功能”的假想回答：

- A：新建账号密码系统；
- B：增加 Google OAuth 并自动按 email 绑定；
- C：增加短信验证码登录并替换现有会话。

#### 2.2 提问

- 哪一份一定符合用户需求？
- 哪些决定在原需求中没有出现？
- 哪些决定可能带来数据或安全后果？
- 在生成代码前，Agent 最应该交付什么？

#### 2.3 预期结论

三份都可能技术上可行，但没有一份能由原需求直接证明正确。此时首先应把任务定义为需求分析或规划，并找出事实、候选方案和必须确认的问题。

### 3. 课堂活动一：任务动词配对

#### 3.1 活动材料

```text
A. 说明登录请求经过哪些模块，不修改代码。
B. 找出会话过期后登录失败的原因，先报告证据。
C. 列出增加 Google 登录需要改变的范围、步骤和风险。
D. 按批准的接口行为加入 Google 登录。
E. 恢复导出下载并保持现有 CSV 格式。
F. 检查当前回调变更是否存在开放重定向问题，只报告发现。
```

#### 3.2 学生任务

将 A—F 分别对应解释、诊断、规划、实现、修复和审查，并指出哪些任务默认会修改代码。

#### 3.3 评价要点

- 任务类型匹配正确；
- 能解释“诊断”和“修复”的区别；
- 能指出规划和审查不应自动执行修改。

### 4. 课堂活动二：三栏证据表

#### 4.1 给定材料

```text
项目已有密码登录。
登录处理函数调用 SessionService.create(userId)。
用户表 email 字段有唯一约束。
需求只写了“增加 Google 登录”。
```

#### 4.2 学生输出

| 已确认事实 | 合理推断 | 必须确认 |
| --- | --- | --- |
| 已有密码登录；会话由 SessionService 创建；email 唯一 | OAuth 成功后可能复用 SessionService | 是否自动开户；是否按 email 绑定；是否限制组织域 |

#### 4.3 教师追问

- email 唯一为什么不能证明可以安全自动绑定？
- “使用 OAuth 2.0”是否已经说明用户身份验证的全部规则？
- 哪些问题可以继续通过读仓库回答？

### 5. 教师现场演示

#### 5.1 第一轮：模糊 Prompt

```text
给这个网站加 Google 登录。
```

记录 Agent 是否直接选择依赖、文件、账号绑定和回调行为。

#### 5.2 第二轮：明确为只读规划

```text
请先分析并规划 Google OAuth 登录，不修改代码。

先读取现有登录、用户、会话、配置和相关测试，然后：
1. 区分已确认事实、合理推断和必须确认的问题；
2. 整理功能需求、非功能需求、约束和验收标准；
3. 从用户入口追踪影响范围，引用真实文件和符号；
4. 生成按依赖与风险排序的任务清单；
5. 为每项任务写明完成证据和主要风险；
6. 明确本次范围外事项。

不要虚构文件或项目规则。仓库无法证明的内容请标记为未确认。
```

#### 5.3 第三轮：补充一个产品决定

```text
产品决定：仅允许已有账号绑定，不允许首次 OAuth 登录自动开户。
请更新受影响的用户场景、任务、错误提示和验收标准，其他已确认内容保持不变。
```

#### 5.4 演示观察点

- 第一轮是否急于实现；
- 第二轮是否先读项目并引用证据；
- 是否把 email 唯一误当成绑定许可；
- 是否找到页面、授权入口、回调、身份关联、会话和配置；
- 第三轮是否只更新受该决定影响的内容；
- 是否仍有未回答但会改变方案的问题。

#### 5.5 教师说明

OpenAI Codex 官方指导建议提示中写明目标行为、相关代码或复现步骤、重要约束和验证方式；复杂任务可以先调查并提出方案。Claude Code 官方最佳实践也直接用 OAuth 展示“先探索、再规划、后实现”。本课借用这一专业实践，但只要求学生产出需求分析与计划。

### 6. 小组练习：修复导出功能

#### 6.1 练习输入

```text
导出功能坏了，帮我处理一下。
```

#### 6.2 小组任务

在 8 分钟内提交：

1. 明确的任务类型；
2. 需要补充的用户场景信息；
3. 至少两项事实、两项候选推断和两项待确认问题；
4. 影响范围类别；
5. 五步以内的诊断与修复计划；
6. 一项必须保持不变的兼容行为。

#### 6.3 参考方向

```text
任务类型：先诊断，证据充分后最小修复。
影响范围：按钮事件、请求封装、导出接口、CSV 生成、响应头、权限、测试。
计划：补全复现 → 观察请求与响应 → 追踪调用 → 确认根因 → 最小修复与原场景验证。
```

教师不公布唯一根因，因为材料并未提供根因证据。

## 六、学习评价与课后任务

### 1. 形成性评价量表

| 维度 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- |
| 任务边界 | 动词、交付物和修改边界一致 | 有动词但边界不完整 | 仍使用“处理一下”等模糊表达 |
| 需求分类 | 四类信息正确且可观察 | 有少量混淆 | 只重复原始需求 |
| 证据意识 | 事实有依据，推断和待确认分开 | 分类基本正确但依据不足 | 把猜测写成事实 |
| 影响范围 | 从入口追踪并含横向影响 | 只覆盖主要代码 | 仅猜一个文件 |
| 任务拆解 | 有依赖、证据、风险和合适粒度 | 可执行但字段不全 | 只有前端/后端/测试 |

总分 10 分。8—10 分表示可以进入计划评审；5—7 分需要补充证据或任务字段；0—4 分需要重新进行需求分析。

### 2. 退出卡

请学生分别写出：

1. 一条必须有仓库证据才能成立的事实；
2. 一条会改变 OAuth 方案、必须由人确认的问题；
3. “规划”与“实现”的一个关键区别。

### 3. 课后作业

选择一个小型开源项目或教师提供的示例项目，对“增加账号停用功能”完成一页计划，必须包含：

- 用户场景和范围外事项；
- 四类需求信息；
- 事实、推断和待确认事项；
- 至少五个真实文件或符号及其证据；
- 按依赖排序的任务；
- 每项任务的完成证据与主要风险。

不得提交实现代码。若项目证据不足，应写“未确认”和下一步确认方法，不得虚构。

## 七、常见课堂问题与处理

### 1. 学生立即开始写代码

教师追问：“这条需求要求实现，还是要求先规划？账号绑定规则已经确认了吗？”让学生回到任务类型和阻塞决策。

### 2. 学生列出大量问题

要求把问题分为“仓库可查”“必须人工确认”“不影响当前任务”。只保留会改变方案的问题。

### 3. 学生把安全写成一句“注意安全”

要求改成可讨论条件，例如非法 redirect、state 不匹配、密钥存储、错误账号绑定和停用账号行为。本课不要求实现这些机制，但计划不能遗漏。

### 4. 学生虚构文件名

要求补上文件存在和调用关系证据。没有项目时，使用“回调路由”“会话服务”等组件类别，不写具体路径。

### 5. 学生计划过于通用

如果计划可以原样用于任何仓库，就说明没有基于项目。要求为每项任务补充真实入口、符号、当前行为或待调查方法。

### 6. 学生把“测试通过”当成全部验收标准

先写用户行为：成功、失败、边界和兼容结果；再说明用什么方式验证。测试命令不能替代需求本身。

## 八、课堂总结与板书

### 1. 课堂总结

1. 先用任务动词确定 Agent 要解释、诊断、规划、实现、修复还是审查。
2. 自然语言需求要还原为用户场景、功能行为、质量要求、约束和验收结果。
3. 事实必须有证据；推断可以保留但必须标记；关键未知项要说明取舍后再提问。
4. 影响范围从入口沿调用与数据追踪，并检查配置、测试、日志和文档。
5. 任务清单要有目的、范围、依赖、完成证据、风险和待确认事项。
6. 任务排序先看阻塞决定与高风险未知，再看依赖、价值和成本。

### 2. 板书设计

```text
原始需求
   ↓
任务类型：解释 | 诊断 | 规划 | 实现 | 修复 | 审查
   ↓
场景：谁—何时—何地—动作—期望—失败
   ↓
需求：功能 | 非功能 | 约束 | 验收
   ↓
证据：事实 | 推断 | 待确认
   ↓
范围：入口—调用—数据—外部 + 配置/测试/文档
   ↓
任务：目标 + 依赖 + 证据 + 风险

先理解正确，再计划具体。
```

## 九、与前后课程的衔接

### 与第二周的衔接

第二周解决“怎样把一次 Prompt 写清楚”；本周把背景、目标、输入、输出和约束应用到真实开发需求，并增加证据、影响范围、依赖和风险。

### 与第四周的衔接

本周识别出的项目事实、规范、关键文件和长期约束，将在第四周学习如何组织为项目上下文、文件上下文和 `AGENTS.md` / `CLAUDE.md` 持久化指令。

### 与第五、六周的边界

本周只要求知道应从入口追踪哪些影响和如何写计划。第五周系统学习陌生项目阅读、调用链与数据流；第六周再展开 Plan–Act–Observe、Plan Mode、小步执行和人机检查点。
