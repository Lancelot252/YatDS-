# 第八周教案：测试驱动的 Agent 开发

## 一、课程基本信息

- **课程名称**：YatOL 人机协作课程
- **授课主题**：测试驱动的 Agent 开发
- **建议课时**：2 学时（90 分钟）
- **适用对象**：能够阅读基础测试代码和失败输出的学生
- **先修内容**：Agent 工作流、工具调用和基础单元测试
- **实践载体**：编码 Agent、pytest 或项目现有测试框架

## 二、教学目标

完成本节课后，学生应能够：

1. 说明 Red–Green–Refactor[^1] 循环及每一步的证据要求。
2. 要求 Agent 先复现 Bug，再实施最小修复。
3. 区分单元、接口、集成、边界和回归测试。
4. 审查断言[^2]是否对应需求、参数化[^3]是否覆盖不同输入类别、异常验证是否检查类型与关键信息，以及 mock[^4]是否只替代外部边界。
5. 识别永远不会失败、复制实现错误或覆盖不足的测试。
6. 把正常、边界、易混淆和失败输入组织成测试矩阵。
7. 根据测试失败阶段区分生产代码、测试代码与环境问题。
8. 把测试、构建、lint[^5] 和必要的页面检查组合为验收证据。

[^1]: Red–Green–Refactor 是先看到测试失败、再做最小修复、最后在测试保护下整理代码的循环。
[^2]: 断言是测试中用于比较实际结果与期望结果的检查语句。
[^3]: 参数化是让同一条测试规则使用多组输入分别运行的方法。
[^4]: Mock 是用可控制的替身代替真实依赖的测试方法。
[^5]: Lint 是按规则检查代码中常见错误和不规范写法的静态工具。

## 三、教学设计与课前准备

### 1. 教学重点与难点

#### 教学重点

- **重点**：先看到正确原因导致的失败；测试表达可观察行为；修复后防止回归。

#### 教学难点

- **难点**：Agent 生成的测试本身也可能错误；测试通过不代表全部正确；mock 只替代网络、时钟或外部服务等边界，不替代本次要验证的业务行为。

#### 课程边界

- 第六周已经讲解验证在工作流中的位置，本周只深入测试怎样驱动实现。
- 第七周已经讲解怎样调用测试工具，本周重点是测试设计、失败解释和验证顺序。
- 第九周再系统讲解 Git 分支、Commit、PR、diff 审查和质量门禁；本周只在结束时检查修改差异。
- 第十周再系统讲解隐私、依赖和安全风险；本周只说明测试不能覆盖全部风险。

### 2. 教学准备

#### 教师准备

- 准备一个能够用固定输入稳定复现、预期输出已明确的 Bug，并确保项目测试命令可运行。
- 准备“永远不会失败”“复制实现错误”“过度 mock”三类测试反例。
- 提前保存 Red、Green 和 Refactor 三个阶段的真实输出。

#### 环境准备

- 示例仓库使用独立测试数据，不连接生产系统。
- 相关测试命令可稳定运行，并能显示收集数量、失败位置和退出状态。
- 保存修改前基线，确保演示开始时不是已有失败状态。
- 能查看新增测试、生产代码和最终 diff。

## 四、核心知识体系

### 1. TDD[^6] 循环

[^6]: TDD 是先用测试表达期望行为，再编写实现使测试通过的开发方法。

```text
Red：写出描述期望行为的测试，并确认它因目标问题失败
Green：做使测试通过的最小实现
Refactor：在测试保护下改善结构，不改变行为
Repeat：加入下一个行为或边界
```

如果没有先运行 Red，就无法证明测试能捕获问题；如果失败原因是导入错误或环境缺失，也不能进入 Green。

### 2. 测试层级

| 类型 | 关注点 | 例子 |
| --- | --- | --- |
| 单元测试 | 单个规则或函数 | 折扣计算 |
| 接口测试 | 请求、状态码、响应契约 | `POST /orders` 的 400 响应 |
| 集成测试 | 多组件真实协作 | 服务与测试数据库 |
| 边界测试 | 空值、上限、重复、异常 | 上传文件恰好 10 MB |
| 回归测试 | 已发生问题不再出现 | 空搜索词不返回全部用户 |

### 3. Agent 生成测试的审查

检查测试是否会在错误实现上失败、断言是否有业务意义、输入与预期是否独立推导、是否误用 mock、是否污染共享状态、是否包含关键边界。

`pytest.mark.parametrize` 可让同一规则覆盖多组输入；`pytest.raises` 可验证异常。测试函数必须使用断言，返回布尔值不会自动使 pytest 失败。

### 4. 从验收标准到测试矩阵

教师把一句“用户名不能为空”展开为可观察行为，而不是让 Agent 自由猜测：

| 输入类别 | 示例 | 期望行为 | 合适层级 |
| --- | --- | --- | --- |
| 正常 | `alice` | 注册成功 | 单元、接口 |
| 边界 | `""`、`"   "` | 拒绝并返回规定错误 | 单元、接口 |
| 易混淆 | `" alice "` | 按产品规则保留或去除空格 | 接口 |
| 失败 | 重复用户名 | 拒绝且不写入第二条记录 | 接口、集成 |

矩阵中的期望必须来自需求、既有契约或已确认产品决定。Agent 可以补充候选边界，但不能自行创造业务规则。

### 5. 测试层级的选择

测试应放在能够捕获原故障、同时又不过度扩大成本的最低合适层级。纯验证函数可先用单元测试；状态码或响应字段错误需要接口测试；数据库唯一约束与事务结果需要集成测试。只给底层函数补测试，可能无法捕获路由、序列化或真实依赖中的问题。

### 6. Red 阶段的证据

Red 不只是出现红色输出。教师要求记录：

```text
命令：pytest tests/api/test_register.py::test_rejects_whitespace_username -q
收集：1 项
结果：1 failed
失败断言：期望 400，实际 201
调用位置：注册接口返回处
结论：测试确实进入目标路径并捕获原缺陷
```

如果测试未被收集、在 fixture 建立时失败、使用错误 URL 或预期了未经确认的状态码，应先修正测试或环境，不能进入 Green。

### 7. Green 与最小修改

Green 只改变使目标行为成立所需的最小责任层。教师要求 Agent 同时验证新增用例和相邻正常行为，防止为了让一个测试变绿而破坏合法用户名、错误映射或已有调用方。

禁止把删除测试、降低断言、添加无理由跳过标记或把异常吞掉当作 Green。

### 8. Refactor 的进入条件

只有目标测试和相关测试保持绿色，才进入 Refactor。结构调整与行为修复应分步进行，每一步后重新运行最相关测试。若没有明确重复或结构问题，可以不做 Refactor；TDD 不要求每一轮都强行重构。

### 9. 测试数据、fixture 与隔离

共享数据库记录、缓存、时间、随机数和环境变量会让测试互相影响。教师要求 Agent 读取项目现有 fixture[^7] 和清理方式，优先复用既有测试基础设施，不自行连接真实服务。

[^7]: Fixture 是为测试准备数据或环境，并在结束后负责清理的可复用设置。

### 10. 验证顺序与停止条件

```text
新增测试
-> 最相关测试文件
-> 相关模块测试
-> 项目规定的完整测试
-> 构建或 lint
-> 最终 diff
```

验证从快到慢扩大。若完整测试需要缺失服务、网络或专用凭据，应准确记录未运行项、原因与影响，不虚构通过。若新增测试一开始就是绿色，应先确认缺陷是否已经修复、测试是否走错路径或断言是否失效。

### 11. 测试作为验收标准

每条需求都应对应可观察证据，但测试不是唯一证据。API 行为适合自动测试；页面布局还需要指定视口下的页面检查；无法复现的外部环境要作为剩余风险报告。第九周会把测试与 lint、安全检查和人工 diff 审查组合起来。

## 五、课堂教学过程（90 分钟）

| 教学环节 | 时间 | 教师讲授内容 | 讲解重点 |
| --- | ---: | --- | --- |
| 情境导入 | 7 分钟 | 展示“已加测试、全部通过”但测试无有效断言的记录 | 绿色输出也要核验 |
| TDD 循环 | 18 分钟 | 演示 Red–Green–Refactor 及进入条件 | 先确认正确失败 |
| 测试层级 | 13 分钟 | 对比单元、接口和集成测试 | 在故障可观察层验证 |
| 边界与回归 | 13 分钟 | 从需求生成测试矩阵 | 正常、边界、易混淆、失败 |
| 测试质量 | 12 分钟 | 审查断言、参数化、fixture 与 mock | 测试代码也需审查 |
| 教师现场演示 | 22 分钟 | 完成 Red、Green、相关验证和 diff 检查 | 保存真实证据 |
| 总结 | 5 分钟 | 回顾验证顺序与未验证项 | 测试是证据而非保证 |

### 各环节实施详案

#### 1. 导入：通过不等于被验证

教师展示一段 Agent 报告：“已添加测试，全部通过。”随后打开测试，发现测试直接返回布尔值且没有断言。让学生意识到测试数量和绿色输出都需要解释，测试代码本身也是可能出错的生成物。

#### 2. Red：确认失败与目标缺陷一致

先运行原有测试建立基线，再添加最小回归测试。失败应来自“纯空格用户名被接受”，而不是导入失败、fixture 缺失或测试数据错误。教师逐行解释 traceback 中期望值、实际值和调用位置。

#### 3. Green：只实现让目标行为成立的修改

对比两种做法：一种仅在用户名验证处使用 `strip()` 后判断；另一种顺便重写整个注册模块。强调 Green 阶段追求最小正确修改，降低引入新变量的机会。

#### 4. Refactor：在绿色保护下改善结构

如果验证逻辑重复，可在测试通过后提取函数或统一错误信息。每次结构调整后再次运行测试，确保重构没有改变错误类型、返回状态或正常用户名行为。

#### 5. 测试层级与边界矩阵

教师把需求写成输入—行为表：空字符串、纯空格、前后空格、正常用户名、重复用户名。说明哪些可在单元层验证，哪些需要接口或数据库集成层验证。

#### 6. 测试审查

使用三个反例检查：测试是否能在旧代码上失败；预期值是否独立于实现；mock 是否把真正需要验证的组件替换掉。最后观察新增测试在完整测试套件中的位置和命名是否符合项目规范。

#### 7. 验证闭环与总结（5 分钟）

教师把演示证据按顺序收束：修改前基线、正确 Red、最小 Green、相关测试、完整检查、最终 diff 和未运行项。强调“测试命令结束”“退出状态为 0”和“任务完成”是三个不同判断。

## 六、典型案例与边界

### 案例一：返回布尔值的“测试”

Agent 写出 `return result == expected`。pytest 会对非 `None` 返回值发出警告，但返回 `False` 不会像失败断言那样判定测试失败。应使用 `assert result == expected` 并观察失败信息。

### 案例二：只测正常路径

金额解析只测试 `"12.50"`，遗漏空字符串、负数、过多小数位和非法字符。可用参数化表格明确每种输入与期望行为。

### 案例三：测试复制了实现错误

生产代码和测试都使用同一个错误公式计算税费，于是测试通过。期望值应来自业务规则或独立样例，而不是调用被测实现生成。

### 案例四：过度 mock

接口测试把数据库、认证、序列化和服务全部 mock 掉，只证明 handler 调用了几个函数，无法发现响应 schema 不兼容。应保留少量端到端或集成验证。

### 案例五：回归测试位置错误

Bug 发生在路由解析，却只给底层纯函数补测试。应在最接近故障可观察行为的层级补一个能捕获原问题的测试。

## 七、教师现场演示

### 演示任务：修复纯空格用户名也能注册的问题

```text
Bug：用户名只有空格时也能注册。

请按 TDD 处理：
1. 找到现有注册行为和最相关测试位置；
2. 添加一个回归测试，先运行并确认它因目标缺陷失败；
3. 若失败原因与缺陷无关，先修正测试环境；
4. 做最小生产代码修改；
5. 运行相关测试，再运行项目规定的完整检查；
6. 审查测试是否同时覆盖空字符串、纯空格和正常用户名；
7. 报告 Red 与 Green 的真实输出摘要。
```

### 现场演示步骤与预期结果

1. 运行原有注册测试，确认基线不是已经失败的状态。
2. 新增 `test_rejects_whitespace_only_username`，运行后看到业务断言失败。
3. 故意展示一次错误测试，例如期望了错误状态码，说明不能为了进入 Green 就修改生产代码。
4. 修正测试预期后实施最小验证逻辑。
5. 运行新增测试及相关注册测试，观察从 Red 变为 Green。
6. 使用参数化覆盖 `""`、`"   "`、`" alice "` 和 `"alice"`，明确每种产品行为。
7. 查看 diff，确认没有为了通过测试而削弱其他验证。

### 课堂追问

- 新测试一开始就是绿色，可能说明什么？
- 为什么测试与实现使用同一个辅助函数计算预期值会有风险？
- mock 越多，单元测试是否一定越稳定？
- 全量测试耗时很长时，Agent 应怎样安排验证顺序？

### 演示交付格式

```text
基线：原有注册测试 24 passed。
Red：新增用例 1 failed；期望 400，实际 201。
修改：仅调整用户名空白判断及对应测试。
Green：新增用例与注册模块 29 passed。
完整检查：项目测试 186 passed，2 skipped；lint 通过。
差异：2 个预期文件，无依赖或配置变化。
未验证：未连接真实邮件服务，与本次输入验证无直接关系。
```

## 八、常见问题与处理

### 测试作为验收标准

好的验收标准可以转换为可观察测试，但并非所有质量都能自动化。例如可访问性、视觉体验和需求是否合理仍需其他检查。测试是证据之一，不是免责证明。

### 常见误区

- 同时写测试和实现，最后只看到绿色结果。
- 测试失败就立刻修改生产代码，未读失败原因。
- 为了通过测试而放宽断言或删除用例。
- 只运行新增测试，不检查相关旧测试和回归。
- 让 Agent 生成大量低价值用例，以数量代替覆盖质量。
- 新增测试一开始为绿色，却没有检查是否走错入口。
- 集成测试留下共享数据，导致后续测试顺序相关。
- 把环境失败汇报成业务代码失败，或把未运行写成通过。

## 九、课堂总结与板书

测试驱动的 Agent 开发强调可证伪：先证明测试能够暴露问题，再让最小修改通过，并在测试保护下改善代码。测试和生产代码都必须接受人工审查。

### 板书设计

```text
Red -> Green -> Refactor -> Repeat
失败原因正确   最小修改   行为不变

测试层级：单元 | 接口 | 集成 | 边界 | 回归
测试也需要审查：会失败吗？断言有意义吗？覆盖关键边界吗？
验证顺序：新增 -> 相关 -> 完整 -> lint/build -> diff
交付：Red 证据 | Green 证据 | 未运行项 | 剩余风险
```

## 十、与前后课程的衔接

### 1. 与第六、七周的衔接

第六周的 Observe 与 Update 由本周测试结果提供更强证据；第七周学会运行测试，本周进一步判断该测试是否值得信任。

### 2. 与第九周的衔接

第九周将把测试结果与 lint、安全检查、Git diff 和人工代码审查组合为完整的质量控制流程。

### 3. 与第十周的边界

本周只指出测试无法覆盖全部风险，不提前展开隐私、依赖、工具执行和人类责任体系。
