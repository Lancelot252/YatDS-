# 第六周：编码 Agent 的完整工作流

## 本章导读

前五周已经学习了怎样写清任务、组织上下文和阅读陌生项目。本周进入实际执行阶段：怎样让编码 Agent 先分析，再计划、修改和验证，而不是找到一个相似文件就直接动手。

完整工作流[^1]可以用两层结构表示：

[^1]: 工作流：把编码任务从开始到交付组织成连续步骤的方法。

```text
主流程：Explore -> Plan -> Implement -> Verify
小循环：Plan -> Act -> Observe -> Update
```

主流程说明任务处于哪个阶段；小循环说明 Agent 每走一步怎样读取结果并调整下一步。本章重点讨论 Plan Mode、小步迭代、Human-in-the-loop、错误反馈和验收点。工具权限与测试驱动开发分别留到第七、八周展开。

---

## 一、完整工作流：从探索到验证

### 1. Explore：先确认当前事实

Explore[^2] 是修改前的探索阶段。

[^2]: Explore：围绕当前任务读取项目并确认真实情况。

Agent 应确认：

- 当前行为能否复现；
- 真实入口、实现和调用方在哪里；
- 已有测试、配置和项目指令是什么；
- 哪些是事实，哪些仍是推断；
- 哪些问题必须由用户决定。

探索不是阅读整个仓库，而是为当前任务建立最小充分证据。

### 2. Plan：把证据变成步骤

计划应说明：

- 改什么、不改什么；
- 步骤顺序和依赖；
- 每一步的验证方式；
- 哪些结果会触发重新规划；
- 哪些节点需要人工确认。

### 3. Implement：按小步骤修改

实现阶段一次只推进一个可验证行为。每一步完成后，都要检查实际文件变化和局部结果，再决定是否继续。

### 4. Verify：证明结果符合目标

验证应回答：

- 原问题是否解决；
- 正常行为是否保持；
- 相关检查是否真实运行；
- 最终 diff[^3] 是否存在无关变化；
- 哪些结果仍未验证。

[^3]: Diff：文件修改前后的内容差异。

### 5. 四个阶段允许回退

```text
Explore -> Plan -> Implement -> Verify
   ^          ^          |          |
   +----------+----------+----------+
```

如果验证发现问题来自另一个模块，应回到 Explore 更新证据；如果影响范围扩大，应回到 Plan 调整步骤。工作流不是只能向前的固定流水线。

## 二、Plan–Act–Observe–Update 小循环

Plan–Act–Observe–Update[^4] 用于控制每一个具体步骤。

[^4]: Plan–Act–Observe–Update：先决定下一步，执行后读取结果，再更新判断的循环。

### 1. Plan：决定当前下一步

```text
当前假设：空格搜索词没有在 route 层规范化。
下一步：定位参数第一次转换的位置。
预期：找到默认值或 trim 处理。
```

这里的 Plan 可以很短，重点是说明当前动作为什么值得执行。

### 2. Act：执行最小相关动作

Act 可以是搜索、读取、编辑或运行命令。动作应直接服务于当前假设。如果正在定位空输入处理，就不应同时升级搜索依赖或重构页面。

### 3. Observe：读取真实结果

Observe[^5] 不是“命令结束了”，而是记录足以支持下一步的证据：

[^5]: Observe：读取文件、命令或程序给出的真实反馈。

```text
命令：pytest tests/api/test_search.py -q
收集：13 项
通过：12 项
失败：1 项
期望：400
实际：200，返回 53 条记录
```

### 4. Update：让结果改变计划

```text
原假设：repository 把空字符串变成通配符。
新证据：route 已经把参数变成 "*"。
更新：不修改 repository，下一步检查 route 默认值。
```

有效循环必须产生信息增量。输入、环境和假设都没有变化时，反复运行同一命令通常不会推动任务。

## 三、修改前分析与基线

### 1. 先建立基线

基线[^6]是修改前可重复的当前状态。

[^6]: 基线：开始修改前记录下来的当前行为或检查结果。

```text
输入：GET /users?q=%20%20
当前：200，返回 53 条记录
目标：400，错误码 EMPTY_QUERY
正常基线：q=alice 返回 2 条记录
```

没有基线，Agent 就无法证明修改解决了原问题，也无法判断正常行为是否被破坏。

### 2. 修改前确认五组信息

| 内容 | 需要确认的问题 |
| --- | --- |
| 目标 | 用户想要什么行为，是否有兼容要求 |
| 现状 | 问题怎样复现，失败发生在哪一层 |
| 范围 | 入口、实现、调用方、配置和测试在哪里 |
| 约束 | 项目规则、用户已有修改和禁止区域是什么 |
| 验证 | 用什么证据判断完成，失败后怎样停止 |

### 3. 环境失败不等于业务失败

如果测试在收集前出现：

```text
ImportError: No module named 'app'
```

当前只能确认测试环境或入口有问题，不能据此修改搜索业务逻辑。Agent 应先分类错误，再决定下一步。

### 4. 何时可以开始实现

进入实现前至少确认：

1. 成功、失败和边界行为可以观察或验收；
2. 修改入口和主要影响范围已有证据；
3. 没有尚未解决的关键产品冲突；
4. 当前步骤可以小范围执行和验证。

## 四、怎样写可执行、可更新的计划

### 1. 避免三行空计划

```text
1. 分析代码
2. 修改代码
3. 测试
```

这份计划没有范围、依赖和完成证据。

### 2. 每一步包含四个字段

| 字段 | 回答的问题 |
| --- | --- |
| 目标 | 本步要确认或改变什么 |
| 动作 | Agent 具体做什么 |
| 证据 | 怎样判断本步完成 |
| 依赖 | 开始前必须满足什么 |

### 3. 按行为拆解，不按文件拆解

```text
建立空搜索基线
-> 定位参数第一次转换位置
-> 确认缺失参数与纯空格的产品规则
-> 做最小修复
-> 验证空输入、正常搜索和分页
-> 检查最终差异
```

“修改 route、修改 service、修改 test”只列出了文件，不能表达行为依赖。

### 4. 写出停止条件

```text
- 如果发现当前行为属于已发布兼容规则，暂停并请求产品决定；
- 如果目标文件包含无法安全合并的用户修改，停止编辑并报告；
- 如果验证命令未进入业务代码，先处理环境，不修改生产逻辑。
```

### 5. 计划长度与风险相称

若任务只有一个目标文件、一个明确行为和一条验证命令，计划可以只写“确认—修改—验证”。跨模块功能或数据迁移还要写明依赖顺序、检查点、停止条件和回滚方法。计划的价值来自决策清楚，不来自篇幅长。

## 五、深入理解 Plan Mode

Plan Mode[^7] 是把“研究和决策”与“正式修改”分开的工作方式。它的核心价值不是让 Agent 多写一段文字，而是在代码改变前暴露误解、未知项、方案分歧和验证困难。

[^7]: Plan Mode：让 Agent 在正式修改前先研究项目、澄清问题并提出可审查方案的模式。

### 1. Plan Mode 解决什么问题

直接执行时，Agent 可能在尚未找到真实入口、没有确认产品规则或没有理解影响范围时就开始编辑。Plan Mode 在实现前增加一个可审查的决策阶段：

```text
模糊请求
-> 只读探索
-> 澄清未知项
-> 比较方案
-> 形成计划
-> 人工审查与批准
-> 小步实现和验证
```

它尤其适合降低三类风险：

- **方向风险**：解决了错误的问题，或选择了不符合产品要求的行为；
- **范围风险**：只看到一个文件，却漏掉调用方、配置、测试或数据影响；
- **验证风险**：计划只写“完成修改”，没有说明怎样证明结果正确。

Plan Mode 不保证计划一定正确。它只是让计划在修改发生前可见、可问、可改。

### 2. Plan Mode 的完整过程

#### 第一步：确认目标和边界

Agent 先复述目标、期望结果、禁止改变的内容和已知约束。如果“纯空格搜索”与“缺失搜索参数”是否同义尚不明确，就应把它列为待确认项，不能自行决定。

#### 第二步：进行只读探索

Agent 读取项目说明、目标文件、调用链、配置和现有验证，必要时运行非破坏性的搜索或诊断命令。探索要回答：

```text
入口在哪里？
值第一次在哪里转换？
哪些调用方依赖当前行为？
现有验证覆盖了什么？
哪些结论是事实，哪些仍是推断？
```

“只读”主要表示不正式修改项目源文件，并不一定表示完全不能运行命令或产生任何文件。允许的工具、命令和计划文件位置由具体产品决定。

#### 第三步：澄清真正影响方案的问题

只有答案会改变实现方向、公共行为或风险时，才需要请求用户决定。能够从仓库中查明的内容，应先自行查证。

```text
需要确认：纯空格应返回 400，还是等同于未提供 q？
不必询问：搜索路由文件在哪里？——应先在项目中定位。
```

#### 第四步：比较可行方案

存在多条路径时，不应只给出一个结论。应说明每个方案的改动位置、兼容性、复杂度和验证成本，再给出有证据支撑的建议。

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| 在 route 规范化输入 | 靠近参数边界，错误响应清楚 | 其他入口可能仍需单独处理 |
| 在 service 统一拒绝空值 | 多个入口可以复用 | 可能改变内部调用者的既有语义 |
| 在 repository 忽略空条件 | 数据访问层改动小 | 无法表达正确的 HTTP 错误行为 |

#### 第五步：生成可执行计划

高质量计划不是文件清单，而是有顺序、有依赖、有证据的行动设计。至少包含：

| 计划字段 | 应回答的问题 |
| --- | --- |
| 目标与当前基线 | 现在发生什么，期望变成什么 |
| 已确认事实 | 结论来自哪些文件、命令或结果 |
| 修改范围 | 哪些模块和行为允许改变 |
| 非目标 | 哪些相邻问题本次不处理 |
| 实施步骤 | 每一步做什么，先后依赖是什么 |
| 验收方法 | 每一步用什么可观察结果证明完成 |
| 风险与检查点 | 哪些情况需要暂停、确认或重新规划 |

一个可直接审查的计划可以写成：

```text
目标：纯空格 q 返回 EMPTY_QUERY，保留缺失 q 的原行为。

证据：route 将 q.strip() 后的空值替换为 "*"；
      repository 只接收转换后的查询词。

范围：参数规范化和对应验证。
非目标：排序、分页、依赖升级和 API 改名。

步骤：
1. 在参数边界区分缺失值与纯空格；
2. 补充纯空格和缺失参数的验证；
3. 验证正常搜索、排序和分页未受影响；
4. 检查最终差异与未验证风险。

暂停条件：发现其他公共入口复用当前转换规则。
```

#### 第六步：审查、修改和批准

用户不应只看计划是否“像计划”，而应检查：

1. 计划是否引用了真实代码证据，而不是凭文件名猜测；
2. 是否覆盖入口、实现、调用方、配置和现有验证；
3. 是否区分事实、推断和必须由人决定的问题；
4. 每一步是否有可观察的完成证据；
5. 是否包含不必要的重构、升级或相邻功能；
6. 风险、停止条件和未验证项是否清楚。

如果计划存在遗漏，可以要求 Agent 继续探索或只修改计划。批准表示认可当前方向和范围，不表示放弃后续监督，也不表示计划中的假设已经全部得到证明。

#### 第七步：执行中继续更新计划

进入实现后，计划仍然可以变化。若新证据只改变目标范围内的文件或验证命令，就更新步骤；若需要新增公共接口、改变产品行为、接触生产数据或执行新的高影响动作，就暂停并重新确认。

```text
原计划：修改 repository
新证据：转换实际发生在 route
处理：撤销该步骤，更新责任层和验证范围
```

### 3. Plan 阶段可以做什么

不同产品有不同限制，但通用目标是“先获得决策所需证据，不提前实施正式改动”。

| 动作 | Plan 阶段通常如何处理 |
| --- | --- |
| 读取代码、配置和文档 | 用于建立项目事实 |
| 搜索符号和调用关系 | 用于确认影响范围 |
| 运行非破坏性诊断 | 用于复现问题或验证假设，是否允许取决于产品 |
| 编写计划产物 | 部分产品允许写入指定计划文件 |
| 修改源代码或配置 | 通常留到计划批准后 |
| 发布、部署、删除或外部写入 | 不属于普通规划动作，需要单独授权和风险判断 |

因此，不能把 Plan Mode 简化成“Agent 什么都不能做”，也不能因为它能运行某些命令，就把它当成已经进入实现阶段。

### 4. 什么时候使用 Plan Mode

| 判断维度 | 更适合直接执行 | 更适合先计划 |
| --- | --- | --- |
| 范围 | 单文件、局部文本 | 跨模块、多入口 |
| 歧义 | 目标行为明确 | 有多种合理方案 |
| 影响 | 低影响、易恢复 | 公共 API、数据结构、迁移 |
| 验证 | 快速、确定 | 多环境或人工判断 |
| 项目熟悉度 | 路径和约束已清楚 | 陌生仓库或隐含规则较多 |

直接执行也不能跳过真实文件确认和结果验证；Plan Mode 也不代表所有任务都要写长计划。修正明确错字时，规划成本可能高于修改本身；涉及认证、迁移或公共接口时，先计划通常更稳妥。

### 5. 没有模式按钮也能分阶段工作

Plan Mode 是一种产品能力，也是一种工作方法。工具没有专门按钮时，可以用 Prompt 明确阶段边界：

```text
第一阶段只读：
请复现问题，定位入口、实现、调用方和现有验证；
列出已确认事实、未知项、方案取舍、实施步骤和验收点。
不要修改项目源文件。

我确认方案后，再进入实现阶段。
实现中如范围或关键假设变化，先暂停并更新计划。
```

若 Agent 在只读阶段直接改代码，应立即停止并重申边界；若它只返回通用步骤，应要求补充仓库证据、具体影响范围和验证方法。

### 6. 不同产品的行为要分别确认

以下内容依据 2026 年 8 月 9 日访问的官方文档：

| 产品 | 当前文档中的 Plan 行为 | 使用时要注意 |
| --- | --- | --- |
| Claude Code | `plan` 是权限模式，用于分析代码库和提出方案；可以读取文件，并可运行探索性命令 | 进入方式、模式切换和批准选项属于 Claude Code，不是通用语法 |
| Gemini CLI | Plan Mode 是受工具限制的只读环境；按“研究、形成计划、审查、批准”推进，并可在指定目录写计划文件 | 计划文件例外和工具限制以 Gemini CLI 当前配置为准 |
| GitHub Copilot CLI | 先分析请求和代码库，可提出澄清问题，生成结构化计划并等待批准 | 官方建议在批准后实施、验证，再决定提交 |
| OpenAI 官方指导 | 强调按用户请求的授权范围区分分析、实现，以及需要确认的外部、高影响或扩大范围动作 | 这说明任务边界与批准原则，不能据此虚构统一的 Codex Plan Mode 命令 |

快捷键、命令、计划文件位置、允许的工具和审批选项都属于具体产品。使用前应查看当前产品的官方文档，而不是把一种编码 Agent 的行为推广给全部产品。

### 7. 四个常见误解

- **“进入 Plan Mode 就不会产生任何副作用”**：部分产品仍允许探索性命令或写计划文件，应检查实际权限；
- **“计划越长越专业”**：计划应与风险相称，关键是证据、依赖和验收清楚；
- **“批准计划等于批准所有后续动作”**：部署、发布、删除、权限扩大等仍需按任务边界处理；
- **“计划完成等于任务完成”**：只有实施结果通过实际验证，任务才可能交付。

## 六、小步迭代与错误反馈

### 1. 使用修改预算

修改预算[^8]限定当前一步允许影响的范围。

[^8]: 修改预算：当前一步允许改变的最大范围。

```text
允许：搜索参数规范化函数和对应验证
不允许：API 改名、依赖升级、排序重构
扩大条件：发现共享函数影响其他公共入口
```

每步结束后检查实际文件变化，避免无关格式化、顺手重构和覆盖用户内容。

### 2. 失败后先分类

| 类别 | 典型情况 |
| --- | --- |
| 需求 | 多种产品行为都合理 |
| 代码 | 目标路径产生错误值 |
| 测试 | 测试预期与正式规则冲突 |
| 配置 | 当前实现绑定与预期不同 |
| 依赖 | 导入、版本或服务不可用 |
| 权限 | 动作被环境拒绝 |
| 环境 | 验证没有进入业务代码 |

分类后再形成新假设，并选择能区分候选原因的最小动作。

### 3. 三种后续处理

- **继续**：结果符合预期，风险没有增加；
- **更新计划**：路径、步骤依赖或验证方式发生局部变化；
- **暂停**：产品行为冲突、出现范围外文件或需要部署、删除、迁移、外部写入等高影响动作。

### 4. 观察完整结果

不要只看命令最后一行。应检查退出状态、收集数量、失败阶段、警告、期望值和实际值。页面任务还要检查指定视口和交互结果。

## 七、Human-in-the-loop 与中间检查点

Human-in-the-loop[^9] 是在关键节点保留人的判断。

[^9]: Human-in-the-loop：让人在自动流程的关键节点参与决定。

### 1. 适合人工介入的节点

- 不同方案会改变产品行为；
- 数据冲突或操作难以恢复；
- 需要扩大权限或写入外部系统；
- 自动证据相互冲突；
- 视觉与体验无法只靠自动检查判断。

### 2. 不要只问“可以继续吗”

Agent 应提供做决定所需的信息：

```text
当前事实：已有 17 个重复用户名。
选项 A：迁移失败并先清理，风险较低。
选项 B：自动添加后缀，会改变用户登录名。
建议：先确认冲突处理规则，再创建迁移。
```

### 3. 不要让所有步骤都等待确认

在已经授权的范围内，读取文件、完成局部修改和运行非破坏性验证可以连续进行。人工检查点应集中在真正会改变方向或风险的节点。

### 4. 中间检查点记录什么

```text
当前目标
已完成步骤及证据
当前修改范围
已否定假设
最新验证状态
唯一下一步
等待人工决定的问题
```

“已经完成大部分工作”不是有效检查点，因为它无法帮助后续继续。

---

## 八、验收点与完成条件

验收点[^10]是证明某一步达到要求的具体证据。

[^10]: 验收点：用来判断某一步是否真正完成的证据。

### 1. 验收点必须可观察

```text
不可观察：代码质量更好。
可观察：公开返回结构不变，相关检查通过，diff 无无关重排。
```

### 2. 分层验收

```text
步骤验收：纯空格输入不再进入查询
阶段验收：空输入与正常查询行为都符合要求
最终验收：需求、相关检查、diff 和剩余风险均已核对
```

局部检查通过不能自动替代最终验收。

### 3. 完成条件

任务结束前至少确认：

1. 原始需求逐项对应；
2. 修改范围已经说明；
3. 相关验证实际运行；
4. 最终 diff 已检查；
5. 未运行检查及原因已披露；
6. 剩余风险和未知事项已说明。

### 4. 交付报告

```text
结果：完成了什么用户目标。
修改：哪些文件发生了什么行为变化。
验证：实际运行了什么，结果是什么。
未验证：哪些检查没有运行及原因。
风险：还存在哪些未知事项。
```

不能把“应该通过”写成“已经通过”。

## 九、贯穿案例：修复空搜索词返回全部用户

### 1. Explore：建立基线并定位

```text
输入：q="   "
当前：200，返回 53 条记录
目标：400，错误码 EMPTY_QUERY
```

Agent 从真实路由开始，追踪参数解析、搜索 service、repository 和现有测试，同时检查项目规则与用户已有修改。

### 2. Plan：形成五步方案

```text
1. 定位 q 第一次转换的位置；
2. 确认缺失 q 与纯空格是否采用同一产品规则；
3. 在责任层做最小修改；
4. 验证空输入、正常查询、排序和分页；
5. 检查最终 diff 与未验证风险。
```

### 3. Observe 改变原计划

```text
Plan：检查 repository 是否把空字符串转为通配符。
Act：读取查询构造函数和调用方。
Observe：repository 只接收 "*"；转换发生在 route 默认值。
Update：不修改 repository，改查 route 参数规则。
```

### 4. Human-in-the-loop

探索发现：缺失 `q` 已用于“列出全部用户”，但纯空格没有正式规则。Agent 应请用户在以下行为中决定：

- 保留缺失参数，只拒绝纯空格；
- 两种输入都拒绝；
- 把列出全部用户迁移到独立接口。

假设用户确认第一种方案，当前修改预算就是：只调整纯空格输入处理，不改变缺失参数、排序和分页。

### 5. Implement 与 Verify

```text
纯空格输入
-> 空字符串输入
-> 缺失 q
-> 正常搜索
-> 排序与分页
-> 相关检查
-> 最终 diff
```

最后报告真实修改、实际验证结果、未连接的真实搜索后端和剩余风险。

## 十、两个边界案例

### 1. 数据库唯一约束迁移

“把用户名改成唯一”可能遇到已有重复数据。计划必须先检查重复情况，再由人决定拒绝迁移、自动重命名或分阶段限制新增。这个案例用于说明高影响任务为什么需要人工检查点和停止条件。

具体迁移命令和权限审批留到第七周，迁移测试设计留到第八周。

### 2. 前端视觉修改

“修复窄屏按钮遮挡”不能只看构建是否通过。Observe 还应包含指定视口、页面滚动、按钮可见性和宽屏回归；视觉层级可能需要人工判断。

本周只说明视觉结果怎样进入反馈循环，不展开浏览器工具调用。

## 十一、常见问题与改进

| 常见问题 | 改进方法 |
| --- | --- |
| 一开始就修改最像的文件 | 先复现并从真实入口定位 |
| 计划只有“分析、编码、测试” | 增加范围、依赖、证据和停止条件 |
| 把计划当固定剧本 | 每次 Observe 后更新计划 |
| 所有任务都写长计划 | 让计划成本与任务风险相称 |
| 没有修改前基线 | 记录可重复输入、当前结果和目标结果 |
| 动作后只看最后一行 | 读取退出状态、数量、失败阶段和警告 |
| 失败后重复同一命令 | 先形成新假设，再选择诊断动作 |
| 一次修改多个独立行为 | 设定当前修改预算 |
| 发现问题就顺手重构 | 把非目标发现记录为范围外事项 |
| 所有步骤都请求确认 | 只在关键决策和高影响节点介入 |
| 局部检查通过就完成 | 区分步骤、阶段和最终验收 |
| 把未运行写成通过 | 明确已运行、未运行、原因和影响 |
| 混写各产品 Plan Mode | 分别依据供应商最新官方文档 |

## 十二、三个可复用 Prompt

### 1. 先分析再修改

```text
第一阶段只读，不修改源文件。

请：
1. 复现或确认当前行为；
2. 定位真实入口、实现、调用方和现有验证；
3. 区分事实、推断和必须由我决定的问题；
4. 给出不超过 5 步的计划；
5. 为每一步写动作、依赖、验收点和停止条件。

方案确认后再进入实现阶段。
```

### 2. 按计划小步实现

```text
按已确认计划开始实现。

一次只推进一个可验证步骤；
每步遵守当前修改预算；
动作后读取真实结果；
结果与预期不同时先更新计划；
不自动加入范围外重构；
遇到产品歧义、高影响动作或范围扩大时暂停说明。
```

### 3. 完成前验收

```text
请对照原始需求逐项验收：
1. 每项需求对应什么修改和证据；
2. 实际运行了哪些检查，结果是什么；
3. 最终 diff 是否包含无关变化；
4. 哪些检查没有运行及原因；
5. 还有哪些剩余风险。

不要把未运行的检查写成通过。
```

## 十三、本章总结

编码 Agent 工作流的核心不是写一份很长的计划，而是让行动、证据和下一步始终保持联系。

```text
Explore -> Plan -> Implement -> Verify

每一步内部：
Plan -> Act -> Observe -> Update
```

实际使用时应记住：

1. 修改前先建立基线；
2. 计划来自真实仓库证据；
3. 任务按可验证行为拆分；
4. 小步修改并限制当前范围；
5. 失败后更新假设，不机械重试；
6. 人工介入集中在关键决策；
7. 完成结论必须依据需求、验证和 diff。

第七周将具体学习工具调用与权限安全；第八周将进一步学习测试怎样驱动实现和防止回归。
