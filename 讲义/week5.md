# 第五周：使用编码 Agent 阅读代码与理解项目

## 本章导读

编码 Agent 不仅可以生成和修改代码，也可以帮助开发者进入陌生仓库、搜索真实文件、解释关键模块并整理项目结构。

但是，“让 Agent 解释整个项目”通常得不到可靠结果。Agent 可能只阅读文件名最显眼的模块，可能把旧实现当作当前入口，也可能生成一份流畅却无法核查的说明。

本章只讨论编码 Agent 的代码阅读与项目理解能力，重点解决以下问题：

1. 怎样让 Agent 在不修改代码的前提下建立项目地图；
2. 怎样找到真实启动入口、功能入口和调用方；
3. 怎样分析核心模块、调用链[^1]和数据流[^2]；
4. 怎样确认配置和第三方依赖是否真正生效；
5. 怎样让 Agent 解释认证、队列或搜索模块，并引用仓库证据；
6. 怎样识别局部阅读、同名符号和旧代码造成的误判；
7. 怎样生成准确、简短、可供下一位开发者继续使用的项目说明。

第四周已经学习如何为编码 Agent 组织项目上下文。本周进一步学习如何让 Agent 从陌生仓库中主动找到这些上下文。第六周才会把探索、计划、实现和验证组织成完整工作流。

[^1]: 调用链：从入口开始的“谁调用谁”路径。
[^2]: 数据流：数据如何输入、变化、保存和输出的过程。

---

## 一、代码阅读的目标不是“看完所有文件”

### 1. 逐行阅读不等于理解项目

进入陌生仓库后，常见做法是打开最大的文件，要求 Agent 逐行解释。这样可能理解一个局部实现，却无法回答：

- 项目怎样启动；
- 外部请求从哪里进入；
- 哪个模块承担核心业务规则；
- 数据经过哪些转换；
- 配置怎样覆盖；
- 修改一个函数会影响哪些调用方；
- 哪些代码根本不会在当前环境运行。

### 2. 项目理解需要一张可核查的地图

一张有用的项目地图至少能回答：

```text
项目是什么
-> 怎样启动
-> 有哪些外部入口
-> 核心模块如何分工
-> 一个具体功能怎样执行
-> 数据怎样变化
-> 配置和依赖怎样生效
-> 怎样用测试或运行证据确认
```

### 3. 阅读应围绕具体问题

过宽的要求：

```text
解释整个项目。
```

改进后的要求：

```text
暂不修改代码。
先建立项目地图，再追踪“创建订单”从 HTTP 入口到数据库写入和事件发布的路径。
关键结论引用真实文件和符号，并标出尚未确认的部分。
```

具体问题帮助 Agent 判断哪些目录和代码值得优先阅读。

### 4. 先声明只读边界

如果目标只是理解项目，应明确：

```text
本次只读分析，不创建、编辑或删除文件，也不安装依赖。
```

“解释”“分析”和“查找”不自动意味着可以修改。第三周学习的任务动词边界，在这里直接用于代码阅读。

### 5. 阅读结果必须能被别人复查

低质量结论：

```text
系统通过认证服务检查用户权限。
```

改进结论：

```text
`POST /login` 在 `src/routes/auth.ts` 的 `loginRoute` 中注册，
它调用 `src/services/auth-service.ts` 的 `authenticate()`；
权限判断由 `src/security/policy.ts` 的 `canSignIn()` 完成。
```

文件、符号和关系使结论能够被复查。

## 二、建立代码阅读的证据标准

### 1. 三类结论

Agent 的阅读结果应区分：

#### 1.1 代码可见事实

可以直接从当前仓库文件证明：

```text
`src/server.ts` 调用 `app.listen()`。
`package.json` 的 `start` 脚本执行 `node dist/server.js`。
```

#### 1.2 运行后验证

通过测试、日志、断点或最小请求确认：

```text
发送 POST /orders 后，日志显示运行路径经过 OrderService.create()。
```

#### 1.3 尚未确认的推断

代码中存在某条可能路径，但尚未证明当前配置会使用：

```text
项目可能在 CACHE_ENABLED=true 时初始化 Redis，当前环境是否启用尚未确认。
```

### 2. 文件路径不是全部证据

只引用文件仍可能过宽：

```text
过宽：认证逻辑位于 `src/auth.ts`。
更清楚：认证入口是 `src/auth.ts` 的 `authenticate()`；
密码比较发生在 `verifyPassword()`，失败被映射为 `InvalidCredentials`。
```

关键结论应尽量引用符号、配置键、路由名或测试名称。

### 3. 注释和文档也可能过期

README、注释和设计文档是重要线索，但不能自动代表当前实现。Agent 应比较：

- 文档描述；
- 当前脚本；
- 当前代码；
- 当前测试；
- 实际运行结果。

如果不一致，应明确报告，而不是静默选择其中一个。

### 4. 证据表模板

```markdown
| 结论 | 类型 | 证据 | 仍需确认 |
| --- | --- | --- | --- |
| Web 入口是 `src/server.ts` | 代码事实 | `app.listen()` | 无 |
| 创建订单会发布事件 | 代码事实 | `OrderService.create()` 调用 publisher | 当前配置是否启用 publisher |
| 本地请求经过该路径 | 运行验证 | 测试日志 | 无 |
```

### 5. 流畅说明不等于真实证据

Agent 很容易把合理推断写成确定描述。阅读时要主动要求：

```text
不要用“通常”“可能存在”的框架经验补全项目事实。
无法从当前仓库确认时，请明确标记为推断或未知。
```

## 三、三遍阅读法

### 1. 第一遍：建立项目地图

目标是低成本回答：

- 项目用途是什么；
- 使用哪些语言、框架和运行时；
- 顶层目录如何分工；
- 从哪里启动；
- 测试和构建入口在哪里；
- 是否存在项目指令。

第一遍不需要深入每个函数。

### 2. 第二遍：追踪一个具体功能

选择一个真实行为：

- 用户登录；
- 创建订单；
- 消息入队和消费；
- 搜索请求；
- 命令行导出；
- 定时清理任务。

从外部入口向下追踪业务逻辑、数据访问和副作用，再从目标函数向上检查调用方。

### 3. 第三遍：验证静态判断

静态阅读得到“可能路径”，运行证据确认“当前输入和配置确实经过这条路径”。

可使用：

- 已有测试；
- 最小请求；
- 日志；
- 调试器断点；
- 调用跟踪；
- 数据库状态；
- 生成产物。

### 4. 三遍阅读的关系

```text
第一遍：项目地图
    ↓ 缩小范围
第二遍：功能路径
    ↓ 形成假设
第三遍：运行验证
    ↓ 修正项目理解
```

### 5. 为什么不一开始就深入代码

如果没有项目地图，Agent 可能：

- 解释已经废弃的旧模块；
- 把测试替代实现当成生产实现；
- 忽略另一个真正的入口；
- 使用错误配置理解代码分支；
- 在生成目录中追踪源逻辑。

## 四、第一遍：分析仓库根目录

### 1. 先看根目录文件

根目录通常提供项目边界：

- README 和贡献指南；
- 依赖清单与 lockfile[^3]；
- 构建脚本和 Makefile；
- 容器与部署配置；
- 测试、lint 和类型配置；
- CI[^4] 工作流；
- `AGENTS.md` 等项目指令；
- 工作区或多包配置。

[^3]: lockfile（依赖锁定文件）：记录依赖准确版本的文件。
[^4]: CI（持续集成）：代码变更后自动运行构建、检查和测试的流程。

### 2. 依赖清单说明什么

依赖清单可以帮助识别：

- 主要语言生态；
- 框架候选；
- 应用与开发依赖；
- 可执行脚本；
- 项目版本和包信息。

但“声明了依赖”不等于“当前运行路径一定使用它”。

### 3. lockfile 为什么重要

依赖清单可能允许一个版本范围，lockfile 记录当前解析版本。Agent 查阅外部 API 文档前，应先确认项目实际锁定版本。

```text
package.json: "library": "^3.0.0"
lockfile: library 3.4.2
```

不能用最新版 5.x 的接口解释当前 3.4.2 代码。

### 4. 脚本比命令猜测更可靠

```text
README 说运行 `npm test`
package.json 实际只有 `test:unit` 和 `test:integration`
CI 执行 `npm run test:unit`
```

Agent 应报告文档可能过期，并以当前脚本和 CI 说明可见事实。

### 5. 多包仓库的识别

monorepo[^5] 可能包含：

[^5]: Monorepo（单体仓库）：在一个代码仓库中管理多个应用或软件包。

```text
apps/web/
apps/api/
packages/domain/
packages/ui/
packages/config/
```

此时要确认：

- 工作区配置；
- 各包入口；
- 包之间依赖；
- 共享配置；
- 根命令和包内命令的区别。

### 6. 根目录阅读 Prompt

```text
请只读检查仓库根目录。
说明项目类型、语言、框架候选、工作区结构、启动脚本、测试和构建入口。
每项引用真实文件；依赖存在但用途未确认时不要下结论。
```

## 五、项目目录结构分析

### 1. 不要只复述目录名

低质量输出：

```text
src 是源代码，tests 是测试，docs 是文档。
```

改进输出：

```text
`src/api/` 注册 HTTP 路由并转换请求响应；代表文件为 `users.ts`。
`src/domain/` 保存不依赖 Web 框架的订单与金额规则；由 service 调用。
`src/repository/` 封装数据库访问；接口在 domain，实现在 infrastructure。
```

### 2. 目录地图的字段

| 目录 | 职责 | 代表文件 | 上游 | 下游 | 对应测试 |
| --- | --- | --- | --- | --- | --- |
| `src/routes` | HTTP 入口 | `orders.ts` | Web 请求 | service | `tests/routes` |
| `src/services` | 业务流程 | `order-service.ts` | route、worker | repository、publisher | `tests/services` |
| `src/repositories` | 数据访问 | `order-repository.ts` | service | database | `tests/integration` |

### 3. 识别架构分层

Agent 可以从以下证据判断分层：

- 目录布局；
- import 方向；
- 接口定义位置；
- 依赖注入[^7]注册；
- 测试替代方式；
- 项目文档和规则。

[^7]: 依赖注入：由外部代码把需要的对象交给当前组件。

仅凭目录名不能断言项目严格遵循某种架构模式。

### 4. 识别生成代码

生成代码常见线索：

- 文件头写有 “generated” 或 “do not edit”；
- 目录名为 `generated`、`gen` 或 `dist`；
- 构建脚本包含 generate；
- 源 schema、IDL 或模板存在；
- 文件在构建时重新创建。

理解项目时应追踪生成源，而不是把生成结果误认为手写核心模块。

### 5. 识别遗留和废弃区域

常见线索：

- `legacy/`、`deprecated/`；
- 无调用方；
- 只被旧测试引用；
- README 或迁移文档说明替换；
- 构建配置不再包含；
- 功能开关永久关闭。

目录仍存在，不代表当前运行路径使用。

### 6. 目录分析的边界

第一遍只建立模块地图。不要在还未确定当前功能入口时，让 Agent解释每个目录中的所有文件。

## 六、定位真实入口

### 1. 入口不只有 main 文件

一个项目可能同时有：

- Web 服务启动入口；
- HTTP 或 GraphQL 功能入口；
- CLI[^6] 命令；
- 消息消费者；
- 定时任务；
- 后台 worker；
- 前端页面或事件处理器；
- 测试入口；
- 插件或扩展注册点。

[^6]: CLI（命令行界面）：通过终端命令操作程序的界面。

### 2. 启动入口与功能入口

```text
启动入口：src/server.ts
  -> 创建应用
  -> 注册插件
  -> 注册路由
  -> 监听端口

功能入口：POST /orders
  -> createOrderRoute
```

找到 `server.ts` 只说明应用如何启动，仍需继续找到目标功能从哪里进入。

### 3. Web 入口定位

可查找：

- 框架初始化；
- 路由注册；
- URL 路径；
- controller 装饰器；
- GraphQL schema 和 resolver；
- 中间件和认证注册。

路由定义可能分散在多个文件，也可能动态注册。

### 4. CLI 入口定位

可查看：

- 包的 executable 配置；
- `main()`；
- 参数解析器；
- 子命令注册；
- shell 脚本；
- 安装后的命令映射。

功能名称可能与实现函数不同，应从命令注册向下追踪。

### 5. 消息和任务入口定位

队列消费者或定时任务可从以下位置寻找：

- topic 或 queue 名称；
- consumer 注册；
- worker 启动脚本；
- cron 表达式；
- scheduler 配置；
- handler 映射；
- 重试和死信[^8]配置。

[^8]: 死信：多次处理失败后被转到专门位置的消息。

### 6. 前端入口定位

可以从用户可见行为开始：

```text
按钮或页面
-> 事件处理器
-> 状态或表单逻辑
-> API 客户端
-> 后端路由
-> 响应状态更新
```

只解释组件中的 `onClick`，不能证明完整功能已经理解。

### 7. 从用户行为搜索

当文件名不明确时，可搜索：

- URL；
- CLI 命令名；
- 事件或 topic 名；
- UI 文本；
- 错误消息；
- 配置键；
- 测试名称；
- 数据库表或字段。

### 8. 入口证据模板

```markdown
## Entry
- External trigger: `POST /orders`
- Registration: `src/routes/index.ts::registerRoutes`
- Handler: `src/routes/orders.ts::createOrderRoute`
- Middleware: `requireUser`, `validateBody`
- Evidence status: code-visible; runtime path not yet verified
```

## 七、识别核心模块和参考实现

### 1. 什么是核心模块

满足以下任一条件，并且与本次阅读目标存在入口或调用关系的模块，应列为核心模块：

- 承担关键业务规则；
- 控制重要状态变化；
- 被多个入口依赖；
- 提供稳定公共接口；
- 连接数据库或外部系统；
- 处理关键安全和一致性边界。

文件大不代表核心，文件短也不代表不重要。

### 2. 核心模块分析字段

1. 模块职责；
2. 公开接口；
3. 输入和输出；
4. 状态与生命周期；
5. 依赖方向；
6. 异常和失败行为；
7. 副作用；
8. 对应测试；
9. 被哪些入口使用。

### 3. 识别公共接口

公共接口不一定是语言中的 `public`。还可能包括：

- HTTP API；
- CLI 输出；
- 导出的函数或类；
- 消息 schema；
- 数据库 schema；
- 插件接口；
- 其他包导入的模块。

### 4. 查找参考实现

理解或准备扩展功能时，可以让 Agent 找一个相似且成熟的实现：

```text
请在仓库中找与“创建优惠券”最相似的现有功能。
比较入口、验证、service、repository、错误处理和测试结构。
说明哪些模式可以复用，哪些差异不能照搬。
```

### 5. 参考实现的选择标准

- 当前仍被调用；
- 与目标位于相同架构层；
- 由当前测试覆盖；
- 使用当前框架和 API；
- 不属于 deprecated 或 legacy；
- 业务语义确实相近。

### 6. 不要机械复制参考实现

两个功能文件结构相似，不代表：

- 权限规则相同；
- 事务[^9]边界相同；
- 输入和错误行为相同；
- 数据敏感等级相同；
- 性能要求相同。

[^9]: 事务：让一组数据操作一起成功或一起撤销的机制。

参考实现用于理解项目惯例，不用于替代需求分析。

## 八、调用链分析

### 1. 调用链回答什么

调用链说明“谁在什么条件下调用谁”。

```text
POST /orders
-> createOrderRoute
-> OrderService.create()
-> InventoryService.reserve()
-> OrderRepository.save()
-> EventPublisher.publish()
```

### 2. 每一跳应记录什么

- 调用者；
- 被调用者；
- 传入参数；
- 返回结果；
- 分支条件；
- 异常传播；
- 状态变化；
- 外部副作用。

### 3. 正向追踪

从外部入口向下寻找：

```text
入口 -> 验证 -> 业务规则 -> 数据访问 -> 外部服务 -> 响应
```

正向追踪适合理解一个用户行为怎样完成。

### 4. 反向追踪

从目标函数向上寻找所有调用方：

```text
谁调用它？
是否还有 CLI、worker 或测试调用？
返回类型变化会影响谁？
异常行为是否被上游依赖？
```

反向追踪适合判断一个模块的真实用途和潜在影响。

### 5. 同名符号问题

仓库中可能存在多个 `save()`、`execute()` 或 `handle()`。Agent 不能只选择文本搜索结果最多的文件，应结合：

- 类型；
- import；
- 实例创建；
- 调用位置；
- 当前入口；
- 运行配置。

### 6. 动态绑定

依赖注入、接口、多态、装饰器和插件机制会使静态搜索只看到抽象类型。

```text
OrderRepository interface
  <- PostgresOrderRepository
  <- InMemoryOrderRepository
```

要确认当前运行使用哪一个，需要继续查看：

- 容器注册；
- factory；
- 环境条件；
- 测试替代；
- 启动配置。

### 7. 事件驱动调用链

事件调用不是直接函数调用：

```text
OrderService.create()
-> publish OrderCreated
-> message broker
-> InventoryConsumer
-> reserve inventory
```

需要同时记录事件 schema、topic、发布位置、消费者注册、重试和幂等[^10]处理。

[^10]: 幂等：同一操作重复执行，结果仍与执行一次相同。

### 8. 异常路径

不要只追踪成功路径。还应找到：

- 输入验证失败；
- 权限拒绝；
- 资源不存在；
- 外部服务超时；
- 数据库事务回滚；
- 重试和死信；
- 错误到响应的映射。

### 9. 调用链输出模板

```markdown
| 步骤 | 调用者 | 被调用者 | 输入/输出 | 条件 | 副作用 | 证据 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | route | service | request -> command | 已认证 | 无 | 文件与符号 |
| 2 | service | repository | entity -> id | 库存足够 | DB 写入 | 文件与符号 |
```

## 九、数据流分析

### 1. 调用链与数据流的区别

```text
调用链：谁调用谁
数据流：数据在每一层怎样验证、转换、保存和返回
```

### 2. 一条典型数据流

```text
原始 JSON
-> 请求 schema
-> 业务命令对象
-> 领域实体
-> 数据库记录
-> 事件消息
-> 响应 DTO
```

这里的 DTO[^11] 用于在系统边界之间传递经过约束的数据。

[^11]: DTO（数据传输对象）：只用来在模块之间传递数据的对象。

### 3. 每一步关注什么

- 字段是否重命名；
- 类型是否转换；
- 默认值在哪里加入；
- 可空性是否变化；
- 金额精度是否丢失；
- 时间和时区怎样处理；
- 隐私字段是否被过滤；
- 标识符怎样生成；
- 序列化[^12]是否改变含义。

[^12]: 序列化：把程序里的数据转成便于保存或传输的格式。

### 4. 输入验证

Agent 应区分：

- 语法验证；
- 类型验证；
- 业务规则；
- 权限检查。

把所有验证都描述成“route 校验”会隐藏真实责任边界。

### 5. 状态变化

记录对象在流程中的状态：

```text
Draft -> PendingPayment -> Paid -> Fulfilled
```

说明每次变化由哪个函数触发、需要什么条件、写入哪里、失败怎样恢复。

### 6. 事务边界

一个业务流程可能同时：

- 写订单；
- 扣库存；
- 写 outbox；
- 发布事件。

Agent 应确认哪些操作位于同一事务，哪些发生在提交之后。只看函数调用顺序无法证明事务语义。

### 7. 隐私与敏感字段

认证和用户模块中应特别关注：

- 密码哈希；
- token；
- cookie；
- 个人信息；
- 日志字段；
- API 响应过滤。

阅读或生成说明时不要复制真实密钥和用户数据。

### 8. 数据流表模板

```markdown
| 阶段 | 数据类型 | 关键字段变化 | 验证 | 保存/发送位置 | 证据 |
| --- | --- | --- | --- | --- | --- |
| Request | JSON | `userId` 输入 | schema | 无 | route |
| Domain | Order | 生成 id、金额量化 | business rules | 内存 | service |
| Storage | OrderRow | 时间转 UTC | DB constraints | orders 表 | repository |
```

## 十、配置文件分析

### 1. 配置会改变运行路径

同一份代码可能因配置不同：

- 使用不同数据库；
- 启用或关闭缓存；
- 选择真实或模拟外部服务；
- 注册不同插件；
- 使用不同认证方式；
- 改变日志或重试策略。

### 2. 配置来源

常见来源包括：

1. 代码默认值；
2. 配置文件；
3. 环境变量；
4. 命令行参数；
5. 容器或部署配置；
6. 测试覆盖配置；
7. 远程配置或功能开关。

### 3. 配置追踪链

```text
定义位置
-> 读取位置
-> 类型转换
-> 默认值
-> 覆盖优先级
-> 注入位置
-> 实际使用位置
```

### 4. 配置存在不等于启用

`.env.example` 中出现 `REDIS_URL`，不能证明当前环境使用 Redis。还需要检查：

- 初始化条件；
- 功能开关；
- 容器环境；
- 依赖注入；
- 实际日志或运行结果。

### 5. 配置优先级

开发者修改 `.env` 后没有生效，可能因为：

- 命令行参数覆盖；
- 容器注入环境变量；
- 测试 fixture[^13] 覆盖；
- 远程配置优先；
- 应用读取另一个文件；
- 进程未重新启动。

[^13]: Fixture：测试前准备好的数据、对象或环境。

### 6. 配置分析 Prompt

```text
请只读追踪配置项 `SEARCH_BACKEND`。
说明它在哪里定义、读取、转换、覆盖和使用；
列出各来源的优先级，并区分代码可见事实与当前环境尚未确认的值。
不要输出真实密钥。
```

## 十一、第三方依赖分析

### 1. 依赖声明不是运行证据

看到 `import redis` 或依赖清单中的 Redis 包，只能证明代码或项目声明了该依赖，不能证明生产环境一定启用。

### 2. 依赖分析字段

- 名称和锁定版本；
- 直接依赖或传递依赖；
- 实际导入位置；
- 项目内部封装层；
- 初始化条件；
- 配置开关；
- 运行环境是否启用；
- 对应测试和替代实现；
- 失败与降级行为。

### 3. 优先找内部封装层

项目可能不直接调用第三方库，而是通过：

```text
业务模块
-> SearchClient interface
-> ElasticsearchSearchClient
-> 第三方 SDK
```

理解内部接口有助于区分项目语义和第三方 API 细节。

### 4. 版本必须准确

查阅外部文档前，确认：

- lockfile 的实际版本；
- 项目是否封装或补丁修改；
- 是否使用旧版 API；
- 当前代码是否处于迁移状态。

### 5. 依赖的替代实现

测试可能使用内存实现：

```text
生产：PostgresUserRepository
测试：InMemoryUserRepository
```

单元测试路径不能自动证明生产实现行为。

### 6. 依赖失败路径

Agent 应说明：

- 超时设置；
- 重试；
- 熔断或降级；
- 错误映射；
- 资源关闭；
- 连接池；
- 健康检查。

这些信息决定模块在真实系统中的职责。

## 十二、把测试当作项目理解证据

### 1. 测试可以说明什么

测试通常展示：

- 公开行为；
- 边界与错误情况；
- fixture 和依赖替代；
- 项目认可的调用方式；
- 重要业务规则；
- 过去修复过的回归问题。

### 2. 测试不能单独说明什么

- 生产环境一定使用相同依赖；
- 所有分支都被覆盖；
- 测试描述仍与实现一致；
- 当前部署配置；
- 未断言的副作用正确。

### 3. 从测试反查入口

当入口难以定位时，可以查看：

- API 测试发送的 URL；
- CLI 测试调用的命令；
- consumer 测试传入的事件；
- fixture 创建的应用和依赖；
- 集成测试启动方式。

测试是寻找真实使用方式的重要线索。

### 4. 比较测试与生产绑定

```text
测试 fixture 注册 InMemoryQueue
生产 bootstrap 注册 RabbitMQQueue
```

如果 Agent只读测试，可能误以为系统没有外部消息代理。

### 5. 本周边界

本周使用测试帮助理解项目。如何生成测试、设计边界输入和建立回归闭环，将在第八周展开。

## 十三、静态阅读与运行验证

### 1. 静态阅读的优势

静态阅读[^14]是在不执行程序的情况下，通过源代码、类型、配置和引用关系理解可能行为。

[^14]: 静态阅读：不运行程序，只通过代码和配置分析行为。

- 快速搜索定义和引用；
- 阅读所有分支；
- 查看类型和依赖；
- 不必启动完整环境；
- 适合建立候选调用链。

### 2. 静态阅读的限制

- 动态注册可能无法直接看出；
- 配置决定的分支可能不明确；
- 反射和插件增加不确定性；
- 死代码仍会出现在搜索结果；
- 并发和时序行为难以证明。

### 3. 运行验证的作用

运行证据可以确认：

- 当前启动入口；
- 当前配置值；
- 实际实现绑定；
- 真实调用顺序；
- 异常和副作用；
- 数据库或消息变化。

### 4. 最小验证优先

如果目标是确认登录路径，可以先运行已有登录测试或发送一个最小请求，不必立刻启动所有外部服务。

### 5. 无法运行时怎样表达

```text
代码可见：route 调用 AuthService.authenticate()。
尚未验证：当前部署是否使用该 route；本地环境缺少数据库，未执行请求。
```

无法运行不等于不能分析，但必须降低结论强度。

### 6. 不提前进入工具权限主题

本周重点是哪些结论需要运行验证。具体工具调用、执行权限和安全审批将在第七周讲解。

## 十四、让 Agent 解释关键代码

### 1. 不要只做逐行翻译

逐行翻译可以解释语法，却无法说明代码在系统中的作用。

### 2. 推荐解释顺序

1. 代码目的；
2. 所属功能路径；
3. 输入和输出；
4. 关键分支；
5. 调用者和被调用者；
6. 状态变化和副作用；
7. 异常与失败行为；
8. 配置影响；
9. 对应测试；
10. 尚未运行验证的部分。

### 3. 函数解释 Prompt

```text
请只读解释 `OrderService.create()`。

按以下顺序说明：
1. 它在创建订单流程中的作用；
2. 谁调用它，它又调用谁；
3. 输入、返回值和异常；
4. 关键业务分支；
5. 数据状态变化和外部副作用；
6. 影响它的配置；
7. 对应测试；
8. 尚未运行验证的推断。

关键结论引用真实文件和符号。
```

### 4. 模块解释 Prompt

```text
请只读解释 `src/search/` 模块。
说明其公开入口、内部组件、索引写入和查询路径、配置、第三方依赖、失败行为和对应测试。
不要逐文件复述；以实际调用关系组织说明。
```

### 5. 解释设计取舍要谨慎

Agent 可以从代码推测某种设计动机，但除非有 ADR、注释或提交说明作为证据，不应把推测写成作者真实意图。

```text
谨慎表达：这种分层可能用于隔离第三方搜索 SDK；仓库中未找到明确设计记录。
```

## 十五、案例一：只读解释认证流程

### 1. 阅读目标

```text
解释 Web 用户从提交登录表单到创建 session 的完整路径。
本次只读，不修改认证代码。
```

### 2. 第一遍项目地图

Agent 应先确认：

- 前端与后端位置；
- Web 框架；
- 认证相关配置；
- 测试目录；
- 项目指令和敏感信息限制。

### 3. 定位外部入口

```text
LoginForm.onSubmit
-> authClient.login
-> POST /login
-> loginRoute
```

不能只因为仓库存在 `auth.py` 就认定它是当前入口。

### 4. 追踪认证调用链

```text
loginRoute
-> AuthService.authenticate
-> UserRepository.findByEmail
-> PasswordVerifier.verify
-> SessionStore.create
-> Set-Cookie response
```

### 5. 追踪数据流

关注：

- 表单字段怎样验证；
- email 是否规范化；
- 密码是否只以明文存在于请求边界；
- 哈希怎样比较；
- session id 怎样生成和存储；
- cookie 的安全属性；
- 用户对象中的敏感字段是否进入响应或日志。

### 6. 追踪失败路径

- 用户不存在；
- 密码错误；
- 账号停用；
- session store 不可用；
- 请求缺少字段；
- 限流或风控拒绝。

### 7. 区分 Web 与其他认证路径

仓库可能同时包含：

- Web cookie session；
- API token；
- 管理后台登录；
- 测试 bypass；
- legacy JWT。

Agent 应说明当前讨论的是哪条入口，不能把多个认证流程混合成一个。

### 8. 认证说明的证据结构

```markdown
## Entry
## Authentication chain
## Session creation
## Error mapping
## Security-sensitive data
## Tests
## Confirmed facts
## Unverified assumptions
```

## 十六、案例二：只读解释消息队列

### 1. 阅读目标

```text
解释“订单创建后发送确认邮件”的消息队列路径。
说明发布者、topic、消息结构、消费者、重试、幂等和失败处理。
```

### 2. 找到发布位置

```text
OrderService.create
-> save order
-> publish OrderCreated
```

需要确认发布发生在事务提交前、提交后，还是通过 outbox 延迟发送。

### 3. 找到消息结构

说明：

- 事件名称和版本；
- 必填字段；
- 标识符；
- 时间格式；
- 是否包含敏感信息；
- 序列化方式；
- 向后兼容要求。

### 4. 找到消费者注册

```text
worker bootstrap
-> subscribe order.created
-> SendOrderEmailHandler.handle
-> EmailClient.send
```

只找到 handler 文件不代表它已经注册。

### 5. 重试和死信

Agent 应查找：

- 最大重试次数；
- 延迟策略；
- 哪些异常可重试；
- 死信队列；
- 人工恢复方式；
- 是否会重复消费。

### 6. 幂等处理

队列可能重复投递。应检查消费者是否：

- 使用事件 id 去重；
- 检查业务状态；
- 使用唯一约束；
- 将副作用设计为可重复执行。

### 7. 测试与生产实现的区别

单元测试可能使用 `InMemoryQueue`，生产使用 RabbitMQ 或 Kafka。Agent 应从启动注册和部署配置确认生产绑定。

### 8. 队列说明的证据结构

```markdown
## Publisher
## Message schema
## Broker/topic
## Consumer registration
## Retry and dead letter
## Idempotency
## Tests and production binding
## Unknowns
```

## 十七、案例三：只读解释搜索模块

### 1. 阅读目标

```text
解释用户搜索请求从前端输入到搜索结果展示的完整路径，
包括查询规范化、索引后端、排序、分页、权限过滤和缓存。
```

### 2. 找到查询入口

```text
SearchPage
-> searchClient.query
-> GET /search
-> searchRoute
-> SearchService.search
```

### 3. 找到搜索后端绑定

项目可能同时存在：

- SQL 模糊查询；
- Elasticsearch；
- 外部搜索服务；
- 内存测试实现；
- legacy 搜索模块。

要从配置、factory 或依赖注入确认当前绑定。

```text
用户输入
-> trim / normalize
-> filter object
-> backend query
-> raw hits
-> permission filtering
-> result DTO
-> UI state
```

### 5. 排序和分页

说明：

- 默认排序；
- 相关性得分；
- 页码或 cursor；
- 最大结果数；

- 空查询行为；
- 重复结果处理。

### 6. 索引写入路径

只理解查询还不够。搜索结果可能过期，需要找到：

```text
数据创建或更新
-> 领域事件
-> 索引任务
-> 搜索后端写入
```

### 7. 权限过滤位置

权限可能在：

- 查询条件中；
- 搜索结果返回后；
- API route；
- 搜索后端索引设计中。

### 8. 搜索说明的证据结构

```markdown
## Query entry
## Query normalization
## Backend selection
## Filters and permissions
## Ranking and pagination
## Index update path
## Cache
## Tests and unknowns
```

## 十八、Agent 生成项目说明

### 1. 项目说明的用途

项目说明应帮助下一位开发者快速继续：

- 知道从哪里启动；
- 知道目标功能在哪里；
- 知道关键模块怎样协作；
- 知道哪些结论已经验证；
- 知道仍有哪些未知。

### 2. 推荐结构

```markdown
# Project overview

## Purpose and stack

## Repository map

## Startup and external entries

## Core modules

## Target feature call chain

## Data flow and state changes

## Configuration and external dependencies

## Tests and validation

## Confirmed facts

## Unverified assumptions
```

### 3. 控制说明范围

针对“创建订单”阅读时，项目说明不需要详细解释用户头像上传或后台报表。范围越大，越容易失去可核查性。

### 4. 引用方式

关键结论至少引用：

- 文件路径；
- 符号或配置键；
- 必要时的行号；
- 运行命令或测试名称。

### 5. 避免复制大量源代码

项目说明应解释关系和职责，而不是把每个文件的代码复制一遍。必要代码片段应短，并服务于一个具体结论。

### 6. 对未知保持诚实

```text
已确认：代码中注册了 Elasticsearch 实现。
未知：当前生产环境是否启用；仓库内没有部署环境值，且本次未连接运行环境。
```

这种表达比“系统使用 Elasticsearch”更可靠。

## 十九、避免局部阅读造成误判

### 1. 只按文件名判断

`auth.py` 可能是旧实现，真实入口可能已经迁移到 `security/`。

### 2. 只看最大的文件

大文件可能只是生成代码；很短的权限函数反而控制关键安全边界。

### 3. 只看一个调用方向

只向下看会遗漏其他调用方；只向上看会遗漏数据库、事件和外部副作用。

### 4. 把定义当成使用

函数、类、配置和依赖存在，不代表当前入口会使用。

### 5. 把注释当作当前事实

注释可能过期，应与实现、测试和运行状态比较。

### 6. 把单元测试路径当生产路径

测试可能使用内存 repository、模拟队列或特殊配置。

### 7. 忽略动态注册

接口、依赖注入、装饰器和插件可能隐藏真实实现绑定。

### 8. 只追踪成功路径

会遗漏权限拒绝、事务回滚、重试、死信和错误映射。

### 9. 把依赖声明当实际启用

依赖存在不等于当前环境启用；应检查初始化和配置。

### 10. 把合理推断当作者意图

没有 ADR 或明确注释时，只能说“可能用于”，不能声称“作者这样设计是因为”。

### 11. 把 Agent 的说明当最终证据

说明必须回到文件、符号、配置、测试和运行结果核对。

### 12. 项目理解无限扩张

阅读应围绕一个目的。目标是理解搜索模块时，不需要先解释整个财务系统。

## 二十、可复用 Prompt 模板

### 1. 建立陌生项目地图

```text
请把当前仓库当作陌生项目，只读分析，不修改文件。

请说明：
1. 项目用途、语言、框架和实际版本依据；
2. 根目录关键文件和主要目录职责；
3. 启动、构建、测试和质量命令；
4. Web、CLI、worker、定时任务等入口；
5. 项目指令、生成目录，以及由弃用标记、未被入口引用或独立旧版本目录证明的遗留区域。

关键结论引用真实文件和符号。
区分代码事实、运行验证和未确认推断。
```

### 2. 定位一个功能入口

```text
请只读定位“[用户行为]”的真实外部入口。
从 URL、命令名、事件名、UI 文本和测试中搜索，
说明入口怎样注册、经过哪些中间件，并引用文件与符号。
不要因为文件名相似就认定它是当前实现。
```

### 3. 追踪调用链

```text
请追踪“[功能]”从外部入口到最终副作用的调用链。
每一跳列出调用者、被调用者、输入输出、分支、异常和副作用。
同时从核心函数反向搜索其他调用方。
动态绑定无法确认时说明需要检查的注册或配置。
```

### 4. 分析数据流

```text
请说明“[功能]”的数据从输入到响应或持久化怎样变化。
记录类型转换、字段重命名、默认值、验证、状态变化、事务、
敏感字段过滤和序列化。关键结论引用代码证据。
```

### 5. 分析配置项

```text
请追踪配置项 `[KEY]` 的定义、读取、类型转换、默认值、
覆盖优先级、注入位置和实际使用位置。
区分代码可见规则与当前环境的未知值，不输出密钥。
```

### 6. 分析第三方依赖

```text
请分析依赖 `[NAME]` 在项目中的真实用途。
确认锁定版本、导入位置、内部封装、初始化条件、配置开关、
生产与测试实现、失败处理和实际调用方。
依赖声明本身不能作为运行启用的证据。
```

### 7. 解释关键函数

```text
请只读解释 `[file::symbol]`。
说明它在系统中的目的、调用者、被调用者、输入输出、关键分支、
状态变化、副作用、异常、配置和对应测试。
不要只逐行翻译；标出未经运行验证的推断。
```

### 8. 查找参考实现

```text
请在当前仓库查找与“[目标功能]”最相似且仍在使用的参考实现。
比较入口、验证、业务层、数据访问、错误处理和测试。
说明可复用的项目模式，以及因业务差异不能照搬的部分。
```

### 9. 生成项目说明

```text
根据已经核查的证据，生成面向下一位开发者的项目说明。
只覆盖当前目标相关的项目地图、入口、模块、调用链、数据流、
配置、依赖、测试、已确认事实和未知事项。
关键结论引用文件和符号，不复制大段源代码。
```

## 二十一、本章总结

使用编码 Agent 阅读陌生项目，可以概括为三遍：

```text
第一遍：建立项目地图
第二遍：追踪功能调用链与数据流
第三遍：用运行证据验证并修正
```

可靠的项目理解应回答：

```text
项目怎样启动
-> 功能从哪里进入
-> 核心模块怎样协作
-> 数据怎样变化
-> 配置和依赖怎样生效
-> 哪些结论已经验证
-> 哪些内容仍然未知
```

编码 Agent 的优势是快速搜索、关联和整理大量文件。它的流畅解释不能代替仓库证据。使用者仍需限定只读范围、要求真实文件与符号引用、区分事实和推断，并在必要时用运行结果确认静态判断。

本周建立的项目地图、功能路径和验证依据，将成为第六周制定计划与执行修改的输入。
