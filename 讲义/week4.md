# 第四周：编码 Agent 的上下文工程与 AGENTS.md

## 本章导读

使用编码 Agent 时，用户通常不是把一道孤立编程题交给模型，而是让它进入一个真实代码仓库，阅读文件、理解项目规则、修改代码并运行验证。

同一句任务：

```text
修复登录失败的问题。
```

如果 Agent 不知道项目使用什么框架、登录入口在哪里、现有错误类型是什么、测试怎样运行，它只能猜测。如果 Agent 能读取真实仓库，并获得准确的项目上下文[^1]和当前错误证据，结果通常会更接近项目需要。

[^1]: 项目上下文：Agent 完成项目任务需要知道的信息。

本章只讨论编码 Agent 使用中的上下文问题。学习重点是：

1. 开始任务前应让 Agent 了解哪些项目事实；
2. 如何提供相关文件、调用关系、规范、测试和修改限制；
3. 上下文不足、过多、过期或冲突时怎样处理；
4. 长会话被旧信息污染后怎样重建；
5. 如何用 `AGENTS.md`[^2] 保存跨任务长期有效的仓库规则。

[^2]: `AGENTS.md`：写给编码 Agent 看的项目规则文件。

本章不会系统讲解代码调用链分析、完整 Agent 工作流或测试驱动开发。这些内容将在后续周次展开。

---

## 一、为什么编码 Agent 需要项目上下文

### 1. 只给任务时，Agent 必须猜测

假设用户输入：

```text
增加一个用户查询接口。
```

编码 Agent 至少需要判断：

- 项目使用哪种语言和框架；
- API[^3] 路由[^4]放在哪个目录；
- 是否已经存在用户服务（service）[^5]和数据访问层；
- 接口应沿用哪种认证方式；
- 响应字段和错误格式是什么；
- 测试放在哪里、使用什么 fixture[^6]；
- 修改后应运行哪些检查。

[^3]: API（应用程序编程接口）：软件之间约定好的调用方式。
[^4]: 路由（route）：把网址和请求方式交给对应处理函数的规则。
[^5]: Service（服务层）：集中处理业务流程的代码层。
[^6]: Fixture：测试前准备好的数据、对象或环境。

如果这些信息既没有写在任务中，Agent 也无法从仓库中取得，它可能生成一段语法正确但不适合项目的代码。

### 2. 打开真实仓库后，Agent 可以使用证据

编码 Agent 可以通过项目搜索、文件读取和命令执行获得上下文。例如：

```text
- package.json 表明项目使用 Node.js 22 和 Fastify；
- src/routes/users.ts 是现有用户路由；
- src/services/user-service.ts 包含查询逻辑；
- tests/routes/users.test.ts 展示接口测试写法；
- AGENTS.md 要求 route 只处理 HTTP 输入输出；
- 当前任务要求保持响应字段兼容。
```

这些信息共同限定了 Agent 应在哪里修改、怎样修改和如何验证。

### 3. 上下文的作用

对于编码 Agent，上下文主要帮助完成四类判断：

1. **理解任务**：本次要解决什么行为；
2. **定位代码**：应查看和修改哪些真实文件；
3. **遵循项目**：应沿用哪些架构、规范和接口；
4. **验证结果**：应运行什么测试和检查。

上下文工程（Context Engineering）[^7]不是把全部资料粘贴给 Agent，而是提供会改变入口定位、行为判断、修改范围或验证方式的可靠信息。

[^7]: Context Engineering：为 Agent 整理任务信息的方法。

## 二、Prompt 与编码 Agent 上下文

### 1. Prompt 说明本次任务

Prompt 通常说明：

- 目标；
- 当前问题；
- 交付物；
- 本次任务特有的边界；
- 验收要求。

```text
修复订单结算中的金额舍入错误，并增加回归测试。
保持现有 API 响应字段和状态码不变。
```

### 2. Context 提供项目事实

```text
- 项目统一使用 Decimal 表示金额；
- 结算入口位于 src/orders/checkout.py；
- 舍入函数位于 src/money/rounding.py；
- 输入 10.005 时当前返回 10.00；
- 业务规则要求返回 10.01；
- 相关测试位于 tests/orders/test_checkout.py。
```

### 3. 二者必须配合

| 情况 | Agent 面临的问题 |
| --- | --- |
| Prompt 清楚，项目上下文不足 | 知道要做什么，但会猜框架、路径和测试方式 |
| 项目上下文充分，Prompt 含糊 | 知道项目怎样工作，但不知道本次要解释、规划还是修改 |
| 两者都清楚 | 能围绕真实项目完成有边界的任务 |

### 4. 与第二周的区别

第二周学习如何写清 Prompt。本周不再重复 Role Prompting、Few-shot 或输出格式，而是研究编码 Agent 怎样从项目文件、工具结果和持久指令中获得工作所需的信息。

## 三、编码 Agent 使用的四层上下文

### 1. 仓库级上下文

仓库级信息在多个任务中长期有效：

- 项目用途；
- 语言、框架和运行时版本；
- 顶层目录职责；
- 标准安装、构建、测试和 lint 命令；
- 全局架构规则；
- 生成文件和敏感区域。

这些内容可能来自 README、依赖清单、脚本、CI[^8]、配置和根目录 `AGENTS.md`。

[^8]: CI（持续集成）：代码变更后自动运行构建、检查和测试的流程。

### 2. 目录级上下文

大型仓库中，不同模块可能有局部规则：

```text
services/payments/：金额计算不得使用 float
legacy/：保持现有格式，避免无关重排
frontend/generated/：不得直接编辑，应运行生成命令
```

局部规则应靠近适用代码，避免把所有例外堆入根目录。

### 3. 任务级上下文

只服务当前任务：

- 本次目标和用户场景；
- 当前错误行为；
- 相关文件；
- 已确认的产品决定；
- 验收标准；
- 本次范围外事项。

这些内容通常应留在当前 Prompt、issue 或任务说明中。

### 4. 运行级上下文

Agent 工作过程中产生的最新状态：

- 测试失败输出；
- 编译错误；
- 日志；
- 页面截图；
- 当前 diff[^10]；
- 刚完成的验证结果。

[^10]: Diff：文件修改前后的内容差异。

运行级信息变化最快。修复完成后，旧失败日志就不能继续代表项目当前状态。

### 5. 四层信息的使用顺序

```text
仓库级：建立项目地图和通用规则
    ↓
目录级：确定当前模块的局部要求
    ↓
任务级：明确本次目标和范围
    ↓
运行级：根据最新结果调整下一步
```

越靠下，信息越接近当前动作，也越容易过期。

## 四、开始任务前建立项目地图

### 1. 不要直接让 Agent 猜目录

进入陌生仓库后，可以先要求 Agent 只读检查：

```text
请先只读检查项目，不要修改文件。
说明：
1. 项目使用的语言、框架和运行时版本；
2. 应用入口与主要目录职责；
3. 测试、lint、类型检查和构建命令；
4. 是否存在 AGENTS.md 或其他项目指令；
5. 哪些结论仍无法确认。
每项结论引用真实文件路径。
```

这条指令的重点不是让 Agent 输出一篇长篇项目介绍，而是建立完成当前任务所需的最小地图。

### 2. 技术栈要从当前文件确认

可靠来源包括：

- `package.json`、`pyproject.toml`、`Cargo.toml` 等依赖清单；
- lockfile[^9]；
- 运行时版本文件；
- 容器配置；
- CI 工作流；
- 实际入口文件。

[^9]: lockfile（依赖锁定文件）：记录依赖准确版本的文件。

看到 `package.json` 不代表项目一定使用 Express；看到 FastAPI 依赖，也不代表当前服务入口一定在 `main.py`。

### 3. 目录名称只是初步线索

```text
src/api/          可能是 HTTP 输入输出
src/core/         可能是业务规则
src/repository/   可能是数据访问
tests/            可能是自动化测试
generated/        可能是自动生成文件
```

Agent 应通过代表文件、导入或项目文档确认职责，不能把目录名推断直接写成事实。

### 4. 让 Agent 区分事实与推断

```markdown
| 结论 | 类型 | 证据 |
| --- | --- | --- |
| 项目使用 Fastify | 已确认事实 | `package.json`、`src/server.ts` |
| `src/core` 不依赖 Web 框架 | 待验证推断 | 仅从目录名推测 |
| 测试命令为 `npm test` | 已确认事实 | `package.json` scripts |
```

这延续了第三周的方法：真实文件可以查证的内容，不应全部抛给用户；尚未证实的内容也不能冒充事实。

### 5. 项目地图应保持简短

```markdown
## Project map
- Stack: Node.js 22, TypeScript, Fastify.
- Entry: `src/server.ts`.
- Routes: `src/routes/`.
- Business logic: `src/services/`.
- Tests: `tests/`, using Vitest.
- Validation: `npm test`, `npm run lint`, `npm run typecheck`.
- Generated code: `src/generated/`; source is `openapi.yaml`.
```

详细教程可以留在项目文档中，当前任务只引用需要的部分。

## 五、向 Agent 提供文件与模块上下文

### 1. 文件上下文需要四个字段

不要只说“请看 `auth.py`”。应说明：

1. 文件路径；
2. 相关符号；
3. 文件职责；
4. 与本次任务的关系。

| 路径 | 关注符号 | 职责 | 与任务的关系 |
| --- | --- | --- | --- |
| `routes/auth.py` | `login()` | HTTP 输入输出 | 接收空密码请求 |
| `services/auth.py` | `verify_password()` | 认证规则 | 当前抛出未处理异常 |
| `tests/auth/test_login.py` | 空密码用例 | 回归验证 | 当前缺少覆盖 |

### 2. 让 Agent 定位真实文件

如果尚未查过仓库，不要在 Prompt 中虚构路径：

```text
错误：请修改 src/auth/login.ts。

改进：请先定位登录入口、认证服务和现有登录测试，
引用真实路径后再说明修改范围。
```

### 3. 同时考虑上下游

修改一个公共函数时，Agent 不仅要知道它依赖哪些模块，还要知道哪些调用者依赖它。

```text
POST /login
  -> login route
  -> AuthService.authenticate
  -> UserRepository.findByEmail
  -> password verifier
  -> session issuer
```

本周只要求建立与任务有关的最小关系图。系统化的入口定位、调用链和数据流分析将在第五周学习。

### 4. 局部代码片段的风险

只粘贴一个函数，可能隐藏：

- 文件顶部的类型和常量；
- 相邻错误处理方式；
- 其他调用方；
- 测试 fixture；
- 当前目录的局部指令；
- 生成文件标记。

代码片段可以用于讨论局部问题；真正修改前，Agent 还应读取目标符号的定义、调用方、相邻错误处理、适用项目指令和相关测试，直到能够说明修改范围与验证方法。

### 5. 控制读取范围

高质量指令不是“读取整个项目”，而是：

```text
先定位登录入口、认证服务和现有登录测试。
读取与空密码行为直接相关的文件和调用方。
若发现公共返回类型会变化，再扩大搜索范围。
```

这样既避免局部误判，也不会让无关模块淹没当前任务。

## 六、给 Agent 提供代码规范上下文

### 1. 常见项目规范

- 命名方式；
- 类型标注；
- 错误处理；
- 日志规则；
- 架构分层；
- 格式化和 lint；
- 测试文件与 fixture 用法；
- API 兼容要求。

### 2. 规范必须有来源

项目规则应优先从以下可核对来源取得：

- 项目规范文档；
- lint、format 和类型配置；
- CI 检查；
- 同模块中经过维护的成熟代码；
- 团队确认的 `AGENTS.md`。

用户个人偏好不能自动当作整个项目的团队规则。

### 3. 把抽象要求改成可执行规则

```text
低质量：代码要优雅。
改进：route 只处理 HTTP 输入输出，业务规则放在 service。

低质量：注意类型安全。
改进：公开函数添加类型标注；完成前运行 npm run typecheck。

低质量：错误处理保持一致。
改进：复用 src/errors 中的错误类型，不直接抛出字符串。
```

### 4. 不要复制自动化工具的全部配置

如果 Prettier、Ruff 或 ESLint 已经定义格式规则，通常只需告诉 Agent 使用哪个项目命令：

```text
修改后运行 `npm run lint` 和 `npm run format:check`。
```

把几十条格式配置重复写进 Prompt 或 `AGENTS.md`，反而容易在配置变化后产生冲突。

## 七、给 Agent 提供测试与验证上下文

### 1. 只说“添加测试”不够

Agent 可能：

- 选择错误测试框架；
- 把测试放错目录；
- 重复创建已有 fixture；
- 使用不存在的命令；
- 没有覆盖真正的错误行为。

### 2. 测试上下文应说明什么

- 测试框架；
- 测试目录和文件命名；
- 可复用的 fixture；
- 最相关测试命令；
- 全量测试命令；
- 本次必须覆盖的行为。

```text
项目使用 pytest。
登录测试位于 tests/auth，复用 client fixture。
本次至少覆盖正常密码、空密码和缺失密码。
相关命令：pytest tests/auth/test_login.py -q
全量命令：pytest -q
```

### 3. 区分“命令存在”和“命令已经通过”

```text
项目事实：标准测试命令是 `npm test`。
运行结果：本次本地执行共有 126 项通过、2 项失败。
```

第一条可能长期有效，第二条只是当前运行状态。不要把一次执行结果永久写入项目指令。

### 4. 要求 Agent 如实报告验证

```text
完成后报告：
1. 实际运行了哪些命令；
2. 每个命令的结果；
3. 哪些检查没有运行及原因；
4. 是否仍有已知风险。
```

“没有运行”不能写成“验证通过”。

### 5. 本周的边界

本周学习的是怎样把测试信息提供给 Agent。如何设计边界测试、回归测试和测试驱动闭环，将在第八周系统展开。

## 八、用修改约束控制 Agent 的边界

### 1. 修改约束要回答三个问题

1. 哪些内容允许修改？
2. 哪些内容禁止修改？
3. 完成前必须执行哪些检查？

### 2. 模糊约束无法执行

```text
不要破坏项目。
尽量少改。
保持兼容。
```

这些表达只有方向，没有告诉 Agent 具体边界。

### 3. 改为具体约束

```text
- 修改只限金额计算函数和对应测试；
- 不改变公开 API 的字段名和状态码；
- 不新增生产依赖；
- 不直接编辑 src/generated/；
- 修改 schema 后运行 npm run generate；
- 完成前运行相关测试并检查最终 diff。
```

### 4. 禁止事项应附有正确路径

只写“不要编辑生成文件”，Agent 仍不知道该改哪里。

```text
不得直接编辑 `src/generated/client.ts`。
应修改 `openapi.yaml`，再运行 `npm run generate`。
```

### 5. 区分长期限制和本次限制

```text
长期：不得直接编辑 generated/。
本次：只修复订单舍入，不调整折扣模块。
```

长期规则可以进入 `AGENTS.md`；本次范围应留在当前任务中。

## 九、编码 Agent 上下文不足时怎样处理

### 1. 上下文不足的表现

- 猜测项目语言或框架；
- 使用不存在的文件；
- 重新实现已有功能；
- 使用错误测试命令；
- 随意改变公开接口；
- 无法引用结论依据；
- 询问本可从仓库查证的问题。

### 2. 不要重复空泛要求

```text
低价值补充：请认真一点，确保正确。

高价值补充：现有 Web 端使用 cookie session；
移动端 token 不在本次范围；相关架构决定见 ADR-007。
```

这里的 session[^11] 指系统为连续请求保存的登录状态。

[^11]: Session（会话）：用来保存用户连续请求状态的信息。

补充的信息应能够改变 Agent 的定位、实现或验证方式。

### 3. 先判断能否从仓库查证

- 框架版本：通常从依赖文件和 lockfile 查证；
- 测试命令：通常从脚本、README 或 CI 查证；
- 登录入口：通常通过项目搜索查证；
- 产品是否允许自行注册：可能必须询问用户。

### 4. 使用诊断 Prompt

```text
先不要继续修改。
请列出当前完成任务仍缺少的信息，并分为：
1. 可以从仓库查证；
2. 可以通过运行命令验证；
3. 必须由用户决定。
只提出会改变方案的澄清问题。
```

这能避免 Agent 把所有不确定性都转交给用户。

## 十、上下文过载与污染

### 1. 编码任务中的上下文污染

上下文污染是指无关、错误、重复、过时或冲突的信息干扰 Agent 判断。

### 2. 常见污染来源

#### 2.1 无关文件

修复后端金额舍入时，把整套前端视觉规范加入当前会话。

#### 2.2 旧代码片段

会话中粘贴过三版 `auth.ts`，但没有标明哪一版是当前文件。

#### 2.3 旧测试日志

修复前有 12 项失败，最新只剩 1 项，Agent 却继续围绕旧错误工作。

#### 2.4 未证实根因

把“可能是缓存问题”写成“根因就是缓存”。

#### 2.5 冲突规则

根目录要求双引号，`legacy/` 又要求保持现有引号以减少 diff。

### 3. 三个筛选问题

面对一条候选上下文，问：

1. 它会改变当前实现或分析方案吗？
2. 它能帮助定位相关代码吗？
3. 它能帮助验证结果吗？

如果全部为“否”，通常不应进入当前核心上下文。

### 4. 清理方法

1. 删除无关文件与重复说明；
2. 重新读取当前磁盘上的真实文件；
3. 用最新测试输出替换旧日志；
4. 把推断重新标记为推断；
5. 为局部规则注明目录作用域；
6. 对无法解决的实质冲突请求确认。

### 5. 不要把整个仓库等权塞给 Agent

正确做法是逐步聚焦：

```text
先建立项目地图
  -> 定位任务入口
  -> 读取相关文件和调用方
  -> 找到现有测试与规则
  -> 根据运行结果补充最新上下文
```

这里强调的是上下文选择，不是第六周完整 Agent 工作流。

## 十一、长会话中的上下文维护

### 1. 长会话为什么容易误导 Agent

一个持续多轮的编码任务可能包含：

- 已经被否定的早期根因；
- 修改前的旧文件片段；
- 多次运行产生的旧日志；
- 已经取消的功能范围；
- 临时试验方案；
- 当前仍然有效的决定。

如果这些内容没有整理，Agent 可能继续使用过期信息。

### 2. 阶段摘要应保留什么

- 当前唯一目标；
- 已确认事实及来源；
- 已确认决定及理由；
- 当前相关文件；
- 最新测试或构建结果；
- 尚未解决的问题；
- 明确的范围外事项。

### 3. 阶段摘要应删除什么

- 已证明错误的猜测；
- 已被替换的旧文件片段；
- 重复对话；
- 已取消的需求；
- 与当前任务无关的日志。

### 4. 低质量与高质量摘要

低质量：

```text
登录已经处理得差不多了，继续修复剩余问题。
```

改进：

```text
- 当前目标：修复 Web 空密码登录返回 500。
- 已确认：Web 使用 cookie session，依据 ADR-007 和 src/auth/session.ts。
- 根因证据：None 被传入 verify_password()。
- 保留约束：token 格式不变，移动端不在范围。
- 最新状态：登录测试只有空密码用例失败。
```

### 5. 要求 Agent 复述当前边界

更新摘要后，可以要求：

```text
请先根据上述摘要复述当前目标、有效事实、修改范围和验证方式。
不要引用已废弃的 JWT 方案。确认无误后再继续。
```

复述不是为了让输出变长，而是尽早发现 Agent 是否仍混用了旧上下文。

## 十二、用干净会话重建编码任务

### 1. 何时考虑重新开启会话

- 早期技术方向已经被完全推翻；
- 会话混入多个无关任务；
- 文件和日志已更新多次；
- Agent 反复引用旧方案；
- 很难说清哪些结论仍然有效；
- 已经形成一个边界清楚的新子任务。

### 2. 新会话不是从零开始

不要复制旧聊天全文。应带入一个重建包：

```markdown
## Current goal
修复 Web 空密码登录返回 500，并增加回归测试。

## Confirmed evidence
- 入口：`routes/auth.py::login`。
- `verify_password(None)` 触发未处理异常。
- Web 认证使用 cookie session，依据 `ADR-007.md`。

## Constraints
- 不改变 token 或 session 响应格式。
- 移动端登录不在本次范围。
- 复用现有 `InvalidCredentials` 错误。

## Validation
- `pytest tests/auth/test_login.py -q`

## Current state
- 最新运行仅空密码用例失败。
```

### 3. 重建步骤

1. 写出当前唯一目标；
2. 删除已取消需求和错误假设；
3. 保留有来源的事实；
4. 保留已确认决定；
5. 列出当前真实文件；
6. 加入最新运行状态；
7. 写清修改限制和验证命令；
8. 在新会话中先确认边界。

### 4. 重要决定不能只留在聊天里

如果“Web 登录使用 cookie session”是长期架构决定，应写入 ADR 或认证文档；如果“生成目录不得手改”是所有编码任务都要遵守的规则，可以写入 `AGENTS.md`。

新会话只负责清理当前上下文，项目级决定还需要持久化到合适位置。

## 十三、什么是 AGENTS.md

### 1. 面向编码 Agent 的仓库指令

`AGENTS.md` 用于保存编码 Agent 在多个任务中反复需要的项目指导。它通常随仓库共享，并在 Agent 开始工作前提供项目特有的约定。

### 2. 适合写入的内容

- 项目用途和主要技术栈；
- 关键目录职责；
- 安装、构建、测试和质量命令；
- 架构与编码规则；
- 生成文件的正确修改路径；
- 不允许改变的公共契约；
- 完成任务前的通用检查；
- 重复出现的代码审查要求。

### 3. 不适合写入的内容

- 当前 Bug 的临时日志；
- 当前分支或本周目标；
- 很快过期的进度；
- 未经验证的猜测；
- 密钥、令牌和用户数据；
- README 的完整复制；
- 已由 lint 配置精确表达的全部细节。

### 4. AGENTS.md 的价值

- 减少每次 Prompt 重复说明；
- 减少 Agent 使用错误框架、路径或命令；
- 让项目规则随仓库共享；
- 把重复纠正转化为未来任务的输入；
- 为不同目录提供局部指导。

### 5. AGENTS.md 不能替代什么

- 当前任务的目标和验收；
- 对真实文件的读取；
- 最新测试与错误证据；
- README 和架构文档；
- lint、测试和 CI；
- 用户对产品冲突的决定。

## 十四、AGENTS.md 与其他项目文件

### 1. AGENTS.md 与 README.md

| 文件 | 主要读者 | 重点 |
| --- | --- | --- |
| `README.md` | 使用者和开发者 | 项目是什么、怎样安装和使用 |
| `AGENTS.md` | 编码 Agent | 怎样修改、验证和避免误改 |

同一个测试命令可能在两个文件中出现，但目的不同。大量复制会造成更新不同步，适合保留一个权威来源并在另一处简短引用。

### 2. AGENTS.md 与当前 Prompt

```text
AGENTS.md：所有 Bug 修复都要增加回归测试。
当前 Prompt：本次只修复空密码登录，不调整移动端认证。
```

前者跨任务稳定，后者只对当前任务有效。

### 3. AGENTS.md 与 CLAUDE.md

`CLAUDE.md`[^12] 是一些编码 Agent 使用的项目指令文件。它与 `AGENTS.md` 都可以承载持久项目指导，但具体发现位置、作用域和优先级取决于所用产品。

[^12]: `CLAUDE.md`：部分编码 Agent 使用的项目规则文件。

如果团队同时使用多个编码 Agent：

- 明确哪个文件或文档是共同规则的权威来源；
- 产品特有文件只记录必要差异；
- 避免复制多份后产生冲突；
- 按各产品当前官方文档核对支持范围。

### 4. 文档规则与自动检查

```text
AGENTS.md：告诉 Agent 应遵守什么、运行什么
lint / test / CI：机械地检查是否做到
```

重要规则不应只依赖自然语言提醒。例如格式、类型和测试要求应尽量由自动化工具执行。

## 十五、AGENTS.md 的目录作用域

### 1. 根目录保存通用规则

```text
repo/
├── AGENTS.md
├── services/
├── frontend/
└── tests/
```

根文件适合记录全仓库通用的项目地图、命令和完成检查。

### 2. 子目录保存局部规则

```text
repo/
├── AGENTS.md
├── services/
│   └── payments/
│       └── AGENTS.md
└── frontend/
    └── AGENTS.md
```

例如支付模块禁止 float，前端模块使用不同测试命令。这些局部要求不应无条件应用到整个仓库。

### 3. 以 Codex 为例

当前 Codex 文档说明，Codex 会从项目根向当前工作目录逐层收集指导；更靠近当前目录的指令用于覆盖更早的通用指导。同一目录还可以使用 `AGENTS.override.md`。Codex 对合并后的项目指导有大小限制，因此指令应保持精简。

这是 Codex 的产品规则，不代表所有编码 Agent 都以完全相同方式工作。

### 4. 从正确工作目录启动

如果 Agent 没有加载预期的局部规则，应检查：

- 当前工作目录是否正确；
- 工具识别的项目根是否正确；
- 指令文件是否为空或命名错误；
- 是否存在更近的覆盖文件；
- 是否需要重新启动会话以重新发现指导。

### 5. 避免故意制造冲突

即使产品支持局部覆盖，也应把例外写清原因和范围：

```text
根目录：TypeScript 使用双引号。
legacy/：保持当前引号风格，不执行全文件格式化，以避免无关 diff。
```

这比在两个文件中分别写“必须双引号”和“必须单引号”更容易理解。

## 十六、编写 AGENTS.md 的步骤

### 1. 只读检查真实仓库

让 Agent 查看：

- README 与贡献指南；
- 依赖清单和 lockfile；
- 根目录与关键模块；
- 脚本和 Makefile；
- CI 工作流；
- lint、format 和类型配置；
- 测试目录与 fixture；
- 生成文件标记；
- 已有项目指令。

### 2. 建立候选规则表

| 候选信息 | 来源 | 作用域 | 跨任务稳定 | 处理 |
| --- | --- | --- | --- | --- |
| 使用 `npm run test:unit` | `package.json`、CI | 全仓库 | 是 | 写入 |
| 本周只修复登录 | 当前任务 | 本次 | 否 | 不写入 |
| 不手改 generated | 文件头、生成脚本 | 前端 | 是 | 写入局部文件 |
| “最好用函数式写法” | 无来源 | 不明 | 不明 | 删除 |

### 3. 优先保留高价值规则

优先写：

- Agent 容易反复弄错的项目事实；
- 不明显的命令入口；
- 生成文件和正确生成路径；
- 重要架构边界；
- 修改后必须执行的检查。

不要把 `AGENTS.md` 写成项目百科全书。

### 4. 使用可执行语言

```text
低质量：遵循项目最佳实践。
改进：API route 只处理输入输出，业务规则放入 service。

低质量：测试要完整。
改进：Bug 修复必须添加回归测试；先运行最相关测试。
```

### 5. 核验每个命令

确认：

- 命令真实存在；
- 工作目录正确；
- 前置依赖明确；
- 与 CI 或项目脚本一致；
- 尚未运行的命令没有被写成“已通过”。

### 6. 用小任务验证指令

选择一个低风险任务，观察 Agent 是否：

- 找到正确文件；
- 沿用现有结构；
- 避开禁止区域；
- 使用规定命令；
- 如实报告未运行检查。

### 7. 根据重复错误维护

Agent 再次犯错时，判断：

- 是当前任务没有写清；
- 是缺少长期项目规则；
- 是现有指令过时；
- 还是应该由 lint、测试或 CI 强制执行。

只有跨任务稳定的问题才适合更新 `AGENTS.md`。

## 十七、AGENTS.md 完整示例

下面是教学示例，不能原样复制到其他仓库。所有路径和命令都要从真实项目核验。

```markdown
# Project guide

## Project

This repository contains a user-management API built with Python 3.12,
FastAPI, SQLAlchemy 2, and PostgreSQL. Use `uv` for dependencies.

## Structure

- `src/api/`: HTTP routes and request/response mapping. Keep handlers thin.
- `src/core/`: framework-independent business rules.
- `src/repository/`: database access.
- `tests/`: mirrors the structure of `src/`.
- `src/generated/`: generated code; do not edit it directly.

## Commands

- Install: `uv sync --dev`
- Narrow test: `pytest path/to/test_file.py -q`
- All tests: `pytest -q`
- Lint: `ruff check .`
- Type check: `mypy src`

## Coding rules

- Add type annotations to public functions.
- Keep business rules out of API routes.
- Reuse exceptions from `src/core/errors.py`.
- Add a regression test for every bug fix.

## Modification limits

- Do not edit `src/generated/` directly. Change `openapi.yaml` and run
  `make generate`.
- Preserve public API fields and status codes unless the task explicitly
  changes the contract.
- Do not add production dependencies without confirmation.

## Before completion

- Run the narrowest relevant test first.
- Run the full suite, lint, and type checks when feasible.
- Review the final diff for unrelated changes.
- Report checks that were not run and any remaining risk.
```

### 1. 示例中值得保留的设计

- 项目地图短而明确；
- 命令与用途对应；
- 架构规则可执行；
- 禁止事项附有正确路径；
- 完成要求能通过命令和报告验证。

### 2. 使用前仍需核验

- 项目是否真的使用这些版本；
- `uv sync --dev` 是否有效；
- `mypy src` 是否为团队认可入口；
- `openapi.yaml` 是否真的生成目标目录；
- 全量测试是否适合每次本地运行。

### 3. 控制文件长度

如果项目规则很多：

- 根文件只保留全局规则；
- 局部规则放入相应子目录；
- 详细教程放在 `docs/`；
- `AGENTS.md` 只写何时读取哪个文档；
- 能由工具配置表达的规则交给工具。

## 十八、完整使用案例：修复金额舍入错误

### 1. 原始任务

```text
修复金额计算错误。
```

问题在于：没有说明错误行为、相关代码、业务规则和验证方式。

### 2. 让 Agent 先定位

```text
请先只读分析，不要修改文件。
定位订单结算入口、金额类型、舍入函数和现有测试。
列出已确认事实、推断和仍需确认的问题，并引用真实路径。
```

### 3. Agent 获得的项目上下文

```text
- 项目使用 Python 3.12 和 Decimal；
- 结算入口：src/orders/checkout.py；
- 舍入函数：src/money/rounding.py；
- 测试：tests/orders/test_checkout.py；
- AGENTS.md 要求金额计算不得转换为 float；
- API 字段和状态码必须保持兼容。
```

### 4. 补充任务级信息

```text
当前行为：输入 10.005 返回 10.00。
预期行为：按 ROUND_HALF_UP 返回 10.01。
范围：只修改金额量化和对应测试，不调整折扣规则。
```

### 5. 形成执行上下文包

```markdown
## Goal
修复订单结算对 10.005 的舍入，使其返回 10.01。

## Evidence
- `src/orders/checkout.py` 调用 `quantize_money`。
- `src/money/rounding.py` 当前没有显式指定业务舍入模式。
- 项目金额类型为 Decimal。

## Constraints
- 禁止转换为 float。
- 不修改折扣逻辑。
- 保持支付 API 契约不变。

## Validation
- 在 `tests/orders/test_checkout.py` 添加回归用例。
- 运行 `pytest tests/orders/test_checkout.py -q`。
```

### 6. 运行后更新上下文

假设第一次修改后测试显示：

```text
金额值已经正确，但响应序列化仍输出 10.00。
```

这条新证据说明问题还涉及序列化。Agent 应更新当前相关文件，而不是继续只改舍入函数。

### 7. 判断哪些信息应长期保存

- “金额不得使用 float”：长期项目规则，可留在 `AGENTS.md`；
- “10.005 当前返回 10.00”：本次错误证据，不写入长期指令；
- `ROUND_HALF_UP`：如果是正式业务规则，应进入业务规范或 ADR；
- 回归行为：写入测试代码；
- 本次只改结算：只留在当前任务。

### 8. 完成报告

```text
修改：明确订单金额的 ROUND_HALF_UP 量化，并修正序列化路径。
测试：新增 10.005 -> 10.01 回归用例。
已运行：pytest tests/orders/test_checkout.py -q，通过。
未运行：全量 pytest，因课堂环境时间限制。
剩余风险：其他货币精度规则未在本次范围内验证。
```

这个报告让用户知道 Agent 使用了什么上下文、做了什么和验证到什么程度。

## 十九、完整使用案例：重建被污染的登录会话

### 1. 会话现状

- 最初计划使用 JWT；
- 后来确认 Web 使用 cookie session；
- 移动端已经移出范围；
- 会话中有三版不同的 `auth.ts`；
- 旧日志显示 12 项失败；
- 最新测试只剩空密码用例失败；
- Agent 仍反复建议修改 JWT 过期时间。

### 2. 判断污染

旧认证方案、旧文件、旧日志和范围外功能同时存在，Agent 已无法稳定识别当前事实。

### 3. 制作重建包

```markdown
## Current goal
修复 Web 空密码登录返回 500，并添加回归测试。

## Confirmed decisions
- Web 使用 cookie session，依据 `ADR-007.md`。
- JWT 和移动端不在本次范围。

## Current files
- 登录入口：`src/routes/auth.ts`。
- 认证服务：`src/services/session-service.ts`。
- 测试：`tests/routes/auth.test.ts`。

## Current state
- 最新测试仅空密码用例失败。

## Constraints
- 复用现有错误响应格式。
- 不修改 session cookie 结构。
```

### 4. 开启干净会话

在新会话中提供重建包，并让 Agent 先复述目标、范围和验证方式。不要附上旧聊天全文，也不要继续使用旧版 `auth.ts` 片段。

### 5. 持久化稳定信息

- cookie session 的架构决定写入 ADR 或认证文档；
- 认证模块的标准测试命令可写入局部 `AGENTS.md`；
- 最新失败数量和当前范围留在任务会话。

## 二十、常见问题与改进方法

### 1. 让 Agent “读取整个仓库再说”

**问题**：无关代码淹没当前任务。

**改进**：先建立项目地图，再围绕入口、调用方、测试和规则逐步聚焦。

### 2. 只给一个代码片段

**问题**：缺少调用方、错误处理、fixture 和目录规则。

**改进**：说明文件职责，让 Agent 读取完成判断所需的相关上下文。

### 3. 把路径猜测写成事实

**问题**：Agent 可能围绕不存在的文件工作。

**改进**：先搜索真实入口并引用路径。

### 4. 把推断写成根因

**问题**：后续修改建立在错误前提上。

**改进**：区分事实、推断和必须澄清的问题。

### 5. 只给源文件，不给验证方式

**问题**：Agent 不知道怎样证明修改正确。

**改进**：提供测试框架、相关命令、必测行为和完成报告要求。

### 6. 使用空泛限制

**问题**：“不要破坏项目”无法转化为操作。

**改进**：写清文件范围、API 兼容、依赖限制和生成路径。

### 7. 把临时任务写入 AGENTS.md

**问题**：未来任务会继承过期要求。

**改进**：只持久化跨任务稳定的项目规则。

### 8. 从模板复制命令

**问题**：不存在的命令会在每个任务中重复失败。

**改进**：从当前脚本和 CI 查证，并实际核验关键命令。

### 9. AGENTS.md 只有禁止事项

**问题**：Agent 知道不能做什么，却不知道正确做法。

**改进**：补充源文件、生成命令或审批条件。

### 10. AGENTS.md 过长

**问题**：关键规则被教程和历史说明淹没。

**改进**：详细内容进入项目文档，根指令只保留高价值路由和规则。

### 11. 长会话继续堆补充说明

**问题**：新证据和旧假设混在一起。

**改进**：生成阶段摘要；污染严重时用重建包开启新会话。

### 12. 假设所有编码 Agent 都遵循同一文件规则

**问题**：不同产品的文件名、作用域和优先级可能不同。

**改进**：通用项目规则与产品发现规则分开，并核对当前官方文档。

### 13. 用 AGENTS.md 替代自动检查

**问题**：自然语言可能被忽略或理解不一致。

**改进**：关键机械规则同时交给 lint、测试、类型检查和 CI。

## 二十一、可复用 Prompt 模板

### 1. 陌生仓库只读分析

```text
请先只读检查仓库，不要修改文件。

目标：为当前任务建立最小项目上下文。

请输出：
1. 技术栈、运行时版本和依据；
2. 应用入口与相关目录职责；
3. 与任务直接相关的文件、符号和调用方；
4. 现有测试位置、fixture 和命令；
5. AGENTS.md 或其他项目指令；
6. 已确认事实、推断和必须澄清的问题。

要求：引用真实路径，不根据模板虚构文件。
```

### 2. 上下文不足诊断

```text
先暂停修改。
请检查当前任务仍缺少哪些信息，并分为：
- 可从仓库查证；
- 可通过命令验证；
- 必须由用户决定。

只保留会改变实现、范围或验收的问题。
```

### 3. 长会话压缩

```text
请根据当前仓库状态整理一份会话摘要，只保留：
- 当前唯一目标；
- 已确认事实及来源；
- 已确认决定；
- 当前真实文件；
- 最新测试或构建结果；
- 修改限制；
- 未解决问题。

明确列出已废弃的假设，不再引用旧代码片段和旧日志。
```

### 4. 生成 AGENTS.md 候选规则

```text
请先只读分析，不要直接创建 AGENTS.md。
从 README、依赖清单、脚本、CI、测试和现有规范中提取候选规则。

对每条规则列出：
- 内容；
- 证据来源；
- 适用目录；
- 是否跨任务稳定；
- 是否可执行或验证；
- 是否建议写入 AGENTS.md。

不要加入本次任务目标、临时日志、无来源偏好或敏感信息。
```

### 5. 完成前检查

```text
完成修改前，请：
1. 运行最相关测试；
2. 按项目规则运行适用的 lint、类型或构建检查；
3. 检查最终 diff 是否有无关修改；
4. 报告实际运行的命令和结果；
5. 明确说明未运行的检查与剩余风险。
```

## 二十二、本章总结

编码 Agent 的结果不仅由 Prompt 决定，也由它获得的项目上下文决定。

```text
Prompt：本次编码任务
Context：完成任务所需的项目事实和最新证据
AGENTS.md：跨任务长期有效的仓库工作规则
```

实际使用时，可以记住下面的顺序：

```text
先建立项目地图
  -> 定位真实文件和关系
  -> 补充规范、测试与修改限制
  -> 根据运行结果更新上下文
  -> 删除旧信息和无关材料
  -> 把稳定规则写入 AGENTS.md
```

高质量编码 Agent 上下文应当相关、准确、足够且不冲突。高质量 `AGENTS.md` 应当简短、项目特有、可执行、可验证，并放在正确目录作用域。

第五周将在本章基础上进一步学习如何阅读陌生代码库、定位入口并分析调用链；第六周再把探索、计划、实现和验证组织成完整工作流。
