# 第九周：代码审查、Git 与质量控制

## 本章导读

测试通过不代表代码可以直接合并。测试只覆盖已有用例，格式工具不理解业务，编码 Agent 的摘要也可能遗漏变化。代码审查[^1]必须回到真实 diff[^2]，确认修改符合需求、范围受控并且风险可接受。

[^1]: 代码审查：在合并前检查代码变化是否正确、必要并且风险可接受的过程。
[^2]: Diff：两个版本之间新增、删除和修改内容的对比。

本章只聚焦编码 Agent 怎样理解变更、辅助审查、整理 Git 记录和交付质量证据。第八周已经讲解测试设计；第十周再系统展开隐私、依赖、工具执行和人类责任。

```text
需求与基线
-> 提交与文件清单
-> 逐文件 diff
-> 测试、依赖与安全检查
-> 审查结论
-> 提交与合并请求说明
-> 人工批准、合并或回滚
```

---

## 一、从 Diff 到审查发现

### 1. 先确认审查对象

Diff Review[^3]不是从第一行新增代码直接读到最后一行，而是先确认需求和比较范围，再逐步寻找高风险变化。

[^3]: Diff Review：围绕版本差异检查行为、范围和风险的审查方法。

#### 确认目标与基线

基线[^4]决定哪些内容被视为本次变化。错误基线会混入其他提交，也可能漏掉已经提交的变化。

[^4]: 基线：本次变化拿来比较的起始版本或目标分支。

让 Agent 在审查前报告：

```text
任务目标
必须改变的行为
不得改变的行为
基线分支或提交
当前分支或提交
比较范围内的提交
工作区是否还有未提交变化
```

例如：

```text
目标：普通用户不能访问 /admin。
基线：main 的共同起点。
当前：feature/auth-guard。
不应改变：登录流程、管理员成功路径、依赖和 CI。
```

#### 明确 diff 命令回答什么

`git diff` 可以比较工作区、暂存区、提交或分支。命令不同，得到的变更集合也不同。

```text
git diff --stat main...HEAD
git diff --name-status main...HEAD
git diff main...HEAD -- src/auth tests/auth
```

这些命令只是示例。实际基线和路径必须来自当前任务。两点比较与三点比较选择的起点不同，Agent 应说明为什么当前命令符合审查目标，不能机械套用。

#### 先看统计和文件清单

先检查文件数量、增删规模和文件类型，可以快速发现任务外变化：

| 文件类型 | 重点问题 |
| --- | --- |
| 生产代码 | 控制流、数据边界、异常、状态和调用方 |
| 测试 | 是否捕获需求与负向路径 |
| 配置与 CI | 是否改变运行方式、权限或检查范围 |
| 依赖与锁文件 | 是否必要、是否一致、是否引入新风险 |
| 迁移 | 旧数据、失败恢复和部署顺序 |
| 生成文件 | 是否由正确源文件和生成命令产生 |

一个“修复管理员页面按钮”的任务如果修改了认证中间件、锁文件和 CI，Agent 应先说明这些变化为何异常，再进入细节。

#### 逐文件阅读

逐文件审查要一起理解旧代码、增加行、删除行和上下文。重点追踪：

- 输入从哪里进入；
- 哪些条件分支发生变化；
- 状态在成功和失败后怎样变化；
- 异常是否被正确处理；
- 调用者是否依赖旧行为；
- 返回结构和配置默认值是否兼容。

文件多时可以按风险排序，但不能只读最显眼的文件。修改公共函数时，应搜索定义、调用方和对应测试；搜索范围要服务于当前 diff，不扩展成无边界的全仓库检查。

#### 识别无关修改

一行功能修复混入全文件格式化、依赖升级和生成文件重排，会掩盖真实行为变化。Agent 应指出哪些变化缺少任务依据，并建议移出本次变更，而不是把“大量变化”误当成“工作更完整”。

---

### 2. 让 Agent 解释代码修改

修改说明应按文件回答四件事：修改目的、外部行为变化、验证证据和剩余风险。

未运行的集成测试[^5]要作为风险明确列出，不能写进“已通过”证据。

```text
src/auth/guard.py
- 原因：普通用户错误进入管理员路径。
- 行为：is_admin=False 时返回 403；管理员路径不变。
- 证据：权限测试覆盖管理员、普通用户和未登录用户。
- 风险：尚未运行依赖真实身份服务的集成测试。
```

[^5]: 集成测试：检查多个真实组件能否按预期一起工作的测试。

可直接使用：

```text
请根据当前分支相对 `[基线]` 的真实 diff 解释修改，不修改文件。

先确认比较范围和文件清单，再按文件说明：
1. 修改目的；
2. 外部行为变化；
3. 对应测试或检查证据；
4. 未验证项和剩余风险。

摘要与 diff 不一致时，以 diff 为准并指出差异。
```

GitHub Copilot Chat 可以辅助解释合并请求或提交，其他编码 Agent 也可能提供相似能力，但入口、命令和可用上下文属于各产品的具体行为。摘要只能导航，不能代替原始 diff。

### 3. 风险优先的 Bug 检查

#### 检查顺序

```text
错误结果
-> 数据损坏
-> 越权或敏感信息暴露
-> 兼容性破坏
-> 资源与并发问题
-> 缺失或无效测试
-> 范围外修改
-> 可维护性
```

严重程度来自触发条件和实际影响。只影响内部名称可读性的建议不得与能让未授权用户取得权限的漏洞处于同一级别。

#### 常见检查面

- 空值、上下限和异常输入；
- 成功、失败和重试路径；
- 状态变化、事务和清理；
- 认证、授权和默认拒绝；
- 并发、重复请求和资源释放；
- 错误码、响应结构和兼容性；
- 依赖、配置、迁移和生成过程。

权限判断反转可能通过格式、lint[^6] 和管理员成功路径测试，却让普通用户获得管理权限。审查必须同时覆盖管理员、普通用户和未登录用户。

[^6]: Lint：按规则检查代码中常见错误和不规范写法的静态工具。

#### 测试是否真正覆盖风险

检查新增测试是否对应本次行为和原 Bug：

- 正向和负向路径是否都存在；
- 测试是否会在错误实现上失败；
- 断言[^7]是否检查公开结果而不是内部细节；
- mock[^8] 是否绕过了需要验证的真实路径；
- 集成状态和清理是否可靠；
- 跳过项是否被错误算作通过。

测试缺口应写出会漏掉的具体触发条件，而不是只说“测试不够”。

[^7]: 断言：在测试中比较实际结果与期望结果，不满足时让测试失败的语句。
[^8]: Mock：用可控制的替身代替真实依赖的测试方法。

## 二、自动质量检查及其边界

### 1. Formatter、Lint 与类型检查

Formatter[^9]统一排版，lint 检查规则命中的常见错误，类型检查[^10]验证工具能够推导的类型关系。

[^9]: Formatter：按固定规则自动统一代码排版的工具。
[^10]: 类型检查：检查值与函数是否按声明的类型关系使用。

它们提高一致性和反馈速度，但都不能证明权限规则、金额计算或产品需求正确。

| 检查 | 可以提供的证据 | 不能保证 |
| --- | --- | --- |
| Formatter | 排版符合配置 | 逻辑正确 |
| Lint | 命中的规则没有报错 | 未配置规则覆盖的问题 |
| 类型检查 | 可推导的类型关系成立 | 业务语义正确 |
| 自动测试 | 已编码用例通过 | 未想到的路径 |
| 代码扫描 | 查询命中的风险状态 | 完整安全性 |
| 人工审查 | 意图、影响与取舍得到判断 | 永不出错 |

Agent 汇报自动检查时应包含真实命令、退出状态、错误与警告、检查范围。只写“质量检查通过”无法判断实际运行了什么。

---

### 2. 安全检查

安全审查包括认证授权、输入验证、敏感日志、危险命令、依赖变化和数据流。代码扫描[^11]可以发现其规则或查询覆盖的潜在漏洞，业务越权仍需要结合需求人工判断。

[^11]: 代码扫描：用自动规则或查询在代码中寻找潜在漏洞和错误的检查。

GitHub code scanning 可以把告警显示在合并请求中，也可以通过规则阻止带有指定告警的合并请求通过。这是 GitHub 的产品能力；是否启用、覆盖哪些分支和使用哪些工具取决于仓库配置。

以下情况不能汇报成“安全检查通过”：

- 仓库没有配置扫描；
- 扫描仍在运行；
- 扫描没有覆盖当前分支或语言；
- 工具退出成功但没有分析目标文件；
- 自动检查无告警，但权限或产品逻辑尚未人工审查。

本周只学习如何把这些信号纳入审查，第十周再系统展开风险与边界。

## 三、Git 变更交付

### 1. 分支管理

Branch[^12]用于从某个基线建立独立开发线。分支应围绕清楚目标，避免同时包含多个无关任务。

[^12]: Branch：从某个基线分出的独立开发线。

```text
确认正确基线
-> 创建目标分支
-> 小步修改与验证
-> 形成有意义的提交
-> 同步基线并解决冲突
-> 重新验证
-> 提出合并请求
```

分支如果从错误基线创建，即使本次代码正确，合并请求也可能混入无关提交。同步基线或解决冲突后要重新运行相关验证，因为冲突处理本身会改变代码。

文件修改、暂存、提交、推送和创建合并请求是不同授权。用户只要求 Agent 修改代码时，不能自动推送远程分支或创建合并请求。

---

### 2. 提交说明自动生成

Commit Message[^13]说明一次提交的目的和背景。Commit[^14]保存一组版本变化及其说明；Agent 可以读取 staged diff[^15]生成 Commit Message，但生成后必须核对真实暂存内容。

[^13]: Commit Message：说明一次提交目的和背景的文字记录。
[^14]: Commit：保存一组版本变化及其说明的 Git 记录。
[^15]: Staged diff：已经放入暂存区、准备进入下一次提交的变化。

```text
fix(auth): reject non-admin access to admin routes
```

标题概括目的，正文可解释原因和关键取舍。不要把未暂存变化写进说明，也不要声称未运行的测试已经通过。

```text
请只读取 staged diff 生成 Commit Message，不执行提交。

先列出暂存文件和行为变化；若包含多个无关目标，先说明，不要强行写成一个提交。
标题描述修改目的，正文解释原因和必要取舍。
不要写入未经验证的测试、发布或兼容性结论。
```

如果暂存区为空，Agent 应说明无法依据 staged diff 生成可靠信息；如果工作区还有未暂存修改，也要明确它们不属于本次提交。

---

### 3. 合并请求自动生成

Pull Request[^16]（PR）用于提出分支之间的变化，并承载上下文、讨论、检查和审查。

[^16]: Pull Request：向目标分支提出合并变化并进行讨论和审查的协作页面。

一份完整 PR 说明包含：

- 背景与问题；
- 行为变化和修改范围；
- 明确的非目标；
- 实际测试与检查结果；
- 截图、迁移或生成信息；
- 审查重点；
- 已知风险和回滚方式。

GitHub 官方建议 PR 小而聚焦，并在请求他人审查前先自查 diff、意外变化以及相关构建或测试。Agent 生成摘要可以帮助导航，但需要补充只有负责人知道的产品背景与风险。

![GitHub 官方示例：在 Pull Request 描述区域使用 Copilot 生成变更摘要](https://docs.github.com/assets/cb-42638/images/help/copilot/copilot-description-suggestion.png "Copilot 生成 Pull Request 摘要")

图片来源：[GitHub Docs：Creating a pull request summary with GitHub Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/copilot-for-github-tasks/create-a-pr-summary)（访问日期：2026-08-12）。截图只展示 GitHub Copilot 的 PR 摘要入口；生成内容仍需结合真实 diff、验证结果和人工掌握的背景审查。

#### PR 说明模板

```text
背景：
为什么需要这次变化，关联什么问题。

修改：
改变了哪些行为；明确不包含什么。

验证：
实际运行的命令、结果、跳过和未运行项。

审查重点：
请优先检查的文件、路径或设计决定。

风险与回滚：
剩余风险、迁移或截图、可用的撤销方式。
```

```text
请根据分支相对目标基线的全部提交和 diff 生成 PR 标题与说明，不创建或推送 PR。

说明包含：背景、修改范围、非目标、实际验证、未运行项、审查重点、已知风险和回滚方式。
引用真实命令结果，不把 Agent 推断写成事实。
```

## 四、合并请求审查

### 1. 怎样评价 Agent 生成结果

评价对象是 Agent 实际交付的代码、测试、配置和说明，而不只是最后一段回答。先把任务要求写成可观察结果，再用正确基线下的 diff 和运行证据逐项核对：

| 评价维度 | 要核对的问题 | 可查看的证据 |
| --- | --- | --- |
| 需求符合度 | 必须改变的行为是否实现，不得改变的行为是否保持 | 需求、关键路径的旧代码与新代码、实际运行结果 |
| 范围与完整性 | 是否漏改调用方、测试或文档，是否混入无关文件、依赖或配置 | 文件清单、逐文件 diff、项目引用关系 |
| 正确性与风险 | 正常、失败、边界和权限路径是否合理，是否引入兼容或数据风险 | 关键分支、调用方、针对性测试与人工检查 |
| 验证可信度 | 检查是否真的运行且覆盖本次变化，跳过或未运行项是否说明 | 命令、退出状态、测试数量、警告和环境条件 |
| 说明可信度 | Agent 的摘要、PR 说明与实际变化和证据是否一致 | 最终说明对照 diff 与原始检查输出 |

例如，Agent 声称“已修复普通用户访问 `/admin`”，审阅者应在 `src/auth/guard.py` 确认普通用户被拒绝，再看管理员和未登录路径、对应测试及测试输出。如果摘要说“只改权限判断”，diff 却还有锁文件和 CI 变化，就要先查明原因。测试通过但没有覆盖普通用户时，不能据此评价为需求已验证。

结论应落到具体证据：符合要求的部分、必须修复的问题、尚未验证的部分及其影响。对有明确错误的结果要求修复；证据不足时要求补充检查或标明限制。不要用“代码看起来不错”或单个通过数量代替判断，也不要把评价 Agent 结果写成对学生或工具的打分。

### 2. 一条可操作发现的结构

| 字段 | 要回答的问题 |
| --- | --- |
| 严重程度 | 是否阻塞合并，影响有多大 |
| 文件位置 | 问题位于哪个最小代码范围 |
| 触发条件 | 什么输入、权限或状态会出现 |
| 实际影响 | 会产生什么错误结果 |
| 证据 | 哪段 diff、调用关系或测试支持结论 |
| 修复方向 | 最小可行方向是什么 |

```text
[阻塞] src/auth/guard.py:42
触发：is_admin=False 的已登录用户访问 /admin。
影响：普通用户获得管理权限。
证据：条件分支反转；新增测试只覆盖管理员。
方向：恢复拒绝分支，并补普通用户与未登录用户测试。
```

这样的意见比“权限逻辑可能有问题”更容易复现、讨论和修复。修改后应检查新增 diff，并验证评论对应的问题真正解决。

### 3. 没有发现问题时怎样报告

“未发现可操作问题”是合格结果，但要同时说明：

- 实际比较的基线与范围；
- 阅读了哪些高风险路径；
- 运行了哪些检查；
- 哪些环境或行为未验证；
- 为什么剩余风险仍需要人工判断。

Agent 不能为了凑数量把低置信猜测写成 Bug。反过来，Agent 没有发现问题也不是批准依据。

### 4. GitHub Copilot code review 的边界

GitHub 官方文档说明，Copilot code review 可以审查 PR 并提供反馈；Copilot CLI 的 `/review` 可以在终端中分析代码变化。这些入口和命令只属于对应 GitHub 产品，不能推广为所有编码 Agent 的统一行为。

GitHub 官方同时明确说明 Copilot 可能漏掉问题或出错，应仔细验证其反馈并补充人工审查。通用做法仍然是给 Agent 明确基线、任务边界、风险优先级和输出格式，再由人核对真实 diff 与证据。

![GitHub 官方示例：Copilot 代码审查意见及反馈按钮](https://docs.github.com/assets/cb-19709/images/help/copilot/code-review/feedback-controls%402x.png "GitHub Copilot 代码审查意见")

图片来源：[GitHub Docs：Using GitHub Copilot code review](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review)（访问日期：2026-08-11）。截图只说明 GitHub Copilot 的界面行为；其他编码 Agent 的审查入口和反馈机制需要分别确认。

### 5. 完整审查 Prompt

```text
请审查当前分支相对 `[基线]` 的 diff，不修改文件。

按严重程度检查：
1. 错误结果、数据损坏、越权和兼容破坏；
2. 缺失或无效测试；
3. 超出任务范围的修改；
4. 依赖、迁移和配置风险；
5. 可维护性问题。

先按需求符合度、范围与完整性、正确性与风险、验证可信度、说明可信度评价 Agent 的实际交付。
每条发现包含严重程度、文件位置、触发条件、实际影响、证据和最小修复方向。
没有高置信问题时，明确说明实际检查与剩余未验证风险；不要为了凑数量而猜测。
```

## 五、回滚与人工责任

### 1. 版本回滚

回滚[^17]前先判断变化是否已共享，以及是否已经产生代码之外的副作用。

[^17]: 回滚：让代码或系统恢复到某个较早可用状态的处理过程。

- 已共享提交通常考虑 revert[^18]，用新提交保留可追踪历史；
- 未共享本地修改应根据工作区、暂存区和提交状态选择恢复方式；
- reset[^19] 和强推可能改变协作者依赖的历史，需要谨慎授权；
- 数据迁移、外部消息和生产数据未必随代码一起恢复。

[^18]: Revert：用一个新提交撤销已有提交效果的 Git 操作。
[^19]: Reset：移动 Git 当前引用，并按选项调整暂存区或工作区的操作。

`git revert` 记录新的反向变化，不等于删除旧提交。具体恢复命令取决于目标状态、是否共享和项目规则。Agent 应先展示精确对象、影响范围、验证方式和可恢复路径，再执行已获得授权的动作。

代码回滚后同样要运行测试和相关质量检查。数据库迁移、已发送邮件或其他外部副作用需要专门恢复方案，不能只运行一个 Git 命令就宣布系统已经回滚。

---

### 2. 人工代码审查的重要性

Agent 擅长导航 diff、解释调用关系和寻找候选问题。人掌握产品意图、组织风险和最终合并权限。最终批准者需要判断：

- 需求本身是否正确；
- 兼容性取舍是否可以接受；
- 自动检查覆盖是否足够；
- 范围外变化是否应该拆分；
- 未验证风险是否阻塞合并；
- 是否真的授权提交、推送、合并或回滚。

审查可以有三种合格结论：

1. 发现可复现、可操作的问题；
2. 未发现可操作问题，但列出实际检查和未验证风险；
3. 因基线、环境或证据不足无法完成审查，并准确说明缺口。

Agent 的流畅说明不是批准证据，人也不应把自动检查通过当成免责证明。

---

## 六、本章总结

```text
Branch 隔离 -> Commit 记录 -> PR 说明
-> 自动检查 -> 人工 Diff Review -> 合并或回滚
```

使用编码 Agent 完成质量控制时，记住：

1. 先确认需求、基线和真实比较范围；
2. 文件清单先于逐行细节，范围异常先调查；
3. Agent 摘要用于导航，diff 才是变更事实；
4. 评价 Agent 结果要核对需求、范围、行为、验证与说明；
5. 发现要写严重程度、位置、触发条件、影响和证据；
6. 格式、lint、类型、测试和扫描各有边界；
7. Commit Message 只描述实际暂存变化；
8. PR 应小而聚焦，并提供验证与剩余风险；
9. GitHub Copilot 的 `/review` 等行为不能推广为所有 Agent 的命令；
10. 已共享历史通常优先考虑可追踪的 revert，但外部副作用需另行恢复；
11. 人对是否批准、合并和发布承担最终责任。
