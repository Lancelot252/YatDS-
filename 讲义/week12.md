# 第十二周：多 Agent 协作与代码重构

## 本章导读

多 Agent 协作不是把同一要求复制给更多模型。它需要把任务拆成可独立完成、可独立验证的子问题；每个角色都要收到完成任务契约所需的上下文、工具和权限；最后由一名负责人整合证据与修改。

Subagent[^1]用于处理目标、输入、范围和完成条件均已写明的子任务。每个 Subagent 都会增加 token、工具调用和结果复核成本；只有当至少两个子任务可以独立推进，或独立上下文能隔离大量日志与搜索结果时，才考虑使用多个 Agent。

[^1]: Subagent：主 Agent 为一个有边界的子任务启动的专业 Agent。

本章还把多 Agent 协作应用到代码重构。重构[^2]是在保持外部可观察行为的前提下改善内部结构；多 Agent 可以帮助分析、测试和审查，但不能替代行为基线、单一写入所有者和最终集成责任。

[^2]: 重构：在保持外部可观察行为的前提下改善代码内部结构。

```text
清楚目标
-> 可独立子任务
-> 角色、上下文、工具和权限
-> 并行或串行执行
-> 汇总冲突与证据
-> 单一实现所有者
-> 集成测试和最终 diff
-> 人工交付判断
```

## 一、什么时候需要多 Agent

### 1. 合适条件

满足以下条件时，可以考虑使用多 Agent：

- 可以拆成互不依赖的证据收集；
- 需要安全、测试、架构等不同专业视角；
- 每个子任务有明确输入和完成条件；
- 写入范围可以分离，或主要任务只读；
- 主 Agent 能比较、去重并验证返回结果；
- 至少两个子任务可以同时开始，且并行执行能减少串行等待时间。

### 2. 不合适条件

- 任务只有一个有边界的输出，没有可独立推进的分支；
- 后一步强依赖前一步的细节；
- 多个角色必须反复编辑同一文件；
- 需求仍有关键歧义；
- 没有统一基线或项目规则；
- 没有人负责最终集成和验证。

### 3. 成本模型

```text
收益：并行时间节省 + 专业视角 + 主会话降噪
成本：更多 token + 更多工具调用 + 上下文准备 + 冲突处理 + 结果复核
```

OpenAI Codex 当前官方文档明确指出，Subagent 工作流通常比可比的单 Agent 运行消耗更多 token。是否使用多 Agent 应由任务形状决定，而不是把“更多”当作质量指标。

### 4. 判断 Prompt

```text
请先判断这个任务是否值得使用多个 Agent，不要立即分派。

列出：
1. 可以独立完成的子任务；
2. 子任务之间的依赖；
3. 是否会修改相同文件或状态；
4. 每个结果怎样独立验证；
5. 并行节省与协调成本；
6. 最终集成和交付负责人。
```

## 二、主 Agent、Subagent 与任务契约

### 1. 主 Agent 的责任

主 Agent 不只是转发消息。它需要：

- 固定用户目标、非目标和授权；
- 读取适用项目指令；
- 选择并行或串行；
- 为子任务准备最小充分上下文；
- 监控依赖和状态变化；
- 比较冲突结论；
- 保护用户已有修改；
- 运行最终集成验证；
- 向用户交付一个一致结果。

### 2. Subagent 的责任

Subagent 应只处理分派范围，并返回：

- 已检查对象；
- 关键事实与文件证据；
- 执行的命令和真实结果；
- 无法确认的内容；
- 可能影响其他角色的变化；
- 是否满足完成条件。

Subagent 的摘要用于减少主会话噪声。涉及公开接口、数据写入、权限、安全或外部操作的结论，主 Agent 仍要核对原始文件、官方文档或运行证据。

### 3. 任务契约

任务契约[^3]明确子任务目标、输入、权限、输出和完成条件。

[^3]: 任务契约：对子任务目标、输入、权限、输出和完成条件的明确约定。

| 字段 | 需要说明 | 示例 |
| --- | --- | --- |
| 目标 | 要回答的单一问题 | 检查权限 diff 的高置信风险 |
| 输入 | 共同事实与基线 | `main...HEAD`、需求、AGENTS.md |
| 范围 | 文件、模块或数据边界 | 只读 `src/auth` 和相关测试 |
| 工具 | 可以使用什么 | 搜索、读文件、运行指定测试 |
| 权限 | 是否允许写入或外部动作 | 不编辑、不推送、不发评论 |
| 输出 | 结构和证据要求 | 严重度、位置、触发、影响、证据 |
| 完成条件 | 何时算完成 | 覆盖所有变更文件并列出缺口 |
| 停止条件 | 何时返回主 Agent | 基线不明、需凭据或用户决定 |

### 4. 不合格与合格的对照

```text
不合格：检查订单代码，看看有什么问题。

合格：
只读分析 src/orders/process.ts 相对 main 的结构职责。
追踪输入验证、金额计算、库存写入和通知副作用。
不要修改文件或提出功能变化。
输出每项职责的文件行、调用方、候选切分点和未知项。
若基线或当前需求不一致，停止并报告。
```

## 三、多 Agent 协作模式

### 1. Manager 模式

Manager[^4]模式中，主 Agent 保持用户对话和最终答案所有权，把专业 Agent 当作工具调用。

[^4]: Manager 模式：主 Agent 保持控制并调用专业 Agent，最终统一汇总结果。

```text
用户
-> Manager
   -> 安全 Agent
   -> 测试 Agent
   -> 架构 Agent
-> Manager 去重、核验、排序并回答
```

适合：

- 多视角代码审查；
- 独立资料核验；
- 多模块只读探索；
- 需要一个统一最终报告的任务。

### 2. Handoff 模式

Handoff[^5]是当前 Agent 把后续处理控制权交给专业 Agent。

[^5]: Handoff：当前 Agent 把后续处理控制权交给另一个专业 Agent。

适合：

- 需要专业 Agent 直接与用户持续交互；
- 路由本身是工作流的一部分；
- 专业角色需要不同指令和对话风格；
- 主 Agent 不必逐条转述专业结果。

Handoff 后哪个 Agent 能看到哪些历史、使用哪些工具，属于具体框架和配置行为。

### 3. 代码编排

应用代码明确决定顺序、并行、循环、重试和停止条件。

```text
分类任务
-> 并行运行三个只读检查
-> 合并结构化结果
-> 若存在阻塞问题则停止
-> 否则进入实现 Agent
-> 运行验证 Agent
```

当执行顺序、重试次数、停止条件或并行分支必须由程序固定并接受测试时，应使用代码编排。

### 4. 三者可以组合

一个路由 Agent 可以 handoff 给专业 Agent；专业 Agent 又可以把窄任务作为 tools 调用；整个执行顺序也可以由代码控制。组合越复杂，越需要清楚状态、失败处理和追踪。

## 四、不同产品与框架的边界

相似术语不代表相同实现。

| 产品或框架 | 官方当前行为重点 | 不能推广的内容 |
| --- | --- | --- |
| OpenAI Codex | 可按直接请求或适用项目/Skill 指令启动 Subagent，主任务汇总结果 | 不能推断其他 Agent 也有相同线程控制 |
| OpenAI Agents SDK | agents as tools、handoffs，也可由代码编排 | SDK API 不是所有编码 Agent 的统一命令 |
| Anthropic Claude Code | 自定义 Subagent 有独立上下文、工具与权限 | 配置文件和委派规则属于 Claude Code |
| Google ADK | LLM 路由与 Sequential、Parallel、Loop 等工作流 | ADK 类名不是通用协议概念 |

### 1. Codex Subagents

OpenAI 官方文档当前建议把并行 Agent 优先用于探索、测试、分诊和总结等读密集任务，对并行写入保持谨慎。主任务收集 Subagent 返回并形成统一回应。

### 2. OpenAI Agents SDK

官方区分：

- Agents as tools：manager 保持控制；
- Handoffs：专业 Agent 接管后续处理；
- Code orchestration：应用代码决定链式、循环或并行执行。

### 3. Claude Code Subagents

Anthropic 官方文档将自定义 Subagent 描述为具有独立上下文、系统指令、工具访问和权限的专业助手。独立上下文有助于把大量搜索和日志移出主会话，但需要明确传入必要背景。

### 4. Google ADK

Google ADK 官方资料区分 LLM 驱动的动态路由与 Sequential、Parallel、Loop 等工作流 Agent。它更接近构建 Agent 应用的代码框架，不等同于本地编码 Agent 的 Subagent UI。

![Google ADK 官方架构图：模型、Agent、工具、会话、运行器、事件与服务共同组成 Agent 应用](https://storage.googleapis.com/gweb-developer-goog-blog-assets/images/ADK-architecture.original.png "Google ADK 官方架构图")

图片来源：[Google Developers Blog：Agent Development Kit—multi-agent applications](https://developers.googleblog.com/agent-development-kit-easy-to-build-multi-agent-applications/)（访问日期：2026-08-11）。该图展示的是 Google ADK 的产品架构，不代表所有编码 Agent 都采用同一结构。

### 5. 通用结论

可以跨产品使用的原则是：边界清楚、上下文最小充分、权限匹配、结果可验证、最终责任明确。触发命令、默认模型、主动委派、历史传递和工具配置必须分别查官方文档。

## 五、角色分工与权限

| 角色 | 核心职责 | 建议权限 |
| --- | --- | --- |
| 需求分析 Agent | 事实、歧义、范围和依赖 | 只读 |
| 代码地图 Agent | 入口、调用链、数据流和影响文件 | 只读 |
| 测试 Agent | 行为基线、测试缺口和验证命令 | 只读或限定测试写入 |
| 安全审查 Agent | 输入、权限、秘密和依赖风险 | 只读 |
| 编码 Agent | 实现一个确认过的最小步骤 | 限定工作区写入 |
| 文档 Agent | 根据已验证实现更新说明 | 限定文档写入 |
| 集成负责人 | 解决冲突、运行完整验证、交付 | 主 Agent 或明确的人 |

### 1. 角色按责任而不是名称区分

“高级 Agent”“专家 Agent”没有说明它能做什么。好的角色描述写清输入、决策范围、工具和输出。

### 2. 分析与实现分离

多角色分析可以并行；确认方案后，为目标文件指定一个写入所有者。其他 Agent 保持只读或只修改互不依赖的文件，以保护用户修改、避免覆盖并保持 diff 可审查。

### 3. 独立测试视角

测试 Agent 可以从需求和公共行为推导边界，避免完全复制编码 Agent 的实现思路。但它仍需要现有测试框架、项目规则和产品契约。

### 4. 文档在实现验证后更新

文档 Agent 应依据最终代码和真实测试结果，不应根据早期计划提前写成“已完成”。

## 六、并行、串行与依赖

### 1. 并行条件

一个子任务适合并行，需要同时满足：

1. 输入可以独立准备；
2. 不依赖其他子任务尚未产生的结果；
3. 写入对象不重叠，或任务只读；
4. 输出可以独立验收；
5. 失败不会留下难以识别的部分状态。

### 2. 适合并行

```text
安全审查 | 测试缺口 | 架构影响 | 官方资料核验
```

这些任务可以查看同一基线，从不同维度返回证据。

### 3. 适合串行

```text
确认需求
-> 建立测试基线
-> 选择方案
-> 修改代码
-> 运行验证
-> 更新文档
```

后一步依赖前一步真实结果时，强行并行只会使用过时假设。

### 4. 不只看文件是否不同

两个 Agent 修改不同文件，也可能发生语义冲突：

- 一个改变接口，另一个按旧接口写调用方；
- 一个修改 schema，另一个按旧 schema 写迁移；
- 一个改配置默认值，另一个按旧默认值写测试。

判断并行要看行为依赖，不只是路径。

### 5. Worktree 的边界

Worktree[^6]可以隔离文件写入状态，却不能自动解决设计和语义冲突。最终仍要选择合并顺序、解决冲突并重新验证。

[^6]: Worktree：让同一 Git 仓库在多个目录中同时检出不同工作状态的机制。

## 七、上下文同步与冲突处理

### 1. 必须共享的共同基线

- 同一需求版本；
- 同一基线提交和比较范围；
- 适用的项目指令；
- 已确认产品决定；
- 当前文件状态和已有修改；
- 输出格式与证据标准；
- 新出现的失败和用户决定。

### 2. 最小充分上下文

不应把全部会话、日志和仓库内容复制给每个 Agent。给代码地图 Agent 提供入口和范围，给测试 Agent 提供行为与测试框架，给安全 Agent 提供信任边界和 diff。

上下文过少会误解任务，上下文过多会增加噪声。目标是让每个角色拥有完成契约需要的最小充分信息。

### 3. 四类冲突

| 冲突 | 示例 | 处理 |
| --- | --- | --- |
| 事实冲突 | API 参数是否存在 | 官方版本文档、本地类型和运行证据 |
| 方案冲突 | 提取函数还是引入类 | 按需求、风险、维护成本取舍 |
| 写入冲突 | 两个 Agent 修改同一段代码 | 停止并指定单一所有者 |
| 优先级冲突 | 性能优化与兼容性冲突 | 由负责人或用户确认 |

### 4. 不能用多数投票决定事实

三个 Agent 都读到同一篇过时博客，可能一起得出错误结论。事实应由当前项目文件、锁定版本官方文档和真实运行支持。

### 5. 状态变化要主动同步

若用户改变需求、基线更新或某个 Agent 已修改公共接口，主 Agent 必须通知受影响角色。独立 Agent 不会自动拥有其他线程的最新状态。

## 八、Agent 辅助重构的边界

### 1. 什么是外部可观察行为

- 公共函数参数和返回值；
- API 状态码和响应结构；
- 数据库写入结果；
- 错误类型和日志；
- 事件、通知和调用顺序；
- 性能与资源使用要求；
- 配置和兼容行为。

重构不仅要“测试通过”，还要明确这些行为哪些必须保持。

### 2. 重构与功能修改对照

| 修改 | 纯重构？ | 说明 |
| --- | --- | --- |
| 将长函数拆成私有函数 | 满足条件时是 | 参数、返回值、副作用和调用顺序均不变 |
| 改内部变量名 | 满足条件时是 | 所有引用已同步，且不影响序列化、反射或公开契约 |
| 改变折扣规则 | 不是 | 产品结果变化 |
| 修改公共 API 参数 | 不是纯重构 | 调用方契约变化 |
| 消除同一概念的重复实现 | 满足条件时是 | 两处由同一规则驱动，合并后结果与错误行为不变 |
| 引入缓存并改变数据时效 | 不是纯重构 | 返回数据的新鲜度发生变化 |

### 3. 不要把修 Bug 和重构混在一步

```text
先用测试复现 Bug
-> 最小行为修复
-> 验证并形成清楚 diff
-> 再在绿色测试保护下重构
```

混合修改会让测试失败时无法判断是行为修复还是结构变化造成。

## 九、重构前建立行为基线

### 1. 基线内容

- 当前相关测试结果；
- 公共接口和调用方；
- 成功、失败和边界行为；
- 数据写入和外部副作用；
- 性能或资源限制；
- 工作区已有用户修改；
- 当前未覆盖风险。

### 2. 特征测试

特征测试[^7]记录遗留系统当前可观察行为，为重构提供比较基线。

[^7]: 特征测试：记录现有系统当前行为、用于保护重构过程的测试。

它并不说明旧行为一定正确。若发现疑似 Bug，应将“保持旧行为的重构”和“改变行为的修复”分成两个决策。

### 3. 基线报告

```text
目标函数：process_order
公共入口：POST /orders、OrderService.process
基线测试：订单模块 38 passed；完整测试 282 passed
关键行为：折扣、舍入、库存回滚、通知顺序
已有修改：tests/orders/test_refund.py 为用户未提交变化，不触碰
未覆盖：库存写入失败后的通知行为
```

### 4. 缺少行为基线时

若关键成功、失败或边界行为没有测试或可重复观察，先为本次重构涉及的行为补特征测试，或记录可重复的只读观察结果。不要让 Agent 依据“应该没变化”开始跨模块移动代码。

## 十、小规模重构

### 1. 命名优化

名称应表达领域含义。修改前搜索全部引用，并区分：

- 局部变量和私有函数；
- 公共函数与类型；
- JSON 字段和序列化键；
- 数据库列和迁移；
- 配置键和环境变量。

后四类可能影响外部兼容，不能当作无风险重命名。

### 2. 函数拆分

按责任和副作用切分：

```text
process_order
├── validate_order_input
├── calculate_order_total
├── reserve_inventory
└── send_order_notification
```

每个函数应有清楚输入、输出和副作用。目标不是让主函数行数最少，而是让责任和测试边界更清楚。

### 3. 重复代码消除

判断两段代码是否应该共用实现：

- 是否表达同一业务概念；
- 是否由同一规则驱动；
- 未来是否因同一原因变化；
- 错误和边界是否一致；
- 抽取后是否产生不必要参数和条件分支。

文本相似但业务不同的代码不应机械合并。

### 4. 小步循环

```text
选择一个结构问题
-> 做一个局部修改
-> 运行最相关测试
-> 检查 diff 和公共行为
-> 提交或形成检查点
-> 决定下一步
```

## 十一、大规模重构

大规模重构可能改变模块边界、依赖方向和数据访问方式。一次性重写难以比较、审查和恢复。

### 1. 分阶段路径

```text
定义目标结构
-> 建立基线与特征测试
-> 引入接口或兼容层
-> 迁移一条完整路径
-> 对比旧新结果
-> 设置阶段检查点
-> 逐步扩大范围
-> 删除旧路径
```

### 2. 单路径迁移

先迁移一个可端到端验证的读路径，比同时搬迁所有模型、服务和写入路径更容易发现问题。

### 3. 双跑与对比

在合适场景中，可让旧实现和新实现对同一合成输入运行，比较输出、错误和性能。双跑也有成本和数据风险，不能在生产中未经评估直接启用。

### 4. 多 Agent 如何参与

适合并行：

- 模块依赖地图；
- 公共 API 清单；
- 测试保护范围；
- 性能与安全风险；
- 迁移顺序候选。

不宜同时进行：

- 多个 Agent 修改共享接口；
- 一个改 schema、另一个独立写迁移；
- 多个 Agent 各自“修复”集成测试。

最终架构选择和迁移集成必须有明确所有者。

## 十二、重构后的验证与说明

### 1. 验证层次

```text
新增或特征测试
-> 最相关测试文件
-> 相关模块测试
-> 项目规定的完整检查
-> 公共接口与数据副作用
-> 性能或资源验证
-> 最终 diff
```

### 2. 验证问题

- 基线行为是否仍一致；
- 公共 API 和序列化结构是否变化；
- 错误类型、日志和通知顺序是否变化；
- 数据事务与失败恢复是否变化；
- 性能是否出现不可接受退化；
- 是否混入功能修复、依赖升级或格式化；
- 未运行哪些环境级验证。

### 3. 重构说明模板

```text
动机：为什么需要改善结构。
范围：修改和未修改哪些模块。
结构变化：责任怎样重新分配。
行为不变项：接口、结果、错误和副作用。
验证：真实命令、结果和对比证据。
剩余风险：未验证环境和路径。
下一步：后续候选，不混入本次 diff。
```

### 4. 不合格说明

```text
重构完成，代码更优雅，所有功能应该正常。
```

它没有说明比较基线、行为边界、运行证据和剩余风险。

## 十三、综合案例：多角色拆分订单处理函数

### 1. 共同任务

```text
目标：在不改变外部可观察行为的前提下，拆分过长的订单处理函数。

共同上下文：
- 基线：main 的指定提交；
- 需求：只做结构重构，不改变折扣、库存、错误和通知行为；
- 项目规则：遵守 AGENTS.md，禁止新增依赖；
- 最终所有者：主 Agent 负责汇总、验证和交付。
```

### 2. 只读角色

```text
代码地图 Agent：
描述职责、调用方、副作用和候选切分点；引用文件证据。

测试 Agent：
检查现有测试能否保护折扣、舍入、库存回滚和通知顺序。

审查 Agent：
列出公共接口、数据一致性、安全和性能风险。
```

三个角色可以并行，因为共享同一基线、只读且输出维度不同。

### 3. 主 Agent 汇总

主 Agent 应：

1. 去重相同发现；
2. 对冲突结论回到代码和测试；
3. 选一个最小重构步骤；
4. 明确本轮不处理的候选；
5. 把确认方案交给单一编码 Agent。

### 4. 单一实现任务

```text
只提取 calculate_order_total。

保持：
- 公共函数参数和返回值；
- 折扣与舍入规则；
- 错误类型；
- 库存和通知调用顺序。

不要：
- 修复其他 Bug；
- 新增依赖；
- 格式化无关代码；
- 继续拆分其他职责。
```

### 5. 验证与交付

```text
动机：订单函数同时承担验证、计算和持久化，难以独立理解。
本轮范围：只提取 calculate_order_total；无依赖和接口变化。
行为不变：折扣规则、舍入、错误、库存和通知顺序。
协作：3 个只读分析角色；1 个实现角色；主 Agent 集成。
验证：订单模块 42 passed；完整测试 286 passed；lint 通过。
差异：1 个生产文件、1 个测试文件，无范围外修改。
未验证：未运行生产性能基准；本次不改变 I/O 路径。
下一步候选：分离库存写入，需先补失败回滚测试。
```

## 十四、十二周能力体系

```text
Week 1  认识编码 Agent 与工具形态
Week 2  用 Prompt 清楚表达目标、输入、输出和约束
Week 3  将自然语言需求转成可执行任务
Week 4  组织上下文与项目指令
Week 5  阅读目录、入口、调用链和数据流
Week 6  用 Plan–Act–Observe 小步执行和纠偏
Week 7  安全调用文件、终端、测试和 Git 工具
Week 8  用测试复现、修复和防止回归
Week 9  审查 diff、Git 记录、PR 和质量证据
Week 10 控制幻觉、数据、依赖、权限和外部影响
Week 11 用 MCP 连接能力，用 Skill 复用方法
Week 12 用多 Agent 分工，在验证保护下重构
```

后面的能力不会替代前面的基础：

- 多 Agent 仍需要清楚需求；
- Subagent 仍需要正确上下文；
- MCP 工具仍需要权限和审批；
- Skill 仍需要真实验证；
- 重构仍需要测试和 diff 审查；
- 最终交付仍由人负责。

## 十五、本章总结

使用多 Agent 和 Agent 辅助重构时，记住：

1. 多 Agent 的价值来自独立分工，不是数量；
2. 主 Agent 负责契约、同步、冲突、集成和交付；
3. manager、handoff 和代码编排解决不同控制问题；
4. 各产品的 Subagent 和 SDK 行为必须分别说明；
5. 并行条件包括输入独立、无前置依赖、写入不重叠和可独立验收；
6. 不同文件也可能产生语义冲突；
7. 技术事实不能用 Agent 多数投票决定；
8. 重构必须明确外部行为并建立基线；
9. 小步修改、持续测试和 diff 检查比一次性重写更可控；
10. 最终必须有一个明确的集成与交付责任人。

成熟的人机协作不是把责任交给更多 Agent，而是让目标、上下文、分工、权限、反馈和验收都可检查，并由人对最终结果负责。
