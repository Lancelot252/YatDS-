# 第二周：提示词工程

## 本章导读

编码 Agent[^1] 根据用户提供的 Prompt[^2] 在工作区中开展任务。它可以读取目录和文件、理解现有代码、创建或编辑文件，并在完成后汇报修改结果。Prompt 可以是一句简短指令，也可以是一份包含工作区范围、目标文件、任务要求、交付位置和限制的完整说明。

提示词工程（Prompt Engineering）[^3]用于把文件任务表达清楚。对于编码 Agent，同一句“帮我完善项目”可能对应许多不同结果：Agent 不知道应该读取哪些文件、修改哪个目标、保持什么接口、能否创建新文件，以及完成后需要执行哪些检查。

[^1]: 编码 Agent：能读取项目并使用工具完成编码任务的 AI 助手。
[^2]: Prompt：用户交给 Agent 的任务说明。
[^3]: Prompt Engineering：改进 Prompt 表达的方法。

本章只讨论提示词工程本身，内容包括：

```text
基础概念
→ Prompt 在编码 Agent 中的作用
→ 背景、目标、输入、输出、约束
→ Role、Few-shot、Step-by-step
→ Markdown、JSON、表格、代码
→ 高质量 Prompt 的设计与改进
→ 简单界面设计与图形绘制提示
```

本章统一假定编码 Agent 已打开课程工作区，并可在授权范围内读取、创建和编辑文件。本周只学习如何写清一次文件任务；项目级上下文、系统化代码库阅读、Agent 工作流、工具调用、测试驱动、代码审查和风险边界将在后续章节分别学习。

已知目标路径时，可以直接写出文件名，帮助 Agent 缩小范围。目标位置尚不明确时，应描述期望结果，并要求 Agent 先检查工作区、定位相关文件，再在确认的范围内修改。无需预先把所有文件内容粘贴进 Prompt。

*注：Prompt 的效果会随模型、工作区内容、可用上下文和任务范围变化。课堂示例用于比较信息是否完整；实际使用时，应按目标行为、修改范围、输出格式和验证结果逐项检查，只修改未满足的部分。短 Prompt 偶尔得到可用结果，不代表其中省略的信息在其他项目中仍可由 Agent 正确推断。*

## 一、Prompt 与 Prompt Engineering

### 1. Prompt 是什么

Prompt 是用户交给编码 Agent 的任务说明。它可以指出要读取的路径、要修改或创建的文件、期望行为、限制条件和完成后的汇报方式。

简单示例：

```text
完善队列代码。
```

较完整的示例：

```text
读取工作区中的 `src/queue.py` 和 `README.md`。
补全 `Queue` 类的 `enqueue`、`dequeue` 和 `peek`，保持现有方法签名；
空队列调用 `dequeue` 或 `peek` 时抛出 `IndexError`；
同步更新 `README.md` 中的使用示例。完成后列出修改文件。
```

第二条 Prompt 增加了读取范围、目标文件、修改要求、接口约束和交付说明，因此 Agent 可以直接操作工作区，并把改动控制在预期范围内。

### 2. Prompt Engineering 是什么

Prompt Engineering 是设计、比较和改进任务说明的方法。基本过程是先提交初始 Prompt，检查 Agent 实际修改了哪些文件、实现是否符合要求，再针对具体偏差补充或修正信息。

示例：

```text
初始 Prompt：把搜索功能补好。
```

Agent 无法确定目标文件，也可能自行创建新文件或改变已有接口。

```text
改进 Prompt：读取 `src/search.py`，补全其中的 `linear_search`，未找到时返回 -1。
```

如果结果仍未说明重复元素，可以继续补充：

```text
保持现有函数签名；找到多个 target 时返回第一次出现的索引；只修改 `src/search.py`。
```

提示词工程关注“具体修改解决了什么问题”，Prompt 长度随任务需要调整。

### 3. Prompt 没有固定万能句式

高质量 Prompt 应让 Agent 能确定目标、相关输入、交付位置、禁止事项和验收方式，且各项要求互不冲突。不存在适用于所有工作区任务的固定句式。修改一个明确位置的拼写错误只需要目标文件和替换内容；跨文件同步接口与文档还要写明路径、兼容行为和验证范围。

简单任务示例：

```text
将 `README.md` 第一个标题中的 `Task Traker` 改为 `Task Tracker`，只修改这一处。
```

复杂任务示例：

```text
读取 `src/array.py`、`src/linked_list.py` 和 `src/stack.py`，
在 `docs/data-structures.md` 中新增 Markdown 表格，比较随机访问、头部插入和典型用途；
复杂度使用大 O 表示法。只修改目标文档，不改动源代码。
```

两条 Prompt 长度不同，原因在于任务需要的信息量不同。Prompt 的长度应服务于执行准确性。

## 二、Prompt 在编码 Agent 中的作用

### 1. Prompt 决定 Agent 如何理解任务

编码 Agent 会根据 Prompt 判断需要读取、创建、修改、移动或检查哪些文件。如果任务动词和目标路径不明确，Agent 可能采取与用户意图不同的操作。

示例：

```text
看看 `src/stack.py`。
```

“看看”没有说明要定位问题、补全实现、修改代码还是只汇报现状。

```text
读取 `src/stack.py`，检查 `Stack` 类的 `push` 和 `pop`。
只汇报两个方法的现有行为以及空栈调用 `pop` 时的结果，不修改文件。
```

第二条 Prompt 使用“读取”和“检查”作为明确动词，同时规定关注范围与只读边界。

### 2. Prompt 决定代码接口

只说“写一个函数”时，Agent 必须自行猜测目标文件、函数名、参数、返回值和类型。

模糊示例：

```text
给项目增加反转列表函数。
```

明确示例：

```text
读取 `src/list_utils.py`，在文件末尾新增：
`def reverse_list(nums: list[int]) -> list[int]`
返回新的逆序列表，不修改传入的 nums；保留文件中的其他代码和导入语句。
```

第二条 Prompt 明确了目标文件、语言、函数签名、数据行为和修改范围。

### 3. Prompt 决定边界行为

边界行为是指空输入、重复值、未找到等容易产生不同解释的情况。

示例：

```text
补全 `src/search.py` 中的 `linear_search(nums, target)`。
```

这条 Prompt 没有说明未找到和重复元素如何处理。

```text
读取 `src/search.py`，补全 `linear_search(nums, target)`。
保持现有签名；找到时返回 target 第一次出现的索引；未找到或 nums 为空时返回 -1。
只修改该函数。
```

第二条 Prompt 明确了两个关键边界行为。

*简单方法：先让 Agent 来找出边界情况，再让它根据这些情况修改函数。*

### 4. Prompt 决定交付形式

同一代码任务可以编辑现有文件、创建新文件或只给出检查报告。交付要求不同，Agent 对工作区采取的操作也会不同。

示例：

```text
只给出 `src/search.py` 的检查结论，不修改文件。
```

```text
直接修改 `src/search.py`，并在 `README.md` 中补充三组调用样例和复杂度说明；
完成后列出修改文件和主要变化。
```

用户应根据任务目的明确“只读检查”或“直接编辑”，并指定交付路径和汇报内容。

## 三、Prompt 的五个基本组成部分

可以用背景、目标、输入、输出和约束五项检查 Prompt。它们是查漏清单，不要求机械地写成五个标题；不会改变结果的项目可以省略。

### 1. 背景（Context）

背景说明工作区的项目环境。它可以包括语言版本、目录位置、已有功能、公开接口和与当前任务直接相关的约定。

示例：

```text
当前工作区是 Python 3.12 数据结构项目。
查找实现位于 `src/search.py`，公开函数已经被 `examples/` 中的脚本调用。
```

这段背景会影响 Agent 读取文件的位置、实现语言和接口兼容性。

无关背景示例：

```text
中山大学成立于100年前，课程一共有十八周，今天的天气很好，我们有三校区五校园……
```

如果这些信息不会影响本次文件修改，就不应加入当前 Prompt。

### 2. 目标（Goal）

目标说明最终要对工作区完成什么。常用明确动词包括读取、定位、补全、修改、创建、更新和检查。

清楚示例：

```text
补全 `src/search.py` 中的 `linear_search`，使其返回 target 第一次出现的索引。
```

模糊示例：

```text
把搜索功能弄好。
```
“弄好”没有说明目标文件、期望行为和修改范围，也无法判断任务是否完成。这样的 Prompt 会导致功能需要通过多次迭代才能完全符合预期。

### 3. 输入（Input）

输入是 Agent 完成任务时可以读取的工作区材料。它可以是文件路径、目录、现有代码、错误日志、配置文件或输入输出样例。文件已经存在于工作区时，直接给出路径可以减少 Agent 搜索范围和实现歧义。

参数示例：

```text
读取 `src/search.py` 和 `docs/search-contract.md`。
`docs/search-contract.md` 规定了参数、返回值和边界行为。
```

样例示例：

```text
输入：nums=[3, 1, 3]，target=3
期望：返回 0
```

准确路径和真实行为样例可以帮助 Agent 理解抽象规则中的细节，项目说明文档可以帮助 Agent 快速理解项目结构和约定。

### 4. 输出（Output）

输出说明 Agent 最终要创建或修改哪些文件，并可以进一步规定文件结构、保存位置和完成后的汇报内容。

示例：

```text
交付要求：
1. 在 `src/search.py` 中完成实现；
2. 在 `README.md` 中补充三组调用样例；
3. 在同一文档中说明时间复杂度和空间复杂度；
4. 完成后列出修改文件，不创建额外说明文件。
```

另一种示例：

```text
将说明写入 `docs/search.md`；只包含“接口”“样例”“复杂度”三个二级标题。
```
明确的输出要求可以减少由于 Agent 私自臆断产生的与用户预期不符的结果，得到更加令人满意的输出。

### 5. 约束（Constraints）

约束规定 Agent 修改工作区时必须遵守的边界。常见约束包括语言版本、禁止使用的函数、必须保持的接口、允许修改的文件和禁止创建的内容。

示例：

```text
- 使用 Python 3.12；
- 不使用 list.index()；
- 保持函数签名为 linear_search(nums, target)；
- 代码包含类型标注；
- 只修改 `src/search.py` 和 `README.md`；
- 不重命名或移动文件。
```

约束应具体并且互不冲突。

冲突示例：

```text
重构整个搜索模块，同时只允许修改 `linear_search` 函数体。
```

可以改为：

```text
只优化 `linear_search` 的实现，保持模块结构、函数签名和其他函数不变。
```

通过明确约束，可以禁止 Agent 进行不必要的修改，减少与用户预期不符的结果。

### 6. 五部分完整示例

```text
背景：当前工作区是 Python 3.12 数据结构项目，查找实现位于 `src/search.py`。

目标：读取并补全 `src/search.py` 中的 linear_search，返回 target 第一次出现的索引，未找到返回 -1。

输入：读取 `src/search.py`；nums 可能为空、包含重复值或负数，target 是整数。

输出：直接编辑 `src/search.py`，并在 `README.md` 中更新三组调用样例和复杂度说明；完成后汇报修改文件。

约束：保持现有函数签名；不使用 list.index() 或其他现成查找函数；只修改 `src/search.py` 和 `README.md`。
```

这个示例把五部分分别写成标题，适合初学者检查，熟练后使用自然语言写出一段完整 Prompt 即可。

合并示例：

```text
读取 Python 3.12 项目的 `src/search.py`，补全带类型标注的 `linear_search(nums, target)`。
nums 可能为空、重复或含负数；返回第一次匹配索引，未找到返回 -1；不得使用 `list.index()`。
直接编辑目标函数，并在 `README.md` 中更新三组调用样例和复杂度；完成后汇报修改文件。
```

## 四、Role Prompting

### 1. Role Prompting 的作用

Role Prompting[^4] 是为编码 Agent 指定与任务有关的角色。角色主要影响检查重点、专业标准、实现风格和维护要求。

[^4]: Role Prompting：给 Agent 设定任务角色。

示例：

```text
你是一名维护初学者教学项目的 Python 工程师。
读取 `src/stack.py`，补全缺失实现；保持代码直观、公开函数包含类型标注，
并保留现有接口和注释风格。只修改该文件。
```

这里的角色告诉 Agent 应按照教学代码的可读性标准实施修改。

### 2. 用角色限定关注重点

不同角色会关注同一材料的不同方面。

示例 A：

```text
你是一名 Python 维护工程师。读取 `src/cache.py`，只检查所用数据结构与复杂度并写入 `docs/cache-review.md`，不修改源代码。
```

示例 B：

```text
你是一名 Python 初学者教材编辑。读取 `docs/cache.md`，检查未定义术语并直接改写该文件，保留原有标题结构。
```

示例 A 生成独立检查文档，示例 B 直接修改现有教学文档。角色与目标路径共同限定工作结果。

### 3. 避免无效角色

无效角色通常只有夸张评价，没有增加任务信息。

无效示例：

```text
你是世界上最厉害、永远不会犯错的程序员，请写完美代码。
```

改进示例：

```text
你是一名维护初学者教学项目的 Python 工程师。
读取 `src/stack.py` 并补全缺失方法；使用 Python 3.12；保持公开接口；
只修改该文件，并在完成后说明变更位置。
```

角色不能代替工作区范围、目标文件、任务行为、交付位置和修改约束。

## 五、Few-shot Prompting

### 1. Few-shot Prompting 的作用

Few-shot Prompting[^5] 是向 Agent 指出工作区中的少量现有示例，或在 Prompt 中提供少量样例，使其理解文件格式、分类边界或表达风格。

[^5]: Few-shot Prompting：用少量示例说明预期写法。

示例：

```text
读取 `docs/complexity.md`，沿用其中的条目格式补充一行。

现有格式示例：
数组按索引访问 -> 按索引访问：O(1)
单链表按值查找 -> 按值查找：O(n)

新增内容：在无序数组中查找目标元素。只修改该文件。
```

Agent 可以根据文件中的现有条目生成格式一致的新内容。

### 2. 示例应当相关

示例与真实任务越接近，越能准确说明要求。

不相关示例：

```text
任务是更新 `CHANGELOG.md`，却只提供 README 的介绍段落作为格式示例。
```

相关示例：

```text
读取 `CHANGELOG.md`，按照文件中已有条目的格式追加一项。

示例：
修复纯空格用户名验证 -> fix(auth): reject whitespace-only usernames
增加搜索分类过滤 -> feat(search): add category filter

本次内容：修复订单金额舍入错误。只修改 `CHANGELOG.md`。
```

### 3. 示例应当多样

过于单一的示例可能让 Agent 把偶然特征误认为规则。

单一示例：

```text
1 -> odd
3 -> odd
5 -> odd
请在 `data/parity.txt` 末尾补充 8 的结果。
```

虽然任务可能是判断奇偶，但所有示例都只有奇数。更好的示例同时包含两类：

```text
1 -> odd
2 -> even
5 -> odd
8 -> even
请在 `data/parity.txt` 末尾补充 12 的结果。
```

### 4. 示例必须正确

Agent 会模仿现有示例中的错误，因此作为格式依据的内容必须先校对。

错误示例：

```text
单链表按值查找 -> O(1)
```

正确示例：

```text
单链表按值查找 -> O(n)
```

Few-shot 的价值建立在示例质量之上。

## 六、Step-by-step Prompting

### 1. Step-by-step Prompting 的作用

Step-by-step Prompting[^6] 使用编号或顺序要求组织 Agent 的可观察操作，适合需要依次读取、修改和核对文件的任务。

[^6]: Step-by-step Prompting：把任务按顺序分成几个步骤。

示例：

```text
请按以下顺序完成：
1. 读取 `src/queue.py` 和 `README.md`；
2. 确认 `Queue` 的现有接口；
3. 补全 `enqueue`、`dequeue` 和 `peek`；
4. 更新 `README.md` 中的使用示例与复杂度表；
5. 检查最终文件并汇报修改摘要。
```

这条 Prompt 能减少遗漏目标文件、接口核对或文档同步的情况。

### 2. 分步提示适合复杂输出

当任务包含多个文件操作时，分步提示可以明确顺序。

示例：

```text
请完成以下内容：
1. 读取 `src/array.py` 和 `src/linked_list.py`；
2. 确认两种结构的随机访问和头部插入复杂度；
3. 在 `docs/comparison.md` 中写明各自适用场景；
4. 在同一文件末尾用 Markdown 表格总结；不要修改源代码。
```

### 3. 简单任务不必强行分步

简单任务本身已经清楚时，加入大量步骤只会增加冗余。

冗余示例：

```text
第一步找到文件，第二步读取文件，第三步思考修改：把 `README.md` 中的 `Task Traker` 改为 `Task Tracker`。
```

简洁示例：

```text
将 `README.md` 中的 `Task Traker` 改为 `Task Tracker`，只修改这一处。
```

### 4. 分步提示不等于索要内部思维

分步提示应要求可观察的文件操作、检查步骤和交付结果，无需要求 Agent 展示冗长的内部思考过程。

推荐示例：

```text
先读取 `src/search.py`，再修改目标函数，最后汇报修改位置和行为变化。
```

不推荐示例：

```text
逐字展示你的全部内部思考过程，再修改文件。
```

用户真正需要的是可检查的文件变更、简洁的修改摘要和必要的验证结果。

## 七、输出格式控制

输出格式是 Prompt 中“输出”部分的进一步规定。对编码 Agent 而言，格式通常落实为工作区中的文件：Markdown 文档、JSON 数据文件、文档内表格或源代码文件。

只写“整理一下”或“结构化输出”仍然存在较大解释空间。更可靠的做法是同时写明：

1. 创建或修改哪个文件；
2. 使用哪一种格式；
3. 格式内部包含哪些字段、标题、列或代码块；
4. 内容按照什么顺序排列；
5. 允许读取和修改哪些其他文件；
6. 完成后如何汇报变更。

示例：

```text
读取 `pyproject.toml`、`src/` 目录和现有 `README.md`，直接更新根目录 `README.md`。
使用 Markdown 编写项目说明，
依次包含“项目简介”“环境要求”“安装步骤”“运行方法”四个二级标题，
命令放入带语言标记的代码块；不要修改其他文件。
```

这条 Prompt 同时规定了读取范围、目标文件、格式、章节、修改边界和代码呈现方式。

### 1. Markdown[^7]：组织供人阅读的内容

[^7]: Markdown：用简单符号排版标题、列表和代码的文本格式。

Markdown 是一种轻量级标记格式，适合编写 README、项目说明、安装指南、部署文档和 API[^9] 使用说明。它的核心价值是用标题、列表、引用和代码块建立清楚的阅读层级，让读者和 Agent 快速了解项目并完成安装、运行等操作。

[^9]: API（应用程序编程接口）：软件之间约定好的调用方式。

#### 1.1 指定标题层级

如果只要求“使用 Markdown”，Agent 仍然需要自行决定目标文件和章节结构。为了得到稳定结果，应直接给出读取路径、写入路径、标题名称和层级。

示例 Prompt：

```text
读取工作区中的 `pyproject.toml`、`src/` 目录和现有 `README.md`。
直接更新根目录 `README.md`，使用 Markdown，并依次包含以下二级标题：
## 项目简介
## 环境要求
## 安装步骤
## 运行方法
## 目录结构
不要增加其他同级标题；不得编造文件中没有依据的依赖、命令或目录；
无法确认的内容标记为“待补充”；不要修改其他文件。
```

预期结构：

````markdown
## 项目简介
Task Tracker 是一个使用 FastAPI 和 SQLite 构建的任务管理项目。

## 环境要求
- Python 3.12
- FastAPI
- SQLite

## 安装步骤
```bash
python -m venv .venv
pip install -r requirements.txt
```

## 运行方法
```bash
python -m app
```

## 目录结构
待补充。
````

#### 1.2 指定列表形式

列表适合步骤、条件、优缺点和检查项。Prompt 中应说明使用有序列表还是无序列表。

示例 Prompt：

```text
读取 `pyproject.toml` 和根目录 `README.md`，直接更新 README 中的“安装与启动”部分。
先用无序列表列出环境要求，再用有序列表列出安装步骤，
最后用无序列表列出启动前检查项；保留其他章节不变。
```

预期片段：

```markdown
- Python 3.12
- Git

1. 克隆项目仓库。
2. 创建并激活虚拟环境。
3. 安装 `requirements.txt` 中的依赖。
4. 执行项目启动命令。

- 已进入项目根目录。
- 依赖已经安装完成。
- 配置文件已经准备完成。
```

#### 1.3 指定代码块语言

Markdown 代码块可以带语言标记。语言标记有助于阅读器进行语法高亮，也能让代码边界更清楚。

示例 Prompt：

```text
读取 `pyproject.toml`、`.env.example` 和 `README.md`，直接更新 README 的“运行方法”部分。
Shell 命令放在标记为 bash 的 Markdown 代码块中；
环境变量示例放在标记为 dotenv 的代码块中；不得把 `.env` 中的真实值写入文档。
```

预期片段：

````markdown
```bash
uvicorn app.main:app --reload
```

```dotenv
DATABASE_URL=sqlite:///./task_tracker.db
```
````

#### 1.4 控制 Markdown 的篇幅和顺序

标题结构只能控制内容位置，不能自动限制篇幅。需要简洁答案时，应同时规定段落数、列表项数量或字数。

示例 Prompt：

```text
读取工作区中的配置文件、源码目录和现有 `README.md`，直接更新该文件。
先用不超过 100 字介绍项目，再列出环境要求；
安装步骤不超过 5 步；运行命令只保留一个 bash 代码块；
最后增加“常见问题”标题，并列出两个问题；保留已有许可证章节。
```

#### 1.5 Markdown 常见问题

常见问题包括目标路径缺失、标题层级混乱、章节顺序变化、命令没有放入代码块，以及 Agent 编造依赖、端口或部署方式。编写项目文档时，Prompt 还应说明读取范围、保留内容和缺失资料的处理方式。

含糊写法：

```text
帮我完善项目说明。
```

改进写法：

```text
读取工作区中的 `package.json`、目录结构和现有 `README.md`，直接更新根目录 `README.md`。
只包含“项目简介”“环境要求”“安装”“运行”“目录结构”五个二级标题；
命令放入 bash 代码块；不得编造未提供的依赖、端口或部署方式；
缺失信息标记为“待补充”；不要修改其他文件。
```

### 2. JSON[^8]：创建可由程序读取的结构化数据文件

[^8]: JSON：用键值和数组保存结构化数据的文本格式。

JSON 适合字段固定、需要由项目程序继续读取的数据文件，例如配置、清单和分析结果。JSON 由对象、数组、字符串、数字、布尔值和 `null` 组成。Prompt 应指定写入路径，并要求文件本身保持合法 JSON。

#### 2.1 明确字段名和数据类型

字段名决定程序从哪里读取数据，数据类型决定程序如何使用数据。Prompt 中应同时规定二者。

示例 Prompt：

```text
读取 `src/stack.py`，将结构摘要写入 `artifacts/stack-summary.json`。
目标文件必须是合法 JSON 对象，
字段定义如下：
- data_structure：字符串；
- operations：字符串数组；
- random_access：布尔值；
- typical_complexity：字符串。
```

预期文件内容：

```json
{
  "data_structure": "stack",
  "operations": ["push", "pop", "peek"],
  "random_access": false,
  "typical_complexity": "O(1)"
}
```

#### 2.2 明确输出对象还是数组

单个结果通常使用对象，多个同类结果通常使用对象数组。

单个对象示例：

```text
读取 `src/stack.py`，创建 `artifacts/stack.json`。
文件根节点使用一个 JSON 对象，包含栈的名称和主要用途。
```

```json
{
  "name": "stack",
  "purpose": "处理后进先出的数据"
}
```

对象数组示例：

```text
读取 `src/array.py`、`src/linked_list.py` 和 `src/stack.py`，创建 `artifacts/data-structures.json`。
文件根节点使用 JSON 数组，数组中每个对象描述一种数据结构。
每个对象包含 name 和 random_access 两个字段。
```

```json
[
  {"name": "array", "random_access": true},
  {"name": "linked_list", "random_access": false},
  {"name": "stack", "random_access": false}
]
```

#### 2.3 限定字段允许值

分类字段、状态字段和等级字段应列出允许值。这样可以减少同义词和拼写变化。

示例 Prompt：

```text
读取 `reports/latest-check.txt`，把结果写入 `artifacts/check-result.json`。
目标文件必须是合法 JSON。
字段 severity 只能取 "low"、"medium" 或 "high"；
字段 passed 必须是布尔值；不要使用其他取值。
```

预期文件内容：

```json
{
  "severity": "medium",
  "passed": false
}
```

#### 2.4 规定缺失值的处理方式

数据缺失时，Agent 可能省略字段、写空字符串、写 `null` 或自行猜测。程序需要稳定结构时，应提前规定处理方式。

示例 Prompt：

```text
读取 `docs/operations.md`，创建 `artifacts/operations.json`。
目标文件中的每个对象都必须包含 name、time_complexity 和 note。
无法确定 time_complexity 时写 null；没有补充说明时 note 写空字符串。
不要省略字段。
```

预期文件内容：

```json
{
  "name": "custom_operation",
  "time_complexity": null,
  "note": ""
}
```

#### 2.5 要求文件只包含 JSON 数据

程序直接解析文件时，JSON 前后的解释文字、Markdown 代码围栏和注释都可能造成解析失败。

示例 Prompt：

```text
创建 `artifacts/queue.json`，文件根节点为一个合法 JSON 对象。
文件中不要添加解释、标题、注释或 Markdown 代码围栏。
```

符合要求的文件内容：

```json
{"name":"queue","principle":"FIFO"}
```

不适合直接解析的文件内容：

````text
下面是结果：
```json
{"name":"queue","principle":"FIFO"}
```
````

#### 2.6 JSON 常见问题

常见问题包括目标路径不明确、使用单引号、添加尾随逗号、混入注释、字段类型不一致，以及在 JSON 数据外添加解释。

含糊写法：

```text
把检查结果整理一下。
```

改进写法：

```text
读取 `reports/search-check.txt`，创建 `artifacts/search-check.json`，文件根节点为合法 JSON 数组。
每个对象包含 name:string、search_complexity:string 和 stable:boolean；
三个字段都必须出现；目标文件中不要添加代码围栏或说明文字；不要修改输入文件。
```

如果暂时无法确定字段，可以先让 Agent 读取相关文件并只汇报建议的数据结构，确认后再要求它创建 JSON 文件。

### 3. 表格：比较多个对象的相同属性

表格适合横向比较、重复字段展示、方案评估和复杂度汇总。表格的每一行通常代表一个对象，每一列代表一个固定属性。

#### 3.1 明确比较对象和列名

如果只写“用表格比较”，Agent 仍然需要自行决定信息来源、目标文档和比较维度。Prompt 应明确读取文件、写入位置、行对象和列名。

示例 Prompt：

```text
读取 `src/array.py`、`src/linked_list.py` 和 `src/stack.py`，
在 `docs/data-structures.md` 的“结构比较”标题下写入 Markdown 表格。
每行对应一种数据结构；
列依次为“结构”“随机访问”“头部插入”“典型用途”；保留文档其他章节。
```

预期文档片段：

| 结构 | 随机访问 | 头部插入 | 典型用途 |
| --- | --- | --- | --- |
| 数组 | O(1) | O(n) | 按索引访问 |
| 单链表 | O(n) | O(1) | 频繁头部插入 |
| 栈 | 不支持 | O(1) | 后进先出处理 |

#### 3.2 统一单元格表达标准

同一列中的内容应采用相同标准。例如，复杂度统一使用大 O 表示法，布尔判断统一写“是/否”，缺失信息统一写“N/A”。

示例 Prompt：

```text
读取 `src/search.py`，在 `docs/search.md` 中更新三种查找方法的 Markdown 表格。
时间复杂度统一使用大 O 表示法；
是否要求有序统一写“是”或“否”；
无法确定的内容写“N/A”。
```

预期片段：

| 方法 | 最坏时间复杂度 | 要求有序 |
| --- | --- | --- |
| 线性查找 | O(n) | 否 |
| 二分查找 | O(log n) | 是 |
| 哈希查找 | O(n) | 否 |

#### 3.3 规定行顺序或排序规则

表格需要按性能、名称或优先级排列时，应明确排序字段和方向。

示例 Prompt：

```text
读取 `src/sort.py`，在 `docs/sort.md` 的“算法比较”标题下写入 Markdown 表格。
按照最坏时间复杂度从低到高排列；复杂度相同时按算法名称排序。
```

#### 3.4 控制单元格内容长度

单元格过长会降低表格可读性。需要简洁表格时，可以限制每格的字数或内容形式。

示例 Prompt：

```text
读取对应源文件，在 `docs/data-structures.md` 中用四列表格比较数组、链表和栈。
每个单元格最多 20 个汉字；典型用途只写一个短语；
表格后再用一段文字补充说明。
```

#### 3.5 表格的适用边界

对象数量少、字段固定时，表格最容易阅读。某个单元格需要多段解释或完整代码时，可以将详细内容移到表格后方。

示例 Prompt：

```text
读取三种数据结构的源文件，更新 `docs/data-structures.md`。
先用表格比较复杂度，表格中只保留结论；表格后分别用一个段落解释原因。
```

#### 3.6 表格常见问题

常见问题包括目标文档不明确、列名含糊、同一列使用不同标准、单元格内容过长，以及把无法横向比较的长篇内容强行放入表格。

含糊写法：

```text
做一个数据结构对比表并放到项目里。
```

改进写法：

```text
读取 `src/array.py` 和 `src/linked_list.py`，更新 `docs/data-structures.md` 中的现有 Markdown 表格。
列为“结构”“随机访问”“头部插入”“内存布局”“典型用途”；
复杂度统一使用大 O 表示法；每格只写一个结论；保留文档其他内容。
```

### 4. 代码：直接创建或修改项目源文件

编码 Agent 可以直接创建或修改函数、类、配置文件和脚本。为了让改动能够直接进入项目，Prompt 需要明确读取范围、目标路径、语言版本、接口、行为、依赖、边界条件和允许修改的部分。

#### 4.1 指定语言和版本

语言版本会影响语法、类型标注和标准库能力。

示例 Prompt：

```text
读取 `src/list_utils.py` 并直接修改该文件。
项目使用 Python 3.12；新增或修改的类型标注使用 `list[int]`，不使用旧式 `List[int]` 写法。
```

#### 4.2 固定函数或类接口

接口包括名称、参数、参数类型和返回类型。修改现有项目时，应要求 Agent 先读取目标文件，并保持已经被调用的接口不变。

示例 Prompt：

```text
读取 `src/search.py`，补全以下现有函数，保持函数名、参数和返回类型不变：
linear_search(nums: list[int], target: int) -> int
找到时返回第一次出现的索引，未找到时返回 -1。只修改该函数体。
```

预期代码：

```python
def linear_search(nums: list[int], target: int) -> int:
    for index, value in enumerate(nums):
        if value == target:
            return index
    return -1
```

*简单使用方法：如果不清楚现有函数，可以要求 Agent 先读取目标文件寻找相关函数，确认后再实施修改。*

#### 4.3 说明是否允许依赖

Agent 可能引入第三方库或使用现成函数。项目不允许额外依赖时，应写进约束。

示例 Prompt：

```text
修改 `src/search.py` 时只使用 Python 3.12 标准库。
不要安装或导入第三方包；不要使用 `list.index()`；不要修改依赖文件。
```

#### 4.4 规定修改范围

在已有代码基础上修改时，应说明哪些部分可以改变，哪些部分必须保留。

示例 Prompt：

```text
读取 `src/search.py`，只修改 `linear_search` 函数体。
保持文件中的函数签名、其他函数、导入语句和注释不变。
直接保存到原文件，完成后说明修改位置。
```

#### 4.5 规定代码与说明分别写到哪里

Agent 可能把实现只写在消息代码块中，或把说明混入源文件。Prompt 应明确代码写入源文件，说明和样例写入哪个文档。

示例 Prompt：

```text
直接修改 `src/search.py` 中的 `linear_search`。
在 `README.md` 的“查找示例”标题下加入一个标记为 python 的代码块，
再用两句话说明时间复杂度；不要在源文件中加入教程文字。
```

#### 4.6 指定创建完整文件或局部修改现有文件

新功能可以创建完整文件，维护任务通常应局部修改现有文件。Prompt 应明确目标路径以及是否允许创建新文件。

完整代码示例：

```text
创建 `examples/search_demo.py`，写入可以直接运行的完整 Python 文件，
包含必要的 import、函数定义和 main 示例；不要修改现有源文件。
```

局部代码示例：

```text
读取 `src/search.py`，只修改现有 `linear_search` 函数体，不创建新文件，不改动文件中的其他代码。
```

#### 4.7 同时要求样例和复杂度

代码能否使用还取决于边界行为和调用方式。要求样例可以帮助检查接口，要求复杂度可以帮助理解实现成本。

示例 Prompt：

```text
读取 `src/list_utils.py`，补全现有 `reverse_list(nums: list[int]) -> list[int]`。
返回新列表，不修改 nums。
在 `README.md` 中给出空列表、单元素列表和普通列表三个调用样例，
并说明时间复杂度和空间复杂度；只修改这两个文件。
```

预期代码：

```python
def reverse_list(nums: list[int]) -> list[int]:
    return nums[::-1]
```

预期样例：

```python
reverse_list([])          # []
reverse_list([7])         # [7]
reverse_list([1, 2, 3])   # [3, 2, 1]
```

#### 4.8 源代码修改常见问题

常见问题包括目标文件不明、语言版本不明、函数签名被改动、引入额外依赖、修改范围扩大、遗漏边界行为，以及只在消息中提供代码却没有编辑工作区文件。

含糊写法：

```text
给项目加一个反转列表函数，代码规范一点。
```

改进写法：

```text
读取 `src/list_utils.py`，在该文件中实现 `reverse_list(nums: list[int]) -> list[int]`。
返回新列表，不修改 nums；只使用标准库；
保持现有代码与导入语句；只修改目标函数；完成后说明修改位置和复杂度。
```

### 5. 四种格式的选择方法

选择格式时，先判断项目需要哪类文件，以及该文件的下一步用途。

| 主要问题 | 推荐格式 | 原因 | 示例场景 |
| --- | --- | --- | --- |
| 人需要连续阅读吗？ | Markdown | 支持标题、段落、列表和代码块 | README、项目说明 |
| 程序需要读取字段吗？ | JSON | 字段和类型便于解析 | 分类结果、接口数据 |
| 需要横向比较吗？ | 表格 | 相同属性可以按列对齐 | 复杂度、方案优缺点 |
| 项目需要直接执行吗？ | 代码 | 作为源文件或脚本进入工作区 | 函数、类、脚本 |

选择示例一：

```text
任务：读取项目配置与目录，并完成说明文档。
选择：Markdown，因为项目说明需要标题、列表、命令代码块和连续文字。
```

选择示例二：

```text
任务：读取错误报告并创建文件供项目程序继续分类。
选择：JSON，因为程序需要读取 severity、category 和 message 字段。
```

选择示例三：

```text
任务：读取三个实现文件，在 `docs/comparison.md` 中比较复杂度。
选择：表格，因为三个对象需要使用相同维度横向比较。
```

选择示例四：

```text
任务：补全现有查找函数。
选择：代码，因为实现需要直接保存在源文件中并保持准确接口。
```

### 6. 组合使用多种格式

一次文件任务可以组合多种格式，但每种格式应承担清楚的作用。常见组合包括：

- Markdown 标题组织说明，代码块展示使用命令；
- 表格呈现比较结果，段落解释原因；
- Markdown 说明使用方法，JSON 提供机器可读结果；
- 源代码文件承载实现，Markdown 表格汇总调用样例和复杂度。

组合示例：

```text
读取 `pyproject.toml`、`.env.example` 和现有 `README.md`，直接更新根目录 `README.md`：
1. 在“安装步骤”标题下用有序列表说明操作；
2. 在“运行方法”标题下放置一个 bash 代码块；
3. 在“配置项”标题下用表格列出变量名、是否必填和说明；
4. 缺失资料统一标记为“待补充”；不要修改其他文件。
```

组合格式的关键是明确目标文件、主格式和嵌入格式。上例以 `README.md` 为目标文件，以 Markdown 为主，内部嵌入代码块和表格。

### 7. *四种格式的可复用 Prompt 模板（可选阅读）

本节供希望进一步整理个人 Prompt 写法的读者选读。以下模板依据 OpenAI Codex、OpenAI Prompt Engineering 与 Claude Code 官方文档中的任务描述原则整理，可按具体工作区、目标文件和修改范围调整。

Markdown 模板：

```text
读取 [项目资料路径] 和现有 `[目标文档路径]`，直接更新该 Markdown 文件。
依次包含“项目简介”“环境要求”“安装步骤”“运行方法”“目录结构”；
安装步骤使用有序列表；命令放入 bash 代码块；
不得编造文件中没有依据的信息，缺失项标记为“待补充”；保留 [不可修改部分]。
```

JSON 模板：

```text
读取 [输入文件路径]，创建或更新 `[目标 JSON 路径]`。
目标文件根节点为合法 JSON [对象/数组]，文件中不要添加解释或代码围栏。
字段为：[字段名:数据类型]。
[字段] 只能取 [允许值]；缺失值统一写 [null/空字符串]；所有字段都必须出现。
```

表格模板：

```text
读取 [来源文件列表]，在 `[目标 Markdown 路径]` 的 [标题位置] 更新 Markdown 表格，比较 [对象列表]。
每行对应 [行对象]；列依次为 [列名列表]；
[某列] 统一使用 [表达标准]；缺失值写 [N/A]；按 [排序规则] 排列。
```

代码模板：

```text
读取 `[目标源文件路径]`，使用 [语言和版本] 实现或修改 [接口]。
行为要求：[正常情况和边界情况]。
依赖限制：[标准库/允许的包]；保持 [不可修改部分] 不变；
直接保存到目标文件；[样例/复杂度/说明] 写入 [文档路径或完成汇报]。
```

## 八、高质量 Prompt 的设计方法

### 第一步：确定主要目标

先写一句最核心的任务。

示例：

```text
补全二分查找功能。
```

目标尚未清楚时，不必急着加入角色、示例和复杂格式。

### 第二步：补充必要背景

背景应只包含会影响工作区修改的信息。

示例：

```text
当前工作区使用 Python 3.12；二分查找位于 `src/search.py`，现有接口不可改变。
```

这条背景决定了目标位置、语言版本和接口边界。

*思考：如果不说明二分查找的位置，会有什么不同？*

### 第三步：说明输入

对文件修改任务，应说明 Agent 要读取的路径、现有接口和关键行为。

示例：

```text
读取 `src/search.py` 和 `docs/search-contract.md`。
契约规定输入列表已经按升序排列，列表可能为空或包含重复值。
```

### 第四步：规定输出

说明 Agent 必须修改哪些文件，以及完成后如何汇报。

示例：

```text
直接补全 `src/search.py` 中的目标函数，并在 `README.md` 中更新三个调用样例和复杂度；完成后列出修改文件。
```

### 第五步：加入约束

约束用于排除不希望出现的方案。

示例：

```text
不使用递归；保持现有函数签名；只修改 `src/search.py` 和 `README.md`；不创建新文件。
```

### 第六步：按需加入 Role、Few-shot 或 Step-by-step

如果维护标准很重要，可以加角色；如果格式难以说明，可以指向现有示例；如果文件操作顺序重要，可以分步。

组合示例：

```text
你是一名维护初学者教学项目的 Python 工程师。请按以下顺序完成：
1. 读取 `src/search.py` 和 `README.md`；
2. 保持接口，使用迭代方式补全二分查找；
3. 在 README 中用表格说明最好、平均和最坏时间复杂度；
4. 只修改这两个文件，完成后汇报变更。
```

如果 Agent 已能从 Prompt 确定目标文件、目标行为、输出位置、禁止事项和验收方式，就不必同时使用全部技巧。

### 第七步：检查 Prompt 质量

发送前检查以下四项：

- **清楚**：Agent 能否确定读取范围、目标文件和期望行为？
- **相关**：每条信息是否影响当前结果？
- **具体**：抽象要求是否已经转化为明确要求？
- **一致**：不同要求之间是否冲突？

问题示例：

```text
重构整个搜索模块，但只允许修改 `linear_search` 的函数体。
```
如果使用这样的 Prompt，Agent 可能会尝试重构整个模块，导致修改范围超出预期，影响其他模块内容。

改进示例：

```text
只优化 `src/search.py` 中 `linear_search` 的实现，保持模块结构、接口和其他函数不变。
```

## 九、简单 UI 设计与 SVG 绘图的 Prompt 方法

### 1. 把“好看”改成可检查的界面要求

UI[^10] 设计也可以使用背景、目标、输入、输出和约束五部分。编码 Agent 要知道页面给谁使用、哪些信息最重要、各区域怎样排列，以及最终修改哪些文件。只写“设计得简洁、美观、现代”，仍然需要 Agent 自行猜测大量细节。

[^10]: UI 是用户在软件中看到和操作的界面，例如页面、按钮和输入框。

模糊示例：

```text
把栈演示页面做得好看一点。
```

可以把视觉要求拆成以下几类：

| 要说明的内容 | 可以写进 Prompt 的具体要求 |
| --- | --- |
| 使用者与目标 | 面向初学者，让人一眼找到当前栈顶和操作按钮 |
| 信息与布局 | 标题在上，栈图在左，数值输入与操作按钮在右 |
| 视觉层次 | 页面标题 24px，正文 16px，主要按钮使用深绿色 |
| 配色与间距 | 白色背景、深色文字，区域间距 24px，按钮间距 8px |
| 窄屏显示 | 页面宽度为 375px 时上下排列，文字和按钮不被裁切 |
| 界面状态 | 空栈显示提示，出栈按钮不可用；非空时明确标出栈顶 |
| 修改范围 | 沿用现有页面结构与依赖，只改指定页面和样式文件 |

这些数值是本例的设计选择，实际项目应优先沿用已有页面约定。OpenAI 的 [Frontend prompt instructions](https://developers.openai.com/api/docs/guides/frontend-prompt) 强调根据受众与应用用途设计界面，并保持现有设计的一致性；本文把这些建议转成便于初学者编写和检查的 Prompt 项目（访问日期：2026-10-14）。

### 2. 一个完整的简单 UI Prompt

下面假设示例工作区已经有 `web/stack.html`、`web/stack.css` 和 `web/stack.js`。它们用于说明文件任务的写法，使用时应替换为自己项目中的实际路径。

```text
背景：当前工作区有一个面向初学者的栈演示页面。
输入：读取 `web/stack.html`、`web/stack.css` 和 `web/stack.js`，
确认现有元素与操作逻辑。
目标：改善页面布局，让人容易看清栈顶、输入值和入栈/出栈按钮。

布局：标题在顶部；宽屏下栈图在左、操作区在右；
页面宽度为 375px 时改为上下排列，不出现横向滚动。
样式：白色背景、深色文字、深绿色主要按钮；
标题 24px、正文 16px，区域间距 24px，按钮间距 8px。
状态：保留空栈提示和出栈按钮的不可用状态，非空时清楚标出栈顶；
不能只用颜色区分栈顶，还要显示“栈顶”文字。

输出：直接修改 `web/stack.html` 和 `web/stack.css`；
完成后列出修改文件与已经检查的显示效果。
约束：保留现有元素标识和操作行为，不修改 `web/stack.js`，不新增依赖。
若状态显示需要修改脚本，先报告原因及需要调整的范围。
请在宽度 1280px 和 375px 下检查布局；
若当前环境无法预览页面，明确说明尚未验证的项目。
```

这条 Prompt 同时给出了使用目标、视觉要求、文件范围和完成条件。文件路径对应“输入与输出”，布局、字号、状态和保留行为对应“目标与约束”。本周只掌握这种表达方法，页面实现细节和浏览器工具的具体操作留待后续学习。

### 3. 用参考图说明风格，用具体反馈缩小修改

如果已有满意的页面，可以向 Agent 提供截图或相关文件，并指出要参考哪些部分，例如布局、配色或按钮大小。不要只写“完全照着做”，因为参考图中的文案和功能未必适合当前页面。

Anthropic 的 [Common workflows：Work with images](https://code.claude.com/docs/en/common-workflows#work-with-images) 介绍了在 Claude Code 中提供图片并据此讨论界面的方法（访问日期：2026-10-14）。其他产品的图片输入和预览能力需按当前界面确认；不能把“能够编辑文件”直接等同于“能够查看截图或自动预览网页”。

在支持图片输入的环境中，可以写：

```text
参考 `design/reference.png` 的左右分区、留白和按钮配色，
调整 `web/stack.html` 与 `web/stack.css`。
文案、栈元素和操作行为以当前项目为准；只参考图片的视觉安排。
```

观察结果后，反馈要指出位置、偏差和期望结果：

```text
375px 宽度下，入栈和出栈按钮挤在同一行，文字被截断。
只调整 `web/stack.css` 的窄屏布局，让两个按钮各占一行；
保留宽屏布局、配色和现有操作行为。完成后重新检查 375px 显示。
```

### 4. 通过 SVG 进行图形化绘制

SVG[^11] 可以把图形写成文本文件。对于队列示意图、简单流程箭头或几何插图，可以让编码 Agent 直接生成 `.svg` 文件，再在浏览器中查看效果；也可以指定修改某个形状、标签或颜色。

[^11]: SVG 是用文字描述形状、线条和文字、并能随尺寸缩放的图形格式。

编写绘图 Prompt 时，用日常语言说清楚想画什么、各部分怎样排列、需要哪些文字，再指定保存位置即可。初次尝试不必先规定画布尺寸、坐标、图形标签或其他制作细节，可以先看结果，再补充需要调整的地方。

示例：

```text
帮我画一张简单的队列示意图，保存为 `docs/images/queue.svg`。
用三个并排的方框表示 A、B、C，左边标“队首”，右边标“队尾”。
整体清楚易读，方便放进项目说明中。
```

如果结果中的文字太小，可以继续说：

```text
把图中的文字放大一些，方框之间留宽一点，其他内容保持不变。
```

重点是把想要的图形和看到的问题表达清楚，具体绘制细节交给 Agent 处理。SVG 的基本结构与常用写法放在选读中，需要时再查阅。

### 5. 用 SVG 绘制 UI 资源

制作界面时，可能需要按钮图标、空状态插图或简单装饰图形。可以让编码 Agent 用 SVG 绘制这些资源，保存到项目中，再放到对应的界面位置。提示词只需说明资源用在哪里、画什么，以及希望的风格。

例如，为栈演示页面绘制入栈和出栈图标：

```text
帮我用 SVG 画两个用于栈演示页面的按钮图标，
分别保存为 `web/images/push.svg` 和 `web/images/pop.svg`。
入栈图标画一个箭头指向栈内，出栈图标画一个箭头从栈内指向外面。
两个图标风格一致，线条简洁、使用深绿色、背景透明，
放在按钮文字旁边时也容易看清。
```

看到结果后，可以直接描述需要的调整：

```text
两个图标缩小后不容易区分。把箭头画得更明显一些，
保留相同的颜色和整体风格，只修改这两个 SVG 文件。
```

也可以为没有数据时的界面绘制一张小插图：

```text
用 SVG 画一张“栈目前为空”的小插图，保存为 `web/images/empty-stack.svg`。
画一个空的容器，风格简单、配色柔和、背景透明，适合放在栈演示区。
图片里不用写字，提示文字由页面显示。
```

资源确认后，再让 Agent 将它们用到页面中：

```text
把 `web/images/push.svg` 和 `web/images/pop.svg` 分别放到
`web/stack.html` 的“入栈”和“出栈”按钮文字旁边。
保留按钮文字和原来的点击功能，调整 `web/stack.css`，
让图标大小一致、与文字对齐。
```

检查时既要看资源本身是否清楚，也要看它在页面中的实际大小、位置和配色是否合适。图标负责传达操作含义，按钮的点击行为仍由原有页面逻辑负责。

### 6. UI 与 SVG Prompt 的检查重点

- 是否写清使用场景、主要信息与布局关系？
- “简洁”“醒目”等词是否有配色、间距或文字层次作为具体依据？
- 是否说明 SVG 资源用在什么位置，图标含义是否清楚、风格是否一致？
- 是否指定文件路径、修改范围和必须保留的行为？
- 是否检查窄屏显示、图中文字和图形含义，并如实记录未能预览的部分？

## 十、从模糊 Prompt 到高质量 Prompt

下面使用线性查找任务逐步展示改写过程。

### 1. 第一版：只有主题

```text
把搜索功能补好。
```

缺失内容包括工作区路径、目标文件、接口、边界行为和修改限制。

### 2. 第二版：加入目标

```text
读取 `src/search.py`，补全其中的 `linear_search(nums, target)`，未找到返回 -1。
```

这一版明确了目标文件、函数名和未找到行为，但没有说明重复元素、空列表和修改范围。

### 3. 第三版：加入输入与边界

```text
读取 `src/search.py`，使用 Python 3.12 补全 `linear_search(nums, target)`。
nums 可能为空、包含重复值或负数；target 是整数。
保持现有签名；找到时返回第一次出现的索引，未找到返回 -1。
```

这一版已经明确主要行为。

### 4. 第四版：加入输出与约束

```text
背景：当前工作区是 Python 3.12 数据结构项目，查找实现位于 `src/search.py`。

目标：读取并补全 `src/search.py` 中的 linear_search，返回 target 第一次出现的索引，未找到返回 -1。

输入：读取 `src/search.py`；nums 可能为空、包含重复值或负数，target 是整数。

输出：直接编辑 `src/search.py`；在 `README.md` 中更新三组调用样例和复杂度；完成后汇报修改文件。

约束：保持现有函数签名；不使用 `list.index()` 或其他现成查找函数；只修改 `src/search.py` 和 `README.md`。
```

第四版补齐了真正影响结果的信息，也省去了夸张角色。

### 5. 版本比较

| 版本 | 新增信息 | 解决的问题 |
| --- | --- | --- |
| 第一版 | 无 | 只能表达大致主题 |
| 第二版 | 目标文件、函数名、未找到行为 | 减少位置与接口猜测 |
| 第三版 | 输入与边界 | 明确重复、空列表和负数 |
| 第四版 | 交付文件与约束 | 控制修改范围和实现限制 |

改进 Prompt 的关键在于每次补充一个真正缺失的信息，字数随任务需要调整。

## 十一、常见 Prompt 问题与改进方法

### 1. 目标模糊

问题示例：

```text
优化一下链表。
```

改进示例：

```text
读取 `src/linked_list.py`，为现有整数单链表增加 `find(value)`，返回第一次匹配位置，未找到返回 -1；只修改该文件。
```

### 2. 背景不足

问题示例：

```text
处理一下搜索算法。
```

改进示例：

```text
读取 `src/search.py`，补全现有二分查找；使用 Python 3.12 和迭代实现，保持函数签名。
```

### 3. 输入不清

问题示例：

```text
整理工作区里的这些数据。
```

改进示例：

```text
读取 `data/search-cases.json`；该文件中的 nums 是升序整数列表，可能为空或含重复值。
```

### 4. 输出不清

问题示例：

```text
整理一下搜索说明。
```

改进示例：

```text
读取 `src/search.py`，在 `docs/search.md` 中更新“接口”“调用样例”“复杂度”三节；保留其他章节。
```

### 5. 约束缺失

问题示例：

```text
补全查找函数。
```

改进示例：

```text
读取 `src/search.py`，补全 `linear_search(nums, target)`；不使用 `list.index()`，保持现有函数签名，只修改函数体。
```

### 6. 信息过多

问题示例：在修改 `src/stack.py` 时加入整门课程安排、项目历史和无关错误日志。

改进示例：

```text
读取 `src/stack.py`，补全现有 `Stack` 类；保持接口和初学者友好的代码风格，只修改该文件。
```

只保留会改变本次文件任务的信息。

### 7. 要求冲突

问题示例：

```text
重构整个项目，同时只能修改一个函数。
```

改进示例：

```text
只优化 `src/search.py` 中的目标函数，保持行为、接口和其他文件不变。
```

### 8. 示例质量差

错误示例：

```text
单链表按值查找 -> O(1)
```

改进示例：

```text
单链表按值查找 -> O(n)
```

Agent 会模仿 Few-shot 或现有文件中的错误，因此示例必须先校对。

### 9. 技巧滥用

冗余示例：

```text
你是世界最强程序员。请分十步思考，并参考五个示例，把 `README.md` 中的一个拼写错误改正。
```

简洁示例：

```text
将 `README.md` 中的 `Task Traker` 改为 `Task Tracker`，只修改这一处。
```

简单任务不需要同时使用 Role、Few-shot 和 Step-by-step。

### 10. 输出格式含糊

问题示例：

```text
把数组和链表的差异整理到项目文档里。
```

改进示例：

```text
读取 `src/array.py` 和 `src/linked_list.py`，在 `docs/comparison.md` 中更新 Markdown 表格；
列为随机访问、头部插入、内存布局和典型用途，只修改该文档。
```

## 十二、如何根据文件变更改进 Prompt

### 1. 指出具体缺失

无效反馈：

```text
改得不对，再处理一下。
```

有效反馈：

```text
检查刚才对 `src/search.py` 的修改。
当前实现没有正确处理重复元素：找到多个 target 时应返回第一次出现的索引。
只修正该行为，保持函数签名、其他文件和已经正确的改动不变。
```

### 2. 保留已经正确的部分

如果代码接口和其他文件改动已经正确，只需修改发现的问题。

示例：

```text
保持 `src/search.py` 中的函数签名和现有实现不变。
只在 `README.md` 的调用样例中增加空列表返回 -1 的示例。
```

### 3. 一次解决一个主要问题

如果同时改变角色、输入、示例、格式和篇幅，就很难知道哪项修改产生效果。

示例记录：

| 版本 | 主要修改 | 观察到的变化 |
| --- | --- | --- |
| V1 | 初始 Prompt | 目标文件与返回值不明确 |
| V2 | 指定 `src/search.py`，明确未找到返回 -1 | 修改位置与未找到行为稳定 |
| V3 | 明确第一次出现并限制修改范围 | 重复元素行为稳定，改动更集中 |

### 4. 删除重复与无关内容

问题示例：

```text
不要使用 list.index()。必须不能使用 list.index()。
再次强调绝对不要用 list.index()。课程在周二上课。
```

改进示例：

```text
读取 `src/search.py`，修改目标函数时不使用 `list.index()`；只修改该函数体。
```

每条要求写一次；若同一约束在多处出现，合并到一个不与其他要求冲突的位置。与目标、输入、输出、约束或验收无关的信息应删除。

## 十三、Prompt 编写检查表

在把任务交给编码 Agent 前，可以用以下问题快速检查 Prompt。简单任务不必机械写出所有项目，但目标、范围和完成标准应当清楚。

### 1. 目标与输入

- [ ] 是否说明要解释、修改、创建还是审查？
- [ ] 是否指出真实的文件、代码、错误信息或其他输入？
- [ ] 是否写清希望得到的具体结果？

### 2. 范围与约束

- [ ] 是否明确允许修改的文件或功能范围？
- [ ] 是否说明必须保持不变的接口、格式或行为？
- [ ] 是否删除了重复、冲突和与任务无关的信息？

### 3. 输出与验收

- [ ] 是否说明需要的输出形式或文件结构？
- [ ] 是否给出可观察、可验证的完成条件？
- [ ] 是否要求 Agent 报告实际修改和验证结果？

### 4. 示例与步骤

- [ ] 示例是否与当前任务直接相关且不会引入冲突？
- [ ] 复杂任务是否拆成必要的步骤或阶段？
- [ ] 简单任务是否避免不必要的角色、示例和长篇步骤？

## 十四、本章总结

Prompt 是编码 Agent 在一次工作中接收的任务说明。Prompt Engineering 是根据实际文件变更设计和改进任务说明的方法。

简单界面与图形任务同样需要明确目标、输入、输出和约束：用布局、配色、状态说明 UI，用形状、文字和位置关系说明 SVG 绘图。SVG 的基础结构见后面的选读。

本章给出的 Prompt 设计样例仅供参考，在实际应用中可以根据自己的习惯结合本章中的基本原则进行调整。高质量 Prompt 的关键在于详细明确的指令和要求，避免模糊、冲突和无关信息。通过逐步改进 Prompt，可以让编码 Agent 更准确地理解任务，从而提高工作效率和代码质量。

## 十五、*Markdown 与 JSON 文件类型详解（可选阅读）

本节进一步介绍编码 Agent 经常创建和编辑的两类文本文件。Markdown 主要用于供人阅读的项目文档，JSON 主要用于供程序读取的结构化数据。使用编码 Agent 处理这两类文件时，应同时说明信息来源、目标路径、文件结构、允许修改的范围和完成后的检查要求。

### 1. Markdown 文件类型

#### 1.1 Markdown 文件是什么

Markdown 是使用纯文本标记表达标题、段落、列表、链接、图片、代码和表格的文件格式。常见扩展名为 `.md` 和 `.markdown`，软件项目中更常见 `.md`。

常见文件示例：

```text
README.md
CONTRIBUTING.md
CHANGELOG.md
docs/installation.md
docs/api.md
```

这些文件可以直接用文本编辑器打开，也可以由 GitHub、GitLab、代码编辑器和文档工具渲染成带有层级与样式的页面。

编码 Agent 示例：

```text
读取根目录中的 `pyproject.toml`、`src/` 目录和现有 `README.md`。
根据工作区中的真实信息更新 `README.md`，保留已有许可证章节；
不得编造依赖、启动命令或端口；不要修改其他文件。
```

#### 1.2 标题

Markdown 使用行首的 `#` 表示标题。`#` 的数量代表标题层级：

```markdown
# 项目名称
## 安装方法
### 创建虚拟环境
#### Windows
```

一个项目说明文档通常只使用一个一级标题，主要章节使用二级标题，章节内部的小主题使用三级标题。标题层级应连续，避免从二级标题直接跳到四级标题。

Prompt 示例：

```text
更新根目录 `README.md`。
项目名使用唯一的一级标题；
“项目简介”“环境要求”“安装方法”“运行方法”使用二级标题；
安装方法中的不同操作系统使用三级标题；
保留文档中已有的许可证章节。
```

#### 1.3 段落与换行

普通文字直接写成段落。两个段落之间通常保留一个空行：

```markdown
Task Tracker 是一个本地任务管理工具。

项目使用 FastAPI 提供 HTTP 接口，并使用 SQLite 保存数据。
```

连续文字中只按一次回车，在部分渲染器中仍可能显示为同一段。需要稳定分段时，应使用空行。

Prompt 示例：

```text
读取 `README.md`，整理“项目简介”部分。
将内容改为两个段落，每段只表达一个主题；
第一段说明项目用途，第二段说明主要技术；
保留后续章节不变。
```

#### 1.4 无序列表与有序列表

无序列表适合并列项目，常使用 `-`：

```markdown
- Python 3.12
- FastAPI
- SQLite
```

有序列表适合需要按顺序完成的步骤：

```markdown
1. 创建虚拟环境。
2. 安装项目依赖。
3. 启动开发服务器。
```

列表项存在从属关系时，可以使用缩进表示嵌套：

```markdown
- 支持的运行环境
  - macOS
  - Linux
  - Windows
```

Prompt 示例：

```text
更新 `README.md` 的“安装方法”章节。
环境要求使用无序列表，安装过程使用有序列表；
每个安装步骤只描述一个动作；
不要改动文档中的“运行方法”和“许可证”章节。
```

#### 1.5 行内代码与代码块

行内代码使用一对反引号包围，适合文件名、命令名、函数名和短代码：

```markdown
运行 `python -m app` 启动项目。
入口函数位于 `app/main.py`。
```

多行代码或命令使用围栏代码块。开头的语言标记可以启用语法高亮：

````markdown
```bash
python -m venv .venv
pip install -r requirements.txt
```

```python
from app import create_app

app = create_app()
```
````

常见语言标记包括 `bash`、`python`、`javascript`、`json`、`yaml` 和 `dotenv`。

Prompt 示例：

```text
读取 `pyproject.toml` 和现有 `README.md`，更新“安装与运行”章节。
Shell 命令放入标记为 bash 的代码块；
Python 调用示例放入标记为 python 的代码块；
行内出现的文件名和命令使用行内代码格式；
命令必须来自工作区文件，不得自行猜测。
```

#### 1.6 链接与图片

Markdown 链接的基本写法为：

```markdown
[FastAPI 官方文档](https://fastapi.tiangolo.com/)
```

图片的基本写法为：

```markdown
![应用首页](docs/images/home.png)
```

方括号中的文字用于说明链接或图片内容，圆括号中写地址。项目内部图片通常使用相对于当前 Markdown 文件的路径。移动 Markdown 文件后，相对路径也可能需要调整。

Prompt 示例：

```text
读取 `README.md` 和 `docs/images/` 目录。
在“界面预览”章节引用 `docs/images/home.png`；
使用相对路径，并将替代文字写为“Task Tracker 应用首页”；
先确认图片文件存在，再修改 README。
```

#### 1.7 引用与分隔线

引用使用 `>`，适合提示、说明或引用内容：

```markdown
> 首次运行前需要复制 `.env.example` 并完成本地配置。
```

分隔线可以使用三个连字符：

```markdown
---
```

分隔线适合区分较大的内容区域。章节结构已经清楚时，无需大量使用分隔线。

Prompt 示例：

```text
在 `README.md` 的安装步骤后增加一条引用形式的配置提示：
首次运行前需要根据 `.env.example` 创建本地配置。
不要增加新的标题或分隔线。
```

#### 1.8 表格

Markdown 表格由表头、分隔行和数据行组成：

```markdown
| 配置项 | 是否必填 | 说明 |
| --- | --- | --- |
| `DATABASE_URL` | 是 | 数据库连接地址 |
| `LOG_LEVEL` | 否 | 日志等级 |
```

每一列应使用统一的表达标准。例如，“是否必填”列统一写“是”或“否”，缺失内容统一写 `N/A`。

Prompt 示例：

```text
读取 `.env.example`，更新 `README.md` 中的“配置项”表格。
列依次为“变量名”“是否必填”“默认值”“说明”；
是否必填统一写“是”或“否”，没有默认值时写 `N/A`；
不得读取或写入 `.env` 中的真实值。
```

#### 1.9 转义与容易产生冲突的字符

Markdown 中的 `#`、`*`、`-`、`>`、反引号和竖线可能被解释为格式标记。需要显示字符本身时，可以在部分字符前使用反斜线：

```markdown
\# 这行显示普通井号
\* 这行显示普通星号
```

表格单元格内的竖线需要转义：

```markdown
| 表达式 | 含义 |
| --- | --- |
| `A \| B` | A 或 B |
```

Prompt 示例：

```text
检查 `docs/operators.md` 中的 Markdown 表格。
确保代码表达式 `A | B` 不会破坏表格列结构；
只修正需要转义的竖线，保留其他内容。
```

#### 1.10 一个完整的 README 文件示例

````markdown
# Task Tracker

Task Tracker 是一个使用 FastAPI 和 SQLite 构建的任务管理项目。

## 环境要求

- Python 3.12
- Git

## 安装方法

1. 创建虚拟环境。
2. 安装依赖。

```bash
python -m venv .venv
pip install -r requirements.txt
```

## 运行方法

```bash
python -m app
```

## 配置项

| 变量名 | 是否必填 | 说明 |
| --- | --- | --- |
| `DATABASE_URL` | 是 | 数据库连接地址 |

## 目录结构

```text
.
├── app/
├── docs/
├── pyproject.toml
└── README.md
```
````

生成此类文件的 Prompt 示例：

```text
读取 `pyproject.toml`、`.env.example`、`app/` 目录和现有 `README.md`。
直接更新根目录 `README.md`，依次包含项目简介、环境要求、安装方法、
运行方法、配置项和目录结构。
命令放入 bash 代码块，目录结构放入 text 代码块，配置项使用 Markdown 表格。
内容必须以工作区文件为依据；无法确认的信息标记为“待补充”；
保留原有许可证内容，不修改其他文件。完成后汇报修改的章节。
```

#### 1.11 Markdown 文件的检查方法

完成 Markdown 文件后，可以检查：

1. 文件路径和扩展名是否正确；
2. 一级标题是否只有一个；
3. 标题层级是否连续；
4. 列表缩进是否一致；
5. 围栏代码块是否成对闭合；
6. 代码块语言标记是否准确；
7. 表格列数是否一致；
8. 相对链接和图片路径是否存在；
9. 文档中的命令是否来自真实项目配置；
10. 是否保留了 Prompt 指定的原有章节。

检查 Prompt 示例：

```text
检查刚才修改的 `README.md`。
核对标题层级、代码围栏、表格列数、相对路径和命令准确性；
发现格式问题时直接修正，只修改 `README.md`；
完成后简要列出修正项。
```

### 2. JSON 文件类型

#### 2.1 JSON 文件是什么

JSON 是使用纯文本表示结构化数据的文件格式，常见扩展名为 `.json`。它经常用于配置、数据交换、清单、缓存和程序生成的结果。

常见文件示例：

```text
package.json
tsconfig.json
data/users.json
artifacts/report.json
config/development.json
```

JSON 文件通常由程序读取，因此语法、字段名和数据类型需要保持稳定。

编码 Agent 示例：

```text
读取 `reports/latest-check.txt`，创建 `artifacts/check-result.json`。
目标文件必须是合法 JSON；根节点使用对象；
只创建目标文件，不修改原始报告。
```

#### 2.2 JSON 的六种基本值

JSON 支持对象、数组、字符串、数字、布尔值和 `null`。

完整示例：

```json
{
  "project": "task-tracker",
  "version": 1,
  "active": true,
  "owner": null,
  "tags": ["python", "fastapi"],
  "runtime": {
    "python": "3.12",
    "port": 8000
  }
}
```

其中：

- `"project": "task-tracker"` 使用字符串；
- `"version": 1` 使用数字；
- `"active": true` 使用布尔值；
- `"owner": null` 表示当前没有值；
- `"tags"` 的值是数组；
- `"runtime"` 的值是对象。

Prompt 示例：

```text
读取 `pyproject.toml`，创建 `artifacts/project-summary.json`。
字段 `project` 和 `python` 使用字符串；
字段 `dependency_count` 使用整数；
字段 `has_dev_dependencies` 使用布尔值；
无法确认的字段值使用 null；所有字段都必须出现。
```

#### 2.3 对象

对象使用花括号包围，由键值对组成：

```json
{
  "name": "queue",
  "principle": "FIFO",
  "mutable": true
}
```

对象的键必须使用双引号。键和值之间使用冒号，相邻键值对之间使用逗号。对象适合表示一个具有多个属性的实体。

Prompt 示例：

```text
读取 `src/queue.py`，创建 `artifacts/queue.json`。
文件根节点使用对象，字段为 name:string、principle:string 和 mutable:boolean；
不要添加未要求的字段。
```

#### 2.4 数组

数组使用方括号包围，适合表示有顺序的一组值：

```json
[
  "array",
  "linked_list",
  "stack"
]
```

数组也可以包含多个对象：

```json
[
  {"name": "array", "random_access": true},
  {"name": "linked_list", "random_access": false}
]
```

同一数组中的对象通常应保持相同字段结构，便于程序逐项处理。

Prompt 示例：

```text
读取 `src/array.py`、`src/linked_list.py` 和 `src/stack.py`，
创建 `artifacts/data-structures.json`。
根节点使用数组；每个元素都是对象，并包含相同的
name:string、random_access:boolean 和 operations:string[] 字段。
```

#### 2.5 字符串

JSON 字符串必须使用双引号：

```json
{
  "status": "ready"
}
```

以下写法不符合标准 JSON：

```text
{'status': 'ready'}
```

字符串中的双引号、反斜线和换行需要转义：

```json
{
  "message": "程序返回 \"ready\"",
  "path": "C:\\projects\\task-tracker",
  "lines": "第一行\n第二行"
}
```

Prompt 示例：

```text
读取 `logs/summary.txt`，将摘要写入 `artifacts/summary.json`。
目标文件使用标准 JSON 双引号；
保留文本中的引号和换行含义，并使用合法 JSON 转义。
```

#### 2.6 数字

JSON 数字不带引号：

```json
{
  "port": 8000,
  "timeout": 2.5,
  "retry_count": 3
}
```

加上引号后，数据类型会变成字符串：

```json
{
  "port": "8000"
}
```

程序需要执行计算时，应明确字段使用数字类型。JSON 标准不支持 `NaN`、`Infinity` 或 `-Infinity`。

Prompt 示例：

```text
读取 `config/runtime.txt`，创建 `artifacts/runtime.json`。
port 和 retry_count 使用整数，timeout 使用数字；
无法解析为有效数字时写 null，不要写 NaN 或 Infinity。
```

#### 2.7 布尔值与 null

JSON 布尔值只能写成小写的 `true` 和 `false`，空值写成 `null`：

```json
{
  "enabled": true,
  "deprecated": false,
  "replacement": null
}
```

`True`、`False` 和 `None` 属于 Python 写法，不能直接写入标准 JSON。

Prompt 示例：

```text
读取 `reports/features.md`，创建 `artifacts/features.json`。
enabled 和 deprecated 必须使用 JSON 布尔值；
没有替代功能时 replacement 写 null；
所有对象必须包含这三个字段。
```

#### 2.8 嵌套结构

JSON 对象和数组可以相互嵌套：

```json
{
  "project": "task-tracker",
  "commands": {
    "install": ["python", "-m", "pip", "install", "-e", "."],
    "run": ["python", "-m", "app"]
  },
  "environments": [
    {"name": "development", "debug": true},
    {"name": "production", "debug": false}
  ]
}
```

嵌套层级过深会增加阅读和维护难度。可以优先使用满足程序需求的最小结构。

Prompt 示例：

```text
读取 `pyproject.toml` 和 `.env.example`，创建 `artifacts/project-config.json`。
根节点包含 project、commands 和 environments；
commands 使用对象，environments 使用对象数组；
嵌套结构最多三层，不得写入真实密钥或密码。
```

#### 2.9 字段命名与类型稳定性

字段命名应遵循项目约定。常见风格包括：

```json
{"project_name": "task-tracker"}
```

```json
{"projectName": "task-tracker"}
```

同一文件中应保持一种命名风格。供程序读取的字段还需要保持类型稳定。例如，`passed` 不应在一条记录中使用布尔值，在另一条记录中使用字符串 `"yes"`。

Prompt 示例：

```text
更新 `artifacts/check-results.json`。
沿用文件现有的 snake_case 字段命名；
每个对象必须包含 name:string、passed:boolean 和 message:string；
保持现有数组根节点，不改变已有字段类型。
```

#### 2.10 缺失值的处理

数据缺失时可以采用以下策略：

- 字段保留，值写 `null`；
- 字段保留，字符串值写 `""`；
- 字段保留，数组值写 `[]`；
- 明确允许省略可选字段。

不同策略会影响程序逻辑，Prompt 中应明确规定。

示例文件：

```json
{
  "name": "custom_operation",
  "time_complexity": null,
  "note": "",
  "examples": []
}
```

Prompt 示例：

```text
读取 `docs/operations.md`，创建 `artifacts/operations.json`。
每个对象都必须包含 name、time_complexity、note 和 examples；
无法确定复杂度时写 null，没有说明时写空字符串，
没有样例时写空数组；不要省略字段。
```

#### 2.11 JSON 不支持注释和尾随逗号

标准 JSON 不支持注释：

```text
{
  "port": 8000 // 开发端口
}
```

标准 JSON 也不允许最后一个字段后保留逗号：

```text
{
  "port": 8000,
}
```

需要说明字段含义时，可以在文档中解释，或在数据结构允许的情况下增加明确的说明字段。

Prompt 示例：

```text
检查 `config/app.json` 的 JSON 语法。
删除注释和尾随逗号，同时保持字段和值不变；
只修改该文件，完成后说明修正了哪些语法问题。
```

#### 2.12 一个完整的 JSON 文件示例

```json
{
  "project": {
    "name": "task-tracker",
    "language": "python",
    "version": "3.12"
  },
  "commands": {
    "install": "pip install -r requirements.txt",
    "run": "python -m app"
  },
  "features": [
    {
      "name": "create_task",
      "enabled": true
    },
    {
      "name": "export_report",
      "enabled": false
    }
  ],
  "notes": null
}
```

生成此类文件的 Prompt 示例：

```text
读取 `pyproject.toml`、项目入口文件和 `docs/features.md`，
创建 `artifacts/project-manifest.json`。
根节点必须包含 project、commands、features 和 notes；
project 与 commands 使用对象，features 使用对象数组；
enabled 使用布尔值，无法确认 notes 时写 null；
目标文件只包含合法 JSON，不添加注释或 Markdown 围栏；
不得修改任何输入文件。完成后汇报创建的文件路径。
```

#### 2.13 JSON 文件的检查方法

完成 JSON 文件后，可以检查：

1. 文件路径和扩展名是否正确；
2. 根节点是对象还是数组；
3. 键和字符串是否使用双引号；
4. 对象和数组是否正确闭合；
5. 相邻元素之间是否有逗号；
6. 最后一个元素后是否存在尾随逗号；
7. 文件中是否混入注释或 Markdown 围栏；
8. 必填字段是否全部存在；
9. 字段类型是否稳定；
10. 是否包含不应写入的密钥、密码或个人信息；
11. 文件内容是否能够被项目使用的 JSON 解析器读取。

检查 Prompt 示例：

```text
检查刚才创建的 `artifacts/project-manifest.json`。
确认文件是合法 JSON，必填字段齐全，字段类型符合要求，
且没有注释、尾随逗号、Markdown 围栏或敏感信息；
发现问题时直接修正目标文件，完成后简要汇报检查结果。
```

### 3. Markdown 与 JSON 的选择

| 判断问题 | 选择 Markdown | 选择 JSON |
| --- | --- | --- |
| 主要读取者 | 开发者、使用者、维护者 | 程序、脚本、接口 |
| 主要内容 | 连续说明、步骤、示例、表格 | 固定字段、对象、数组 |
| 常见文件 | `README.md`、`CHANGELOG.md` | `package.json`、数据清单 |
| 结构重点 | 标题层级与阅读顺序 | 字段名、类型与合法语法 |
| 允许说明文字 | 可以 | 只能作为合法字符串字段 |
| 常见检查 | 标题、链接、围栏、表格 | 解析、字段、类型、敏感信息 |

选择示例：

```text
任务一：编写面向项目使用者的安装指南。
选择：Markdown，目标文件为 `docs/installation.md`。

任务二：生成供部署脚本读取的环境清单。
选择：JSON，目标文件为 `artifacts/environments.json`。
```

同一任务也可以同时使用两种文件：

```text
读取 `pyproject.toml`、`.env.example` 和项目入口文件。
更新 `README.md` 中的安装与运行说明，供开发者阅读；
同时创建 `artifacts/runtime.json`，供启动脚本读取。
两个文件中的 Python 版本和启动命令必须保持一致；
不得写入真实环境变量值。完成后列出两个文件的主要内容。
```

## 十六、*SVG 文件与简单绘图（可选阅读）

### 1. 为什么编码 Agent 可以直接修改 SVG

SVG 的英文全称是 Scalable Vector Graphics，通常保存为 `.svg` 文件。它用文本描述图形，编码 Agent 可以像修改源代码一样修改其中的形状、坐标和文字。几何形状在放大时能保持清晰，但复杂图形并不一定比其他图片格式更小；本节主要用它表达简单示意图。

例如，可以让 Agent 把队列图中的矩形改宽、将某个节点改为绿色，或纠正箭头方向。相比只交付一张无法分别修改图形元素的图片，这种方式更便于继续调整。

### 2. 读懂一个最小示例

SVG 使用标签组织内容。最外层的 `svg` 包含绘图区域，里面依次放入形状和文字。`viewBox`[^12] 规定内部绘图范围，`width` 与 `height` 指定本例的显示尺寸；它们不是同一个概念。

[^12]: viewBox 是规定 SVG 内部坐标起点及绘图宽高的属性。

下面的示例画出左右排列的两个队列元素；可要求 Agent 将其保存到 `docs/images/queue-pair.svg`，再用浏览器打开。

```svg
<svg xmlns="http://www.w3.org/2000/svg"
     width="320" height="140" viewBox="0 0 320 140">
  <title>包含两个元素的队列</title>
  <desc>左侧 A 为队首，右侧 B 为队尾。</desc>
  <rect x="0" y="0" width="320" height="140" fill="white" />
  <rect x="40" y="30" width="100" height="60"
        fill="#dcfce7" stroke="#166534" stroke-width="2" />
  <rect x="180" y="30" width="100" height="60"
        fill="#dcfce7" stroke="#166534" stroke-width="2" />
  <g font-family="sans-serif" font-size="20" fill="#14532d"
     text-anchor="middle">
    <text x="90" y="67">A</text>
    <text x="230" y="67">B</text>
    <text x="90" y="120">队首</text>
    <text x="230" y="120">队尾</text>
  </g>
</svg>
```

可以先认出以下部分，无需背诵全部写法：

| 写法 | 本例中的作用 |
| --- | --- |
| `xmlns` | 为独立 SVG 文件声明它使用的图形格式 |
| `viewBox="0 0 320 140"` | 内部坐标从 0、0 开始，绘图范围宽 320、高 140 |
| `rect` | 绘制矩形；`x`、`y` 表示左上角位置，`width`、`height` 表示宽高 |
| `fill`、`stroke`、`stroke-width` | 分别指定填充颜色、边框颜色和边框粗细 |
| `text` | 在指定位置放置文字；`text-anchor="middle"` 让文字水平居中 |
| `g` | 将若干元素放在一组，让它们共用颜色、字号等设置 |
| `title`、`desc` | 提供图形名称与说明，不作为图中文字直接显示 |

默认坐标方向是向右增大、向下增大。这里的坐标值是内部绘图单位，不必在每个数字后加 `px`。单纯把显示尺寸改成 `640×280` 并保留相同的 `viewBox`，可以让同一图形按比例放大显示。

上述结构、描述标签和坐标含义依据 W3C 的 [SVG 文档结构](https://www.w3.org/TR/SVG/struct.html)与[坐标系统](https://www.w3.org/TR/SVG/coords.html)，矩形属性依据[基本形状](https://www.w3.org/TR/SVG/shapes.html)（访问日期均为 2026-10-14）。

### 3. 让 Agent 选择简单的图形元素

| 要表达的内容 | 可以在 Prompt 中指定的 SVG 元素 |
| --- | --- |
| 节点或方框 | `rect` 矩形 |
| 圆形节点 | `circle` 圆形 |
| 连接线 | `line` 直线 |
| 折线、简单箭头 | `polyline` 折线或 `polygon` 多边形 |
| 曲线或复杂轮廓 | `path` 路径 |
| 节点名称、方向说明 | `text` 文字 |

描述关系通常比逐个指定坐标更容易。可以先说“三个矩形水平等距排列”，再让 Agent 计算位置；只有位置必须精确时，才给出具体坐标。这里的元素只是帮助表达要求，不需要先学完整绘图语法才能使用 Agent。

### 4. 从自然语言生成、预览和局部调整

```text
读取 `docs/images/queue-pair.svg`。
保持画布、配色与字号，在 A 和 B 之间新增元素 C，
使图中顺序变为 A、C、B，三个矩形等大、水平等距。
必要时缩小矩形宽度，保持矩形之间至少 16 个绘图单位的间距；
保留 A 下方的“队首”和 B 下方的“队尾”，文字不得超出画布。
只修改该 SVG；完成后说明调整了哪些元素。
```

预览后发现问题，可以进一步写：

```text
中间元素 C 的文字偏左。只修正它的文字横坐标与水平对齐设置，
让文字中心与所在矩形中心一致，保留其他元素的位置和样式。
```

要让 SVG 出现在项目文档中，还可以写：

```text
在 `docs/queue.md` 的“队列示意图”小节引用 `images/queue-pair.svg`，
添加图片说明“左侧为队首，右侧为队尾”；只修改该文档。
```

这里的相对路径从 `docs/queue.md` 所在目录计算。SVG 能在浏览器打开，不代表所有文档查看器都支持相同显示方式，需在实际使用的查看器中检查。

### 5. 完成后的检查

- 目标文件是否为 `.svg`，文件内是否只包含 SVG 内容而没有消息说明或代码围栏？
- 标签是否闭合，独立文件是否声明 `xmlns`，绘图范围是否合理？
- 图形、文字是否完整显示，标签与颜色是否对应正确含义？
- 放大和缩小后，文字是否仍可读，边框和箭头是否清楚？
- 文档引用路径是否正确，实际查看器是否能显示？
- Agent 是否区分已经预览的结果与仅检查文本、尚未预览的部分？
