# 第三周：需求分析与任务拆解

## 本章导读

第二周学习了如何把一次 Prompt 写清楚。本周继续解决一个更靠前的问题：面对“加一个登录功能”“导出坏了”“把搜索做快一点”这样的自然语言需求，究竟应该让编码 Agent 做什么？

未经整理的自然语言需求常会省略用户场景、当前行为、边界条件、项目影响范围或完成证据。只要其中一项会改变实现，Agent 就不能用未标注的推断补齐。代码即使能够运行，也可能解决了错误的问题。

本章学习路线如下：

```text
识别任务类型
→ 还原用户场景与开发目标
→ 区分事实、推断和待确认事项
→ 整理功能、非功能、约束与验收标准
→ 识别项目影响范围
→ 拆分任务并安排优先级
→ 形成可审查的开发计划
```

本周聚焦需求分析和任务计划。其中，影响范围[^1]用于说明一个需求可能涉及哪些模块、接口、数据和测试。完整代码实现、项目级上下文组织、代码库系统阅读、Plan–Act–Observe、工具权限、测试驱动和代码审查将在后续周次分别展开。

[^1]: 影响范围：一项需求可能涉及的文件、模块、数据、配置和测试。

## 一、从模糊需求到明确任务

### 1. 为什么不能从一句需求直接开始编码

#### 1.1 自然语言会省略工程细节

用户说：

```text
给系统加一个登录功能。
```

这句话至少留下了以下选择：

- 使用账号密码、短信验证码，还是第三方身份提供商；
- 用户来自已有用户表，还是首次登录时自动创建；
- 登录成功后跳转到哪里；
- 会话保存在 Cookie、服务端存储还是其他位置；
- 哪些页面需要保护；
- 登录失败、账号停用和用户取消授权时如何处理；
- 是否需要退出、续期、账号绑定和审计记录。

这些选择会改变数据模型、路由、页面、配置、安全规则和测试。Agent 若没有证据仍直接选择其中一种，就是把推断当成了需求。

#### 1.2 从“能生成代码”走向“理解正确”

编码 Agent 可以迅速生成完整文件，需求是否理解正确仍需单独验证。常见偏差包括：

- 用户要求修复，Agent 却重写整个模块；
- 用户要求解释，Agent 却直接修改文件；
- 用户要求规划，Agent 却先安装依赖；
- 用户要求登录，Agent 自行选择 OAuth[^2] 提供商；
- 用户要求“更快”，Agent 未测量就增加缓存；
- 用户要求停用账号，Agent 实现成永久删除。

[^2]: OAuth：让应用在不获取用户密码时得到有限访问权限的授权方式。

需求分析的价值，是在修改成本还很低时发现这些偏差。

#### 1.3 需求分析的可交付结果

一份可进入任务拆解的需求分析必须回答：

1. 用户或业务最终想得到什么结果；
2. 当前已经确认了什么；
3. 哪些内容只是暂时推断；
4. 哪些问题必须由人决定；
5. 哪些系统部分可能受影响；
6. 工作应按什么顺序展开；
7. 如何证明每项工作和整体目标完成。

因此，“先分析”需要生成可执行、可检查的中间产物。

### 2. 用任务动词确定 Agent 的工作边界

#### 2.1 任务动词为什么重要

第二周已经学习目标要使用明确动词。在编码 Agent 场景中，动词还决定是否允许改变项目状态。

| 任务动词 | 核心问题 | 典型交付物 | 默认是否修改代码 |
| --- | --- | --- | --- |
| 解释 | 现有内容如何工作 | 原理、调用关系、示例 | 否 |
| 诊断 | 问题为什么发生 | 复现、证据、根因或候选原因 | 否 |
| 规划 | 为达到目标需要做什么 | 影响范围、步骤、风险、待确认事项 | 否 |
| 实现 | 如何增加已定义行为 | 代码、配置、测试与说明 | 是 |
| 修复 | 如何消除已确认缺陷 | 最小修复、回归验证 | 是 |
| 审查 | 现有变更有什么问题 | 按严重性排列的发现与证据 | 否 |

“看看”“处理一下”“把它弄好”没有清楚指定以上任何一种任务。

#### 2.2 区分解释与实现

模糊 Prompt：

```text
看看登录模块。
```

明确 Prompt：

```text
解释当前登录请求从页面到会话创建的流程。
列出涉及的模块及各自职责，不修改文件。
```

解释任务以读者能够理解现状为完成标准，仓库应保持不变。

#### 2.3 区分诊断与修复

```text
诊断用户会话过期后首次登录失败的问题。
先复现并定位原因，报告实际行为、证据和影响范围；暂时不要修改代码。
```

诊断要求找原因。只有当用户进一步授权修复，或原任务明确包含“诊断并修复”，Agent 才进入修改阶段。

#### 2.4 区分规划与执行

```text
为增加 Google OAuth 制定计划。
先读取现有认证与会话实现，列出需要改变的文件、步骤、依赖、风险和待确认事项，不修改源文件。
```

OpenAI 和 Claude Code 的官方指导都建议复杂、跨文件或方案不确定的任务先调查和规划。计划必须基于当前项目，内容应体现真实入口、模块关系和约束。

#### 2.5 实现与修复的区别

实现通常增加此前不存在的行为：

```text
实现管理员停用账号功能，按已批准的计划完成后端、页面和相关测试。
```

修复通常恢复已经约定却失效的行为：

```text
修复导出页面提示成功但没有下载文件的问题，保持现有 CSV 格式和接口不变。
```

修复需要实际行为、期望行为和复现条件；否则 Agent 可能连“缺陷是什么”都无法确认。

#### 2.6 区分审查与重写

```text
审查当前分支的登录回调变更。
重点检查开放重定向、账号绑定错误和错误处理。
只报告可操作问题，不修改代码。
```

审查任务应说明审查对象、关注点和输出方式。本周只学习如何把审查定义为一种任务，第九周再系统学习 Diff Review 和严重级别。

#### 2.7 复合任务要写清阶段

```text
先诊断导出失败的根因并报告证据。
如果根因可以由仓库和本地复现确认，再进行最小修复并运行相关检查；
如果需要改变导出格式或权限规则，先停止并列出待确认问题。
```

这类 Prompt 明确了阶段顺序和转入下一阶段的条件，避免 Agent 在尚未理解问题时直接修改。

### 3. 从自然语言需求还原用户场景

#### 3.1 用六个问题补全场景

可以从以下六个问题开始：

| 问题 | 作用 | 登录示例 |
| --- | --- | --- |
| 谁 | 确定使用者与权限 | 未登录访客 |
| 在哪里 | 确定入口和环境 | Web 端个人页 |
| 何时 | 确定前置状态 | 会话已过期时 |
| 做什么 | 确定用户动作 | 点击“登录” |
| 期望什么 | 确定可观察结果 | 完成登录并返回原页面 |
| 失败时怎样 | 确定异常行为 | 显示可理解提示，不创建会话 |

六个问题是一份检查清单。实际分析应聚焦会改变系统行为的关键信息。

#### 3.2 把愿望改写成场景

原始需求：

```text
导出功能坏了。
```

场景化描述：

```text
管理员在订单列表选择日期范围并点击“导出 CSV”。
页面提示导出成功，但 Chrome 与 Edge 都没有开始下载。
该问题在包含 50 条订单的测试账号中可以稳定复现。
期望浏览器下载包含当前筛选结果的 UTF-8 CSV，现有列名和顺序保持不变。
```

这段描述补充了角色、入口、操作、实际行为、期望行为、复现条件和兼容约束。

#### 3.3 不要用技术方案替代用户结果

```text
使用 Redis 优化搜索。
```

如果 Redis 已经是确定的架构约束，这可以是实施要求；如果用户只是想让搜索更快，它就过早锁定了方案。

更合适的目标是：

```text
在 10 万条测试数据下，将商品搜索接口 P95 从 1.8 秒降至 500 ms 以内；
结果内容和排序保持不变。先定位查询、序列化和网络各阶段耗时，再提出方案。
```

这里的序列化[^9]是指把程序内部数据转换为接口响应或传输格式的过程。

[^9]: 序列化：把程序里的数据转成便于保存或传输的格式。

目标描述结果，方案则应在理解现状后选择。

## 二、形成可验证的需求

### 1. 把需求整理成四类信息

#### 1.1 功能需求[^3]

[^3]: 功能需求：系统必须提供的功能或行为。

功能需求描述系统必须提供的行为。

```text
用户可以使用学校统一身份账号登录。
登录成功后返回发起登录前的站内页面。
管理员可以停用账号。
订单可以按当前筛选条件导出为 CSV。
```

功能需求应包含可观察的输入、动作或结果，而不只是“支持认证”“完成导出”等主题词。

#### 1.2 非功能需求[^4]

[^4]: 非功能需求：对性能、安全、可靠性等质量的要求。

非功能需求描述行为需要达到的质量属性，例如：

- 性能；
- 安全；
- 可靠性；
- 兼容性；
- 可用性；
- 可维护性。

```text
登录回调不得将用户重定向到站外地址。
十万条数据下搜索接口 P95 小于 500 ms。
导出的文件应能被常见表格软件正确读取。
认证提供商短暂不可用时，页面应给出可恢复提示。
```

“要快”“要安全”“体验要好”无法直接验收。只要这些要求影响交付判断，就要改写为指标、规则或可观察结果；暂时无法量化的内容应标为待确认。

#### 1.3 约束

约束说明实现不能突破的边界。

```text
- 不改变现有密码登录接口；
- 不新增未经批准的第三方依赖；
- 保持现有用户主键和公开 API 稳定；
- 密钥不得写入仓库；
- 本次只支持 Web 端，不包含移动端。
```

其中，公开 API[^5] 稳定表示已有调用方依赖的接口行为不能在未说明的情况下改变。

[^5]: API（应用程序编程接口）：软件之间约定好的调用方式。

约束可以来自用户、项目规范、法律政策或既有兼容承诺。无法证明来源时，应写明“待确认”，不能把自己的偏好写成项目规则。

#### 1.4 验收标准[^6]

[^6]: 验收标准：判断需求是否完成的具体条件。

验收标准描述怎样判断需求已经完成。

```text
Given 用户从 /orders/42 发起登录
When 用户在身份提供商完成授权
Then 系统建立有效会话并返回 /orders/42
```

还应覆盖失败和边界场景：

```text
- 用户取消授权时不创建本地会话；
- 回调 state 不匹配时拒绝请求；
- 非站内 redirect 参数不能生效；
- 已停用账号不能建立新会话；
- 原有密码登录行为保持不变。
```

验收标准关注可观察结果。具体采用哪一种测试工具属于后续实现计划。

#### 1.5 四类信息不能混写

| 句子 | 正确分类 | 原因 |
| --- | --- | --- |
| 用户可用学校账号登录 | 功能需求 | 描述系统行为 |
| 登录回调 2 秒内完成 | 非功能需求 | 描述性能质量 |
| 不修改已有用户主键 | 约束 | 限定实现边界 |
| 取消授权后不创建会话 | 验收标准 | 描述完成证据 |

同一句话可能同时提供多类线索，但分析记录应拆开，以便分别检查。

### 2. 把开发目标写成可验证结果

#### 2.1 目标包含四个部分

一条清楚的开发目标通常包含：

```text
对象 + 行为 + 范围 + 完成状态
```

示例：

```text
修复用户搜索接口把空字符串当作“返回全部用户”的行为；
空字符串和纯空格输入都应返回 400；
正常关键词的结果与排序保持不变；
相关回归场景能够稳定验证。
```

#### 2.2 区分目标与任务清单

目标回答“最终要达到什么状态”；任务清单回答“按什么步骤达到”。

目标：

```text
管理员可以停用违规账号，停用立即阻止该账号继续访问受保护资源。
```

任务：

```text
确认会话撤销策略、调整用户状态、增加管理接口、更新页面、补充验证。
```

如果一开始就把目标写成文件修改列表，可能漏掉真正的用户结果。

#### 2.3 用范围外事项防止任务膨胀

```text
本次范围内：Google OAuth 登录、回调、现有账号绑定与错误提示。
本次范围外：其他提供商、移动端深链、账号合并后台、重新设计密码登录。
```

范围外事项用于控制本次交付边界，避免任务不断吸收相邻需求。

## 三、用证据处理不确定性

### 1. 区分已知事实、推断和待确认事项

#### 1.1 已知事实必须有来源

已知事实可以来自：

- 用户明确说明；
- 项目代码、配置或测试；
- 可复现的运行结果；
- 已批准的设计文档或接口契约；
- 权威外部规范。

示例：

```text
事实：项目已有 GET /auth/callback 路由。
证据：路由定义和对应接口测试。
```

“看起来应该有”缺少事实依据。

#### 1.2 推断要写出依据与置信度

```text
推断：新登录流程可能继续复用现有服务端会话。
依据：当前密码登录和退出流程都调用同一个 session service。
影响：若改用纯 Token 方案，页面中间件和退出逻辑都需重新评估。
```

这里的 session[^7] 表示系统为连续请求保存的登录状态。

[^7]: Session（会话）：用来保存用户连续请求状态的信息。

推断可以帮助分析，前提是明确标记。团队随后可以验证、修正或接受它。

#### 1.3 待确认事项必须会改变方案

```text
待确认：首次通过学校账号登录时，是自动创建用户，还是仅允许绑定已有账号？
```

两种选择会改变用户模型、账号绑定、安全风险和错误提示，因此必须由产品或业务决定。

#### 1.4 可查证问题不要全部抛给用户

低效提问：

```text
认证代码在哪里？项目使用什么测试框架？配置文件叫什么？
```

这些通常能从仓库获得，Agent 应先搜索。需要用户确认的问题具有两个特征：仓库无法证明，并且不同答案会实质改变产品行为或风险边界。

#### 1.5 使用三栏记录

| 已确认事实 | 合理推断 | 必须确认 |
| --- | --- | --- |
| 已有密码登录与服务端会话 | OAuth 可复用现有会话创建服务 | 首次登录是否自动开户 |
| 用户表 email 唯一 | 可用 email 尝试关联账号 | 是否允许仅凭 email 自动绑定 |
| 登录后支持站内 redirect | OAuth 也需保留返回位置 | 未登录时默认返回页 |

注意：email 唯一并不能自动证明“相同 email 就可以安全绑定身份”。这仍是需要身份策略与安全评估的产品决定。

### 2. 提出高价值澄清问题

#### 2.1 先判断是否真的需要问

提出问题前依次检查：

1. 需求文本是否已经回答；
2. 仓库、测试或文档是否能证明；
3. 是否存在安全、法律或业务默认规则；
4. 不同答案是否会改变交付结果；
5. 能否先完成不依赖该答案的只读分析。

只有关键未知项才应打断用户。

#### 2.2 问题要附带选择影响

普通问题：

```text
停用账号后会话怎么办？
```

高价值问题：

```text
停用账号后，可以立即使全部既有会话失效，也可以只阻止新登录并等待旧会话自然过期。
前者安全性更高，但需要现有会话存储支持按用户撤销；后者改动较小，但停用不会立即生效。
请确认期望行为。
```

提问应帮助决策者理解取舍；仓库调查仍由 Agent 先行完成。

#### 2.3 按阻塞程度排序

| 级别 | 判断 | 处理方式 |
| --- | --- | --- |
| 阻塞 | 不回答就无法确定核心行为 | 实现前必须确认 |
| 重要 | 影响部分方案，但可先调查 | 先完成不依赖部分，再确认 |
| 可延后 | 不影响当前最小交付 | 记录到后续事项 |

例如“选哪一家 OAuth 提供商”通常是阻塞项；按钮文案可能是重要或可延后项，取决于设计规范是否已经存在。

#### 2.4 不要提出伪问题

```text
是否需要高质量代码？
是否需要考虑安全？
```

这类问题没有形成可选择的行为，也不能帮助规划。应改成具体问题，例如“是否允许首次登录自动创建账号”或“回调失败后是否返回原页面”。

## 四、从影响范围到有序任务

### 1. 识别项目影响范围

#### 1.1 从用户入口与证据开始追踪

典型影响链：

```text
页面或调用方
→ 路由或控制器
→ 业务服务
→ 数据模型与存储
→ 外部服务
→ 配置与部署环境
→ 测试、日志与文档
```

OpenAI 的 Codex 实践建议在理解代码时定位核心逻辑、模块关系和数据流。文件名只能提供候选，真实影响范围需要引用调用、导入、路由、数据或测试证据。

#### 1.2 检查入口

入口可能是：

- 页面按钮；
- HTTP API；
- CLI[^8] 命令；
- 定时任务；
- 消息队列事件；
- 外部服务回调。

[^8]: CLI（命令行界面）：通过终端命令操作程序的界面。

OAuth 至少有“发起授权”和“接收回调”两个入口；只找到登录按钮仍不足以覆盖完整流程。

#### 1.3 同时看上游和下游

修改公共服务时：

- 下游：它调用哪些数据库、外部 API 和工具；
- 上游：哪些页面、路由、任务或其他服务调用它；
- 横向：哪些测试、类型、文档和监控依赖其行为。

只看实现文件，容易遗漏调用方兼容性。

#### 1.4 建立影响范围表

| 文件或符号 | 当前职责 | 受影响原因 | 证据 | 计划中的处理 |
| --- | --- | --- | --- | --- |
| 登录页面 | 发起登录 | 增加入口 | 现有页面路由 | 修改 |
| 认证回调路由 | 接收提供商响应 | 新增回调行为 | 路由注册 | 新增或修改 |
| 会话服务 | 建立本地会话 | 登录成功后复用 | 当前密码登录调用 | 复用 |
| 用户模型 | 保存身份关联 | 需要 provider subject | 模型字段缺失 | 待确认 |
| 环境配置 | 保存 client id/secret | 外部身份配置 | 配置加载方式 | 修改 |
| 认证测试 | 验证成功和失败路径 | 行为变化 | 现有测试目录 | 扩展 |

“可能有 `oauth.ts`”缺少证据。若尚未拿到真实仓库，应记录“待调查的组件”，避免虚构文件路径。

#### 1.5 区分确定影响与候选影响

```text
确定影响：登录入口、回调处理、会话创建。
候选影响：用户表迁移、账号绑定页面、审计日志。
确认方法：检查现有 identity 字段、绑定流程和日志规范。
```

影响范围分析需要逐步收集证据，并把候选项连同确认方法写清楚。

### 2. 从影响范围生成任务清单

#### 2.1 每项任务需要哪些字段

建议至少包含：

- 任务目标；
- 影响文件或组件；
- 前置依赖；
- 预期结果；
- 验证方式；
- 主要风险；
- 待确认事项。

#### 2.2 低质量任务清单

```text
1. 做后端
2. 做前端
3. 测试
```

问题在于：任务没有行为、依赖和完成证据，“后端完成”也无法独立判断。

#### 2.3 改进后的任务清单

```text
1. 确认 OAuth 提供商、账号创建/绑定规则和登录后返回行为。
2. 读取现有登录、会话、用户模型与配置加载方式，形成影响范围表。
3. 定义授权发起与回调的接口行为、失败响应和安全约束。
4. 增加身份关联数据能力，保持现有用户主键和密码登录兼容。
5. 接入授权入口与回调，并复用现有会话创建流程。
6. 更新登录页面和错误提示。
7. 验证成功、取消、state 异常、停用账号和非法 redirect 场景。
8. 更新配置说明和运维文档，检查是否还有遗漏调用方。
```

每一项都应进一步绑定真实文件和验证方式。

#### 2.4 任务描述模板

```text
任务：定义 OAuth 回调行为
目标：把授权结果转换为本地身份与会话结果
影响范围：回调路由、身份服务、错误页面
前置依赖：已确认账号绑定规则
预期结果：成功、取消和异常响应均有明确行为
验证方式：接口示例或相关自动化场景
主要风险：错误账号绑定、CSRF、开放重定向
待确认：首次登录是否自动创建用户
```

#### 2.5 先拆交付物，再拆技术动作

优先按“可以独立说明价值和完成状态”的交付物拆分，例如“回调行为”“账号关联”“页面入口”。函数级修改通常属于任务内部步骤。

### 3. 判断任务粒度

#### 3.1 任务过粗的表现

- 需要跨越多个独立目标；
- 涉及大量不相关文件；
- 中途失败无法判断完成到哪里；
- 没有单一验证方式；
- 描述只能写成“完成某模块”。

#### 3.2 任务过细的表现

- 每个变量或函数都成为一项任务；
- 单项没有独立用户或工程价值；
- 大量步骤共享同一个验证；
- 清单很长，却看不出业务目标。

#### 3.3 合适粒度的判断问题

对每项任务检查：

1. 是否只有一个主要目的；
2. 是否能指出明确输入和结果；
3. 是否能单独验证；
4. 失败时能否清楚定位；
5. 是否仍保留与整体目标的关系；
6. 是否小到可以安全审查和调整。

任务粒度没有固定行数。OpenAI 的实践建议给 Agent 范围清楚的工作单元；Claude Code 也指出，小到一句话能说明变更的任务不一定需要专门规划，而跨文件、方案不确定或陌生代码更适合先规划。

### 4. 安排依赖与优先级

#### 4.1 依赖优先

如果任务 B 必须使用任务 A 的输出，就先完成 A。

```text
账号绑定规则
→ 数据模型与接口契约
→ 回调实现
→ 页面与测试
```

在账号规则未定时先做页面，往往会造成返工。

#### 4.2 高风险未知项尽早验证

例如：

- 身份提供商是否提供稳定且唯一的用户标识；
- 现有会话存储是否支持按用户撤销；
- 数据迁移是否会破坏旧账号；
- 第三方接口是否满足回调和环境要求。

这些问题一旦答案为“否”，可能改变整体方案，因此应先调查或做最小验证。

#### 4.3 再考虑用户价值和成本

在依赖和风险得到控制后，再比较：

- 哪项最早产生可用价值；
- 哪项可以独立交付；
- 哪项实现或验证成本较低；
- 哪项会阻塞其他团队。

优先级需要在 P0、P1、P2 等标签之外解释排序依据。

#### 4.4 区分“重要”与“紧急”

紧急 Bug 仍需最小需求分析：实际行为、期望行为、影响用户、复现方式和不能破坏的行为。时间紧张时也必须确认核心需求。

## 五、综合案例：从需求层次到开发计划

### 1. 复杂需求的五层模型

#### 1.1 五层结构

```text
业务目标
→ 用户场景
→ 功能行为
→ 技术任务
→ 验收证据
```

#### 1.2 “管理员停用账号”示例

| 层次 | 内容 |
| --- | --- |
| 业务目标 | 阻止违规账号继续访问受保护资源 |
| 用户场景 | 管理员在用户详情页执行停用并确认 |
| 功能行为 | 状态改变；新请求被拒绝；重复操作有明确结果 |
| 技术任务 | 状态规则、权限接口、会话失效、页面提示、审计记录 |
| 验收证据 | 正常停用、越权、重复停用、旧会话和审计场景 |

如果从业务目标直接跳到某个数据库字段，容易遗漏用户行为和验收结果。

#### 1.3 检查上下层是否一致

```text
业务目标：临时阻止访问
技术任务：永久删除用户和全部数据
```

业务目标是“减少注册流失”，技术任务却只有“升级依赖”，两者之间没有可验证的因果或功能连接。任务计划应能反向解释每项技术工作服务于哪一个功能行为和业务目标。

### 2. 完整案例：规划 Google OAuth 登录

#### 2.1 原始需求

```text
给网站加 Google 登录。
```

#### 2.2 第一轮：确定任务类型

当前信息不足以安全实现，因此先定义为规划任务：

```text
请先分析并规划 Google OAuth 登录，不修改代码。
读取现有认证、用户、会话、配置和测试实现；
区分事实、推断和待确认事项；
列出影响文件、依赖、风险和验收场景。
```

这与 Claude Code 官方最佳实践中的 OAuth 示例一致：先阅读认证与会话实现，再询问哪些文件需要改变以及会话如何流转。

#### 2.3 第二轮：记录事实、推断和待确认

```text
已确认事实：
- 项目已有账号密码登录；
- 登录成功后统一调用 session service；
- 用户 email 在当前数据模型中唯一；
- 登录页支持站内 redirect 参数。

合理推断：
- OAuth 成功后可能复用现有 session service；
- 登录页可能保留密码登录并增加第二入口。

必须确认：
- 首次登录是否自动创建用户；
- 是否允许按相同 email 自动绑定已有账号；
- 是否仅允许特定组织域账号；
- 用户取消授权时返回哪里；
- 本次是否包含解绑与账号合并。
```

注意：示例事实只有在真实仓库能证明时才成立。课堂练习中应要求 Agent引用真实文件或测试。

#### 2.4 第三轮：需求分类

```text
功能需求：
- 用户可从登录页发起 Google 登录；
- 授权成功后建立本地会话并返回原站内页面；
- 取消或失败时不建立会话并显示明确提示。

非功能需求：
- 登录回调只接受预期流程产生的响应；
- 外部服务失败不能泄露密钥或底层异常；
- 原有密码登录行为不退化。

约束：
- client secret 不进入仓库；
- 使用项目现有配置加载方式；
- 不在本次加入其他提供商。

验收标准：
- 成功、取消、state 异常、非法 redirect、停用账号均有明确结果；
- 相关认证检查通过；
- 配置说明包含本地环境所需变量。
```

OAuth 的具体安全机制应遵循相应协议与身份提供商文档。需求分析阶段至少应把 state/nonce、PKCE、重定向 URI、身份关联和密钥处理列为必须确认或验证的安全条件，Agent 不得自行发明规则。

#### 2.5 第四轮：影响范围

```text
登录页面
→ OAuth 发起路由
→ 提供商授权端点
→ 回调路由
→ 身份验证与账号关联
→ 本地会话创建
→ 登录后重定向

横向影响：
用户模型 | 配置 | 错误页面 | 日志 | 测试 | 部署说明
```

#### 2.6 第五轮：按依赖形成计划

| 顺序 | 任务 | 前置条件 | 完成证据 | 主要风险 |
| ---: | --- | --- | --- | --- |
| 1 | 确认开户、绑定、域限制和范围外事项 | 产品决定 | 决策记录 | 账号归属错误 |
| 2 | 追踪现有登录与会话流 | 可读仓库 | 真实文件与调用关系 | 遗漏调用方 |
| 3 | 定义授权与回调契约 | 1、2 | 成功/失败行为表 | CSRF、开放重定向 |
| 4 | 确定身份数据设计 | 1、3 | 字段与兼容策略 | 重复或错误绑定 |
| 5 | 接入后端流程 | 3、4 | 回调可建立现有会话 | 密钥、异常泄露 |
| 6 | 更新页面与提示 | 3、5 | 各状态可观察 | 用户困惑 |
| 7 | 完成验收与说明 | 5、6 | 场景结果与配置文档 | 环境差异 |

这份计划没有假装知道真实文件名。拿到项目后，应把组件名替换为可核验的文件与符号。

### 3. 完整案例：从“导出坏了”到修复计划

#### 3.1 先形成最小问题描述

```text
实际行为：页面提示成功，但浏览器未下载文件。
期望行为：下载当前筛选结果对应的 CSV。
复现条件：管理员、指定日期范围、Chrome 与 Edge、稳定复现。
保持不变：列名、列顺序、权限和筛选语义。
```

#### 3.2 不要未经证据锁定根因

以下都是候选原因：

- 点击事件未发出请求；
- 请求失败但页面错误地显示成功；
- 响应头或响应体不符合下载要求；
- 前端没有把响应转换为下载；
- 权限或筛选条件导致空结果；
- 浏览器兼容行为不同。

诊断前不能直接写“后端响应头错误”。

#### 3.3 诊断与修复计划

```text
1. 按给定步骤复现并记录页面、网络请求和服务端结果。
2. 找到点击入口、请求封装、导出接口和响应生成位置。
3. 根据证据把问题定位到未发请求、错误响应或下载处理。
4. 记录根因与受影响范围；若需要改变文件格式或权限，先确认。
5. 实施保持接口与 CSV 结构稳定的最小修复。
6. 用原复现步骤和相邻场景验证结果。
```

这里提到验证是为了定义完成证据；测试驱动和工具执行将在第七、八周深入学习。

## 六、分析检查、模板与常见问题

### 1. *需求分析与任务规划 Prompt 模板（选读）

本节提供三份可直接改写使用的 Prompt 模板，供课后练习或实际项目参考，不作为课堂必讲与核心考核内容。使用模板时仍需根据真实需求和项目证据调整，不能直接照搬。

#### 1.1 通用只读分析模板

```text
请暂时不要修改代码。

任务：分析以下需求并形成可审查的开发计划。

请完成：
1. 判断任务属于解释、诊断、规划、实现、修复还是审查；
2. 将原始需求改写为用户场景和可验证目标；
3. 区分功能需求、非功能需求、约束和验收标准；
4. 分开列出已确认事实、合理推断和必须确认的问题；
5. 从入口追踪影响范围，引用真实文件、符号或其他证据；
6. 生成按依赖与风险排序的任务清单；
7. 为每项任务写明影响范围、前置条件、完成证据和主要风险；
8. 列出明确的范围外事项。

规则：
- 能从仓库或现有文档确认的内容先自行查找；
- 无法证明的结论标记为“推断”或“待确认”；
- 不虚构文件、接口、命令或项目规则；
- 若关键产品决定缺失，说明各选项影响后再提问。
```

#### 1.2 Bug 诊断模板

```text
请先诊断，不修改代码。

实际行为：……
期望行为：……
复现步骤：……
已知环境：……
必须保持：……

请复述问题，检查能否复现，列出证据支持的根因或候选原因，
追踪受影响入口与调用关系，并给出最小修复计划和验证方式。
如果现有信息不足，请区分可自行调查的问题和必须向我确认的问题。
```

#### 1.3 计划质量检查模板

```text
审查这份计划，不执行它。

检查：
- 每项任务是否服务于明确需求；
- 是否把推断写成事实；
- 是否遗漏入口、调用方、数据、配置、测试或文档；
- 顺序是否符合依赖和风险；
- 每项任务是否能独立验证；
- 是否存在范围膨胀、过粗或过细任务；
- 是否仍有会改变方案的未决问题。

按“问题—影响—改进建议”输出。
```

### 2. 常见问题与改进方法

#### 2.1 动词与交付物不一致

```text
问题：要求“解释”，结尾又写“直接完成修改”。
改进：拆成解释现状与批准后实现两个阶段。
```

#### 2.2 把方案当作需求

```text
问题：“用 Redis 让搜索更快”。
改进：先写性能基线、目标、不能改变的结果，再评估方案。
```

#### 2.3 把推断写成事实

```text
问题：看到 email 唯一就认定可自动绑定 OAuth 账号。
改进：记录为候选策略，并确认身份归属和安全规则。
```

#### 2.4 所有问题都询问用户

```text
问题：询问测试目录和认证入口在哪里。
改进：先搜索仓库，只把产品决定和无法证明的风险边界交给用户。
```

#### 2.5 影响范围只列相似文件名

```text
问题：根据名字猜测 auth.ts、user.ts。
改进：从入口追踪路由、调用、数据和测试证据；无仓库时写组件类别。
```

#### 2.6 任务清单只有技术名词

```text
问题：数据库、后端、前端、测试。
改进：写出每项行为、前置依赖、预期结果和完成证据。
```

#### 2.7 粒度过细或过粗

```text
过粗：“完成 OAuth。”
过细：“创建变量 providerName。”
合适：“实现回调中的身份验证与本地会话创建，并覆盖明确失败行为。”
```

#### 2.8 计划没有顺序理由

```text
问题：按想到的顺序列出任务。
改进：先处理阻塞决定和高风险未知，再按依赖安排实现与验收。
```

#### 2.9 验收标准只有“测试通过”

```text
问题：没有说明哪种用户行为需要通过。
改进：先列成功、失败、边界和兼容行为，再绑定相应验证方式。
```

#### 2.10 需求分析无限扩张

```text
问题：增加一个登录提供商演变成重写全部认证架构。
改进：明确本次范围、范围外事项和必须保持的公开行为。
```

### 3. 需求分析与任务拆解检查表

#### 3.1 任务边界

- [ ] 是否明确任务属于解释、诊断、规划、实现、修复还是审查？
- [ ] 交付物、修改权限和范围外事项是否清楚？
- [ ] 是否避免把未经确认的方案直接当作需求？

#### 3.2 需求与验收

- [ ] 是否写清用户场景、实际行为和期望结果？
- [ ] 功能需求、非功能需求和约束是否分开？
- [ ] 成功、失败、边界和兼容行为是否可以验证？

#### 3.3 事实与问题

- [ ] 已确认事实是否有文件、运行结果或文档证据？
- [ ] 推断是否明确标记，没有被写成事实？
- [ ] 能从仓库确认的问题是否先自行查找？
- [ ] 必须由用户决定的问题是否说明了不同选择的影响？

#### 3.4 影响范围与任务拆解

- [ ] 是否从真实入口追踪调用、数据、配置、测试和文档？
- [ ] 每项任务是否有单一目的、前置依赖和完成证据？
- [ ] 任务顺序是否优先处理阻塞决定和高风险未知？
- [ ] 粒度是否既能独立验证，又保留完整业务目标？

## 七、本章总结

需求分析把模糊愿望转化为开发者和 Agent 都能执行、检查和讨论的共同理解。

首先，用任务动词确定工作边界：解释、诊断、规划、实现、修复和审查有不同交付物，也有不同修改权限。其次，把自然语言还原为用户场景、功能需求、非功能需求、约束与验收标准。然后，把已知事实、合理推断和必须确认的问题分开，避免 Agent 替用户做产品决定。

影响范围应从真实入口沿调用、数据和外部依赖追踪，并补充配置、测试、日志和文档。任务拆解则要兼顾单一目的、依赖关系、风险、完成证据和整体业务目标。复杂任务先处理阻塞决定与高风险未知，再进入实现。

本章核心可以概括为：

```text
先确定要 Agent 做哪一种工作，
再确定用户真正要什么结果；
事实要有证据，推断要有标签，
问题要说明影响，任务要能够验收。
```
