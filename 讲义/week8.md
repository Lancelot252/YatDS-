# 第八周：测试驱动的 Agent 开发

## 本章导读

Agent 可以快速生成代码，也可以快速生成错误代码。测试把期望行为转化为可以重复执行的证据。

测试不仅放在开发最后。它可以帮助复现问题、限定修改范围、判断修复结果和防止旧问题再次出现。

本章只讨论编码 Agent 怎样设计、运行、解释和交付测试证据。第七周已经学习工具调用，第九周再把测试与 Git、PR 和代码审查组合起来。

### 测试在 Agent 开发中的作用

```text
自然语言需求
-> 可观察行为
-> 测试
-> 代码修改
-> 运行结果
-> 验收证据
```

测试提供反馈，但只能覆盖已经写入的预期。视觉体验、未知安全问题和需求本身的合理性还需要其他检查。

## 一、TDD 工作循环

Test Driven Development[^1]（TDD）的基本循环是 Red–Green–Refactor[^2]。

[^1]: Test Driven Development：先用测试表达期望行为，再编写实现使测试通过的开发方法。
[^2]: Red–Green–Refactor：先确认测试失败，再做最小修复，最后在测试保护下整理代码的循环。

### 1. Red

先写测试，并确认它因目标缺陷失败。

如果失败来自导入错误、fixture[^3] 缺失或错误预期，就不能证明目标 Bug 被捕获。

### 2. Green

做使目标测试通过的最小修改。Green 阶段不适合顺便重写整个模块。

### 3. Refactor

在测试保持绿色的条件下改善命名、重复和结构，不改变外部行为。

### 4. Repeat

一次循环只推进一个行为。该行为的失败测试已转绿、相关测试未回归且 diff 只包含本轮目标后，再加入下一个边界，避免一次生成大量测试和实现，最后无法判断哪一步引入错误。

### 5. 每一步需要什么证据

| 阶段 | Agent 应提供的真实证据 | 不能接受的替代说法 |
| --- | --- | --- |
| Red | 测试命令、收集数量、失败断言[^4]、期望与实际 | “这个测试应该会失败” |
| Green | 最小修改、目标与相关测试结果 | “代码看起来正确” |
| Refactor | 结构变化和再次运行的测试结果 | “只是重构，不用测试” |
| Repeat | 下一条行为及其依据 | 无依据地批量生成用例 |

[^3]: Fixture：为测试准备数据或环境，并在结束后负责清理的可复用设置。
[^4]: 断言：在测试中比较实际结果与期望结果，不满足时让测试失败的语句。

### 6. 完整案例：纯空格用户名注册

Bug：纯空格用户名可以注册。

本案例先添加回归测试[^5]捕获原问题，再用参数化[^6]覆盖遵循同一规则的其他边界。

```text
1. 运行现有测试建立基线
2. 添加纯空格用户名回归测试
3. 确认旧实现因业务断言失败
4. 在用户名验证处做最小修改
5. 运行新增和相关测试
6. 参数化补充其他边界
7. 检查完整测试和 diff
8. 仅在测试保持绿色且重复逻辑妨碍理解时整理结构
```

[^5]: 回归测试：用于确认已经修复的问题不会再次出现的测试。
[^6]: 参数化：让同一测试使用多组输入分别运行的方法。

Agent 在执行前还要确认当前分支或工作区已有修改，避免测试和修复覆盖用户内容。完整测试不可运行时，要记录缺少的服务、依赖或环境，以及这会留下什么未验证风险。

#### 一轮合格的结果记录

Lint[^7]结果也要与测试结果分开记录。

```text
基线：注册模块 24 passed。
Red：新增测试 1 failed；期望 400，实际 201。
修改：只调整用户名空白判断。
Green：新增与注册模块测试 29 passed。
完整检查：186 passed，2 skipped；lint 通过。
差异：生产代码 1 个文件、测试 1 个文件，无依赖变化。
```

[^7]: Lint：按规则检查代码中常见错误和不规范写法的静态工具。

## 二、Agent 生成与设计测试

生成测试前应提供：

- 被测接口；
- 业务规则；
- 输入与输出；
- 边界情况；
- 测试框架；
- 现有 fixture；
- 项目命名与目录规范。

生成后需要审查：

- 测试能否在错误实现上失败；
- 断言是否表达业务行为；
- 预期值是否独立推导；
- mock[^8] 是否过多；
- 测试是否相互污染；
- 异常与清理是否正确。

[^8]: Mock：用可控制的替身代替真实依赖的测试方法。

### 1. 先给规则，再让 Agent 生成

```text
业务规则：用户名去除首尾空格后不能为空。
保持行为：正常用户名仍可注册；重复用户名仍返回 DUPLICATE_USER。
测试框架：pytest；复用 tests/conftest.py 的 client fixture。
范围：注册接口及其验证函数。
不要连接生产数据库，不新增依赖。
```

如果“前后空格应自动去除还是直接拒绝”没有正式规则，Agent 应把它列为待确认项，而不是在测试中替产品做决定。

### 2. 生成后先审查测试，再修改生产代码

重点检查测试是否进入真实目标路径、测试名称是否描述行为、输入与期望是否独立、失败信息是否可定位，以及是否复用了项目现有清理方式。测试文件同样属于生成代码，不能因位于 `tests/` 就降低审查标准。

### 3. 单元测试

单元测试[^9]验证单个规则或函数。

[^9]: 单元测试：把范围限制在一个较小代码单元上的测试。

```python
def test_rejects_whitespace_only_username():
    assert validate_username("   ") is False
```

单元测试速度快、定位清楚，适合 TDD 的快速反馈。

常见问题是只验证实现细节，或者用 mock 代替真正需要验证的规则。

Agent 应优先断言公开结果，而不是内部函数被调用几次。内部结构变化但外部行为不变时，过度依赖实现细节的测试会制造无意义失败。

### 4. 接口测试

接口测试[^10]从公开接口观察行为，例如 HTTP 请求、状态码、响应字段和认证。

[^10]: 接口测试：通过程序公开入口检查请求与响应约定的测试。

```python
def test_register_rejects_whitespace_username(client):
    response = client.post("/users/register", json={"username": "   "})
    assert response.status_code == 400
    assert response.json()["code"] == "INVALID_USERNAME"
```

它可以发现路由解析、错误映射和序列化问题。

接口测试要同时检查成功和失败契约。只断言状态码可能漏掉错误码或响应结构变化；只断言响应字段又可能漏掉错误状态。

### 5. 集成测试

集成测试[^11]验证多个真实组件协作。

[^11]: 集成测试：检查多个真实组件能否按预期一起工作的测试。

示例：

- 注册服务与测试数据库；
- 订单服务与库存服务；
- 文件上传与对象存储；
- API 与认证中间件。

集成测试更接近实际系统，但运行较慢，并需要可靠的环境隔离和数据清理。

运行前让 Agent 确认测试数据库、容器、服务、网络和环境变量。环境未准备好时，报告“未运行”或“环境失败”，不能据此修改业务代码。

### 6. 边界条件测试

边界条件测试[^12]检查规则临界点、空值和异常输入。边界来自业务规则。

[^12]: 边界条件测试：专门检查空值、上下限及刚好越界输入的测试。

| 类型 | 用户名示例 |
| --- | --- |
| 空输入 | `""` |
| 纯空格 | `"   "` |
| 最小长度 | `"a"` |
| 最大长度 | 规则上限 |
| 刚刚越界 | 上限加一 |
| 非法字符 | 按产品规则 |
| 重复值 | 已存在用户名 |

参数化测试可以用同一规则覆盖多组输入。

参数化适合相同规则的多组输入，不适合把不同产品行为硬塞进一个难读的测试。

```python
@pytest.mark.parametrize("username", ["", " ", "   "])
def test_rejects_blank_usernames(username):
    assert validate_username(username) is False
```

pytest 会直接把参数值传给测试；如果参数是可变对象并在测试中被修改，后续用例可能看到被改变的状态。Agent 应避免共享可变测试数据，或为每次运行创建独立值。

#### 从需求建立测试矩阵

| 输入类别 | 例子 | 预期 | 依据 |
| --- | --- | --- | --- |
| 正常 | `alice` | 成功 | 现有公开行为 |
| 边界 | `""`、`"   "` | `INVALID_USERNAME` | 本次需求 |
| 易混淆 | `" alice "` | 待确认 | 产品规则未说明 |
| 失败 | 已存在的 `alice` | `DUPLICATE_USER` | 现有接口契约 |

矩阵先写期望依据，再交给 Agent 转换为测试。这样能减少“用大量输入掩盖业务规则不清”的问题。

### 7. 回归测试

回归测试把已经发生的问题转化为永久用例。

一个有效回归测试应：

1. 在旧实现上失败；
2. 在修复后通过；
3. 接近用户可观察的故障层；
4. 不依赖偶然实现细节；
5. 名称能够说明原问题。

回归测试的位置要接近用户可观察故障。若 Bug 发生在路由对空格参数的转换，只给底层字符串函数补测试仍可能漏掉原路径。可以同时保留一个快速单元测试和一个接口级回归测试，但两者要各自回答不同问题。

## 三、失败处理与验收

### 1. 根据测试结果修复代码

测试失败后先阅读：

- 失败阶段；
- 期望值；
- 实际值；
- traceback；
- 日志和警告；
- 环境差异。

Traceback[^13]应从第一处业务相关失败向上理解，而不是只复制最后一行。

[^13]: Traceback：程序出错时显示的调用路径和具体失败位置。

根据原因选择动作：

| 原因 | 处理方式 |
| --- | --- |
| 生产逻辑错误 | 修改最小实现 |
| 测试预期错误 | 修正测试依据 |
| fixture 缺失 | 修复测试环境 |
| 依赖或配置错误 | 修复环境配置 |
| 需求不明确 | 暂停并澄清 |

删除失败测试、放宽断言或标记跳过，不属于修复。

### 2. 失败后的 Agent 决策顺序

```text
测试是否被收集？
-> 是否进入目标路径？
-> 失败是否来自目标行为？
-> 期望是否有正式依据？
-> 环境与测试数据是否可靠？
-> 才决定修改生产代码、测试或环境
```

同一输入、环境和假设没有变化时，机械重跑通常不会增加证据。Agent 应先提出能区分候选原因的最小诊断动作。

### 3. 测试作为验收标准

将每条需求对应到一种或多种证据。

| 需求 | 验收证据 |
| --- | --- |
| 空用户名被拒绝 | 单元与接口测试 |
| 权限控制 | 允许与拒绝路径测试 |
| 数据写入正确 | 集成测试和数据库状态 |
| 页面布局正确 | 浏览器检查和截图 |
| 性能达标 | 固定环境性能测量 |

测试报告应记录真实命令、环境、通过数量、失败和跳过项。

### 4. 分层验证顺序

```text
新增测试
-> 最相关测试文件
-> 相关模块测试
-> 项目规定的完整测试
-> 构建、lint 或类型检查
-> 必要的页面或接口检查
-> 最终 diff
```

先运行最接近故障路径的测试，以最早暴露本轮错误，再按项目规则扩大范围。完整测试耗时很长时，不能只因成本高就省略；应运行能够运行的部分，并准确说明剩余未验证项。

### 5. 测试不能独自证明什么

- 未写成用例的产品要求；
- 未想到的安全路径；
- 指定视口下的页面布局和交互感受；
- 生产数据、权限与第三方服务的真实状态；
- Agent 是否做了范围外修改。

因此，测试通过后仍要检查构建结果、页面或接口行为以及最终 diff。第九周将进一步学习完整的质量控制组合。

## 四、无效测试与测试审查

### 1. 返回布尔值而不断言

```python
def test_total():
    return calculate_total() == 10
```

pytest 会对测试函数返回非 `None` 值发出警告；返回 `False` 仍不会像失败断言那样判定测试失败。应使用断言。

### 2. 用被测代码生成预期值

生产代码和测试共享同一错误公式时，两边同时出错，测试仍然通过。

### 3. 过度 mock

把认证、数据库、服务和序列化全部 mock 后，只能证明若干函数被调用，无法证明真实系统协作。

### 4. 只测正常路径

只测试正常用户名，无法捕获本次空格输入问题。

### 5. 新测试一开始就是绿色

可能表示缺陷已不存在、测试走错路径或断言无效。需要先确认测试确实具有捕获能力。

### 6. 测试污染共享状态

Agent 创建数据库记录后没有清理，单独运行通过，整套运行时却因顺序不同失败。应复用项目 fixture 与 teardown[^14]，保证测试能够重复运行。

[^14]: Teardown：测试结束后释放资源和清理测试数据的步骤。

### 7. 用跳过掩盖失败

为不稳定或失败测试直接增加 skip/xfail，会改变质量信号。只有项目规则和明确原因支持时才可使用，并应记录影响；不能把跳过项算作通过。

### 8. 可复用 Prompt

```text
Bug：纯空格用户名可以注册。

请按 TDD 处理：
1. 找到当前注册行为和相关测试；
2. 添加一个回归测试；
3. 先运行并确认测试因目标缺陷失败；
4. 若失败来自环境或错误预期，先修正测试；
5. 做最小生产代码修改；
6. 运行新增、相关和完整测试；
7. 检查空字符串、纯空格、前后空格和正常用户名；
8. 汇报 Red 与 Green 的真实输出和最终 diff。
```

#### 从验收标准生成测试矩阵

```text
请先只分析，不修改文件。

把需求转换为测试矩阵，至少区分：
正常输入、边界输入、易混淆输入和失败输入。
每一行写出输入、期望行为、依据、合适测试层级和是否需要我确认。

不要自行创造产品规则；能从现有接口、测试或文档确认的先查证。
```

#### 审查 Agent 生成的测试

```text
请审查本次新增测试，不修改文件。

检查：
1. 旧错误实现是否会让测试失败；
2. 断言是否对应公开行为；
3. 预期是否独立于被测实现；
4. mock 是否绕过目标路径；
5. fixture、数据和清理是否会互相污染；
6. 哪些关键边界仍未覆盖。

每个问题说明文件位置、触发方式和实际影响；无证据时不要猜测。
```

### 9. 测试审查清单

- 测试名称说明行为；
- 旧错误实现会让测试失败；
- 断言表达业务结果；
- 预期值来源独立；
- 边界覆盖有依据；
- mock 没有绕过目标行为；
- 测试可以重复运行；
- 失败信息容易定位；
- 相关与完整测试均已考虑。
- 测试命令、收集数量、失败和跳过是否真实记录；
- 最终 diff 是否只包含本次行为和对应测试；
- 未运行项、原因和影响是否说明。

## 五、本章总结

```text
Red：先证明问题
Green：最小修复
Refactor：保持行为整理结构
```

测试是重要证据，但测试代码也可能错误。可靠的 Agent 开发需要同时审查生产代码、测试设计和真实运行结果。

使用编码 Agent 完成测试驱动任务时，记住：

1. 先从需求和现有契约推导可观察行为；
2. Red 必须以正确原因失败；
3. Green 只做使目标行为成立的最小修改；
4. Refactor 需要绿色测试保护，也可以在没有必要时省略；
5. 单元、接口与集成测试回答不同问题；
6. 正常、边界、易混淆和失败输入要有依据；
7. 测试代码、fixture 和 mock 同样需要审查；
8. 交付时报告实际测试、未运行项和最终差异。
